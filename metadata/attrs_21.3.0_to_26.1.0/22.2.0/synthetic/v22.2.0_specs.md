# Upgrade Specification from 22.1.0 to 22.2.0

## New Features

### Task 1 Add attrs field alias support
Ensure that attrs users can explicitly control the generated constructor keyword for each field, including private attributes, and that object construction, field introspection, and evolve-style copying all use the same effective field names.

- **Expectation**: Users should be able to choose the public constructor keyword for an attrs field without changing the stored attribute name. The same name that works during object creation should also be visible through introspection and should be accepted when creating updated copies.

- **Constraints**: The new alias capability must be non-breaking for existing callers who do not opt into it. It should preserve current defaults while adding a consistent way to override externally visible constructor names.


### Task 2 Add inverse validator composition with attrs.validators.not_
Ensure that the library supports composing negative validation rules through a public `attrs.validators.not_` validator so users can declare that a value must fail another validator, with configurable captured exception types and a customizable failure message.

- **Expectation**: Users should be able to express rules such as 'value must not satisfy this validator' by wrapping an existing validator with `attrs.validators.not_`. Validation should pass when the wrapped rule rejects the value with one of the configured exception types, fail when the wrapped rule accepts the value, allow the caller to customize the failure message, and reject invalid exception-type configuration.

- **Constraints**: Negation must not hide unrelated validator failures or change behavior outside the configured exception types. It should only flip the success condition of the wrapped validator and should fail fast if its exception capture configuration is invalid.


## Bug Fixes

### Task 3 Correct ABC abstractness for dict-backed attrs classes
Ensure that on Python 3.10 and later, dict-backed attrs classes correctly reflect abstract base class status after attrs finishes building the class, so classes that satisfy inherited abstract methods become usable and classes with missing abstract methods remain abstract.

- **Expectation**: After upgrading, attrs classes should report abstract or concrete status based on the methods they actually expose once attrs has finished constructing the class. Users should be able to instantiate classes that have become concrete, and still be prevented from instantiating classes that remain abstract.

- **Constraints**: Only the correctness of abstractness detection should change. Existing class-construction behavior outside the affected runtime and class style should remain stable.


### Task 4 Harden attrs pickling against class attribute changes
Ensure that pickled attrs-based objects can be unpickled safely even if the current class definition no longer exactly matches the version that produced the pickle, without misassigning persisted values to the wrong attributes.

- **Expectation**: Pickle compatibility for attrs classes should be resilient to schema evolution. Restoring an older serialized object should keep matching fields intact, ignore fields that no longer exist, and avoid placing old data into newly added or differently ordered fields.

- **Constraints**: The upgrade must preserve existing pickle behavior for unchanged models while preventing data corruption when a class evolves. Missing fields should be ignored, and new fields should not be populated with unrelated legacy values.


## Dependency Updates

### Task 5 Deprecate Python 3.6 in attrs 22.2.0
Ensure that attrs 22.2.0 explicitly warns users that Python 3.6 is deprecated and will lose support in the next release, while keeping current imports usable during the deprecation window.

- **Expectation**: Users running the library on Python 3.6 should be clearly notified that the runtime is nearing end of support without having their current usage break immediately. Users on supported Python versions should see no new warning behavior.

- **Constraints**: The update should provide advance notice of upcoming support removal without creating a breaking change in this release, and it should avoid affecting users on still-supported runtimes.


### Task 6 Adopt enum-backed attrs.NOTHING sentinel
Ensure that upgrading to attrs 22.2.0 exposes `attrs.NOTHING` as an enum-backed public sentinel that remains usable as the absence marker distinct from `None`, while also allowing downstream typing use cases such as `Literal[NOTHING]`.

- **Expectation**: After the upgrade, applications and extensions should continue to treat `attrs.NOTHING` as the library's distinct "no value" marker, but it should now also behave like a typed constant that can be referenced precisely in type annotations.

- **Constraints**: The upgrade should add typing precision without changing what the sentinel means in normal application code or breaking common checks that rely on its established sentinel behavior.


### Task 7 Add PEP 681-compatible unsafe_hash support to attrs decorators
Ensure that supported attrs class decorators accept the dataclass-style `unsafe_hash` option so callers upgrading to 22.2.0 can control generated hashing behavior through the PEP 681-compatible keyword, with consistent results when both `unsafe_hash` and `hash` are present.

- **Expectation**: Users should be able to use the standard `unsafe_hash` keyword on supported attrs decorators to opt classes into or out of generated hashing without changing the existing meaning of `hash`. If both keywords are supplied, the explicit `unsafe_hash` choice should win.

- **Constraints**: The upgrade should be additive and non-breaking for existing decorator usage. It must preserve prior hashing behavior unless a caller deliberately uses the new keyword, and it must not silently accept unsupported hash settings.


## Breaking Changes

### Task 8 Drop Python 3.5 support and standardize on Python 3.6+ behavior
Ensure that upgrading to attrs 22.2.0 is handled as a runtime-compatibility change: Python 3.5 must no longer be treated as supported, Python 3.6+ behavior must rely on normal ordered `dict` semantics, and the public `attr` API must remain consistent for supported runtimes.

- **Expectation**: The library should now be treated as Python-3.6+-only. Supported runtimes should expose one consistent attribute-ordering model based on normal dictionary insertion order, preserve that order in user-visible metadata and representations, and continue exposing the modern top-level `attr` APIs. Python 3.6 remains usable in this release but should warn that it is nearing end of support.

- **Constraints**: Users should not need special container types or version-specific workarounds to get stable field ordering on supported Python versions. The upgrade must keep observable ordering behavior intact while clearly ending compatibility with Python 3.5.


## Typing Updates

### Task 9 Restore AttrsInstance on the attrs top-level namespace
Ensure that upgrading to attrs 22.2.0 restores `AttrsInstance` as a supported top-level symbol on `attrs`, so users do not encounter regressions when referencing `attrs.AttrsInstance` in typed code or attrs-aware object handling.

- **Expectation**: The main `attrs` import should again provide the attrs instance marker that users and type checkers expect. After the upgrade, code that relies on the public `attrs` namespace for attrs-specific typing should behave consistently instead of failing because the marker is missing.

- **Constraints**: The fix should restore the missing public symbol without changing existing attrs detection or serialization semantics. Existing consumers should see a compatibility restoration, not a broader behavioral shift.


### Task 10 Expose AttrsInstance at Runtime for Pyright Compatibility
Ensure that `AttrsInstance` is available as a public runtime type in both `attr` and `attrs`, so users can reference it consistently in application code and type annotations without tool-specific type errors or missing runtime symbols.

- **Expectation**: Users should be able to use `AttrsInstance` from either public namespace as a normal exported type. Referencing that type in annotations or runtime-aware tooling should work consistently instead of failing because the symbol only existed in typing metadata.

- **Constraints**: The upgrade should add missing type availability without changing unrelated library behavior. Existing consumer code should continue to work, with the only observable difference being that the previously missing public type can now be resolved normally.


## Performance Improvements

### Task 11 Restore attrs initializer performance in 22.2.0
Ensure that upgrading to attrs 22.2.0 removes the 22.1.0 constructor slowdown for attrs classes whose generated initialization must bypass __setattr__ hooks, especially frozen or slotted classes with many assigned attributes, without changing the instances produced or their hash-related behavior.

- **Expectation**: Construction of affected attrs classes should be faster in 22.2.0, particularly for classes with more initialized attributes, while producing the same field values, immutability behavior, and hashability semantics that users already rely on.

- **Constraints**: This upgrade must behave as a non-regression in functionality: constructor signatures, resulting attribute values, mutation rules, and hash behavior should stay the same, with only the execution cost improving for affected classes.


### Task 12 Improve attrs class creation performance
Ensure that upgrading to attrs 22.2.0 preserves the observable behavior of attrs-generated classes while delivering the documented class-creation performance improvement, including for simple classes and for generated initialization, representation, comparison, and hashing behavior.

- **Expectation**: The upgrade should improve attrs class creation speed without changing how attrs-decorated classes behave. Existing application code should keep seeing the same constructor behavior, object representations, comparisons, and hashing semantics, but with lower overhead when attrs builds those classes.

- **Constraints**: Treat this as a non-breaking performance upgrade. All existing attrs field options and generated-method edge cases should continue to work the same way from a user perspective.


## Additional Changes
- Ensure that upgrading to 22.2.0 provides improved static typing for attrs class detection so that a positive attrs.has() or attr.has() check is recognized by type checkers as proof that the checked value is an attrs instance.
- Ensure that typed consumers can call `attrs.cmp_using()` without being forced to supply every optional comparator and configuration argument when they only need a subset of the API.
