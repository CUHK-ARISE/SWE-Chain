# Upgrade Specification from 22.2.0 to 23.1.0

## New Features

### Task 1 Support field-name strings in attrs filters
Ensure that upgrading to attrs 23.1.0 allows users to pass literal field-name strings to `attrs.filters.include()` and `attrs.filters.exclude()` when filtering attrs fields, while preserving existing behavior for class selectors and `attrs.Attribute` selectors.

- **Expectation**: Users should be able to choose attrs fields by name in the same filtering APIs they already use for type-based or attribute-based selection. Name-based filtering should feel additive and consistent with the existing include/exclude behavior.

- **Constraints**: The new string input is a convenience extension, not a redesign. Existing filtering behavior must remain stable, and unknown field names should simply have no effect.


### Task 2 Preserve typing extras in attr.resolve_types
Ensure that applications using attr.resolve_types() can preserve typing extras during annotation resolution on supported Python versions, while still allowing callers to opt out when they need the pre-upgrade stripped-type behavior.

- **Expectation**: When attrs resolves annotations for a class, metadata-bearing type hints should be retained by default on runtimes that support them, so callers can observe the same enriched types they declared. Callers should also be able to request the legacy simplified result when they do not want typing extras preserved.

- **Constraints**: The upgrade should add extra-type preservation without regressing normal annotation resolution, forward-reference handling, or compatibility across supported Python versions.


### Task 3 Support type metadata in attrs.field() for dynamic class creation
Ensure that dynamically generated attrs classes can declare field type metadata directly in attrs.field() definitions used with attrs.make_class().

- **Expectation**: Users defining attrs classes dynamically should be able to attach a field's type at the point where they declare the field, and the generated class should preserve that type information for runtime inspection.

- **Constraints**: This should be a backward-compatible enhancement that preserves existing behavior while exposing declared types as runtime metadata only.


### Task 4 Support tuple validators in attrs.validators.optional
Ensure that `attrs.validators.optional()` accepts validator tuples as a supported input form, so optional attributes can be declared with multiple validators using either a list or a tuple while preserving the existing behavior that `None` is allowed and non-`None` values are validated.

- **Expectation**: Users should be able to define optional validation with either one validator or multiple validators supplied as a list or tuple. The optional wrapper should still permit `None`, and any real value should satisfy every validator that was provided.

- **Constraints**: The update should extend accepted input shapes without changing established optional-validation behavior. Existing usages must keep working the same way, and only the newly supported tuple form should be added.


## Bug Fixes

### Task 5 Generic attrs class introspection support
Ensure that parameterized generic attrs classes are recognized and introspected consistently by the public attrs helpers, while non-attrs generic classes and invalid inputs continue to produce the existing unsupported-input behavior.

- **Expectation**: Users should be able to pass a parameterized generic attrs class to the same introspection APIs they use for ordinary attrs classes. Those APIs should treat the parameterized generic as a valid attrs class, expose the same field metadata as the underlying generic definition, and continue to reject unsupported inputs through the established public behavior.

- **Constraints**: The upgrade should extend generic-class support without altering the current contract for existing valid or invalid inputs. Current callers should see the same results unless they are using parameterized generic attrs classes, which should now work.


### Task 6 Allow frozen attrs exceptions to participate in normal traceback and chaining flows
Ensure that frozen attrs-based exception classes can be raised, propagated, and wrapped by normal Python exception-handling flows without failing when exception metadata is updated.

- **Expectation**: Frozen exceptions should still behave like normal Python exceptions. When the runtime or a framework attaches traceback or chaining information during raise, re-raise, or wrapping, the exception should continue through that flow without being rejected for immutability.

- **Constraints**: This fix must be narrowly scoped to exception bookkeeping. It should not weaken immutability for ordinary frozen objects or allow unrelated fields on frozen exceptions to become mutable.


### Task 7 Restore backward-compatible unpickling for pre-22.2.0 attrs objects
Ensure that upgrading to attrs 23.1.0 allows applications to unpickle previously persisted or cached attrs instances created by versions earlier than 22.2.0, so existing serialized data remains readable after upgrade.

- **Expectation**: After upgrading, old serialized attrs objects should load successfully even if they were created by older releases. The library should remain compatible with both old and current pickle formats, and deserialization should restore the object's data rather than breaking on legacy cached values.

- **Constraints**: The compatibility fix must not break deserialization of objects serialized by newer versions, and it must not invent or mutate state beyond what was actually stored.


### Task 8 Fix slotted attrs class closure updates without __code__ on Python 3.8+
Ensure that slotted attrs classes continue to work on Python 3.8 and newer even when function __code__ introspection is unavailable, and that methods relying on the class closure still observe the correct generated class.

- **Expectation**: Upgrading to 23.1.0 should make slotted attrs classes reliable in modern Python runtimes, including compiled or restricted environments that do not expose normal function introspection. Class methods should keep behaving as if they were defined on the final class, with __class__ and super() continuing to work normally.

- **Constraints**: The fix should only remove the compatibility failure in newer Python environments and must not change established behavior for users who already rely on normal slotted attrs class semantics or older-version compatibility.


## Dependency Updates

### Task 9 Deprecate zope-interface validator support in attrs
Ensure that applications upgrading from 22.2.0 to 23.1.0 treat `attrs.validators.provides` as deprecated `zope-interface` support: existing uses should still validate values as before, but use of the validator must surface a deprecation signal so consumers can migrate before removal.

- **Expectation**: After upgrading, code that relies on the `provides` validator should keep working for now, but the library should clearly warn that this `zope-interface` integration is deprecated and scheduled for removal. Users should be able to detect the deprecation at runtime without losing the current validation behavior.

- **Constraints**: The upgrade should introduce a warning, not an immediate break. Existing consumers should see the new deprecation notice while all current pass/fail validation outcomes remain stable until the feature is actually removed.


## Breaking Changes

### Task 10 Drop Python 3.6 support and deprecate legacy module metadata access
Ensure that upgrading to attrs 23.1.0 enforces Python 3.7+ support and preserves legacy packaging metadata access on `attr` and `attrs` in a backward-compatible but deprecated form.

- **Expectation**: The upgrade should require a supported Python runtime and keep old module metadata lookups working long enough for consumers to migrate to standard package metadata APIs. Deprecated metadata reads should still succeed with warnings, structured version info should remain available without warning, and invalid attribute access should continue to fail normally.

- **Constraints**: Maintain compatibility for existing metadata consumers without silently accepting unsupported runtimes or masking invalid module attributes.


### Task 11 Adopt positional-instance usage for attrs evolve
Ensure that attr.evolve() and attrs.evolve() are used with the source instance as a positional argument so objects with a field named inst can be evolved correctly, while avoiding deprecated keyword-based instance passing that now warns and will later stop working.

- **Expectation**: Evolving an attrs object should take the original object as the first argument, and every legitimate field, including one named inst, should remain updateable. Older keyword-based instance passing should still function temporarily with a deprecation warning, while malformed calls should fail with normal argument errors.

- **Constraints**: The upgrade should preserve existing correct evolve behavior and only alter the API contract around how the original object is supplied. Backward compatibility should remain temporary rather than silently changing results for existing callers.


## Additional Changes
- Ensure that classes declared with `@frozen` are treated as frozen by type checkers that implement PEP-681, so assigning to an instance attribute after construction is reported as an error instead of being accepted.
- Ensure that upgrading to attrs 23.1.0 recognizes attrs-based instances passed to attrs.asdict() and attrs.astuple() as valid typed inputs, so users get consistent static typing across the attrs and attr namespaces.
- Ensure that contributors upgrading to 23.1.0 have clear documentation of the expected pull request workflow and submission checklist, without changing the library's runtime behavior.
- Ensure that upgrading from attrs 22.2.0 to 23.1.0 removes the runtime deprecation warning from `attr.assoc()` while preserving its existing copy-and-update behavior.
