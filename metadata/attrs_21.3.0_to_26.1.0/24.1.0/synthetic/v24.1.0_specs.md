# Upgrade Specification from 23.2.0 to 24.1.0

## New Features

### Task 1 Add context-aware wrapped converters for attrs fields
Ensure that attrs users can define field converters that optionally receive the instance being initialized and the current field definition, so conversion logic can depend on object state or field metadata during initialization.

- **Expectation**: Users should be able to opt into richer field conversion by wrapping a converter so it can see the object under construction and the field definition. This richer conversion must work anywhere attrs normally performs conversion during initialization, without breaking existing simple converters. Converter composition through `attr.converters.pipe()` should remain usable under the new model, but the feature should be treated as a runtime capability rather than a statically typed one.

- **Constraints**: The upgrade must preserve backward compatibility for existing converter usage while adding optional context-aware conversion. The new behavior should be observable only through supported public APIs and normal object construction, without forcing any particular implementation strategy or depending on internal class layout details.


### Task 2 Support type resolution for classes generated with attrs.make_class
Ensure that classes created with `attrs.make_class()` preserve declared field types in a way that allows later type resolution to work on the generated class, while continuing to accept the legacy hashing option with the library's deprecation behavior.

- **Expectation**: Dynamically created attrs classes should behave like normally declared classes for type-aware consumers: typed fields remain discoverable on the class, deferred type resolution can resolve declared types afterward, and older hashing configuration continues to work only through a deprecation path.

- **Constraints**: The change should add missing annotation visibility without inventing types for untyped fields or breaking existing generated-class behavior. Backward compatibility should be maintained for older hashing usage, but users should receive a clear deprecation signal.


### Task 3 Add disjunctive attrs validator composition
Ensure that applications using attrs can declare a single validator that accepts an attribute value when any one of multiple alternative validators succeeds, and rejects the value only when none of the alternatives are satisfied.

- **Expectation**: Users should be able to model alternative valid shapes for one attribute with a built-in OR validator. A value should be accepted if it matches at least one allowed validation rule, and rejected only when it matches none of them.

- **Constraints**: The new validator must preserve OR semantics: one successful branch is enough, later alternatives must still be considered after earlier failures, and complete failure must surface as a single validation error from the composite.


### Task 4 Support inherited __attrs_init_subclass__ hooks
Ensure that attrs-decorated subclasses invoke an inherited __attrs_init_subclass__ hook after class creation is complete, so subclass registration and other post-assembly setup logic works consistently.

- **Expectation**: Applications using attrs should be able to define subclass-initialization logic once on a base class and have it automatically run for each derived attrs class after the derived class is ready. This should make class registration and similar subclass lifecycle behavior work reliably without depending on incomplete class state.

- **Constraints**: The new capability should be additive and narrowly targeted. Existing attrs class creation should continue to behave the same unless a project opts into the subclass hook pattern.


## Bug Fixes

### Task 5 Fix slotted cached_property behavior in attrs 24.1.0
Ensure that slotted attrs classes using functools.cached_property behave correctly after class rebuilding: cached properties must support inherited access patterns such as zero-argument super() and must not keep the discarded original class alive.

- **Expectation**: Slotted classes with cached properties should behave like normal Python classes for inherited property logic, and the internal slotting process should not leak stale class objects.

- **Constraints**: Only correct the cached-property inheritance and cleanup issues. Do not change normal caching semantics or unrelated attribute lookup behavior.


### Task 6 Preserve AttributeError for slotted cached_property access
Ensure that slotted attrs classes using functools.cached_property preserve the original AttributeError raised during property access, instead of converting it into a generic missing-attribute failure, and ensure attribute lookup follows normal Python fallback semantics when inherited attribute handlers are present.

- **Expectation**: Accessing a cached property on a slotted attrs class should behave like normal Python attribute access: real AttributeError exceptions raised by dependent properties should be surfaced as-is, and fallback lookup should only happen when an actual fallback handler exists.

- **Constraints**: The fix must avoid masking real runtime failures while preserving existing successful attribute and cached-property behavior. It should not introduce extra fallback handling for classes that do not define one.


### Task 7 Fix attrs pre-init handling for keyword-only defaults
Ensure that attrs-based classes can be instantiated when __attrs_pre_init__ accepts arguments and a field combines keyword-only initialization with a default value, without crashing and while making the resolved keyword-only value available during pre-init.

- **Expectation**: Classes that use attrs pre-initialization hooks should continue to work even when some constructor inputs are keyword-only and optional. If a keyword-only value is omitted, normal default resolution should happen and pre-init should observe that resolved value.

- **Constraints**: The change should be limited to correcting initialization behavior for the failing combination and must not alter the normal calling pattern for other attrs-based constructors.


### Task 8 Keep attrs.validators.in_() usable with mutable option collections
Ensure that fields using attrs.validators.in_() remain usable in attrs workflows that require hashable validator metadata even when the allowed options are provided as a list, dict, or set, while validation continues to reflect the original allowed options seen by users.

- **Expectation**: Users should be able to define an in_ validator from common mutable collections without breaking other attrs features that inspect or filter fields. The validator should still behave like the same allowed-values check, and any visible error or introspection output should describe the options the user originally supplied.

- **Constraints**: The upgrade should remove compatibility problems caused by unhashable option collections without changing what values are considered valid or making diagnostics look like a different set of allowed options.


## Dependency Updates

### Task 9 Handle attrs 24.1.0 decorator deprecations
Ensure that upgrading to attrs 24.1.0 does not rely on deprecated decorator arguments by removing use of `repr_ns` and replacing legacy `hash` configuration with supported `unsafe_hash` behavior, while preserving the intended repr and hash outcomes for attrs-based classes.

- **Expectation**: The application should adopt the current attrs decorator contract for Python 3: class reprs should not depend on the deprecated namespace override, and hash behavior should be configured through the supported API so the upgrade does not introduce deprecation warnings or future compatibility risk.

- **Constraints**: Preserve the visible behavior of attrs classes while removing reliance on deprecated options. The upgrade should reduce warning noise and future breakage risk without altering the intended identity, representation, or hashability semantics of supported classes.


### Task 10 Deprecate attrs `hash` in favor of `unsafe_hash` and preserve `make_class` annotations
Ensure that upgrading to attrs 24.1.0 preserves class-generation behavior while surfacing the new public contract: `hash` is deprecated in favor of `unsafe_hash` for attrs-based class builders, and `make_class()` should expose declared attribute types through class annotations.

- **Expectation**: After the upgrade, code that still uses the old `hash` option should keep working but clearly signal that callers need to migrate to `unsafe_hash`. Dynamically created attrs classes should also retain visible type metadata for attributes that declare a type so consumers can inspect or resolve those annotations after class creation.

- **Constraints**: The upgrade should be backward-compatible at runtime aside from deprecation signaling, and it should only expose annotation data that the caller already declared. Existing class creation flows should continue to work without requiring immediate rewrites.


## Breaking Changes

### Task 11 Require positional instance argument for attrs.evolve
Ensure that code using attrs.evolve remains compatible with attrs 24.1.0 by passing the source instance as the first positional argument and no longer relying on the deprecated inst keyword form.

- **Expectation**: The upgrade should preserve normal object-copying behavior for attrs.evolve when the instance is passed positionally, while making the old keyword-based calling style invalid. Applications should treat the instance parameter as positional-only and expect incorrect argument counts to fail as errors.

- **Constraints**: The upgrade should only remove the deprecated keyword calling convention and tighten argument validation. Existing valid evolve calls should keep working the same way, and unrelated error conditions should not be loosened or hidden.


### Task 12 Remove dependency on the deprecated provides() validator
Ensure that applications upgrading from attrs 23.2.0 to 24.1.0 no longer depend on the removed `attrs.validators.provides()` validator and continue to enforce any required interface-conformance checks through supported application behavior.

- **Expectation**: After the upgrade, built-in zope interface validation support should be treated as removed. Any feature that still needs interface validation must keep the same user-visible validation outcome without relying on `provides()` being present in attrs.

- **Constraints**: Removing usage of the deleted validator should not introduce broader validation regressions. Existing validation behavior should remain stable except for the absence of the removed built-in interface validator.


### Task 13 Remove legacy module metadata aliases from attr and attrs
Ensure that applications upgrading to attrs 24.1.0 no longer depend on legacy packaging metadata attributes exposed on the `attr` and `attrs` modules, while preserving continued access to version information through the remaining supported compatibility attributes.

- **Expectation**: The library should no longer expose general package metadata through the `attr` or `attrs` modules. Only version-related compatibility access should remain available there, and all other package metadata should be obtained through the standard Python metadata interfaces.

- **Constraints**: Keep existing version lookup behavior intact while removing the obsolete metadata alias surface. Removed metadata names should clearly behave as no longer supported instead of continuing to work in a degraded compatibility mode.


### Task 14 Adapt to attrs 24.1.0 generated equality semantics
Ensure that attrs-generated equality reflects the 24.1.0 behavior: compare each equality-participating attribute directly, preserve any configured equality key transformation, and no longer treat identity-only matches such as NaN-like values as equal.

- **Expectation**: Equality for attrs classes should be evaluated field by field using the class's declared equality rules, including any configured equality normalization. This should deliver faster comparisons while making results depend on actual value equality rather than object identity in edge cases.

- **Constraints**: Keep the existing equality contract for which fields matter, while updating only the comparison semantics. The upgrade must not broaden or narrow the set of fields considered equal; it only changes how their equality is evaluated.


## Additional Changes
