# Upgrade Specification from 24.1.0 to 24.2.0

## Bug Fixes

### Task 1 Keep the `hash` argument supported without deprecation warnings
Ensure that upgrading to 24.2.0 preserves compatibility for applications that still pass the `hash` argument to attrs class-definition APIs, eliminating deprecation-warning noise while keeping hashing behavior stable and allowing `unsafe_hash` to remain the effective override.

- **Expectation**: Existing code that still uses the older `hash` option should continue to work quietly after the upgrade. The option remains discouraged for new code, but it is not being removed, and newer hash settings should still override it when both are provided.

- **Constraints**: The upgrade should reduce ecosystem warning noise without forcing migrations or changing the effective hashing behavior that callers already rely on.


### Task 2 Restore attrs converter pipelines during attribute assignment
Ensure that converter pipelines declared with attrs.converters.pipe() or list-style converter syntax continue to work correctly during both initialization and later attribute assignment when on_setattr includes attrs.setters.convert, including the default behavior of attrs.define.

- **Expectation**: Converter chains should behave consistently when objects are created and when attributes are reassigned later. Converters that declare instance-aware or field-aware behavior should keep receiving that context, reassignment should apply the same conversion semantics as construction, and public typing or introspection metadata exposed by the converter chain should stay accurate.

- **Constraints**: The fix should be backward-compatible for existing simple converters and non-converting setters, while restoring correct behavior only for converter pipelines and context-aware converters.


### Task 3 Restore attrs annotation compatibility for Python 3.14 semantics
Ensure that annotation-based attrs class definitions continue to work on Python runtimes implementing PEP 649 / 749 semantics, including Python 3.14-style deferred annotations, so annotated fields are still discovered during class creation.

- **Expectation**: Users should be able to keep defining attrs classes with type-annotated fields on newer Python runtimes with deferred annotation semantics, and attrs should interpret those annotations correctly without requiring user code changes just because the interpreter changed how annotations are stored.

- **Constraints**: Add support for the new interpreter annotation model without regressing behavior on already supported Python versions or changing how annotation-based attrs declarations behave for users.
