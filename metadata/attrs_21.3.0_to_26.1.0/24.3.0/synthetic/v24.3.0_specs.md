# Upgrade Specification from 24.2.0 to 24.3.0

## New Features

### Task 1 Support copy.replace() for attrs instances on Python 3.13+
Ensure that attrs-defined instances can be copied with field updates through Python 3.13's copy.replace() API, with behavior consistent with attrs.evolve, without overriding custom replacement hooks or weakening frozen-instance protections.

- **Expectation**: Users running Python 3.13+ should be able to call copy.replace() on attrs instances to create modified copies in the same way they already can with attrs.evolve. Existing custom replacement behavior must remain authoritative, unsupported field names must still fail loudly, and frozen attrs exceptions must stay frozen except for interpreter-managed exception bookkeeping.

- **Constraints**: The upgrade must be additive and compatibility-safe: it should enable the new standard-library replacement workflow without changing existing custom APIs, without silently accepting unsupported field updates, and without making frozen objects broadly mutable.


## Bug Fixes

### Task 2 Allow exception metadata updates on frozen attrs exceptions
Ensure that frozen attrs classes which inherit from BaseException continue to behave like normal Python exceptions when exception metadata is updated, including support for note and suppressed-context state, while remaining frozen for ordinary attribute changes.

- **Expectation**: Frozen exceptions should still support the standard Python exception state that the runtime and application code may attach to raised exceptions. Updating or clearing exception notes or suppressed-context state should work normally instead of being blocked by the class being frozen.

- **Constraints**: This change must unblock normal exception bookkeeping without weakening the general immutability contract of frozen objects.


### Task 3 Restore optional() compatibility with pipe() and Converter inputs
Ensure that converter composition remains compatible when using attrs.converters.optional() with attrs.converters.pipe() or any other Converter-based converter, so optional conversion still short-circuits None values and otherwise applies the wrapped conversion chain correctly.

- **Expectation**: Optional and piped converters should compose transparently. Wrapping a converter with optional behavior must still return None unchanged, and any non-None value must be processed through the wrapped converter or converter chain with the same externally observable behavior and context support as before.

- **Constraints**: Existing simple converter usage should keep working unchanged. Context-aware conversion should only be enabled when the wrapped converter actually depends on attribute metadata, and composed converters should not alter ordering or the special handling of None values.


## Breaking Changes

### Task 4 Drop Python 3.7 support in attrs 24.3.0
Ensure that upgrading to attrs 24.3.0 is treated as a Python-version support change: Python 3.7 is no longer a supported runtime, while supported Python 3.8+ environments must retain existing attrs behavior for slotted classes, cached properties, typing protocols, and package metadata access.

- **Expectation**: The upgrade should be understood as ending Python 3.7 compatibility while preserving normal library behavior for users already on supported Python versions. Supported environments should keep seeing the same public attrs capabilities through the standard Python 3.8+ library surface.

- **Constraints**: Keep the change scoped to the supported-Python baseline. Users on supported Python versions should not lose existing runtime functionality or need extra compatibility shims because of this upgrade.


## Typing Updates

### Task 5 Expose NothingType for attrs.NOTHING annotations
Ensure that users can annotate APIs that accept or return the attrs omitted-value sentinel consistently by using a public NothingType that corresponds to attrs.NOTHING.

- **Expectation**: Applications should be able to rely on a supported public type for the attrs 'no value supplied' sentinel. Developers should be able to import that type from the main public packages and use it to document and type-check APIs that work with the sentinel.

- **Constraints**: The update should add typing support without altering how omitted values behave at runtime. Existing sentinel-based code paths should remain compatible and keep the same observable behavior.


## Additional Changes
- Ensure that attrs.validators.instance_of() supports union-type declarations in user code so developers can express multiple accepted types with native union syntax without changing the validator's observable runtime contract.
- Ensure that attrs applies configured field converters based on whether a converter is present, not on the converter object's truthiness, so falsey callable converter instances still run during initialization.
