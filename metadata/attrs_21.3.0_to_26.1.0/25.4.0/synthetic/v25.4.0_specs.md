# Upgrade Specification from 25.3.0 to 25.4.0

## New Features

### Task 1 Relax deep_mapping validator requirements
Ensure that `attrs.validators.deep_mapping()` supports partial deep validation for mappings by allowing callers to validate only keys or only values, while rejecting configurations that provide neither.

- **Expectation**: Users should be able to configure deep mapping validation for just keys, just values, or both, without being forced to provide unused validators. The API should still reject a configuration that performs no deep key or value checks at all, and it should accept multiple validators for each validation stage in a single call.

- **Constraints**: The upgrade must broaden valid configurations without weakening validation guarantees. It should remain impossible to create a deep-mapping validator that skips both key and value checks, and any configured validation step should still fail visibly when its rules are violated.


### Task 2 Expand attrs deep validators to accept validator collections
Ensure that attrs deep iterable and deep mapping validators accept grouped validators in addition to single validators, and that deep mapping supports key-only or value-only validation while rejecting configurations that specify neither key nor value validation.

- **Expectation**: The deep validation helpers should let callers express multiple checks per collection element or mapping layer without manually composing them first. Deep mapping should also support scenarios where only keys or only values need validation, but it should reject being configured with no key or value validation at all.

- **Constraints**: Current valid deep-validator usage should continue to work unchanged. The new grouped-validator support must be additive rather than replacing existing behavior, and partial deep mapping validation must only skip the part the caller left unspecified.


### Task 3 Add experimental attrs class inspection API
Ensure that upgrading to attrs 25.4.0 exposes a public experimental way to inspect the effective construction settings of an attrs-decorated class, so consumers can observe the resolved behavior of the class instead of inferring it from decorator arguments alone.

- **Expectation**: Users should be able to ask attrs how a decorated class was ultimately configured and receive a structured description of the class's final behavior. The inspection result should reflect defaults and automatic decisions that attrs made for the class, including method generation, hashing, keyword-only semantics, match support, pickling support, and relevant class-level hooks. Calling the API on a non-attrs class should fail with the library's dedicated not-an-attrs-class error.

- **Constraints**: The new capability should expose metadata without altering runtime behavior. It should describe what attrs actually produced for the class, and it should only succeed for classes that were decorated by attrs.


## Bug Fixes

### Task 4 Correct `__attrs_pre_init__` argument forwarding
Ensure that `attrs` classes invoking `__attrs_pre_init__` pass through the actual constructor argument values for non-keyword-only attributes, including attributes with defaults or factories, instead of substituting default-derived values when callers supplied explicit input.

- **Expectation**: Pre-init hooks should see the same inputs that object construction received. If a caller passes a value into an `attrs` class constructor, `__attrs_pre_init__` should observe that value rather than a fallback default.

- **Constraints**: Keep normal construction behavior stable and limit the fix to what pre-init hooks observe during initialization.


## Dependency Updates

### Task 5 Add Python 3.14 compatibility for attrs forward references and slotted classes
Ensure that upgrading to attrs 25.4.0 makes attrs-based models work correctly on Python 3.14 by supporting forward-referenced annotations under PEP 749 and by fixing reference handling for classes created with `slots=True`.

- **Expectation**: After the upgrade, attrs classes should behave correctly on Python 3.14: forward-referenced annotations should no longer break class creation or later type resolution, and slotted attrs classes should not retain incorrect references that interfere with normal class lifecycle or cleanup.

- **Constraints**: This should remain a compatibility-focused upgrade: current attrs usage patterns should continue to work as before, with changes limited to correcting Python 3.14 annotation handling and slotted-class reference cleanup.


## Breaking Changes

### Task 6 Align attrs kw_only behavior with dataclasses
Ensure that upgrading to attrs 25.4.0 preserves the intended constructor behavior for classes using `kw_only=True`, especially when inheritance and field-level `kw_only=False` are involved, while allowing applications that depend on the legacy all-fields keyword-only behavior to opt into compatibility mode.

- **Expectation**: Classes that enable keyword-only mode should now behave like dataclasses: the setting applies to that class's own fields, not automatically to inherited fields, and an individual field can explicitly remain positional. Codebases that relied on the older blanket keyword-only behavior should be able to opt back into it. If the new positional layout reveals an invalid required-after-default ordering across inheritance, that failure should surface instead of being masked.

- **Constraints**: Only keyword-only classification and the resulting constructor shape should change. Explicit field intent must still win, and existing applications that need the previous behavior must have a supported compatibility option instead of being forced into the new semantics.


## Typing Updates

### Task 7 Broaden typing for attrs.validators.or_
Ensure that attrs users can combine different validator types with attrs.validators.or_() without false static type errors when modeling fields that accept multiple value types.

- **Expectation**: Users should be able to express "value may be one of several types, each with its own validator" through attrs.validators.or_() and have that pattern type-check cleanly without checker-specific workarounds.

- **Constraints**: Upgrading should improve static-analysis acceptance of mixed validator combinations without changing how validation behaves at runtime or breaking existing attrs models.


## Performance Improvements

### Task 8 Optimize attrs.asdict() for common values
Ensure that upgrading to attrs 25.4.0 makes `attrs.asdict()` faster for common object graphs without changing the user-visible recursive serialization behavior of attrs instances, collections, mappings, serializer hooks, or subclass handling.

- **Expectation**: Common scalar values should serialize more quickly, but the serialized result should remain consistent with previous releases. Recursive serialization should still walk attrs objects, containers, and mappings correctly, keep honoring serializer hooks and container options, and avoid changing the behavior of user-defined subclasses just because they inherit from built-in scalar types.

- **Constraints**: Treat this as a performance-only upgrade in terms of output correctness: speed may improve, but callers should not have to change how they interpret serialized data or how they use existing options and hooks.


### Task 9 Speed up attrs.astuple() for atomic fields
Ensure that upgrading to attrs 25.4.0 preserves attrs.astuple() output behavior while delivering the documented runtime improvement for objects that contain atomic built-in values and nested attrs-managed data.

- **Expectation**: Calling attrs.astuple() after the upgrade should be faster for common scalar-like field values, without changing what callers observe from recursive serialization of attrs objects, collections, mappings, and custom values.

- **Constraints**: The optimization must not alter serialized results or broaden which values are treated as simple pass-through values beyond the intended built-in atomic cases.


## Additional Changes
- Ensure that `attrs.field(converter=...)` accepts tuple-based converter declarations with any number of converters in the library's public type surface, so valid multi-converter usage does not trigger incorrect static type errors.
- Ensure that `attr.VersionInfo` behaves as a hashable immutable version value after upgrading to 25.4.0, so callers can hash instances and use equal version descriptors interchangeably in hashed collections.
