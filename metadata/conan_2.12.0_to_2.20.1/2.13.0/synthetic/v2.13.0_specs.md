# Upgrade Specification from 2.12.2 to 2.13.0

## New Features

### Task 1 Expose FOUND and VERSION for additional CMake Find prefixes
Ensure that CMakeDeps-generated Find modules expose consistent package discovery variables for every prefix declared through `cmake_additional_variables_prefixes`, so consumers using alternate or legacy prefixes can detect whether the package was found and read its version.

- **Expectation**: Generated CMake Find modules should treat configured alternate prefixes as first-class aliases for package discovery. Consumers checking an alternate prefix should be able to tell that the package was found and know which version was resolved, just as they can with the main package prefix.

- **Constraints**: Do not alter discovery behavior for packages that do not opt into extra prefixes, and do not remove or rename the existing default discovery variables.


### Task 2 Expose incubating CMakeConfigDeps generator
Ensure that upgrading to 2.13.0 exposes the new incubating `CMakeConfigDeps` generator for Conan users while keeping it explicitly gated, warning that it is experimental when enabled, and preventing it from being used silently without the required `tools.cmake.cmakedeps:new` opt-in.

- **Expectation**: Users should be able to opt into a new experimental CMake dependency configuration generator during Conan installs and generation flows. The feature must be clearly marked as experimental, require an explicit configuration opt-in, and fail clearly if referenced without that opt-in. Existing stable `CMakeDeps` behavior should remain unchanged unless users explicitly request the new behavior.

- **Constraints**: The upgrade must preserve backward compatibility for existing CMake dependency generation by default, keep the new generator strictly opt-in, and avoid implicit fallback or surprise activation when the experimental gate is missing or only partially enabled.


### Task 3 Warn on unsupported revision requests for local-recipes-index remotes
Ensure that requesting a specific recipe revision from a `local-recipes-index` remote produces a clear warning when the requested revision is different from the currently available revision, while still failing resolution for that unavailable revision.

- **Expectation**: If a user asks a local-recipes-index remote for a recipe revision that is not the one currently available in that source, the client should explain that the remote cannot serve that exact revision and should still report the revision as unavailable. Requests that already match the currently available revision should continue to resolve normally.

- **Constraints**: Normal installs must keep working as before, and unsupported revision requests must still fail. The only new observable behavior should be clearer guidance in the case where a local index remote cannot honor an explicitly requested different revision.


### Task 4 Expose repository selection in coordinates_to_conandata
Ensure that Git SCM coordinate capture can opt into repository-level resolution when saving source coordinates to conandata, without changing the existing default behavior for current callers.

- **Expectation**: Users should be able to request repository-level SCM coordinates when exporting Git metadata to conandata, while calls that do not opt in should continue to behave as before.

- **Constraints**: The upgrade must add capability without breaking existing recipes: current calls keep their existing result, and opting in only changes which SCM coordinates are captured.


### Task 5 Support MCF threading in GCC MinGW settings
Ensure that GCC MinGW configurations can declare the `mcf` threading model as a supported compiler setting so newer `mingw-builds` toolchains work out of the box.

- **Expectation**: Users should be able to select the MCF threading model for MinGW GCC in normal configuration flows, and projects using that toolchain should no longer require manual settings customization just to recognize that threading option.

- **Constraints**: The change should be additive only: current MinGW GCC configurations must keep working as before, while the new threading option becomes available without altering unrelated compiler behavior.


### Task 6 Add incubating monolithic workspace install flow
Ensure that workspaces with multiple editable packages can be installed as a single monolithic consumer using `conan workspace install`, so users can generate one shared install result for the workspace while only external dependencies are installed and surfaced as consumer dependencies.

- **Expectation**: Users should be able to install an entire workspace once, rather than installing each editable package separately. The install result should represent the workspace as one top-level consumer, include only external dependencies in generated consumer outputs, and honor normal install options and profile/lockfile resolution.

- **Constraints**: This feature is opt-in and intentionally limited. It only applies to enabled workspaces, it only works when the workspace actually contains editable packages, and custom workspace-level configuration can customize the root consumer context without redefining dependency ownership or package build logic.


### Task 7 Generate an install-ready CMake workspace scaffold
Ensure that `conan new workspace` generates a default workspace that users can open and use as a monolithic CMake super-project with `conan workspace install`, without losing the standard editable products or their dependency relationships.

- **Expectation**: Creating a new workspace should produce a ready-to-use multi-project CMake starter that supports Conan workspace installation flows out of the box. Users should receive a complete top-level workspace build setup, and optional template inputs should extend the starter package behavior without changing the default workspace topology or package identities.

- **Constraints**: Keep the default starter workspace recognizable and backward-compatible for users of the built-in workspace template. The new install-ready behavior must add top-level workspace support without renaming the generated packages, changing their default relationships, or affecting other templates.


### Task 8 New CMakeDeps adds library and include search paths
Ensure that projects using the new CMakeDeps generator automatically expose dependency library, header, and tool search locations to CMake so consumers can resolve packages without manually extending search paths.

- **Expectation**: Using the new CMakeDeps flow should make CMake aware of dependency executables, libraries, and headers automatically. Tool lookup should remain limited to directly declared dependencies, while library and header lookup should also work through applicable host and test dependency graphs, and overlapping contributions should resolve deterministically with a visible notice.

- **Constraints**: Existing executable discovery behavior must continue to work, new search paths should appear only when dependencies actually expose them, build-only tools must not start affecting library or header lookup, and duplicate dependency contributions must resolve predictably rather than producing ambiguous search order.


### Task 9 Expose library and include search paths in new CMakeDeps
Ensure that projects using the new CMakeDeps generator automatically expose dependency library and include directories to CMake, while preserving existing executable path behavior and deterministic handling when the same package name contributes paths from multiple dependency contexts.

- **Expectation**: Using the new CMakeDeps generator should make dependency headers and libraries discoverable by normal CMake search behavior without extra manual path setup. Executable lookup should remain limited to direct dependencies, and conflicting contributions from the same package name should resolve predictably with a visible notice.

- **Constraints**: The new search-path support must not leak tool-only header or library directories into consumer resolution, and it must not change existing executable discovery beyond the current direct-dependency scope.


### Task 10 Expose dependency extension properties to Conan extensions
Ensure that Conan extensions and recipe-side dependency inspection can read `extension_properties` from dependency entries so dependency metadata can participate in user-visible behaviors such as custom compatibility or transitive policy decisions, without failing when a dependency does not define any extension properties.

- **Expectation**: Users upgrading to Conan 2.13.0 should be able to build extensions and dependency-aware logic that read extension metadata from dependencies directly. Dependency metadata should be observable consistently across the dependency graph, and missing metadata should behave as empty rather than causing failures.

- **Constraints**: Existing consumers should not break when some dependencies do not provide extension metadata. The upgrade should expand what metadata can be observed from dependencies, but it should not automatically impose new transitive rules unless user logic explicitly does so.


### Task 11 Add direct version-range checks on Version objects
Ensure that consumers can evaluate whether a `Version` instance matches a version range expression directly from the `Version` object, including control over prerelease resolution, without requiring a separate range object in user code.

- **Expectation**: Users should be able to call `in_range()` on a version object to check whether it falls within a declared version range. The result should match the library's existing interpretation of range expressions, and callers should be able to opt into or override prerelease handling when needed.

- **Constraints**: This should be a convenience addition, not a semantic rewrite. Existing version comparison and range-matching behavior should stay consistent, and malformed range inputs should fail the same way they already do elsewhere in the library.


### Task 12 Add experimental `conan lock upgrade` command
Ensure that Conan provides an experimental `lock upgrade` workflow that can refresh one or more selected dependencies in an existing lockfile by resolving the graph again, without requiring users to manually remove lock entries or choose the exact replacement version in advance.

- **Expectation**: Users should be able to upgrade specific locked dependencies directly from the CLI. Conan should determine the new concrete versions through normal dependency resolution using the current project graph and configuration, then write back an updated lockfile.

- **Constraints**: Only the dependency groups explicitly requested for upgrade should be refreshed, and the command should behave like a normal graph resolution operation rather than a manual lockfile editing step.


### Task 13 Expand Premake wrapper configuration and action handling
Ensure that the Premake CLI wrapper allows recipes to customize the Premake action, the root Lua script path, and additional command-line arguments while preserving automatic default action selection from compiler settings.

- **Expectation**: Users upgrading should be able to use the Premake wrapper as a configurable CLI front end instead of a fixed helper. By default it should still choose a sensible Premake action from the active compiler, but consumers must be able to point it at another Premake Lua entry file, override the action when needed, and append extra Premake options through the wrapper API.

- **Constraints**: The new configurability must extend the existing Premake integration without breaking the default experience. Existing recipes that rely on automatic action selection should keep working, while advanced consumers gain control over which Premake script and options are used.


## Bug Fixes

### Task 14 Preserve Shared-Library Symlinks in runtime_deploy
Ensure that `runtime_deploy` deploys shared libraries with the runtime-visible names applications expect, instead of only copying the resolved library file and omitting versioned shared-library entries or symlink aliases.

- **Expectation**: Runtime deployment should include the actual shared library plus the alias names the dynamic loader expects when symlink handling is enabled, so deployed applications can resolve libraries normally. When symlink handling is disabled, deployment should still provide the real library file without emitting the link aliases.

- **Constraints**: The fix should improve runtime compatibility without changing the deployer's overall layout model or turning it into a different deployment mode.


### Task 15 Clarify CMakeDeps tool-require linking guidance
Ensure that incubating CMakeDeps does not instruct consumers to link targets coming from tool requirements, while still showing the relevant package discovery guidance for those dependencies.

- **Expectation**: Users should see accurate CMake integration instructions: packages needed only as tools may still need discovery, but they must not be presented as libraries that should be linked into consumer targets.

- **Constraints**: The fix should narrow misleading guidance without hiding legitimate dependency discovery steps or changing how normal library dependencies are presented.


### Task 16 Fix CycloneDX SBOM license calculation
Ensure that CycloneDX SBOM generation reports each component's declared licenses correctly, including recipes that declare multiple licenses, without borrowing license entries from another component in the dependency graph.

- **Expectation**: Generating a CycloneDX SBOM should preserve every package's own declared license information at the component level. Packages with one license should show one license entry, and packages with multiple declared licenses should show all of them under the correct component regardless of what else is present in the graph.

- **Constraints**: The change should be limited to correcting license reporting accuracy and should not alter which components appear in the SBOM or how unrelated SBOM fields behave.


### Task 17 Propagate build-profile conf into GNU cross-build toolchains
Ensure that cross-building consumers using `AutotoolsToolchain` or `GnuToolchain` can read build-context configuration from the build profile `conf`, so build-machine compiler executables are correctly applied during toolchain generation.

- **Expectation**: Cross-build toolchains should honor compiler executable settings from the build profile, not just the host profile, so generated GNU-based toolchains use the correct compilers for build-machine tasks.

- **Constraints**: The fix should only affect build-context resolution for cross-builds, keep current target-context behavior intact, and remain safe when no build-profile compiler override is provided.


### Task 18 Support custom separators in profile environment variables
Ensure that profile-defined environment variables can explicitly declare a non-default separator so inherited environment values remain correctly composed in subsystem builds such as msys2. Ensure that invalid profile entries combining custom-separator semantics with path-style semantics are rejected.

- **Expectation**: Users should be able to declare how a profile-managed environment variable is joined when it inherits or combines with existing values, so Windows-style lists such as semicolon-separated include or path variables work correctly in subsystem-based builds. Conan should keep that declared separator visible when it reports the environment configuration, and it should fail fast on ambiguous qualifier combinations.

- **Constraints**: Existing profiles without an explicit custom separator should continue to behave as before. Custom joining rules must not silently trigger path-specific rewriting, and ambiguous profile syntax should be rejected instead of guessed.


### Task 19 Clarify component and runtime conflict errors
Ensure that invalid component dependency definitions and runtime-only package conflicts produce clear, actionable errors that identify the failing relationship and the affected packages or components.

- **Expectation**: Users should receive error messages that clearly distinguish misconfigured component requirements from runtime dependency conflicts. The errors should tell them what kind of mismatch occurred, which package or component caused it, and whether the conflict is specific to runtime composition rather than compile-time dependency resolution.

- **Constraints**: Improve diagnostics without changing the expected success path for correctly declared dependencies. Errors should be more informative, not broader in scope or triggered in unrelated scenarios.


### Task 20 Correct Conan client migration success output for compatibility.py updates
Ensure that Conan client migration output for compatibility file updates is correctly formatted and does not show malformed success text when upgrading.

- **Expectation**: Users upgrading Conan should see a clean, correctly formatted success notice if the migration updates their compatibility configuration, and they should not see malformed migration text.

- **Constraints**: Keep the migration behavior unchanged apart from correcting the user-visible output. The fix should improve message quality without altering when migration runs or what files it updates.


### Task 21 Protect read-only CppInfo.required_components access
Ensure that accidental writes to CppInfo.required_components are rejected as invalid, so users can inspect required component relationships without being able to overwrite the computed result.

- **Expectation**: Users should be able to read the resolved required component information, but they must not be able to assign to that property directly. Invalid writes should surface as a clear API error, while normal requirement aggregation continues to behave the same.

- **Constraints**: The fix should be limited to protecting the read-only property. It must not change how valid CppInfo configuration works or alter the dependency information returned when the property is read.


### Task 22 Fix CMakeDeps transitive linking for shared libraries
Ensure that the new `CMakeDeps` generator correctly handles transitive dependencies when a shared library or shared component depends on another shared library, so downstream consumers receive the needed dependency information without incorrect full-link propagation.

- **Expectation**: Upgrading should make transitive shared-library usage work correctly with `CMakeDeps`: shared libraries should no longer over-link other shared libraries, but downstream consumers should still inherit the required dependency information and build successfully. Existing non-shared transitive linking behavior should remain intact, and unsupported CMake versions should fail clearly instead of producing incorrect linkage.

- **Constraints**: Keep the fix limited to the incorrect shared-to-shared propagation case. Existing dependency consumption patterns, especially component-based and aggregate target consumption, should continue to behave as before unless the old behavior was specifically wrong for shared-library transitives.


### Task 23 Bundle new Conan tool namespaces in PyInstaller builds
Ensure that the self-contained Conan executable generated with PyInstaller includes newly added `conan.tools` modules, especially `conan.tools.sbom`, so users can run packaged Conan workflows that depend on those tool namespaces without module-loading failures.

- **Expectation**: The standalone Conan binary should behave like a normal installation for supported tool modules. After upgrading, workflows that rely on newly introduced Conan tool areas, especially SBOM generation, should work from the packaged executable without failing because those modules were omitted from the bundle.

- **Constraints**: The upgrade should expand packaged-module coverage without regressing existing packaged workflows or changing behavior outside the standalone executable distribution.


## Breaking Changes

### Task 24 Migrate Conan workspaces to the new class-based `conanws.py` model
Ensure that custom Conan workspaces are defined with the new class-based `conanws.py` contract so workspace metadata, editable package discovery, and workspace-level installs behave consistently with Conan 2.13.0.

- **Expectation**: Workspace customization should follow the same object-oriented pattern as package recipes: a workspace file defines one workspace class, can read shared YAML configuration, can customize how editables and metadata are derived, and can install the whole workspace as one consumer-facing unit instead of handling each editable independently.

- **Constraints**: The upgrade must preserve simple YAML-based workspaces, reject ambiguous or invalid custom workspace definitions early, keep editable references bounded to the workspace itself, and avoid treating a workspace install as a collection of separate editable installs. Any custom root used for whole-workspace installation should only describe the workspace shell, not redefine package behavior.


## Documentation

### Task 25 Clarify `conan remote auth` username environment variable guidance
Ensure that `conan remote auth` user guidance names the correct username environment variables for non-interactive remote authentication, so users relying on CLI help for CI, scripting, or `--with-user` filtering are directed to `CONAN_LOGIN_USERNAME*` rather than ambiguous `CONAN_LOGIN*` references.

- **Expectation**: Users reading the CLI help for remote authentication should see the correct environment variable names for providing usernames in automated workflows, and option help should consistently explain when a remote is considered to already have user credentials.

- **Constraints**: The change is limited to clarifying user-facing guidance. Existing authentication behavior and command semantics should remain the same.


## Performance Improvements

### Task 26 Improve tar.gz extraction performance and strip-root validation
Ensure that tar.gz extraction stays efficient and reports realistic progress when unpacking archives, including filtered extractions and root-folder stripping. Ensure that root-folder stripping only succeeds when the relevant archive entries belong to one shared top-level directory, and fails for archives that place files directly in the archive root or mix different top-level roots.

- **Expectation**: Selective tar.gz extraction should be faster and should not appear to run past 100% progress. When `strip_root` is enabled, extraction should remove exactly one shared top-level directory from the extracted content, preserve valid links under that directory, and reject archives that do not have a single removable root.

- **Constraints**: The upgrade must preserve existing extraction behavior for ordinary tar.gz unpacking, keep filtering behavior intact, and add stricter validation only for root-stripping scenarios that would otherwise produce ambiguous or incorrect output.


## Additional Changes
- Ensure that upgrading to Conan 2.13.0 removes the previous restriction that blocked compatible urllib3 2.0 releases, while still allowing environments that need the older urllib3 1.26 series to install and use Conan successfully.
- Ensure Docker runner executions keep working for recipes located under a declared layout root and for isolated cache modes that rely on host/build profiles, while allowing runner configuration to forward an optional Docker image build platform.
- Ensure users who depend on the previous multi-remote update resolution behavior can opt back into it explicitly, while making the compatibility mode visible as deprecated.
- Ensure generated CPS dependency metadata matches newer CPS/CMake discovery expectations for both file location and serialized package prefix information.
- Ensure `conan new` CMake templates generate compilable example code for packages and requirements whose names contain dots, without breaking identifier-oriented template substitutions that still need sanitized names.
