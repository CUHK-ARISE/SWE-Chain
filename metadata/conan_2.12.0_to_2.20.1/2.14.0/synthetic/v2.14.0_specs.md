# Upgrade Specification from 2.13.0 to 2.14.0

## New Features

### Task 1 Add conan audit vulnerability scanning
Ensure that Conan users can audit package references and dependency graphs for known vulnerabilities through a new `conan audit` workflow, configure and authenticate the vulnerability provider they want to use, and receive clear results when vulnerabilities, missing packages, authentication issues, or rate limits are encountered.

- **Expectation**: Users should be able to run a built-in audit command to check either a dependency graph or explicit package references for known CVEs, choose or manage the security provider used for the lookup, authenticate once or override credentials from the environment, and get readable or machine-consumable output that distinguishes clean scans from vulnerable, missing, unauthorized, or rate-limited responses.

- **Constraints**: The audit capability should be opt-in and predictable: invalid user input should fail early, provider configuration should be explicit, clean and vulnerable results should both be clearly reported, unavailable catalog entries should not hide successful results for other packages, and fatal provider or authentication failures should not be presented as successful audits.


### Task 2 Add Clang 20 compiler setting support
Ensure that Conan accepts Clang 20 as a supported `compiler.version` for the `clang` compiler so users can configure, install, and create packages with Clang 20 toolchains.

- **Expectation**: Users should be able to select Clang 20 in Conan the same way they select other supported Clang versions, and Conan should treat that compiler choice as supported during normal package operations.

- **Constraints**: The upgrade should add support for the new compiler release without regressing existing compiler-version handling or changing how current supported Clang configurations behave.


### Task 3 Selective workspace install by editable path
Ensure that `workspace install` can target only the selected editable packages in a workspace when one or more package paths are provided, instead of always installing the entire workspace.

- **Expectation**: Users should be able to run `workspace install` for just the part of a workspace they are actively working on by naming one or more editable package paths. A normal `workspace install` with no extra paths should still behave like a full workspace install. The command should not silently succeed when there is nothing installable in the requested scope.

- **Constraints**: This feature is a scoped install option, not a change to how full workspace installs work. Selecting a subset should avoid pulling in unrelated workspace packages as top-level install targets, and empty selections should still be treated as an error.


### Task 4 Add validate lifecycle hooks for recipe validation
Ensure that Conan exposes lifecycle hooks around recipe validate() execution so CI and other integrations can apply additional validation logic during package evaluation without changing the recipe.

- **Expectation**: Users should be able to attach custom logic immediately before and after recipe validation, allowing environment-specific validation policies to run automatically wherever Conan evaluates a recipe. Recipes that explicitly reject a configuration should continue to be treated as invalid configurations, while still allowing the post-validation hook to observe the completed validation outcome.

- **Constraints**: The feature should extend validation observability without changing how unrelated lifecycle hooks behave or altering the meaning of an invalid recipe configuration. It should add hook coverage only where recipe validation actually exists.


### Task 5 Add Apple framework support to CMakeConfigDeps
Ensure that CMakeConfigDeps fully supports Apple framework-based dependencies, including packaged frameworks, system frameworks, and framework search paths, so consumers can use framework-only packages without extra manual integration metadata.

- **Expectation**: Consumers using CMakeConfigDeps should be able to consume Apple framework dependencies the same way they consume other Conan packages: packaged frameworks should link correctly, required system frameworks should no longer be ignored, and framework search locations should be available automatically. Invalid framework exports should fail clearly instead of producing incomplete package metadata.

- **Constraints**: The new capability should extend framework handling without regressing ordinary package consumption. Framework packages should work from their own metadata rather than from workarounds, and malformed framework declarations should be rejected instead of partially accepted.


### Task 6 Support Apple package frameworks in CMakeConfigDeps
Ensure that upgrading to Conan 2.14.0 lets Apple framework packages be consumed correctly through CMakeConfigDeps, including both packaged frameworks exported by a dependency and Apple system frameworks declared in package metadata.

- **Expectation**: Consumers using CMakeConfigDeps should be able to depend on Apple frameworks the same way they depend on normal Conan packages: generated CMake package targets should carry the right framework linkage and framework-specific metadata so builds work without special manual wiring.

- **Constraints**: The new framework support must not break existing non-framework package consumption, and framework packages must still provide enough metadata for consumers to resolve the actual framework artifact and link model safely.


## Bug Fixes

### Task 7 Improve Conan Jinja2 Profile Syntax Error Reporting
Ensure that invalid Jinja2 syntax in Conan profile templates fails with a clear profile-rendering error tied to the affected profile, including when the faulty template is loaded indirectly through profile includes.

- **Expectation**: Users should get a consistent Conan profile error whenever a templated profile is malformed, with enough context to see which profile caused the failure and why, even if that profile was pulled in by another profile.

- **Constraints**: The upgrade should improve failure clarity without changing how working profiles load or how profile inclusion behaves in successful cases.


### Task 8 Suppress false auto-deduce warnings for exact library matches
Ensure that automatic library location deduction does not warn users about multiple matches when the resolved library file is already an exact match for the requested library name, while preserving warnings for genuinely ambiguous matches.

- **Expectation**: When Conan can clearly identify the intended library from the available files, it should resolve it quietly instead of reporting a misleading ambiguity warning. Users should still be warned when the available matches remain meaningfully ambiguous.

- **Constraints**: Limit the change to warning behavior for clearly identifiable matches. Keep location deduction behavior stable and retain warnings for cases that are still ambiguous from a user perspective.


### Task 9 Deprecate cmake_set_interface_link_directories in CMake dependency generators
Ensure that packages upgrading to Conan 2.14 no longer depend on cmake_set_interface_link_directories for generated CMake dependency metadata, and that any use of this property is treated as deprecated for CMakeDeps and invalid for CMakeConfigDeps in favor of complete package_info() declarations.

- **Expectation**: The upgrade should make standard package metadata the only supported source of CMake dependency information. The old opt-in property may still be recognized for compatibility signals, but users should see that it is no longer needed in CMakeDeps and should not be used with CMakeConfigDeps.

- **Constraints**: Packages that already describe their libraries and components correctly should keep generating usable CMake metadata. The change should only remove reliance on the legacy property and should not force consumers to adopt new behavior beyond using normal package declarations.


### Task 10 Preserve Windows Paths in MSBuildDeps
Ensure that MSBuild dependency files generated by `MSBuildDeps` preserve Windows-style path separators so MSBuild features that depend on native `\` paths continue to work correctly.

- **Expectation**: Generated MSBuild dependency metadata should use Windows-native path formatting where applicable, so consumers can rely on the output with MSBuild functionality that expects standard Windows paths.

- **Constraints**: Keep the change narrowly focused on path formatting. The generated files should remain usable by existing MSBuild workflows while avoiding path shapes that are invalid or unexpectedly rooted.


### Task 11 Isolate local-recipes-index cache from workspace home_folder overrides
Ensure that using a local-recipes-index remote from within a workspace does not let the workspace home_folder redefine the remote's auxiliary cache location. Ensure that direct ConanAPI cache_folder configuration only accepts absolute paths.

- **Expectation**: Users should be able to work with a local recipes index remote even when a workspace relocates the main Conan home. The remote's internal metadata and cache should remain self-contained, and explicit API cache paths should be accepted only when they identify an unambiguous absolute location.

- **Constraints**: Workspace configuration may change the main working environment, but it must not corrupt or relocate special-purpose remote storage. Cache path validation should reject ambiguous relative locations.


### Task 12 Preserve prepend order in environment profile dumps
Ensure that dumping environment definitions from profiles preserves the user-declared prepend order so serialized output reflects the intended environment composition for both regular and path variables.

- **Expectation**: Serializing environment settings should round-trip user-authored prepend operations without reordering them. Users who load and re-dump a profile should see prepended values stay in the intended order, including when prepend and append operations are combined.

- **Constraints**: Keep existing environment dump behavior intact except for correcting the order of prepended values. The output should remain stable for append-only cases and continue to distinguish prepends from appends correctly.


### Task 13 Support VCVars generation for WindowsStore targets
Ensure that the VCVars generator produces the expected Visual Studio environment setup script when the host operating system is WindowsStore and the build operating system is Windows.

- **Expectation**: Windows Store application targets should be handled like other Windows targets by the Visual Studio environment generator. Installing for a WindowsStore target from a Windows build machine should yield the same usable compiler setup script that users expect for Windows-based builds, including cross-target setups.

- **Constraints**: The fix should expand support only to the missing WindowsStore target case without broadening the feature to unrelated operating systems or altering existing Windows behavior.


### Task 14 Avoid self-referential build-profile tool requirements
Ensure that build-profile `[tool_requires]` entries do not create a self-dependency or graph loop when a tool package matches itself, including when the self-reference is expressed as a version range.

- **Expectation**: Build-profile tool requirements should never cause a package to depend on itself. Self-references must be skipped whether they are written as the same version or as a version range that resolves to the current package, while valid non-self tool requirements remain unaffected.

- **Constraints**: Only real self-dependency loops should be blocked. Unrelated tool requirements and valid alternative-version requirements should continue to resolve as before.


### Task 15 Fix reduced recipe build-order to exclude non-build packages
Ensure that reduced, recipe-ordered `conan graph build-order` output only reports package configurations that still require a build, instead of keeping non-build packages under recipes that are otherwise part of the build order.

- **Expectation**: In reduced recipe-level build-order output, Conan should show only the package variants that actually need to be built. A recipe may still appear in the build order, but any package variant that does not require a build should be omitted from the reported work set.

- **Constraints**: The fix must narrow the reduced output without changing which recipes still require work. It should preserve the same build ordering while hiding package variants that are already satisfied or otherwise not scheduled to build.


### Task 16 Detect user and channel conflicts in version-range dependency resolution
Ensure that dependency graph resolution raises a conflict when requirements for the same package are compatible by version expression but differ by package user or channel, including cases where one or both requirements use a version range.

- **Expectation**: When Conan evaluates overlapping dependency requirements, package namespace differences must be treated as real conflicts. Requirements that point to different users or channels should fail resolution even if their versions or version ranges would otherwise match.

- **Constraints**: The fix should only tighten incorrect acceptance of mismatched package identities. Compatible dependencies in the same namespace should continue resolving as before, and conflict detection should be consistent regardless of traversal order.


## Additional Changes
- Ensure that the Docker runner supports explicit Docker platform selection, correctly mounts projects whose conanfile lives under a subfolder layout, resolves and stages the requested host and build profiles even when those profiles are outside the Conan home, and presents clearer runner execution logs without changing the basic Docker runner workflow.
- Ensure that `workspace add --ref` is only accepted when the user supplies an actual reference value to add to the workspace.
