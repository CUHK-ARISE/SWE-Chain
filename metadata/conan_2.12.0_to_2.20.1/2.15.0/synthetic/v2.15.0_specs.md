# Upgrade Specification from 2.14.0 to 2.15.0

## New Features

### Task 1 Clarify graph vs package-list JSON inputs
Ensure that list and package-list workflows clearly distinguish graph JSON files from package-list JSON files, provide actionable user-facing errors when the wrong JSON format is supplied, and honor graph context filtering semantics for host/build and exclusive host-only/build-only use cases.

- **Expectation**: When a user passes the wrong kind of JSON file into a graph-based or package-list-based command, Conan should fail with a clear, corrective error that explains the mismatch and points to the right way to generate the expected JSON. Graph filtering should continue to respect build and host contexts, including exclusive modes that return only the packages unique to the requested context.

- **Constraints**: This change must improve diagnostics without weakening existing success paths or masking unrelated file problems. Correct inputs should keep working as before, and exclusive context views should stay strictly limited to the requested side of the dependency graph.


### Task 2 Add graph-context filtering to graph-based conan list
Ensure that `conan list` can filter graph-based listing results by dependency context, including build-only and host-only views, so users can inspect the relevant subset of a dependency graph without losing the default combined behavior.

- **Expectation**: Users should be able to run `conan list` on a graph file and ask for only build-context results, only host-context results, or only entries unique to one context. The command should preserve the existing unfiltered view when no context filter is supplied, and it should clearly reject JSON files that are not graph exports instead of producing misleading graph-processing errors.

- **Constraints**: The new option should narrow graph-based output without changing existing default listing behavior or unrelated list operations. Exclusive views should hide only true overlap between host and build contexts, not dependencies that exist only on the requested side or differ between the two sides.


### Task 3 Support trailing wildcard version-range patterns
Ensure that version ranges accept trailing-wildcard patterns so users can declare dependencies against a version prefix, such as a specific release line or metadata-prefixed series, without enumerating every matching version.

- **Expectation**: Users should be able to express version ranges as prefix patterns by placing a wildcard at the end of the version expression. Matching versions should be accepted based on sharing that prefix, while all existing non-pattern range syntax continues to behave the same way.

- **Constraints**: Wildcard support should be narrowly scoped to the new end-of-expression pattern syntax and must not change how existing exact-version or comparator-based ranges are interpreted. A match should require the intended prefix, not a loosely related version.


### Task 4 Expose Apple subsystem metadata in MesonToolchain cross builds
Ensure that MesonToolchain includes Apple subsystem information when cross-compiling between Apple operating systems so Meson can correctly identify macOS, device, and simulator targets.

- **Expectation**: Cross-compiling from one Apple platform to another with MesonToolchain should provide enough platform metadata for Meson to distinguish macOS from Apple device and simulator targets. Users should get the correct Apple target classification automatically during Meson toolchain generation.

- **Constraints**: The change should be additive and limited in scope: it should improve Apple cross-platform identification without altering unrelated build configurations or introducing failures when detailed Apple SDK information is unavailable.


### Task 5 Expose Apple build-context detection and Meson subsystem metadata
Ensure that Apple-to-Apple cross-compilation generated through `MesonToolchain` exposes the correct Apple platform subtype for both build and host machines, and ensure that `is_apple_os` can evaluate either the host context or the build context when callers need to distinguish Apple build profiles.

- **Expectation**: Users generating Meson files for Apple cross-builds should get platform-specific machine metadata that differentiates macOS from iOS, tvOS, watchOS, or visionOS on both the build side and the host side. Users of `is_apple_os` should also be able to ask whether the build profile is an Apple OS, not just the host profile.

- **Constraints**: Do not change behavior outside Apple-to-Apple cross-build scenarios, and keep the new capability backward-compatible for callers and Meson consumers that ignore the extra metadata.


### Task 6 Add cross-platform chmod helper to tools.files
Ensure that Conan recipes can change file and directory permissions through a public `tools.files.chmod` API that controls owner read/write/execute access, supports recursive updates when requested, and fails clearly for invalid or missing targets.

- **Expectation**: Users should be able to change permissions from a Conan recipe through a supported, cross-platform helper instead of manually composing permission masks. The API should let them toggle owner access, preserve any permission they did not ask to change, optionally update directory contents recursively, and report invalid usage or missing targets as explicit failures.

- **Constraints**: This feature should stay a thin, safe wrapper around native permission changes: it should change only the requested owner access, avoid unexpected side effects on unrelated permissions or paths, respect operating-system limits, and reject no-op or invalid requests.


## Bug Fixes

### Task 7 Clean unknown-ref backup sources during cache cleanup
Ensure that `conan cache clean --backup-sources` removes cached backup source entries even when Conan cannot associate those entries with a known reference and they are recorded as unknown.

- **Expectation**: Cache cleanup should delete stale backup source artifacts even if they are orphaned from any known package or recipe reference. Upload behavior should remain scoped to the references the user is actually uploading.

- **Constraints**: The fix should only make cleanup more complete for unknown backup sources. It should not cause unexpected uploads, ignore existing exclusions, or change normal handling of known references.


### Task 8 Fix CycloneDX SBOM author attribution
Ensure that generated CycloneDX SBOMs report the actual author for the root package and dependency components, and provide a consistent fallback when author metadata is not declared.

- **Expectation**: CycloneDX SBOM output should attribute each package to its own declared author instead of labeling everything as the build tool, and it should still produce a usable SBOM when author information is missing.

- **Constraints**: Only author attribution and the consistency of the affected component metadata should change; the rest of the SBOM structure and generation flow should behave as before.


### Task 9 Preserve matching library symlink paths during auto-deduction
Ensure that Conan's automatic shared library location deduction preserves a matched symlink path when that symlink file is the library name being exposed, instead of rewriting the location to the symlink's final target.

- **Expectation**: Users upgrading to 2.15.0 should get the library location they actually published under the expected library name. If that published library file is a symlink, Conan should preserve that visible path rather than replacing it with a deeper resolved file.

- **Constraints**: The fix should only stop unwanted path canonicalization for matching symlinked libraries. It must not change normal library discovery behavior for ordinary files or otherwise alter how libraries are identified.


### Task 10 Move CLI-facing graph, remote lookup, and runner support onto ConanAPI
Ensure that upgrading to Conan 2.15.0 uses supported ConanAPI entry points for CLI-related package listing, outdated dependency inspection, and runner selection instead of private internals. Ensure that custom graph output templates continue to render correctly by consuming serialized dependency graph data and no longer depending on the removed deprecated graph proxy.

- **Expectation**: After the upgrade, supported public APIs should cover the CLI workflows that previously depended on private modules, while the observable command behavior remains consistent for users. Graph template customization should keep working through the serialized dependency graph contract, without relying on the old legacy graph helper.

- **Constraints**: Keep the upgrade focused on replacing private access paths with supported ones, without changing which packages are considered present, which dependencies are actually outdated, or when configured runners are allowed to take control. Any newly exposed outdated-query API should be treated as unstable rather than a fully committed long-term contract.


### Task 11 Warn on deprecated recipes in dependency graphs
Ensure that Conan visibly warns users when a dependency graph includes packages coming from recipes marked with the `deprecated` attribute.

- **Expectation**: Users should be explicitly notified whenever a resolved dependency graph contains deprecated packages, so deprecation status is clear during normal CLI workflows.

- **Constraints**: The upgrade should improve visibility of deprecated dependencies without breaking successful operations or adding noise to graphs that are not affected.


### Task 12 Shorten generator-relative dependency paths
Ensure that generated dependency and build-integration files use the shortest valid relative path to referenced package or deploy locations when the generators folder is nested, instead of emitting unnecessarily long path references.

- **Expectation**: Generated Conan build files should prefer the shortest correct relative path from the generator output location to package or deploy folders. If a safe relative path cannot be determined, Conan should keep the existing path rather than emit an invalid one.

- **Constraints**: Shorten paths only when doing so is safe and unambiguous. Keep current behavior for layouts that do not support a valid relative path, and preserve format-specific path conventions.


### Task 13 Fix CMakeDeps component type handling for shared dependencies
Ensure that CMakeDeps can consume packages that declare component dependencies without failing on component metadata lookup, and ensure that shared-library dependency relationships are generated correctly for dependencies within the same package, across packages, and when requiring another package's root target.

- **Expectation**: Packages that model libraries through `cpp_info` components should remain consumable through CMakeDeps. Declaring shared-library components or transitive requirements must not cause generator failures, and the generated dependency relationships should match whether the consumer and dependency are shared libraries.

- **Constraints**: Keep existing target naming and dependency resolution stable except for correcting the broken component metadata lookup and the resulting shared-library linkage behavior. Non-shared consumers should continue to receive the dependency links they previously relied on.


### Task 14 Fix global.conf and profile [conf] precedence
Ensure that configuration values defined in global.conf do not take precedence over profile [conf] values, and ensure that per-package pattern configuration inherited from global.conf is applied in an order that lets profile-specific package configuration override or extend it predictably.

- **Expectation**: Global configuration should supply defaults, not win conflicts. If the same configuration is declared globally and in a profile, the profile should determine the effective result. Package-scoped configuration coming from the global level should still be inherited, but profile package rules should be applied after it so overrides and ordered value composition match user intent.

- **Constraints**: Preserve all independent configuration that does not conflict, and limit the change to how global and profile settings are merged. Existing behavior for configurations defined in only one source should remain intact.


### Task 15 Respect lockfile revisions with legacy update policy
Ensure that Conan operations using `core:update_policy=legacy` remain compatible with lockfiles, and that references already pinned to a revision by a lockfile are not reprocessed through the legacy update path.

- **Expectation**: Using the legacy update policy together with lockfiles should be stable. If a lockfile has already pinned a dependency or package revision, update-enabled execution should respect that pinned revision instead of trying to refresh it through the legacy update mechanism.

- **Constraints**: Keep current update behavior for unresolved references, while treating lockfile-pinned revisions as authoritative and non-updatable within the legacy policy flow.


### Task 16 Fix untargz extraction for restrictive directory modes
Ensure that `untargz()` can extract tar archives even when archived directories have restrictive permission modes, including during selective extraction flows such as `strip_root` and pattern-based extraction, without requiring callers to modify the archive or relax permissions first.

- **Expectation**: Tar extraction should succeed for valid archives even if some archived folders are marked with restrictive permissions. Optional filtering and root-stripping features should continue to work the same way from the caller’s perspective, and users should not depend on percentage progress updates during extraction.

- **Constraints**: The fix should remove the permission-related failure mode without changing which files are extracted, how root stripping behaves, or how archive filtering works. It should preserve existing validation behavior for unsupported archive layouts.


### Task 17 Prioritize exact library filename matches in CppInfo auto-deduction
Ensure that Conan's automatic C/C++ library location deduction prefers the exact library requested by `cpp_info.libs` before matching similarly named library files, so packages resolve the intended artifact when exact and suffixed library names coexist.

- **Expectation**: Library auto-detection should choose the exact requested library whenever it is available, and only fall back to close-name variants when no exact match exists.

- **Constraints**: The fix should be narrowly scoped: keep current compatibility with normal library naming conventions and fallback matching, but remove incorrect preference for similarly named libraries over the exact one.


### Task 18 Fix JSON output for class-based custom tool generators
Ensure that Conan JSON output does not crash when a tool-require provides a custom generator as a class reference instead of a string name, and that the serialized generator list remains readable and usable to clients consuming `--format=json` output.

- **Expectation**: JSON-formatted Conan output should support custom generators from tool packages regardless of whether they were declared by name or by class, and it should present those generators as normal names instead of failing.

- **Constraints**: Existing JSON consumers should continue receiving the same overall generator list structure, with the only change being that previously failing class-based custom generators now appear as names and do not break output generation.


### Task 19 Fix CycloneDX SBOM metadata and empty-component generation
Ensure that CycloneDX SBOM generation reports correct metadata for the package or consumer being described and still succeeds when the resolved graph produces no emitted components after root-node and context filtering.

- **Expectation**: When a CycloneDX SBOM is generated, the top-level metadata should describe the actual package or consumer that requested the SBOM, not one of its dependencies. Package author details should come from package metadata when available. SBOM generation must also work for edge cases where the filtered dependency graph contributes no output components.

- **Constraints**: Keep the current inclusion rules for build and test dependencies, and preserve normal dependency reporting behavior. If there is nothing to list as a component, the SBOM should still be generated cleanly without inventing extra package entries.


## Additional Changes
- Ensure that `MSBuildDeps` generates component dependency imports using the actual resolved dependency package name, so MSBuild generator output remains valid when dependency replacement changes the package name seen in the graph.
