# Upgrade Specification from 2.15.1 to 2.16.0

## New Features

### Task 1 Add GCC 15.1 compiler support
Ensure that GCC 15.1 is supported as a valid compiler version for Conan package settings so users can configure profiles and package builds with that compiler version without version-rejection errors.

- **Expectation**: Users should be able to select GCC 15.1 in Conan the same way they can select previously supported GCC versions. The upgrade should make GCC 15.1 a first-class supported compiler target while leaving the overall GCC configuration experience consistent with earlier releases.

- **Constraints**: The change should expand compatibility to GCC 15.1 without regressing existing GCC workflows or altering unrelated compiler-setting behavior.


### Task 2 Support multilib components in CMakeConfigDeps with deprecation warnings
Ensure that upgrading to 2.16.0 allows CMakeConfigDeps consumers to use packages whose cpp_info.components entries expose more than one library, while warning package authors that multi-library components are deprecated and should be modeled as one component per library.

- **Expectation**: Packages that still group several libraries under one declared component should continue to work with generated CMake package configuration files after the upgrade. Consumers should be able to link the advertised component or package target and receive all underlying libraries, but authors should be clearly warned that this component shape is deprecated and should be split in the future.

- **Constraints**: The compatibility addition should be backward-compatible for consumers, limited to supporting a previously problematic deprecated component layout, and should not change the expected behavior of already-correct package and component definitions.


### Task 3 Expose dependency CMake modules through CMakeConfigDeps
Ensure that projects using CMakeConfigDeps can include CMake modules provided by dependencies without manually managing the module search path.

- **Expectation**: When a dependency or tool dependency ships reusable CMake modules, consumers using the generated CMake integration should be able to load those modules with normal include() calls, with no extra manual path wiring.

- **Constraints**: The upgrade should expand module discovery without changing unrelated dependency lookup behavior or requiring consumers to change how they locate programs, libraries, headers, or frameworks.


### Task 4 Configurable audit scan severity threshold
Ensure that `conan audit scan` supports a configurable vulnerability severity threshold and fails the command when scanned dependencies contain findings at or above that threshold, with critical findings causing failure by default.

- **Expectation**: `conan audit scan` should let users define how severe a vulnerability must be before the scan is considered a failure. By default, critical vulnerabilities should make the command fail, but users should be able to raise the threshold to avoid failing on lower-severity findings or effectively disable this failure mode. The scan should still present the vulnerability results even when it fails.

- **Constraints**: Only scans that meet the configured severity cutoff should fail because of vulnerability severity. Regular scan output should remain available, and unrelated audit commands should not be implicitly changed by this requirement.


### Task 5 Align GnuToolchain with recent Autotools and Android cross-build behavior
Ensure that upgrading to 2.16.0 makes `GnuToolchain` mirror the latest `AutotoolsToolchain` behavior for Apple builds and cross-builds: preserve Apple-specific extra flags, configure Android NDK host tools more completely, avoid overwriting user-provided build-environment compilers, and continue exposing build-machine compilers separately during cross-building.

- **Expectation**: After the upgrade, `GnuToolchain` should behave consistently with the GNU/autotools-oriented toolchain flow: Apple-specific compiler and linker flags are propagated correctly, Android cross-builds auto-wire the expected NDK tools, user customizations in the build environment are preserved, and native build-machine compilers remain available separately from host-target compilers.

- **Constraints**: The upgrade should improve generated toolchain behavior without forcing new Android configuration just to identify the target, without clobbering user-provided environment settings, and without mixing native build-machine tools with target-host tools.


### Task 6 Add CycloneDX 1.6 SBOM support
Ensure that users can generate CycloneDX 1.6 SBOMs and that CycloneDX SBOM output correctly identifies application packages while reflecting the schema changes introduced in CycloneDX 1.6.

- **Expectation**: Users should be able to opt into CycloneDX 1.6 output and receive SBOMs that match the 1.6 schema, while both supported CycloneDX formats should accurately identify applications as applications rather than always treating them as libraries.

- **Constraints**: The upgrade should add the new schema support without changing which dependencies are included or regressing existing SBOM content outside the documented CycloneDX 1.6 differences.


### Task 7 Add opt-in no-skip requirement trait for exceptional dependency edges
Ensure that recipes can mark exceptional requirements as non-skippable so privately required application or tool dependencies that are still needed remain available instead of being skipped by Conan.

- **Expectation**: Users upgrading should be able to opt specific dependency relationships out of skip pruning when those dependencies are still needed for actual package behavior, especially for wrapper-style applications or tools that privately rely on other applications.

- **Constraints**: Existing dependency behavior should remain unchanged unless a package author explicitly marks a requirement as non-skippable. The new trait should preserve needed dependencies without broadly changing how the dependency is exposed or classified.


### Task 8 Early validation for invalid conf_info value types
Ensure that `conf_info` rejects raw Conan settings and option objects as configuration values and reports the misuse as soon as the recipe assigns them.

- **Expectation**: Recipes should only publish configuration data through `conf_info` using normal Python values such as strings, numbers, booleans, or lists of such values. If a recipe tries to expose a live settings or options object directly, Conan should stop immediately with a clear error.

- **Constraints**: The change should be limited to preventing invalid configuration value types. Valid `conf_info` data should behave as before, and the upgrade should not introduce new behavior changes for correctly typed configuration entries.


### Task 9 Expose former command workflows through ConanAPI
Ensure that integrations upgrading to Conan 2.16.0 can perform template generation, remote authentication, and build-order operations through ConanAPI instead of command-layer internals, while preserving the existing observable behavior of those workflows and reporting `graph info` warnings only for actionable missing or invalid package states.

- **Expectation**: The supported automation surface for these package-management workflows should be ConanAPI rather than internal CLI helpers. Consumers should be able to generate project templates, log into remotes, and compute or merge build orders programmatically with the same observable outcomes they previously got from the commands, and graph inspection should warn only about packages that are actually missing or invalid.

- **Constraints**: The upgrade should reduce reliance on private internals without changing the practical results of the supported workflows. Diagnostics should become narrower and more actionable, not noisier.


### Task 10 Public MSBuildDeps platform override for WiX x86 projects
Ensure that MSBuild dependency generation provides a supported way to customize the platform name used in generated property sheets so projects with nonstandard platform naming, including WiX x86 builds, can consume Conan-generated imports without platform-condition mismatches.

- **Expectation**: Users should be able to rely on a public API to override the platform label used in generated MSBuild dependency metadata. If they do nothing, the library should keep using the normal architecture-based platform name; if their build system expects a different identifier, they should be able to replace it.

- **Constraints**: Existing builds that do not customize the platform should continue to behave the same way. The supported customization should be limited to the observable platform identifier used for MSBuild selection and should not change unrelated dependency-generation behavior.


### Task 11 Add support for newer intel-cc compiler releases
Ensure that Conan recognizes newer `intel-cc` compiler releases so users can configure Intel oneAPI 2024.1, 2025.0, and 2025.1 in their profiles and recipes without unsupported-version failures.

- **Expectation**: After upgrading, users should be able to select recent Intel oneAPI compiler releases in Conan just like older supported `intel-cc` versions, and those selections should behave consistently with the existing Intel compiler integration.

- **Constraints**: Existing Intel compiler configurations must remain compatible, and the upgrade should expand support rather than changing how the compiler family is configured.


### Task 12 Show package configuration during source builds
Ensure that when packages are built from source, users can see the effective configuration being used for each package in the build output.

- **Expectation**: When Conan builds a package from source, the user should be able to inspect the build log and immediately understand the configuration that package is being built with.

- **Constraints**: Show only real, effective configuration data for each built package, keep the output concise, and avoid changing the underlying build result or introducing misleading placeholders for missing values.


### Task 13 Show per-dependency configuration in debug graph output
Ensure that dependency graph output shown with `-vv` includes the effective configuration for each dependency entry, so users can inspect what every required, test-required, and build-required package is being built or resolved for.

- **Expectation**: Using debug-level verbose output should reveal a per-dependency configuration summary directly under each dependency in the graph, while standard verbosity continues to show only the existing dependency status lines.

- **Constraints**: The feature should add diagnostic detail without changing the structure or meaning of normal graph output, and users who do not opt into higher verbosity should not see extra output.


## Bug Fixes

### Task 14 Improve conan audit reporting for unscanned packages
Ensure that `conan audit` explicitly reports packages that could not be scanned, continues processing remaining packages when a single package lookup fails, and still surfaces fatal provider failures after showing any partial audit results already collected.

- **Expectation**: Audit reports should no longer silently omit packages that the vulnerability service cannot resolve. If one package cannot be scanned, the report should still include that package with a clear not-scanned outcome and continue auditing the rest. If the provider encounters a fatal condition that prevents the audit from continuing, the command should preserve any results gathered so far and then fail with a provider-level error.

- **Constraints**: Single-package lookup problems should degrade gracefully without hiding other audit results, while true provider-wide failures should still stop the command. Normal clean-scan results must remain unchanged, and the reporting model must clearly distinguish a package that was scanned successfully from one that was never scanned.


### Task 15 Fix audit HTML severity sorting and layout
Ensure that the HTML vulnerability audit report orders rows by actual severity rank, places vulnerabilities with unknown severity below ranked severities when sorting descending, and renders the severity column without content overflow.

- **Expectation**: The HTML audit report should sort vulnerabilities by meaningful severity rather than by the presentation text. Unknown-severity items should sort after real severity levels, and the severity column should display cleanly within the report layout.

- **Constraints**: Keep the report appearance consistent for visible severity labels while correcting sort behavior. The fix must improve ordering and layout without changing the meaning of displayed severity information.


### Task 16 Improve audit HTML report ordering and text layout
Ensure that the audit HTML output remains readable when vulnerability descriptions are long, and ensure that descending severity ordering presents rated vulnerabilities before entries with unavailable severity information.

- **Expectation**: Users should be able to open the audit HTML report and read long vulnerability descriptions without broken table formatting, and sorting by highest severity should prioritize entries that actually have a severity over unknown or unavailable ones.

- **Constraints**: The upgrade should make the report clearer and better ordered without hiding data, changing what vulnerabilities are reported, or requiring users to adopt a different reporting workflow.


### Task 17 Restrict saved audit provider file permissions
Ensure that persisted audit provider configuration is stored with access limited to the current user so sensitive provider data is not left readable or writable by other users.

- **Expectation**: Whenever audit provider settings are persisted, the configuration file should be secured as a private user-owned file. Users should be able to continue managing audit providers normally, while stored credentials and provider metadata are no longer exposed through overly broad filesystem permissions.

- **Constraints**: The upgrade should tighten file privacy without changing how users add, update, or use audit providers, and without altering the configuration data they expect Conan to store.


### Task 18 Correct Apple SDK version settings
Ensure that Apple platform configuration only exposes real released OS and SDK versions, so users can select missing legitimate versions and cannot continue using bogus SDK version values in Conan settings.

- **Expectation**: Apple-related Conan settings should reflect actual released Apple platform versions. Valid released versions that were missing should become selectable, and non-existent SDK versions should no longer be treated as valid configuration choices.

- **Constraints**: Keep existing Apple configuration behavior stable except for correcting the affected version lists. Users with already valid Apple settings outside the corrected entries should see no behavior change.


### Task 19 Decouple Conan CLI commands from legacy imports
Ensure that Conan CLI workflows remain usable after legacy `from conans` imports are removed, including remote authentication, graph reporting and build-order commands, profile detection output, list timestamp display, and graph export rendering.

- **Expectation**: Users upgrading to 2.16.0 should be able to keep using the same Conan CLI commands even if old compatibility modules are unavailable. Remote login, build-order generation, graph inspection and export, profile detection, and package-list timestamp output should continue to work, and graph inspection should clearly call out packages that are missing binaries or are invalid.

- **Constraints**: Keep the upgrade backward-compatible for normal CLI usage. Removing the old compatibility dependency must not break established command invocations, hide dependency problems, or force users to change how they specify remotes, graph inputs, profiles, or list queries.


### Task 20 Fetch SCM commits explicitly before Conan Git checkout
Ensure that recipes using Conan's Git SCM integration can retrieve and check out the commit recorded in `conandata.yml` even when that commit is not included in the refs obtained by a normal clone.

- **Expectation**: When a recipe restores sources from stored SCM coordinates, Conan should reliably obtain the exact requested commit before checkout, including commits that exist on the remote but are not reachable through the branch or tag refs fetched by default.

- **Constraints**: The fix should preserve normal SCM checkout behavior for existing recipes while adding support for less common remote commit layouts, without changing the intended source revision that users receive.


### Task 21 Add ARM64EC support to Microsoft build helpers
Ensure that Conan's Microsoft build integrations recognize and propagate the `arm64ec` architecture as a valid Visual Studio/MSBuild platform so users can generate, configure, and invoke Windows builds targeting ARM64EC without missing-platform failures or incorrect platform selection.

- **Expectation**: Users targeting ARM64EC should see Conan treat that architecture as a first-class Visual Studio/MSBuild platform across project generation, dependency property sheets, layout selection, and build command creation. Generated MSBuild invocations should remain valid and consistently formatted, while existing supported Windows architectures continue to behave the same.

- **Constraints**: The upgrade should add ARM64EC coverage without changing how previously supported Windows targets are selected. It should keep established Windows-specific behavior working and avoid introducing unrelated build configuration changes.


### Task 22 Expose build_args for editable packages in graph build-order
Ensure that `conan graph build-order` includes usable build arguments for editable packages that must be built, so users can consume build-order output consistently for both editable and non-editable dependencies.

- **Expectation**: Users should receive the same actionable rebuild instructions for editable dependencies that they already receive for regular packages when those dependencies appear in build-order results as needing a build.

- **Constraints**: Only dependencies that are actually scheduled for a build should gain build instructions, and the fix must not alter existing build-order behavior for packages that are not being built.


### Task 23 Clarify private audit provider curation errors
Ensure that private audit provider failures explain when JFrog Curation is likely unavailable, and ensure that package-not-found audit results are reported as packages not scanned rather than as vague or misleading provider errors.

- **Expectation**: Private audit integrations should fail with actionable guidance when the backing service does not support the required curation capability, and missing-package audit responses should clearly state that the package could not be scanned because it was not found.

- **Constraints**: Keep error handling specific and informative without hiding the real failure, and avoid changing unrelated audit-error cases beyond the targeted missing-curation and package-not-found scenarios.


### Task 24 Treat local recipes index user/channel mismatches as not found
Ensure that resolving recipes or packages through a local recipes index fails as not found when the exported recipe's user/channel does not match the requested reference, and ensure that revision-mismatch failures are only triggered for explicitly requested revisions.

- **Expectation**: A local recipes index should only satisfy requests for the exact recipe identity the user asked for, including owner/channel. It should fail with a not-found outcome instead of silently serving a different identity, and it should only reject on revision mismatch when the user asked for an exact revision.

- **Constraints**: Never fall back to a different owner/channel than requested, and do not reject a request simply because the source resolves to its current revision when no exact revision was requested.


### Task 25 Fix visionOS MesonToolchain target flag generation
Ensure that MesonToolchain correctly supports visionOS cross-compilation by emitting valid compiler target flags for both device and simulator targets, so users can configure and build Meson projects for visionOS without manual workarounds.

- **Expectation**: MesonToolchain should transparently generate the correct compiler target option for visionOS builds, for both devices and simulators, so the build toolchain recognizes the requested target platform and version.

- **Constraints**: The fix should address the broken visionOS behavior only and must not change how unrelated Apple targets are configured.


### Task 26 Preserve imported configurations for INTERFACE targets in CMakeConfigDeps
Ensure that CMakeConfigDeps-generated imported targets for INTERFACE libraries expose their available build configurations so consumers can resolve and link them correctly in configuration-specific CMake workflows.

- **Expectation**: Consumers using CMakeConfigDeps should be able to use packages that expose INTERFACE libraries without losing configuration awareness. INTERFACE targets should advertise which configurations they support so CMake can resolve them consistently in multi-configuration or cross-configuration consumer builds.

- **Constraints**: The change should be additive and non-disruptive: it should improve configuration handling for INTERFACE libraries without altering established behavior for other generated package targets.


### Task 27 Honor Apple bitcode, ARC, and visibility settings in generated GNU, Autotools, and Meson toolchains
Ensure that Apple-specific build configuration for bitcode, Objective-C ARC, and symbol visibility is applied when generating GNU, Autotools, and Meson toolchains so Apple builds use the requested compile and link behavior.

- **Expectation**: For Apple-targeted builds, Conan’s GNU, Autotools, and Meson toolchain generators should now respect the user’s configured Apple bitcode, ARC, and visibility preferences in the produced compile and link settings. Debug builds should use the debug-safe bitcode form, non-Debug builds should use normal bitcode, and non-Apple builds should remain unaffected.

- **Constraints**: The fix should extend current toolchain output rather than alter unrelated flag generation. It should only affect Apple targets, should not invent behavior when the user has not set these options, and should keep explicit disable requests observable in the generated flags where applicable.


## Breaking Changes

### Task 28 Migrate remote integrations to Conan 2.16.0 supported APIs
Ensure that integrations upgrading to Conan 2.16.0 no longer depend on remote command helper functions or direct sub-API internals that have become private, and that remote authentication flows use the supported ConanAPI remote-login behavior with the same observable credential resolution and validation outcomes.

- **Expectation**: After upgrading, remote-management automation should rely only on the supported Conan API surface. Multi-remote login should be available through ConanAPI.remotes.login, preserve the before-and-after login state for each remote, use explicit credentials when provided, fall back to configured credentials when needed, and fail clearly if a caller requests a different username than the one resolved from configuration.

- **Constraints**: Avoid depending on internal CLI helpers or internal object state that is no longer part of the supported API. The upgrade must keep remote login behavior predictable across explicit credentials and configured credentials, and it must reject ambiguous or conflicting identity selection rather than guessing.


## Additional Changes
- Ensure that cache-backed recipe path resolution works when callers provide a recipe reference without an exact revision, by resolving the current latest cached revision before looking up the recipe layout.
- Ensure that remote authentication output does not emit the generic connection banner during `authenticate`, so `conan remote login` output stays focused on the login result itself.
