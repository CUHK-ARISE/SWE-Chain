# Upgrade Specification from 2.16.1 to 2.17.0

## New Features

### Task 1 Add support for newer GCC patch versions
Ensure that Conan accepts newer GCC patch releases as valid `compiler.version` values when `compiler=gcc`, so users can configure supported GCC toolchains without rejection.

- **Expectation**: Users should be able to declare the newly supported GCC releases in normal Conan configuration and have those compiler versions recognized as supported rather than treated as unknown values.

- **Constraints**: The upgrade should broaden compatibility for newer GCC releases without changing existing compiler configuration behavior outside of recognizing the new versions.


### Task 2 Honor conanws directory as workspace search boundary
Ensure that Conan workspace discovery respects a directory named `conanws` as the top search boundary and resolves the workspace from that directory when it contains a valid `conanws.py` or `conanws.yml` definition.

- **Expectation**: Workspace lookup should stop at a `conanws` directory. That directory becomes the workspace root only when it contains a supported workspace definition file; otherwise the lookup should fail as no workspace being defined rather than silently using one from above.

- **Constraints**: Existing workspace discovery should keep working for normal directory layouts, but a `conanws` folder must act as a hard boundary and must not allow fallback to a workspace outside that boundary.


### Task 3 Allow workspace packages outside the workspace folder
Ensure that Conan workspaces can register, persist, and manage packages and products that are located outside the workspace directory, while preserving consistent workspace naming and safe cleanup behavior.

- **Expectation**: Users should be able to keep a workspace file in one location and still register packages or products stored elsewhere on disk. Workspace lifecycle commands should support initializing a workspace, cleaning generated build output when defined, and showing a stable workspace name in user-visible output.

- **Constraints**: The update should broaden valid workspace layouts without weakening validation of invalid path inputs, breaking removal semantics, or making cleanup destructive beyond explicitly configured build-output folders.


### Task 4 Support extra configure arguments in GNU toolchains
Ensure that users can provide additional GNU `configure` command arguments through Conan configuration when using Autotools-based toolchains.

- **Expectation**: Users should be able to extend the generated `configure` command with extra flags through configuration instead of replacing the toolchain's standard arguments.

- **Constraints**: Leaving the option unset should preserve current behavior. Any added flags should only influence the `configure` step and should be supplied in the expected structured format.


### Task 5 Expand GCC version support to 13.4 and 14.3
Ensure that Conan accepts newer GCC patch releases, including GCC 14.3, in user-visible compiler settings so profiles and package configurations using those compilers are treated as valid.

- **Expectation**: Users should be able to select newly supported GCC patch releases in their compiler configuration and have Conan recognize them anywhere compiler settings are checked.

- **Constraints**: The upgrade should broaden GCC compatibility without changing existing valid configurations or affecting unrelated compiler behavior.


### Task 6 Add default C standard detection
Ensure that Conan can report the default C language standard for the active compiler/version combination so recipes can reason about `compiler.cstd` consistently during an upgrade from 2.16.1 to 2.17.0.

- **Expectation**: Users upgrading should be able to ask Conan for the default C standard implied by a compiler and version, either from the current recipe settings or from explicit inputs. Conan should return a normalized default standard when it knows the compiler family behavior, return no inferred default for compiler families it cannot determine safely, and fail clearly when the compiler context is incomplete.

- **Constraints**: The new capability is informational rather than prescriptive. It should help recipes understand compiler defaults without changing explicit user configuration, and it should stay conservative by avoiding guesses for compilers whose default C standard is not defined by the feature.


### Task 7 Generate cl-like compiler cache entries in CMake presets for Ninja
Ensure that CMakeToolchain-generated presets automatically define the active C and C++ compiler for MSVC cl-like toolchains when using the Ninja generator, so consumers can configure builds with the intended compiler without manual preset edits.

- **Expectation**: Generated CMake presets should automatically carry the intended C and C++ compiler for Windows MSVC-style Ninja builds, including clang-cl workflows, so CMake sees the correct compiler during configuration.

- **Constraints**: The automatic compiler injection should stay narrowly scoped to supported MSVC-style compiler flows and must not change unrelated generators or non-MSVC compiler configurations.


### Task 8 Add a built-in header-only library template to conan new
Ensure that `conan new` provides a built-in `header_lib` template for creating header-only library packages, including package metadata, exported headers, optional declared requirements, and a generated example consumer project.

- **Expectation**: Users should be able to scaffold a header-only Conan package directly from `conan new` without starting from a generic template. The generated project should behave like a standard header-only package: headers are exported and packaged, package identity does not vary by build settings, no binary or library folders are advertised, optional dependencies can be declared at generation time, and the sample consumer project should demonstrate consuming the package through Conan's CMake integration.

- **Constraints**: This should extend template generation without changing existing templates. The generated scaffold must reflect header-only packaging semantics, avoid implying compiled library outputs, and handle optional dependencies only when the user supplies them. The included example should be usable as a normal consumer example and avoid assuming the executable can always run in every environment.


### Task 9 Expand Meson standard flag generation
Ensure that Meson C and C++ standard flag generation supports configured standard values beyond a fixed predefined subset, including GNU dialects and newer language versions, while leaving the flag unset when no standard is configured.

- **Expectation**: When Meson toolchain generation is given a C or C++ language standard, it should emit the matching Meson standard setting for that requested mode, including newer standard versions and GNU dialects. If no language standard is configured, no standard flag should be produced.

- **Constraints**: Existing standard selections should keep working, GNU dialect requests should stay GNU dialect requests, and compiler-specific behavior should remain intact where special handling already exists.


### Task 10 Expose subprocess in Jinja profile rendering
Ensure that Jinja-rendered Conan profiles can use the `subprocess` module during template evaluation so profile values can be computed from external command output when needed.

- **Expectation**: Users should be able to write dynamic profile templates that invoke external commands while the profile is being rendered. A profile that uses `subprocess` in its Jinja expressions should render successfully and produce configuration values based on the command result.

- **Constraints**: The upgrade should add one new template capability without removing or altering the profile features users already rely on. Existing profile templates should keep working as before, and only templates that choose to use `subprocess` should observe the new behavior.


### Task 11 Add source exclusion and slimmer cache-save archives
Ensure that `conan cache save` can produce smaller, portable cache archives by excluding transient downloaded artifacts from saved snapshots and by allowing users to omit recipe sources when they do not want them included.

- **Expectation**: Users should be able to create cache backups that restore usable recipes and packages without carrying redundant downloaded blobs, and they should be able to intentionally exclude recipe sources to keep the archive smaller.

- **Constraints**: The new option must be opt-in, existing save/restore workflows should keep working for actual restorable content, and the archive should stay focused on durable cache state rather than temporary downloaded data.


### Task 12 Add verbose progress output for conan cache clean
Ensure that `conan cache clean` provides visible progress updates in verbose mode while cleaning cache contents, so users can tell the command is actively processing temporary folders, backup sources, recipes, and packages.

- **Expectation**: Users who opt into verbose output for cache cleanup should see clear progress information for each major cleanup stage and each targeted recipe or package, making long-running cleanup work observable rather than silent.

- **Constraints**: The enhancement should improve visibility only. It must not change the meaning of the command, the cleanup scope, or the behavior users get when they do not request verbose output.


### Task 13 Support package-list input for cache maintenance commands
Ensure that `conan cache clean` and `conan cache check-integrity` support selecting local cache entries from a package list file via `--list`, so users can run these operations on an explicit cache selection instead of only a reference pattern.

- **Expectation**: Users should be able to provide a package list file to both cache-cleaning and cache-integrity commands and have the command act on exactly that explicit local-cache selection. Pattern-based selection should still work as before, but the CLI should reject ambiguous or incomplete selection inputs.

- **Constraints**: Existing wildcard and pattern workflows should remain intact, while the new list-based workflow must behave as a mutually exclusive alternative. The commands should fail fast when the user input is contradictory or missing.


### Task 14 Expose remote allowed_packages in JSON output
Ensure that remote information exported in JSON includes each remote's configured package allowlist so users and tooling can detect remote package restrictions directly from the JSON output.

- **Expectation**: JSON remote listings should expose whether a remote is restricted to specific packages, so users and automation can read the remote's package access scope from the same JSON payload as the rest of the remote metadata.

- **Constraints**: Existing JSON consumers should continue to receive the same remote data as before, with one additional field that consistently communicates package restriction metadata.


### Task 15 Expose upload URLs in conan upload JSON output
Ensure that `conan upload` JSON output includes per-file upload destination information so users and tooling can identify where each uploaded recipe and package artifact is stored and verify the associated file content.

- **Expectation**: The upload report should let consumers inspect, for every uploaded artifact, the final remote location and integrity metadata in a machine-readable form. Both recipe-level and package-level uploads should expose this information consistently in the JSON result.

- **Constraints**: Existing upload JSON data should continue to work, with the new URL metadata added as an extension. The feature should not invent entries for nonexistent artifacts or produce malformed destination links.


### Task 16 Add workspace initialization and clean support for editable package workspaces
Ensure that Conan workspaces can be initialized and cleaned from the CLI, that default cleanup removes only configured output folders for workspace packages, and that workspace package metadata remains usable for packages referenced by relative paths, including paths outside the workspace directory.

- **Expectation**: Users should be able to bootstrap a workspace, register workspace packages from nearby folders, and clean generated build/output directories from the workspace CLI. Cleanup should follow workspace-specific behavior when the workspace defines its own clean routine; otherwise it should remove only the configured output directories and leave packages without such directories unchanged.

- **Constraints**: Initialization should not overwrite an existing workspace definition. Cleanup should be limited to generated output folders, not package sources or workspace membership. Workspace commands should continue working when packages live outside the workspace folder, and one cleanup problem should not stop the rest of the workspace from being processed.


### Task 17 Refine cache save archives and add source exclusion
Ensure that `conan cache save` creates clean, restorable cache snapshots without re-bundling transient downloaded artifact archives, and allow users to exclude recipe source folders from the saved `.tgz` by using `--no-source`.

- **Expectation**: Saving the Conan cache should produce a focused backup of reusable recipe and package state rather than a recursive copy of every cache subfolder. By default, local recipe sources remain included, and users can explicitly opt out of saving those sources with `--no-source` without losing the rest of the restorable cache contents.

- **Constraints**: The new archive filtering must reduce unwanted transient content without breaking normal cache backup and restore flows. Excluding sources must be a narrow opt-out that removes only recipe source material and leaves the rest of the saved cache usable.


## Bug Fixes

### Task 18 Fix Conan PyInstaller packaging to exclude test modules correctly
Ensure that Conan executables built with the PyInstaller integration package the Conan runtime without traversing Conan test-only modules, so users do not see spurious missing-import failures from conan.test subpackages during build or due to omitted bundled imports at runtime.

- **Expectation**: Building the standalone Conan executable with PyInstaller should include the modules needed for normal Conan usage, omit Conan's test-only packages, and avoid packaging-time or runtime import failures that come from PyInstaller trying to bundle internal test modules.

- **Constraints**: Only test-only Conan modules should be excluded. Normal Conan functionality and existing supported packaging modes must continue to work after the upgrade.


### Task 19 Update conan audit guidance links
Ensure that `conan audit` surfaces current, relevant help URLs when showing vulnerability results or rate-limit guidance, so users are directed to the active Conan audit documentation pages instead of obsolete product pages.

- **Expectation**: The audit CLI should present up-to-date support and product information links wherever it explains vulnerability results or request limits, so users land on the correct current documentation and service pages.

- **Constraints**: Only the user-facing references should change. The audit command's functional behavior, results, and existing support flow should otherwise remain the same.


### Task 20 Validate CycloneDX SBOM licenses against SPDX compatibility
Ensure that generated CycloneDX SBOMs only encode licenses as SPDX identifiers when the declared license is SPDX-compatible, while preserving non-SPDX or custom licenses as names. Ensure that packages with multiple licenses keep one entry per declared license and that CycloneDX 1.6 component author information is emitted in structured author form.

- **Expectation**: SBOM generation should distinguish standard SPDX licenses from custom license labels instead of treating every license as an SPDX identifier. Known SPDX licenses should appear as license identifiers, unknown or project-specific licenses should appear as names, and mixed multi-license packages should classify each license independently. CycloneDX 1.6 author metadata should use the structured author format expected by downstream consumers.

- **Constraints**: The upgrade should improve standards compliance without removing license information or requiring users to rename custom licenses. Packages with one, many, or mixed license declarations should continue to produce complete SBOM metadata.


### Task 21 Support Windows LLVM/Clang frontends in GNU-style toolchains
Ensure that Windows builds using Conan's GNU-style toolchains work correctly when `compiler=clang` is configured with either `clang` or `clang-cl`, and that the generated compile and link flags match the selected LLVM/Clang frontend and MSVC runtime behavior.

- **Expectation**: Users should be able to switch between `clang` and `clang-cl` on Windows without hand-fixing Conan's generated GNU-style toolchain flags. Standard-selection, runtime-library, and linker behavior should automatically match the chosen frontend so builds complete with the intended runtime linkage.

- **Constraints**: The fix should be narrowly scoped to the affected Windows LLVM/Clang cases and must not regress other compiler or platform configurations. Runtime selection should stay consistent with the user's chosen static or dynamic MSVC runtime mode.


### Task 22 Clarify unzip extraction output wording
Ensure that archive extraction status output from the unzip tool uses wording that correctly describes uncompressing supported archive formats rather than implying ZIP-only behavior.

- **Expectation**: When users invoke the archive extraction helper, the status text they see should accurately describe a generic archive decompression operation, so the output is correct for all supported archive types and not misleadingly ZIP-specific.

- **Constraints**: The update should be non-disruptive: archive extraction should behave exactly as before, with the only user-visible change being clearer status wording during extraction.


### Task 23 Deduplicate generated component dependencies in PkgConfigDeps and BazelDeps
Ensure that upgrading to Conan 2.17.0 stops PkgConfigDeps and BazelDeps from emitting duplicate dependency names when a package component declares the same requirement more than once.

- **Expectation**: Generated pkg-config and Bazel dependency metadata should treat repeated declarations of the same logical component dependency as a single dependency. Consumers should see one dependency entry per resolved dependency, even if the recipe declared that dependency multiple times.

- **Constraints**: The fix should remove duplicates without altering normal dependency naming or causing dependencies to disappear. Existing generator behavior should remain the same aside from duplicate entries no longer being repeated.


### Task 24 Handle grafted commits in Conan Git helper remote checks
Ensure that Conan's Git helper accepts grafted commits that are actually available from the configured remote, so SCM metadata generation does not incorrectly fail or skip repository coordinates for valid checkouts.

- **Expectation**: When a recipe runs from a repository checked out at a grafted commit, Conan should still recognize that revision as valid if the remote can provide it. Users should be able to export or inspect SCM coordinates from such repositories without the tooling behaving as though the commit is missing.

- **Constraints**: The fix should broaden support for valid repository histories without changing how clearly unavailable commits are handled. Standard repositories must keep working as before, and invalid remote revisions must still fail safely.


### Task 25 Honor excludes for symlinked directories in copy()
Ensure that `conan.tools.files.copy()` applies `excludes` patterns to symlinks that target directories, so excluded linked folders are not copied while other matching files and directories continue to be copied normally.

- **Expectation**: Directory symlinks should respect exclusion rules just like ordinary files, ordinary folders, and symlinked files. If a caller excludes a linked folder by name or pattern, the copy operation should leave it out, and exclusion matching should honor the API's configured case-sensitivity rules.

- **Constraints**: The fix should be additive and targeted: excluded linked folders should stop being copied, while all previously valid non-excluded copy behavior should remain unchanged.


### Task 26 Clarify filtered graph errors in conan list
Ensure that `conan list --graph=...` reports a clear, actionable error when the supplied graph JSON is missing required graph data, including the common case where the graph file was generated with graph filtering.

- **Expectation**: If a user passes an incomplete graph export to `conan list`, the command should fail with a helpful message that explains the input is missing required graph information and that filtered graph outputs cannot be reused for listing.

- **Constraints**: The fix should only improve diagnostics for incomplete graph inputs without changing normal list results or collapsing different input errors into the same generic failure.


### Task 27 Deterministic override serialization
Ensure that Conan serializes dependency override data deterministically so equivalent override configurations produce the same observable output regardless of accumulation order.

- **Expectation**: Serialized override metadata should be stable across runs: the same override content should always produce the same ordered output, including cases where some override entries are absent or unset.

- **Constraints**: The update should remove nondeterministic ordering without changing the meaning, membership, or validity of override data.


### Task 28 Allow mixed numeric conf values during composition
Ensure that composing Conan conf values across profiles, scopes, or other merged configuration sources accepts values that are all numeric even when they use different numeric categories, instead of failing solely because one value is an integer and another is a floating-point number.

- **Expectation**: Configuration merging should accept mixed numeric values for the same setting. Users should be able to define a setting as one kind of number in one source and another kind of number in another source without the merge failing, and the usual override behavior should still decide which value is seen in each scope.

- **Constraints**: Only numeric-to-numeric combinations should gain the new flexibility. Other value categories should keep their current merge semantics, including existing protections against incompatible type combinations.


### Task 29 Fix python_requires test_package warning and create flow with tool_requires profiles
Ensure that `python_requires` packages can be created and tested without spurious `tested_reference_str` deprecation warnings, and ensure that `conan create` for a `python_requires` package still succeeds when the active profile includes `tool_requires`.

- **Expectation**: Testing or creating a Python-require package should only warn when the test package is actually using an outdated declaration pattern. Valid `tested_reference_str` usage should be accepted quietly, and adding tool requirements to the selected profile must not break package creation.

- **Constraints**: Keep the warning narrow and accurate, preserve existing Python-require test-package resolution, and avoid introducing regressions in package creation when extra tool requirements are present in the profile.


### Task 30 Fix CycloneDX 1.6 SBOM authors field shape
Ensure that CycloneDX 1.6 SBOM generation outputs author information in the correct schema-defined format for both the root component metadata and dependency components.

- **Expectation**: CycloneDX 1.6 SBOMs should represent authors in the format required by the specification so that author data is valid and interoperable wherever it appears in the document.

- **Constraints**: Only the author representation should change; other SBOM content and cases without author information should continue to behave as before.


### Task 31 Relocatable CMakeConfigDeps paths for deployers
Ensure that `CMakeConfigDeps` produces relocatable generated CMake metadata for deployer-based installs, so consumers can resolve dependency package roots, include locations, runtime library directories, and declared CMake build modules from the deployed output instead of depending on original absolute package cache paths.

- **Expectation**: Using `CMakeConfigDeps` with a deployer should generate CMake metadata that keeps working after deployment because all consumer-visible dependency paths are expressed relative to the generated files. Projects should be able to find and use deployed dependencies, their runtime search paths, headers, and auxiliary CMake modules without relying on machine-specific absolute locations.

- **Constraints**: The fix should improve relocatability without changing which dependencies, headers, runtime directories, or build modules are advertised. Consumers should observe the same dependency information as before, except that it remains valid from the deployed layout.


### Task 32 Bundle Full Conan Package in PyInstaller Builds
Ensure that Conan builds produced with PyInstaller include the complete runtime Conan package so packaged executables can load shipped Conan commands and tool modules without missing-module failures, while excluding test-only content from the bundle.

- **Expectation**: A frozen Conan executable should behave like a normal Conan installation with respect to loading built-in Conan modules. Users should be able to invoke bundled commands and recipe/tooling functionality without runtime import errors caused by incomplete packaging, while test-only code remains absent from the shipped artifact.

- **Constraints**: The upgrade should expand runtime module availability without introducing test content into the distributable or regressing existing frozen-build compatibility behavior.


### Task 33 Remove libtool setup from autotools executable template
Ensure that `conan new autotools_exe` creates executable-only Autotools projects without enabling libtool, so newly generated templates do not impose unnecessary libtool-related configuration on users building executables.

- **Expectation**: Creating a new Autotools executable project should produce a configuration suitable for a plain executable build, without adding library-tooling setup that the project does not need. The generated project should remain ready for normal Autotools configure and build flows for executables.

- **Constraints**: Only the unnecessary library-specific behavior should be removed. The executable template should keep the existing build setup needed to configure and build successfully, without expanding scope into unrelated template behavior changes.


### Task 34 Fix CMakeConfigDeps conditional link flags
Ensure that CMakeConfigDeps-generated package targets propagate exported link flags correctly so shared-library and module-library flags apply only to compatible library consumers, executable flags apply only to executable consumers, and consumer builds do not lose or mis-handle those link options.

- **Expectation**: Packages that publish CMake link flags should have those flags reach consumers in a form CMake interprets correctly. Conditional link flags must be honored for the right consumer target kinds, without being suppressed or malformed by how they are emitted.

- **Constraints**: Limit the change to correcting conditional link-option propagation. The fix must not alter which kinds of consumers are eligible for those flags or change unrelated package metadata.


### Task 35 Prevent conan audit threshold crashes on unscanned packages
Ensure that `conan audit` does not crash while applying an error threshold when the audit response includes packages that were not scanned or not found and therefore do not provide vulnerability information.

- **Expectation**: Threshold-based audit evaluation should consider only packages with vulnerability data. Packages that could not be scanned should not crash the audit command, and real threshold violations from successfully scanned packages should still be reported normally.

- **Constraints**: Ignore incomplete audit entries for threshold comparison, but preserve the existing failure behavior for actual vulnerabilities that meet the configured severity threshold.


### Task 36 Fix missing require details for the first HTML graph edge
Ensure that the HTML output from `conan graph info -f=html` displays require information when the first dependency edge in the graph is selected, instead of behaving as if nothing was selected.

- **Expectation**: Users viewing the HTML dependency graph should be able to click the first dependency relationship and see the same dependency details they would expect from any other edge, including its require information.

- **Constraints**: The fix should only correct the missing-details case for the first selectable graph element and must not regress normal graph inspection for the rest of the HTML view.


### Task 37 Support creating python-requires packages with profile tool_requires
Ensure that `conan create` can create a package meant to be used as `python_requires` even when the active profile contains `tool_requires`, without failing due to unrelated dependency graph resolution.

- **Expectation**: Creating a helper package for reuse through `python_requires` should work under the same profiles used elsewhere in the workspace, including profiles that add tool dependencies. The command should only resolve dependency information that is relevant to that package instead of failing on an unnecessary graph calculation.

- **Constraints**: Limit the fix to the failing edge case. Normal package creation and dependency handling should behave the same for recipes with real dependencies.


### Task 38 Honor parent .conanignore files during config install
Ensure that `conan config install` applies `.conanignore` rules when installing a nested configuration folder, including cases where the relevant `.conanignore` is stored in an ancestor directory of the selected source folder within the configuration being installed, so unrelated files are not copied into the Conan cache.

- **Expectation**: Installing configuration content from a subdirectory should still honor the repository's intended ignore rules if they are defined higher in that configuration tree. Only ignore rules that belong to the configuration being installed should affect the result.

- **Constraints**: The fix should be additive and safe: existing installs without ignore files should behave the same, the ignore file should not be copied as payload, and outside directories must not unexpectedly influence the install.


## Breaking Changes

### Task 39 Rename workspace editables to packages
Ensure that workspace-managed local packages are defined, discovered, and reported using `packages` instead of `editables`, so existing workspace flows continue to work after upgrading to Conan 2.17.0.

- **Expectation**: After upgrading, users should interact with workspaces in terms of packages, not editables. Any workflow that defines local workspace packages, inspects workspace contents, or derives package references from a custom workspace should continue to work with the new naming and preserve the same observable package resolution behavior.

- **Constraints**: This change should update terminology without weakening existing workspace behavior. Local package entries should still behave the same way, and erroneous package removals should still surface as errors.


### Task 40 Remove workspace home overrides
Ensure that upgrading to Conan 2.17.0 no longer relies on `conanws.yml` or `conanws.py` to select the Conan home/cache folder, and that workspace behavior follows the 2.17.0 package model for naming, persisted package entries, relative paths, and cleanup.

- **Expectation**: After the upgrade, a workspace should describe packages and products, not redefine where Conan stores its cache. Workspaces may expose a user-defined display name, continue to reference package locations relative to the workspace even when those locations live outside the workspace directory, and support a standard cleanup operation that removes generated output directories for packages that declare them while reporting non-fatal cleanup issues.

- **Constraints**: Do not let workspace metadata silently override global Conan home selection, reject valid workspace packages only because they are located outside the workspace directory, or delete directories that are not declared as package output folders. If no workspace name is configured, the previous folder-based default should continue to apply.


## Additional Changes
- Ensure that `conan config install` only recognizes and extracts supported archive containers for configuration installation, and no longer accepts a standalone `.gz` file as a compressed config source.
- Ensure that `CMakeDeps2` surfaces unsupported `cmake_find_mode=module` settings clearly and continues with config-mode generation instead of silently pretending to honor module mode.
