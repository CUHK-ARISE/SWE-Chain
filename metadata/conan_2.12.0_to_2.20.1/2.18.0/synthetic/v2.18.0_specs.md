# Upgrade Specification from 2.17.1 to 2.18.0

## New Features

### Task 1 Support Meson-style static archives in MSBuildDeps
Ensure that MSBuildDeps can consume package libraries built with Meson when a dependency declares a bare library name but the packaged archive is exposed as a lib<name>.a file, without breaking existing handling of explicit library filenames or standard .lib libraries.

- **Expectation**: MSBuildDeps should understand both conventional MSBuild library naming and Meson-produced static archive naming for package libraries. Consumers should be able to install dependencies generated by Meson without manually renaming library files, while existing dependency declarations that already work should keep the same observable output.

- **Constraints**: The change should be additive and narrowly scoped. It must preserve current behavior for explicit filenames and normal Windows library layouts, and it should only switch to Meson naming when that is the actual packaged artifact being consumed.


### Task 2 Support Meson/MSVC static library names in CMakeDeps
Ensure that Windows static libraries produced by Meson with MSVC can be consumed from Conan without renaming the packaged library files, especially when CMakeDeps is used with older CMake releases.

- **Expectation**: Users should be able to publish and consume Meson/MSVC static libraries on Windows through Conan using their natural artifact names. CMakeDeps should transparently recognize the packaged library for older supported CMake versions so consumers can link dependencies without recipe-side or artifact renaming workarounds.

- **Constraints**: This compatibility handling should be narrowly scoped to the environments that need it and must not alter library resolution rules globally. Platforms and toolchains that already work should continue to behave as before.


### Task 3 Model Emscripten thread modes in Conan settings and toolchains
Ensure that Conan models Emscripten threading as part of the `emcc` compiler configuration so binaries built without threads, with POSIX threads, and with Wasm Workers are treated as distinct configurations, and ensure generated toolchains automatically emit the matching compile and link flags for the selected thread mode.

- **Expectation**: Users configuring Conan for Emscripten should be able to declare the threading model as part of the compiler settings, and Conan should treat that choice as part of the binary identity while automatically generating consistent compiler and linker flags for supported toolchains.

- **Constraints**: This change should only affect Emscripten builds that opt into the new thread-mode setting. Other compilers and non-threaded Emscripten builds should continue to behave as before, and enabling a thread mode should augment normal toolchain generation instead of disrupting it.


### Task 4 Reverse lookup Conan cache references by path
Ensure that Conan provides a debugging-friendly way to reverse look up a local cache path with `conan cache ref <path>` and report the cached artifact reference that owns that folder.

- **Expectation**: Users should be able to point Conan at a folder from the local cache and see which cached recipe or package it belongs to. The lookup should work for both artifact roots and direct child folders within them, stay read-only, and fail clearly when the path is invalid or does not correspond to any cached artifact.

- **Constraints**: Treat this as a non-destructive debugging aid. It should identify only real cached artifacts, keep the reported reference format stable and concise, and avoid broad or ambiguous path guessing.


### Task 5 Separate Emscripten linker-only architecture flags in generated toolchains
Ensure that Conan-generated toolchains distinguish architecture flags that are safe for compilation from architecture flags that are linker-only, so Emscripten asm.js profiles link correctly without polluting compile commands, while other architecture- and thread-derived flags continue to be applied in the appropriate stages.

- **Expectation**: Architecture options inferred from the active profile should be sent to the build stage that actually understands them. Linker-only Emscripten settings should affect only the final link step, while normal architecture and thread settings should keep working across generated toolchains.

- **Constraints**: The upgrade should only change where stage-specific flags are applied, not broadly alter unrelated toolchain behavior. Existing builds should continue to receive the same effective architecture and thread configuration unless a linker-only flag needed to be separated from compilation.


### Task 6 Support editable executable targets in CMakeConfigDeps
Ensure that CMakeConfigDeps supports executable artifacts from editable packages, including Windows .exe outputs, so consumers can discover and use those executables through generated CMake package configuration the same way they can for non-editable packages.

- **Expectation**: Editable Conan dependencies that provide executables should behave like packaged dependencies when consumed from CMakeConfigDeps. If a package declares an executable and its location for editable development, downstream CMake consumers should receive a usable imported executable target that resolves to the actual built executable, including platform-specific .exe filenames on Windows.

- **Constraints**: The change should only improve editable artifact resolution. It must not break existing dependency metadata merging, and missing editable-specific executable details should fall back to the normal package information instead of causing loss of previously available artifact data.


### Task 7 Support custom build directories in basic_layout
Ensure that `basic_layout` lets recipe authors override the build output directory, including using a path outside the source tree, while preserving the current default layout when no custom build folder is requested.

- **Expectation**: Users should be able to choose the name or location of the build directory used by `basic_layout`, including out-of-source builds, without affecting recipes that continue to use the default layout.

- **Constraints**: Existing recipes should behave the same unless they opt into a custom build folder. Choosing a custom build location should not alter unrelated layout behavior beyond where build and generator outputs are placed.


### Task 8 Allow PkgConfigDeps to skip package-level .pc generation
Ensure that `PkgConfigDeps` lets a package opt out of generating its package-level pkg-config file by setting `pkg_config_name` to `"none"`, so consumers only receive the intended public `.pc` files.

- **Expectation**: Users should be able to declare that a package has no public top-level pkg-config entry. In that case, `PkgConfigDeps` should omit the package's main `.pc` file while continuing to generate and connect any other valid pkg-config outputs.

- **Constraints**: Skipping the top-level pkg-config file should be a narrow opt-out. It must not create fake dependency names, disturb unrelated pkg-config outputs, or change behavior for packages that do not enable this setting.


### Task 9 Support SBOM and lockfile inputs in conan audit list
Ensure that `conan audit list` can list vulnerabilities from a CycloneDX SBOM file or a Conan lockfile, while preserving existing direct reference and package list support and requiring exactly one input source per invocation.

- **Expectation**: Users should be able to run `conan audit list` against a single package reference, a package list, a CycloneDX SBOM, or a lockfile and receive vulnerability information for the dependencies represented by that input. Unsupported SBOM formats should be rejected clearly instead of being interpreted as valid audit input.

- **Constraints**: Each invocation should accept one explicit source of dependency data. Existing audit workflows must stay compatible, and invalid or unsupported artifact formats must fail safely rather than producing misleading vulnerability results.


### Task 10 Add first-class Emscripten emcc and wasm64 support
Ensure that Conan treats Emscripten as a first-class target by accepting emcc-based profiles, supporting wasm, asm.js, and wasm64 architectures, and generating the correct observable compiler, linker, standards, and target-metadata behavior for those web builds.

- **Expectation**: Users should be able to declare Emscripten builds with emcc and web-target architectures directly in Conan profiles, and Conan should consistently understand those targets, expose the right language-standard availability for the selected emcc version, and emit the observable build and link settings needed for wasm64 and asm.js outputs.

- **Constraints**: The upgrade should extend web-target support without changing unrelated platform behavior, and it should stay conservative by only enabling target-specific flags and standards when the selected compiler and architecture actually require them.


### Task 11 Shared install-strip config for CMake and Meson
Ensure that install-time stripping can be configured consistently across both CMake and Meson workflows, and that existing CMake consumers using the legacy install-strip configuration continue to get stripped installs while being notified to migrate.

- **Expectation**: Users should be able to turn on stripped installs through one shared configuration across supported build helpers. Existing CMake projects that still use the older setting should keep working for now, but they should receive a clear deprecation signal telling them to move to the shared option.

- **Constraints**: Do not change install behavior unless stripping is explicitly requested. Keep current CMake users working during migration, avoid deprecation noise for users already on the new shared setting, and extend the same stripping capability to Meson without introducing tool-specific migration burdens.


### Task 12 Add local file opening support to TestClient
Ensure that local Conan test workflows can open generated files directly from TestClient, including files created in the current test workspace and files stored in the client home/cache area, while refusing to perform interactive file opening in CI environments.

- **Expectation**: Users should be able to ask the test client to open files it created on disk using the normal desktop application for their operating system. The same convenience should work for files in the test workspace and in the client's home/cache location, but the feature must be unavailable in non-interactive CI runs.

- **Constraints**: The new capability should only trigger the machine's normal file-opening behavior for local files and should preserve clear separation between workspace files and client-home files. It should behave appropriately across supported desktop operating systems and avoid attempting interactive UI actions in automated environments.


### Task 13 Orchestrated workspace package creation
Ensure that Conan workspaces can orchestrate creation of selected workspace packages into the Conan cache in correct dependency order, using the active profile, lockfile, remote, and build context, and provide a workspace-level way to run package source retrieval.

- **Expectation**: Users should be able to create some or all packages from a workspace as cache packages, not local editables, and have Conan determine the right order automatically from the dependency graph, including required external builds and host/build context differences. Users should also be able to trigger source retrieval for selected workspace packages directly from the workspace CLI, and quoted arguments should continue to work when the workspace command delegates to other Conan commands.

- **Constraints**: The orchestration should not silently do nothing for an invalid package selection, should not rebuild packages that are already resolved, should not confuse cache creation with editable workspace builds, and should respect the distinction between normal requirements and build requirements.


### Task 14 Add profile Jinja rendering context
Ensure that Jinja2-rendered profiles can detect whether they are being evaluated as a host profile, a build profile, or without an explicit profile role, so users can author profile templates that adapt settings, options, or configuration to the active resolution context.

- **Expectation**: Users should be able to branch inside a profile template based on whether the profile is being used for host resolution, build resolution, or a generic single-profile operation. That role information should stay consistent across the full profile expansion, including any included profiles.

- **Constraints**: This feature should add role-awareness to profile templates without altering existing profile merging behavior or breaking templates that ignore the new variable.


### Task 15 Expose `cpp_info.sources` in CMakeConfigDeps
Ensure that Conan recipes can declare packaged source files as dependency metadata and that consumers using `CMakeConfigDeps` receive those files on the generated dependency target, including component targets.

- **Expectation**: Packages should be able to publish source files as part of their public CMake-facing metadata. When a consumer installs such a dependency with Conan's CMake dependency generator, the imported dependency target should carry those source files so CMake can treat the dependency as a source target. The same capability should work for both the main package target and named components.

- **Constraints**: Existing packages should keep their current behavior unless they opt in to publishing source files. Source metadata should augment generated dependency targets without regressing existing link, include, or component behavior.


### Task 16 Support cpp_info.sources in CMakeConfigDeps targets
Ensure that CMakeConfigDeps exposes source-based dependency metadata so packages that declare cpp_info.sources are consumed as CMake source targets through the generated dependency targets.

- **Expectation**: Consumers using CMakeConfigDeps should automatically receive dependency source files declared by the package as part of the dependency target interface, enabling source-target consumption through normal CMake target usage.

- **Constraints**: The new source-target support should not disturb existing dependency target behavior. Packages that do not declare sources should behave exactly as before, and packages that do declare sources should gain source propagation without losing other dependency metadata.


### Task 17 Add Conan recipe diff reporting
Ensure that users can inspect the differences between two Conan recipes, including recipe revisions or versions and their associated source content, through a dedicated reporting command that works for both reference-based and local-path comparisons and produces usable human-readable or machine-readable output.

- **Expectation**: Users should be able to run a single report command to compare two Conan recipes by version, revision, or local working copy and see what changed in the recipe and related source material. The comparison should work whether the inputs come from cache, remotes, or local recipe files, automatically picking the newest revision when the user omits one. The result should be available as raw diff text, structured JSON for tooling, or an HTML report that is easy to browse and filter by file path. Missing references should fail clearly instead of producing an empty or misleading report.

- **Constraints**: The new diff feature should stay compatible with existing Conan reference lookup behavior, work without extra revision bookkeeping when Conan can determine the latest revision itself, and let local recipe directories participate in the comparison without first publishing them. The report should remain a content-producing command rather than launching external viewers, and each output format should retain enough detail for users to inspect file-level changes.


### Task 18 Add PremakeToolchain-based premake5 integration
Ensure that premake5-based Conan consumers can use a Conan-generated Premake toolchain so dependency setup, compiler and linker settings, architecture selection, and build execution are integrated consistently across supported platforms and project layouts.

- **Expectation**: Using Premake with Conan should become a complete premake5 workflow: Conan should generate the build setup consumed by Premake, carry dependency and compiler settings into the generated project files, choose the correct platform and architecture representation, and run the appropriate backend build command with consistent verbosity and parallelism behavior.

- **Constraints**: The upgrade should not silently break existing configure-only flows, should fail clearly for unsupported architectures instead of producing unusable build files, and should respect explicit project-level build choices while still allowing Conan to supply defaults and shared configuration.


## Bug Fixes

### Task 19 Improve CMakeDeps errors for invalid component requirements
Ensure that CMakeDeps reports an actionable user-facing error when a recipe declares an incorrect component requirement for another package, instead of failing with a generic internal assertion, while preserving support for valid root-package requirements.

- **Expectation**: If a package recipe points CMakeDeps at a dependency component that does not exist, the generator should fail with a clear configuration error that tells the user which package/component reference is invalid. Valid references to the dependency's top-level target should continue to work as before.

- **Constraints**: Keep successful dependency generation unchanged for valid package-level references, and only improve the error behavior for misdeclared component dependencies.


### Task 20 Handle absolute -of paths correctly in generators
Ensure that running `conan install` with an absolute `-of` output folder does not cause generators to emit incorrect absolute filesystem paths where paths relative to the generated output should be produced.

- **Expectation**: Using an absolute install output directory should behave the same as using an equivalent relative output directory from the perspective of generated files. Generator metadata should keep referring to installed content through the intended relative layout rather than baking in incorrect machine-specific absolute paths.

- **Constraints**: Only correct false path mismatches for the same location. Do not rewrite unrelated external paths or alter valid generator output structure beyond making absolute-output installs resolve paths correctly.


### Task 21 Clarify invalid cpp_info.requires component references
Ensure that incorrectly defined `cpp_info.requires` entries produce a clear dependency and component resolution error, including when a requirement string contains more than one `::` separator.

- **Expectation**: Users who declare an invalid component dependency should receive an actionable error that identifies the wrong component and the dependency it belongs to, even if the declaration includes extra scope separators.

- **Constraints**: Correct dependency declarations should behave exactly as before. The change should only improve diagnostics for invalid declarations and should not alter how valid requirements are resolved.


### Task 22 PowerShell-safe MSBuild verbosity for CMake Visual Studio builds
Ensure that Visual Studio CMake builds launched through the PowerShell virtualenv configuration preserve the configured MSBuild verbosity setting without causing the downstream build tool to misparse the verbosity argument and fail.

- **Expectation**: PowerShell-based CMake builds for Visual Studio should honor user-selected build verbosity without breaking command-line parsing. Users who enable PowerShell virtual environments should get the same effective MSBuild verbosity behavior as before, but in a command format that is compatible with PowerShell.

- **Constraints**: The fix should be narrowly scoped to the PowerShell and Visual Studio verbosity case and must not change unrelated CMake argument handling or other build configurations.


### Task 23 Improve artifact-scoped cache integrity output
Ensure that `conan cache check-integrity` clearly identifies the exact cached recipe or package artifact being checked and presents missing-manifest and manifest-mismatch failures in a consolidated, readable form.

- **Expectation**: Running the cache integrity command should tell users exactly which cached artifact each success or failure belongs to, and corruption reports should be grouped into a clear summary that explains whether the manifest is missing or which files differ from the manifest.

- **Constraints**: Improve clarity of the integrity report without changing the underlying corruption detection behavior, and keep the reporting consistent across recipes and packages.


### Task 24 Fail fast on invalid conf_info definitions
Ensure that packages cannot publish invalid `conf_info` entries. Invalid configuration keys defined through `conf_info` should fail during package evaluation, and malformed `user` configuration names should be reported as format errors rather than generic unknown-configuration errors.

- **Expectation**: Upgrading to 2.18.0 should make malformed package configuration metadata fail immediately and clearly. Custom `user` configuration keys need the documented namespace format, and unsupported configuration keys should be rejected as unknown instead of being treated as vaguely invalid.

- **Constraints**: Do not change the behavior of correctly defined configuration metadata. Only tighten validation for bad keys, and keep the failure scoped to cases where a package exposes invalid configuration information.


### Task 25 Recognize QCC C++20 support on QNX 8.0
Ensure that Conan recognizes modern `qcc` toolchains used with QNX 8.0 as supporting `compiler.cppstd=20` and `compiler.cppstd=gnu20`, instead of incorrectly treating them as limited to C++17.

- **Expectation**: Users targeting QNX 8.0 with a recent `qcc` compiler should be able to request C++20 in Conan and have it recognized as a supported configuration. Older `qcc` toolchains should keep their previous limits so unsupported standards are still rejected.

- **Constraints**: The change should be narrowly scoped to the affected `qcc` capability mapping. It must not expand C++20 support for unrelated compilers or for older `qcc` toolchains that do not support it.


### Task 26 Fix CycloneDX component bom-ref generation for special root graphs
Ensure that CycloneDX SBOM generation assigns each component a package-derived bom-ref even when the dependency graph includes a synthetic root node, so exported SBOMs expose correct component identities to downstream consumers.

- **Expectation**: CycloneDX exports should always identify components by their real Conan package identity. A synthetic project root must not replace the component reference that external SBOM tooling uses to recognize the package.

- **Constraints**: Only correct how component references are chosen. The update must not otherwise change which SBOM components are emitted or alter unrelated SBOM fields.


### Task 27 Deprecate Node.dependencies in favor of Node.edges
Ensure that graph-inspection integrations move from `Node.dependencies` to `Node.edges`, while legacy reads from `Node.dependencies` remain temporarily functional and clearly deprecated during the 2.18.0 upgrade.

- **Expectation**: The dependency graph model should expose outbound links under `Node.edges`. Older code that still reads `Node.dependencies` should keep working in 2.18.0, but it should receive a clear deprecation warning so consumers know they need to migrate before the alias disappears.

- **Constraints**: This rename should be backward compatible for existing consumers in the current release. The only new observable effect for legacy usage should be a deprecation signal, not a change in dependency graph results.


### Task 28 Graceful errors for broken local-recipes-index remotes
Ensure that operations using a local-recipes-index remote, especially version-range resolution, fail predictably when the repository layout is incomplete by showing a clear user-facing remote error instead of an internal stack trace, while still allowing non-exact lookups to discover available versions for the requested package.

- **Expectation**: Commands that consult a local recipes index, including installs that use version ranges, should either inspect the package versions available in that index or fail with a clear remote-access error explaining that the local repository is missing its recipes area. Users should not see an unhandled stack trace for this condition.

- **Constraints**: Do not alter normal behavior for healthy remotes or exact package lookups. Limit the change to making broken local index layouts report cleanly and ensuring non-exact local searches still consider the requested package's available versions.


### Task 29 Fix Git remote URL parsing for tree-less repositories
Ensure that `Git.get_remote_url()` returns only the configured repository URL for tree-less Git repositories and does not expose Git remote direction annotations in the value returned to users.

- **Expectation**: When users request a Git remote URL through Conan, they should receive the real repository location, not extra text added by Git for tree-less clones or remote direction labels. Local repository paths should continue to work even if they contain spaces or parentheses.

- **Constraints**: The fix should only remove Git-added annotations and must not corrupt valid remote locations. Existing remote URL handling should remain stable, including for local paths with spaces or parentheses.


### Task 30 Normalize mixed-visibility dependency graph convergence
Ensure that dependency graphs remain well-formed when the same package is required through both `visible=True` and `visible=False` paths. Ensure that incompatible resolutions still fail as a normal dependency conflict, and that compatible resolutions keep a single clean graph while warning users that mixed visibility was detected.

- **Expectation**: If a package is pulled into the graph once as visible and once as hidden, Conan should no longer produce a malformed graph. A real version mismatch should be reported as the same kind of dependency conflict users see elsewhere. If the dependency can be unified to one resolved package, the command should succeed, warn about the mixed visibility, and show only the normalized dependency graph.

- **Constraints**: The fix must preserve real dependency conflict detection, avoid introducing warnings for normal graphs, and leave users with a clean final graph that contains only dependencies that still participate in the resolved topology.


### Task 31 Normalize Windows CMake preset include paths
Ensure that Conan-generated CMake user presets remain valid on Windows by writing portable include paths for referenced preset files.

- **Expectation**: Generated CMake user presets should use portable include paths so preset chaining works reliably for Windows users, including workflows where the presets are consumed from shared folders or by non-Windows tooling.

- **Constraints**: The fix should improve path portability without changing which preset file is referenced or altering unrelated preset-generation behavior.


### Task 32 Reduce verbosity in default conan upload output
Ensure that the default human-readable output of `conan upload` stays concise by hiding upload URL metadata from routine upload summaries while still clearly showing whether each item was uploaded or skipped.

- **Expectation**: Users running `conan upload` in the standard CLI format should see a compact status-oriented summary, not low-level transport details about where individual files would be uploaded.

- **Constraints**: Make the CLI quieter without changing upload behavior or hiding the status information users rely on to understand the outcome.


### Task 33 Create Missing Folders for `--out-file`
Ensure that commands using `--out-file` can write output to files inside directories that do not yet exist by automatically creating the required parent folders.

- **Expectation**: Users should be able to send command output to a file in a new folder with `--out-file` without creating folders manually first. The command should succeed and place the output in the requested file.

- **Constraints**: The fix should remove the need to pre-create folders, but it must not change the existing behavior for already valid output paths or where the command writes its redirected output.


### Task 34 Fix Windows LLVM/Clang runtime and clang-cl build flags
Ensure that Windows builds using LLVM/Clang through Conan generate the correct Debug dynamic MSVC runtime settings in `AutotoolsToolchain` and `GnuToolchain`, and ensure that `clang-cl` uses MSVC-compatible build-type flags instead of generic Clang/GNU-style flags when it is configured as the compiler frontend.

- **Expectation**: Windows LLVM/Clang builds should keep Debug and Release runtime intent consistent across generated toolchains. Debug builds that use the dynamic MSVC runtime must behave like true debug-runtime builds, and `clang-cl` should inherit the same build-type semantics users expect from other MSVC-compatible frontends rather than GNU-style Clang defaults.

- **Constraints**: Keep existing non-debug and non-dynamic Windows toolchain behavior stable while fixing the mismatch in Debug dynamic runtime handling and `clang-cl` flag selection. The update should refine compatibility, not broaden behavior changes beyond the affected Windows LLVM/Clang scenarios.


### Task 35 Restore legacy GCC default version normalization
Ensure that automatic GCC compiler version detection preserves legacy compatibility for older GCC releases by defaulting pre-5 versions to major.minor instead of full major.minor.patch values.

- **Expectation**: When Conan infers a GCC version for default settings, older GCC releases should be represented in the shortened form users historically received, while newer GCC releases should keep their current simplified version format.

- **Constraints**: The fix should be limited to preserving compatibility for older GCC defaults and must not alter how newer compiler versions or other compiler families are interpreted.


### Task 36 Restore source retrieval after resetting local recipe-index remotes
Ensure that resetting a local recipe-index remote does not break later retrieval of exported recipe sources for recipes resolved from that remote.

- **Expectation**: After a local recipe-index remote is recreated or reset, Conan should still be able to obtain the sources required by recipes stored in that remote. Users should only see a failure when the recipe truly does not exist, not because the remote's local metadata was rebuilt.

- **Constraints**: Keep normal successful source downloads unchanged, and do not turn real missing-recipe situations into silent recovery.


### Task 37 Correct Multi-Digit Compiler Version Detection
Ensure that compiler auto-detection preserves the full reported compiler version when a minor or later dotted component contains more than one digit, so detected settings do not shorten versions such as 8.12 or 15.15.0.

- **Expectation**: Automatic compiler detection should report the full GCC/Clang version that the compiler exposes, rather than truncating multi-digit components. Users relying on detected compiler settings or generated profiles should see the same version number the compiler reports for supported formats.

- **Constraints**: Keep existing auto-detection behavior intact for already supported compiler outputs. The fix should only expand version parsing so larger numeric components are handled correctly without introducing false matches or formatting artifacts.


### Task 38 Preserve ConanInvalidConfiguration from validation hooks
Ensure that raising ConanInvalidConfiguration from validation hooks marks the configuration as invalid instead of surfacing as a generic hook exception.

- **Expectation**: Validation hooks must be able to reject unsupported configurations using ConanInvalidConfiguration, and Conan should treat that outcome as a normal invalid-configuration result rather than an unexpected hook error.

- **Constraints**: Do not change normal hook failure handling for unrelated errors, and do not alter the standard validation flow for configurations that remain valid.


### Task 39 Handle tuple recipe generators with tool-provided generators
Ensure that installing or creating a package does not crash when a recipe declares `generators` as a tuple and a tool requirement contributes additional generators through `self.generator_info`, and ensure that both sets of generators are still honored.

- **Expectation**: Users should be able to combine recipe-declared generators and tool-require-provided generators regardless of whether the recipe expresses its generators as a tuple or another sequence. Package installation should proceed normally, with all expected generators still applied and the usual warning behavior preserved.

- **Constraints**: The fix should remove only the crash condition for tuple-declared generators. It should not otherwise change which generators run, the order in which combined generators are considered, or the visible warning that informs users about tool-require generator injection.


### Task 40 Fix Meson architecture mapping for riscv64
Ensure that Meson toolchain generation reports the correct target CPU information for 64-bit RISC-V builds and recognizes 64-bit WebAssembly targets so generated Meson machine definitions match the requested architecture.

- **Expectation**: Generating a Meson toolchain for a 64-bit RISC-V target should identify that target consistently as 64-bit RISC-V, and 64-bit WebAssembly targets should be treated as supported named architectures rather than falling back to incorrect architecture metadata.

- **Constraints**: The update should be narrowly scoped to accurate architecture reporting and must not change behavior for unrelated target architectures.


### Task 41 Scope Apple ARC flags to Objective-C toolchains
Ensure that Apple ARC configuration affects only Objective-C and Objective-C++ build settings, and that generic C, C++, and linker settings no longer receive ARC-specific switches when generating toolchains for Apple targets.

- **Expectation**: On Apple builds, enabling or disabling ARC should change only Objective-C and Objective-C++ compilation behavior. Shared C/C++ compiler settings and linker settings should still receive other Apple-related options such as bitcode or visibility, but they should not carry ARC-only flags.

- **Constraints**: Keep existing Apple platform flag behavior intact except for removing ARC from language-agnostic outputs. The change must not drop other shared Apple build settings, and it must not add ARC anywhere outside Objective-C and Objective-C++ compilation channels.


### Task 42 Fix mocked HEAD request handling in TestClient
Ensure that mocked HEAD requests made through TestClient behave correctly, so users can rely on HEAD-based existence checks in mocked client flows for both existing and missing resources.

- **Expectation**: When a user performs a mocked HEAD request through TestClient, it should behave like a real HTTP HEAD call: existing resources succeed with a normal success response, and missing resources report not found.

- **Constraints**: Keep the missing-resource behavior unchanged while making successful mocked HEAD requests reliable and standards-aligned from the caller's perspective.


### Task 43 Scope Conan core configuration to internal use
Ensure that `core.xxx` configuration supplied through `global.conf` or `-cc` is treated as Conan-internal only and does not leak into profiles or recipe-visible configuration.

- **Expectation**: Global internal settings should stay internal. Upgrading to 2.18.0 should stop `core` options from affecting recipe-facing profile configuration, without changing how ordinary user configuration is inherited.

- **Constraints**: The fix must be narrowly scoped to internal Conan settings and must not break existing configuration inheritance for normal user options.


### Task 44 Honor Apple-specific deployment targets in XcodeToolchain
Ensure that XcodeToolchain applies the configured minimum deployment version through the correct Apple-platform deployment target setting for each supported OS, so Xcode builds honor os.version consistently on macOS, iOS, tvOS, watchOS, and visionOS.

- **Expectation**: XcodeToolchain should make Xcode honor the minimum supported OS version for each Apple platform by exposing the correct platform-specific deployment target setting whenever a deployment version is configured.

- **Constraints**: The fix should be limited to deployment target selection, leave unrelated toolchain output unchanged, preserve configuration scoping behavior, and remain a no-op when no deployment version is specified.


### Task 45 Fix `conan export-pkg` version string handling
Ensure that `conan export-pkg` exposes the conanfile version as a string during recipe evaluation so package export remains consistent with other Conan CLI flows and recipes do not fail because `self.version` is provided as a non-string type.

- **Expectation**: `conan export-pkg` should present the version to recipe code exactly as users typed it, so recipes can treat `self.version` like a normal string and behave the same way they do in other Conan commands.

- **Constraints**: The upgrade should remove the version-type inconsistency without introducing new command options or changing how users specify package coordinates.


### Task 46 Honor core-conf overrides in cache backup uploads
Ensure that `conan cache backup-upload` honors `-cc` and `--core-conf` overrides so users can run source-backup uploads with temporary Conan core configuration instead of relying only on persisted settings.

- **Expectation**: Users should be able to pass temporary core configuration directly to the backup-upload command and have the upload behave as if those settings were active for that invocation. The command should no longer act as though no override was provided.

- **Constraints**: The upgrade should preserve the command's existing default workflow and scope. Only the missing application of user-supplied runtime configuration should change; default executions should continue to behave the same.


### Task 47 Fix repeated Conan CMake package discovery in nested directories
Ensure that Conan-generated CMake package configuration files can be used with multiple `find_package()` calls across parent folders and subfolders without causing target reconfiguration problems, and that package-declared system libraries remain part of the imported target's transitive link requirements.

- **Expectation**: Calling `find_package()` for the same Conan package from multiple `CMakeLists.txt` files in a project tree should just work. The imported package target should remain stable and should still carry the system libraries consumers need to link successfully.

- **Constraints**: The fix should remove the duplicate-discovery failure mode without forcing consumers to rewrite their CMake usage or changing the dependency contract of package resolutions that already behaved correctly.


### Task 48 Respect folders.root during source() path resolution
Ensure that recipes using layout() with a defined folders.root have source() and its source-related paths resolved from the rooted layout location rather than from the recipe directory.

- **Expectation**: Recipes that opt into a custom layout root should see the source step operate from that rooted workspace, so source files are read from or written to the expected location instead of an unrooted recipe directory.

- **Constraints**: Keep existing unrooted recipes working as before, and only alter behavior for recipes that explicitly define a custom root. Rooted layouts should behave consistently even when the root points outside the recipe directory.


## Breaking Changes

### Task 49 Migrate Conan workspaces to list-based package entries
Ensure that Conan workspaces remain usable after upgrading to 2.18.0 by declaring workspace packages as list entries with a package path and optional reference, without relying on the previous reference-keyed `packages` map or a separate `products` section.

- **Expectation**: A Conan workspace should describe editable packages as package entries rather than as a map keyed by reference. Each entry identifies where the editable package lives, may explicitly name its reference, and should still work when the reference can be read from the recipe. Workspace inspection should show the same list-based view that Conan actually uses.

- **Constraints**: The upgraded workspace format must stay unambiguous and safe: every declared package path should correspond to a real editable recipe, package identities must be valid and unique, repeated additions should not duplicate entries, and cleanup or removal should work from the package declarations alone.


### Task 50 Adopt package-oriented Conan workspace orchestration
Ensure that workspace workflows no longer depend on a separate product definition, and that users can add, inspect, install, and build workspace packages using package-based orchestration that respects dependency order. Ensure that monolithic workspace installation remains available under the dedicated `conan workspace super-install` command.

- **Expectation**: After upgrading, workspaces should behave as a package-oriented orchestration feature rather than a product-oriented one. Users should be able to build or install either the whole workspace or selected workspace packages, and Conan should process them in dependency order automatically. The command named `workspace install` should now mean ordered per-package installation, while the old one-shot workspace-wide install remains available under `workspace super-install`.

- **Constraints**: The upgrade should not require users to maintain a separate list of build targets inside the workspace. Selection must stay explicit and predictable, partial package operations must not silently act on unrelated workspace packages, and existing workspace-specific output locations should continue to apply. Dependency orchestration should extend to external packages only when Conan determines they need to be built.
