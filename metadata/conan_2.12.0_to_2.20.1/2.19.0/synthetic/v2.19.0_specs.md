# Upgrade Specification from 2.18.1 to 2.19.0

## New Features

### Task 1 Expose MesonToolchain built-in Meson options as public overrides
Ensure that MesonToolchain users can override the generated built-in Meson option values through public attributes before generation, including backend, buildtype, b_ndebug, b_staticpic, default_library, cpp_std, c_std, and b_vscrt, while preserving the expected precedence and default derivation rules.

- **Expectation**: Users should be able to customize the main built-in Meson configuration values by setting documented MesonToolchain attributes before generating the toolchain file. Those overrides should appear in the generated Meson configuration, except when an explicit external configuration for the backend is already defined, in which case that external backend choice should still win.

- **Constraints**: Existing MesonToolchain behavior should remain unchanged for callers who do not set the new public attributes. User overrides should be honored predictably, and configuration sources that already had higher priority must keep that priority. Related options should not silently re-derive themselves after a manual override unless the user changes them explicitly.


### Task 2 PremakeDeps honors requirement traits
Ensure that PremakeDeps only propagates dependency header metadata, library metadata, and runtime binary directories to generated Premake data when the corresponding Conan requirement traits are enabled.

- **Expectation**: Premake consumers should only inherit the parts of a dependency that were actually requested. Header-only usage should provide header-related build information, linkable usage should provide library linkage information, and runtime usage should provide executable or shared-library search paths.

- **Constraints**: The change should stop over-propagation without causing supported dependency information to disappear for valid consumer scenarios.


### Task 3 Support CMake target aliases in CMakeConfigDeps
Ensure that CMakeConfigDeps exposes additional consumer-facing CMake target aliases for packages and components through `cmake_target_aliases`, so projects upgrading to Conan 2.19.0 can preserve or introduce alternate target names without changing the primary target identity. Ensure that invalid alias definitions are rejected before generating ambiguous or conflicting CMake targets.

- **Expectation**: Consumers using `find_package` should be able to reference additional supported target names for a package or one of its components, and those names should behave as aliases to the real Conan-generated target. The feature must preserve the existing primary target naming contract and fail early when alias names would make target resolution ambiguous or invalid.

- **Constraints**: Do not change the canonical target name or link behavior just because alternate names are added. Reject conflicting alias configurations and avoid generating duplicate CMake target declarations.


### Task 4 Expose conan_data in serialized ConanFile output
Ensure that recipe conan data becomes visible in user-facing serialized Conan metadata so users can inspect the data attached to a recipe through commands such as `conan graph info` and other outputs built from serialized `ConanFile` information.

- **Expectation**: Users should be able to see a recipe's conan data anywhere Conan already exposes serialized recipe metadata. If a recipe has no meaningful conan data, command output should remain unchanged.

- **Constraints**: Do not regress existing metadata output. Only expose recipe conan data when it actually exists, and present it in the same structure users defined.


### Task 5 Associate `conan source` backup sources with recipe references
Ensure that backup sources generated by `conan source` are associated with a meaningful recipe reference whenever the recipe defines enough identity information, so users can manage those backup sources through normal reference-based Conan workflows instead of relying only on a generic fallback bucket.

- **Expectation**: When users run `conan source` on a recipe that identifies itself, Conan should remember downloaded backup sources under that recipe reference so later Conan operations can recognize them more naturally. Recipes that still do not provide enough identity should keep the previous fallback behavior, and explicitly uploading backup sources should remain possible when the stored reference does not match the later recipe reference.

- **Constraints**: Only complete recipe identities should produce reference-based backup source associations. Incomplete identities should still use the generic fallback, and backup sources tied to one recipe reference should not be silently treated as belonging to a different reference later.


### Task 6 Include Conan user and channel in CycloneDX SBOM references
Ensure that CycloneDX SBOM references include Conan package user and channel information when available so packages published under different namespaces are uniquely identified in component and dependency references.

- **Expectation**: Generated CycloneDX documents should expose the full Conan package identity in their reference fields, including namespace information when it exists, so downstream SBOM consumers can distinguish otherwise similar packages and follow dependency links correctly.

- **Constraints**: The change should be additive and backward-compatible for packages without namespace information, and it should only refine identifier content rather than alter the SBOM structure or dependency graph.


### Task 7 Honor test_package_folder in conan export-pkg
Ensure that `conan export-pkg` recognizes a recipe-defined custom test package folder so packages using `test_package_folder` behave consistently during export packaging, while still allowing an explicit command-line test folder override.

- **Expectation**: Users who place their test package in a custom folder declared by the recipe should be able to run `conan export-pkg` without extra configuration and have the command pick up that test package automatically. If a user explicitly names a test folder on the command line, that choice should override the recipe's default.

- **Constraints**: The new support should extend custom-folder discovery without breaking current export flows. Explicit user input should still win, and projects that rely on the default test package layout should continue to behave the same way as before.


### Task 8 Add GCC 12.5 settings support
Ensure that GCC 12.5 is recognized as a supported compiler setting so users can declare and use that toolchain version without configuration rejection.

- **Expectation**: Users upgrading to this version should be able to specify GCC 12.5 in normal compiler configuration and have the library treat it as a supported GCC release.

- **Constraints**: Support for GCC 12.5 should extend current behavior without altering how previously supported compiler versions or other settings work.


### Task 9 Support custom makefile names in Autotools build and install flows
Ensure that Autotools-based package builds and installs can target a custom makefile name instead of requiring the default Makefile, while preserving existing behavior when no custom makefile is specified.

- **Expectation**: Users should be able to build and install Autotools projects through the public helper API even when the project uses a non-default makefile name. The new option should work consistently for both build and install operations, and existing calls that do not use it should behave exactly as before.

- **Constraints**: The feature must be opt-in, must not disrupt standard Autotools packaging flows, and must not alter normal build or install semantics except for choosing a different makefile when explicitly requested.


### Task 10 Improve HTML graph and diff search usability
Ensure that generated HTML graph and diff reports provide more usable search interactions by delaying repeated updates while users type, keeping visible navigation and content synchronized, showing when a diff search returns no matches, and letting users focus a searched package from the graph search box by pressing Enter.

- **Expectation**: HTML report search should stay responsive on large outputs without reprocessing on every keystroke. Diff pages should clearly reflect whether anything matches the current filters, and graph search should let users jump directly to a matching package from the keyboard.

- **Constraints**: These UX changes must preserve existing search semantics, avoid surprising navigation during normal typing, and never leave the report navigation out of sync with the content being shown.


### Task 11 Premake Windows platform override support
Ensure that Conan's Premake integration on Windows allows consumers to choose a custom MSBuild platform for Visual Studio-based Premake builds and that generated Premake toolchain references remain consumable with Windows paths, without regressing existing Premake behavior on other actions.

- **Expectation**: When using Conan's Premake support on Windows, developers should be able to explicitly select the platform label that Visual Studio or MSBuild uses for the generated solution, and the generated Premake files should work with Windows path syntax without manual fixes. Existing usage that does not request a custom platform should keep working as before.

- **Constraints**: The change should be backward compatible for current Premake consumers. It should add Windows-specific configurability and path compatibility without altering how other Premake actions build or weakening existing failure behavior when required generated files are missing.


### Task 12 Support composing compatible Conan runner profiles
Ensure that Conan profile composition supports runner-enabled profiles by combining compatible runner configuration across profiles and rejecting incompatible runner type combinations.

- **Expectation**: Users should be able to split runner settings across multiple composed profiles as long as those profiles refer to the same kind of runner. If composed profiles request different runner kinds, Conan should stop and report the configuration conflict.

- **Constraints**: Composing profiles should remain predictable: compatible runner settings can be combined, but incompatible runner declarations must never be auto-resolved by implicitly picking one.


## Bug Fixes

### Task 13 Explicitly reject Conan channel values without a user
Ensure that Conan rejects any recipe reference that specifies a `channel` without a corresponding `user`, and reports a clear user-facing error instead of allowing the operation to continue into a lower-level failure.

- **Expectation**: Any Conan operation that resolves a recipe reference must treat `channel` as dependent on `user`: a standalone channel is invalid, and the command should stop immediately with a clear configuration error rather than an assertion or ambiguous failure.

- **Constraints**: Preserve normal recipe reference behavior and only reject the invalid case where a channel exists without a user, regardless of how those values were supplied.


### Task 14 Validate required Conan version before loading hooks
Ensure that Conan validates `core:required_conan_version` before loading hooks so users with an unsupported Conan version receive the version compatibility failure immediately and hook-loading problems cannot mask it.

- **Expectation**: Conan should fail fast on version incompatibility before hooks influence startup, while normal hook-enabled commands should keep working consistently and pick up refreshed hook configuration after reinitialization.

- **Constraints**: Supported environments should see the same hook-based behavior as before, and refreshing configuration should consistently apply updated hooks without requiring a new process.


### Task 15 Always show remote login credential prompts
Ensure that interactive remote authentication always shows the username and password request prompts even when normal output is filtered by the selected verbosity level, so users can complete login without hidden credential requests.

- **Expectation**: Whenever the CLI needs credentials for a remote, the user must always see the prompt telling them what value to enter. Lower verbosity settings must not hide these interactive prompts, and providing a username up front should only leave the password prompt visible.

- **Constraints**: Only the prompt visibility issue should change. The login flow, credential handling, and overall authentication behavior should stay the same apart from making the prompts reliably visible and readable.


### Task 16 Support spaced compiler paths in auto-detection
Ensure that compiler/profile auto-detection works when the configured compiler executable path contains spaces, and that compiler version detection remains accurate for `cc` outputs that include extra build metadata or extended numeric version formats.

- **Expectation**: Compiler auto-detection should behave the same for compiler binaries located in paths with spaces as it does for ordinary paths. Users should still get correct compiler-family detection, standard library inference where applicable, and version detection from common `cc --version` formats that include extra metadata.

- **Constraints**: This update should make auto-detection more robust without changing normal detection results for already supported compilers. Failed compiler invocations should still fail cleanly rather than being misclassified, and existing successful detections should remain stable.


### Task 17 Fix untargz for Windows long-path destinations
Ensure that `untargz()` can extract tar archives into Windows destination paths that use the `\\?\` long-path prefix without failing, while preserving the expected extracted directory structure when root stripping is enabled or disabled.

- **Expectation**: Users should be able to unpack tar archives into Windows long-path locations with `untargz()` the same way they can into normal paths. The extraction should complete successfully and create the expected files and folders instead of failing on path-format issues.

- **Constraints**: The fix should be limited to the Windows long-path edge case and must not alter how tar extraction behaves for standard paths or change the resulting archive layout beyond making long-path extraction work correctly.


### Task 18 Filter application package requirements from generated CMake base targets
Ensure that CMakeConfigDeps does not automatically propagate package requirements whose dependency has package_type=application as base link dependencies in generated CMake targets, while still honoring explicitly declared component dependencies from those packages.

- **Expectation**: Generated CMake dependency files should not make a library or package link against an executable-style dependency just because it is listed as a normal requirement. If the package explicitly depends on a specific usable component from that dependency, that explicit component relationship should still be preserved.

- **Constraints**: Only the unintended automatic linkage to application packages should be removed. Existing behavior for ordinary package dependencies and intentionally declared component dependencies should continue to work.


### Task 19 Fix concurrent startup in self-contained Conan binaries
Ensure that Conan distributed as a self-contained executable can start and run concurrent operations correctly, instead of failing because frozen-binary process startup is not initialized properly.

- **Expectation**: Users running Conan as a packaged standalone binary should see the same successful startup and concurrent command behavior they would expect from a normal Conan installation, without special failures caused by the packaging format.

- **Constraints**: The update should remove standalone-binary startup incompatibilities without changing ordinary Conan command semantics or introducing unrelated behavior changes.


### Task 20 Improve cc compiler version auto-detection
Ensure that automatic `cc` compiler detection correctly identifies the compiler version for common gcc and clang `--version` outputs, including outputs that include parenthesized build metadata before the version number, outputs that expose only a major or major.minor version, and compiler executable paths that require quoting.

- **Expectation**: Automatic compiler detection should accept the version formats commonly emitted by wrapped or toolchain-provided `cc` compilers and return the correct compiler family and version instead of failing or misreading metadata as the version.

- **Constraints**: The fix should broaden supported `cc` outputs without changing established detection behavior for already supported compilers or turning failed compiler invocations into successful detections.


### Task 21 Honor Apple deployment targets in XcodeBuild invocations
Ensure that Apple builds launched through Conan's XcodeBuild helper use the deployment target configured in the profile and handle project paths and target names safely when invoking xcodebuild.

- **Expectation**: Xcode-based Apple builds should reflect the minimum OS version declared in the user's Conan profile, and build commands should remain valid even when project or target names contain spaces.

- **Constraints**: The fix should only add the appropriate deployment target when the profile provides one and should not alter unrelated build options or change how builds behave when no explicit target is requested.


### Task 22 Honor deployment targets and preserve spaced XcodeBuild arguments
Ensure that `XcodeBuild` honors the deployment target declared in the Apple profile and correctly handles Xcode project paths or target names that contain spaces.

- **Expectation**: Building through `XcodeBuild` should preserve project and target names exactly, including spaces, and Apple builds should automatically respect the deployment target specified in the user's profile whenever one is available.

- **Constraints**: Do not alter unrelated build options or require new inputs. Builds without a deployment target should continue to run as before, and builds with spaces in names should no longer be misparsed by the command line.


### Task 23 Stabilize configuration package IDs against config_mode
Ensure that packages declared with `package_type="configuration"` keep a stable `package_id` that does not depend on `core.package_id:config_mode`, so configuration packages do not produce different binaries or become coupled to configuration-version changes when they are created or installed.

- **Expectation**: Configuration packages should have a stable binary identity of their own instead of changing with configuration-version tracking. After upgrading, these packages should be reusable across config-mode settings, while non-configuration packages should continue to behave as before.

- **Constraints**: Keep the fix narrowly scoped to configuration packages. Other packages must retain their current package identity rules, and the change must not broadly disable configuration-based package version tracking.


### Task 24 Fix PremakeDeps dependency link ordering
Ensure that projects using PremakeDeps link Conan dependencies in a deterministic dependency-aware order so dependent libraries are linked before the libraries they require, avoiding linker failures on order-sensitive linkers and preserving correct behavior across build configurations.

- **Expectation**: Using PremakeDeps should automatically produce stable, correct link ordering. Consumers should not need to manually reorder Conan-provided libraries, and each generated build configuration should keep its own dependency order data.

- **Constraints**: The fix should be additive and non-disruptive: existing Premake integration should continue to work, multiple generated configurations should coexist, and the main behavior change should be corrected link ordering.


## Additional Changes
- Ensure that remote metadata cached by Conan is invalidated before recipe or package upload and removal operations, so subsequent lookups against the same remote in the same Conan session reflect the remote's updated state instead of stale cached results.
- Ensure that invoking Conan's SSH runner without the optional Paramiko dependency fails immediately with a clear, actionable `ConanException` instead of exposing a raw `ImportError` from Paramiko imports.
