# Upgrade Specification from 2.19.1 to 2.20.0

## New Features

### Task 1 Add a built-in minimum compiler version validator for recipes
Ensure that Conan recipes can declare minimum supported compiler versions through a built-in validator and that package consumers receive consistent validation failures when their compiler is too old or compiler metadata is missing.

- **Expectation**: Recipes should be able to express minimum compiler support with a single standard validator instead of hand-written version checks. When a consumer uses an unsupported compiler version, Conan should reject the configuration with a clear explanation of the required version and why it is required, while missing compiler metadata should fail as an explicit configuration error.

- **Constraints**: The new validator should only apply rules that the recipe explicitly declares, should leave unrelated compilers unaffected, and should clearly separate invalid environment metadata from a genuine compiler version incompatibility.


### Task 2 Add default support for Clang 21 settings
Ensure that the built-in compiler settings accept Clang 21 as a valid compiler version so users can configure and consume that toolchain without custom settings overrides, while preserving existing default C++ standard behavior.

- **Expectation**: Users should be able to declare Clang 21 with the library's standard compiler settings out of the box. Upgrading should expand recognized compiler coverage without changing the expected default language-standard behavior.

- **Constraints**: The upgrade should be additive and backward-compatible for existing compiler configurations. It must not silently change unrelated compiler-setting behavior while adding support for the new version.


### Task 3 Add support for newer Apple OS and SDK versions
Ensure that Conan recognizes the latest released Apple operating system versions and matching SDK versions across iOS, tvOS, watchOS, visionOS, and macOS, and that unsupported SDK versions remain invalid.

- **Expectation**: Users targeting current Apple platform releases should be able to declare those OS and SDK versions in normal Conan settings without validation errors. The accepted SDK list should only include versions Apple has actually released, so speculative or nonexistent SDK versions are not treated as valid.

- **Constraints**: The upgrade should be backward compatible for existing Apple targets while tightening correctness around what SDK versions are considered real and supported.


### Task 4 Allow opting out of IntelCC environment script generation
Ensure that users can disable Conan's automatic Intel compiler environment setup when using `IntelCC` by explicitly setting `tools.intel:installation_path` to an empty string, for cases where the Intel compiler environment has already been activated outside Conan.

- **Expectation**: Users who already initialize the Intel compiler environment themselves should be able to tell Conan not to emit its Intel setup script by leaving the Intel installation path intentionally empty.

- **Constraints**: This opt-out should be narrow and explicit: it should affect only intentionally empty Intel installation path configurations and should not change the default behavior for normal Intel compiler setups.


### Task 5 Make generated Conan workspace super-builds follow package names and build order
Ensure that workspaces generated by `conan new workspace` can be used as super-builds even when a package's folder name differs from its Conan package name, and ensure the generated super-build adds projects from the workspace's real build order instead of a hard-coded sample sequence.

- **Expectation**: A newly generated Conan workspace should automatically adapt to the packages and dependency order present in that workspace. CMake configuration should continue to work if a package lives in a differently named directory, library packages should still expose the expected namespaced targets, and executable packages should be added without being treated as libraries.

- **Constraints**: Existing generated workspaces should keep building in dependency order, but the generated build should no longer depend on folder names matching package names. The update must not misclassify executables as libraries or break the default generated workspace layout.


### Task 6 Prefer config-based package discovery in CMakeConfigDeps
Ensure that projects using the CMakeConfigDeps generator automatically prefer config-based package discovery so dependency resolution selects generated package configuration files ahead of module-based lookup when both are available.

- **Expectation**: Consumers using the generator should get config-first package discovery by default. If the same dependency could be found either through a package config file or through a Find-module, the config-based result should win without requiring extra user configuration.

- **Constraints**: The upgrade should strengthen dependency resolution precedence without removing existing discovery hints or introducing extra setup steps for users already relying on the generator.


### Task 7 Support exclusion patterns in archive get/unzip APIs
Ensure that archive download and extraction workflows can omit unwanted files or directories by pattern when using the public `get()` and `unzip()` APIs, while preserving current behavior for calls that do not request exclusions.

- **Expectation**: Users should be able to download or unpack archives and specify path patterns that must be left out of the extracted result. Exclusions should work consistently across supported archive formats, combine predictably with existing include filtering, and leave existing callers unaffected unless they opt in.

- **Constraints**: This should be an additive capability rather than a breaking change. Existing extraction flows should keep working the same way by default, and other extraction options should remain compatible with the filtered result.


### Task 8 Add GCC 15.2 compiler support
Ensure that Conan accepts GCC 15.2 as a supported `compiler.version` for `compiler=gcc`, so users can configure profiles and builds for that toolchain without unsupported-setting failures.

- **Expectation**: Users should be able to target GCC 15.2 anywhere they declare Conan compiler settings, and the tool should treat that compiler release as officially supported rather than unknown or invalid.

- **Constraints**: Support for the new compiler release should not disturb existing working configurations. The upgrade should only expand the set of valid GCC versions and leave other compiler behavior unchanged.


### Task 9 Add newer Apple platform versions to Conan default settings
Ensure that Conan's default Apple settings recognize newly released Apple platform versions so users can target current iOS, tvOS, watchOS, visionOS, and macOS releases without custom settings edits or invalid setting rejections.

- **Expectation**: Users should be able to declare current Apple OS and SDK versions in Conan's default settings without being forced to patch the shipped settings list themselves.

- **Constraints**: The upgrade should add support for newer Apple platform versions without breaking any existing settings combinations that already worked.


### Task 10 Stabilize the public Conan ConfigAPI
Ensure that Python integrations use the stabilized ConfigAPI surface to inspect and manage Conan configuration, and that configuration changes become visible immediately through public API calls without depending on internal configuration objects or loaders.

- **Expectation**: Applications embedding Conan should use a small, documented configuration API to discover the active Conan home, install configuration from supported sources, read individual or filtered configuration values, list built-in settings, clean user configuration, and install configuration packages. After any configuration install, later API calls should immediately observe the updated settings through the public methods.

- **Constraints**: Resetting configuration must not delete cached packages. Callers should rely only on the supported configuration methods rather than internal state objects. Temporary configuration overrides applied to the active API session should remain visible through normal configuration reads once they take effect.


### Task 11 Expose and honor workspace super-install build order
Ensure that `conan workspace super-install` reports the dependency-safe build order of editable workspace packages and makes that same ordered workspace information available to workspace definitions so generated builds can add projects consistently and in the correct order.

- **Expectation**: Running the workspace super-install flow should show users which local packages are built first and allow workspace-specific build integrations to follow that exact dependency order when assembling the overall build.

- **Constraints**: The feature should add build-order visibility and ordered workspace generation without changing which packages are installed or built, and it should keep build-system integration safe for both libraries and executables.


### Task 12 Aggregate options for workspace super-build roots
Ensure that a workspace super-build propagates effective root-level configuration into the workspace root ConanFile and aggregates the resolved options of editable workspace packages so root-level workspace logic can make consistent build and generation decisions.

- **Expectation**: Running a workspace super-build should give the workspace's root project a faithful view of the resolved configuration: it should see its own effective options and settings, and it should be able to inspect the final option values of each editable workspace package from a single aggregated structure.

- **Constraints**: The feature should add visibility into workspace package configuration without changing unrelated dependency handling or mixing the root project's own options with per-package option data.


### Task 13 Support install_strip in Autotools installs
Ensure that Autotools-based package installs honor the tools.build:install_strip configuration so users can request stripped install artifacts through the standard Conan build configuration.

- **Expectation**: Autotools installs should support the same strip-on-install option already available in other Conan build helpers. Enabling the strip configuration should make the default install step produce stripped installed binaries, while explicit custom install targets should continue to behave exactly as requested by the caller.

- **Constraints**: Only the default install behavior should change when strip-on-install is requested. Existing install customization and non-strip installs must keep working without behavior changes.


### Task 14 Version-aware system package installs and stricter APT package detection
Ensure that the system package tool accepts version-qualified package requests and only reports APT packages as already installed when the installed package matches the requested architecture and, when specified, the requested version.

- **Expectation**: Users should be able to request a specific system package version through the system package tool and have supported package managers install and detect that exact version. APT should stop treating a package as present just because the same package name exists under a different architecture. When an exact version cannot be verified by the underlying package manager, the tool should remain usable while making that limitation visible.

- **Constraints**: Existing recipes that request plain package names should not regress. Cross-build behavior should continue distinguishing host packages from build-machine tools, and architecture-independent packages should still count as valid while false positives across architectures are eliminated.


## Bug Fixes

### Task 15 Clarify build-folder file conflict failures
Ensure that `conan build` detects when the configured build folder location is already occupied by a file and fails with a clear, user-facing explanation of the conflict.

- **Expectation**: Starting a build should immediately surface an actionable error if the chosen build directory name collides with an existing file. Users should be told that the build directory cannot be created at that location and which path caused the problem, while unaffected builds continue to work normally.

- **Constraints**: Only the invalid file-conflict case should change. Normal builds and valid directory-based layouts should behave the same as before.


### Task 16 Normalize multi-arch names in cmake_layout build folders
Ensure that `cmake_layout` correctly handles Apple universal or multi-architecture `arch` setting values when those values are used to derive folder names, so multi-arch builds produce usable and consistent layout output.

- **Expectation**: Projects using `cmake_layout` should be able to use Apple multi-architecture build settings without getting malformed or inconsistent generated folder names. The layout should expose a stable, filesystem-friendly name for multi-arch builds while preserving existing behavior for normal architecture values.

- **Constraints**: The fix should be narrowly scoped to multi-architecture folder naming and must not alter unrelated layout variables or ordinary single-architecture builds.


### Task 17 Clarify and harden ConanOutput text message handling
Ensure that ConanOutput public messaging methods remain text-oriented APIs, are clearly documented for their intended verbosity/notice usage, and do not fail during output solely because an emitted message value is not already a string when newline-terminated output is produced.

- **Expectation**: The output API should be easier to understand and more tolerant of accidental non-string message values during normal text emission, while still making it clear that callers are expected to provide text messages rather than rely on generic object-to-string behavior.

- **Constraints**: Keep the logging surface and visibility rules stable, preserve backwards-compatible method semantics, and avoid implying that any object type is a supported message input.


### Task 18 Stabilize and document the ConanOutput text logging API
Ensure that `ConanOutput` exposes a clearly documented public logging interface and that its message methods behave consistently as text-oriented, chainable APIs without incidental output failures during newline handling.

- **Expectation**: Upgrading users should get a clearly documented `ConanOutput` API with consistent chaining behavior across its logging methods. The logging surface remains intended for text messages, but the upgrade should eliminate incidental type errors caused by newline processing rather than broaden the API into general object serialization.

- **Constraints**: Keep current log levels, scoping, filtering, and warning-to-error behavior intact. Improve robustness and documentation of the output API without changing it into a generic formatter for arbitrary objects.


### Task 19 Suppress conflicting visibility risk warnings for test_requires
Ensure that conflicting dependency visibility is not reported as a risk when the conflict comes from test_requires, while preserving the existing warning for equivalent conflicts in normal non-test requirements.

- **Expectation**: Test-only dependency paths should not be treated as risky public visibility conflicts. Users should only see the conflicting-visibility warning when the mismatch affects the regular dependency graph rather than test-specific requirements.

- **Constraints**: Keep dependency resolution behavior stable except for removing this specific warning noise from test-only scenarios. Ordinary visibility conflicts outside test requirements must continue to surface.


### Task 20 Preserve runtime_deploy subfolder layout
Ensure that the runtime_deploy deployer preserves the relative subfolder structure of deployed runtime artifacts so nested libraries and binaries remain available in their original layout and deployed symlinks do not break when they reference files inside subdirectories.

- **Expectation**: Upgrading to 2.20.0 should make runtime_deploy mirror the dependency runtime folder layout in the deploy output. Users should be able to rely on nested runtime files and relative symlinks remaining usable after deployment, without flattening everything into a single directory.

- **Constraints**: The fix should preserve existing runtime deployment behavior apart from keeping subfolders. It should not change which runtime artifacts are eligible for deployment or require a different deployment flow.


## Dependency Updates

### Task 21 Support versioned system packages and accurate APT package detection
Ensure that Conan's system package manager tool accepts version-qualified system package requirements and that APT only considers a package satisfied when the installed package matches the requested package architecture and, when requested, the required version.

- **Expectation**: Users should be able to express a desired system package version through Conan's system package tooling, and Conan should honor that version when the underlying package manager can verify it. On APT-based systems, Conan should no longer report a package as already installed merely because the same package name exists for a different architecture.

- **Constraints**: Existing non-versioned package usage should remain compatible. The fix must avoid false positives in multi-architecture environments without turning unsupported version pinning into a hard failure.


## Breaking Changes

### Task 22 Drop Python 3.6 support and require Python 3.7+
Ensure that upgrading to Conan 2.20.0 is treated as a Python runtime compatibility change: Conan must only support Python 3.7 and newer, and users on Python 3.6 must be prevented from installing or running it.

- **Expectation**: The upgraded release must require Python 3.7 or newer everywhere users install or run Conan. Unsupported interpreters should be rejected immediately rather than allowed to continue with a warning.

- **Constraints**: The upgrade should only tighten the minimum Python version boundary. Users already on supported Python versions should keep the same Conan behavior apart from updated compatibility rules.


### Task 23 Privatize undocumented Conan Python API members
Ensure that integrations upgrading to Conan 2.20.0 use only the documented Conan Python API surface, no longer depend on undocumented sub-API attributes or helper members that were previously reachable, and initialize `ConanAPI` only on supported Python runtimes.

- **Expectation**: The upgrade should make the Python API surface explicit: supported workflows must go through documented methods for configuration, listing, cache, upload, and download operations, while internal state and helper objects are no longer available for direct use. Integrations should also run only on supported Python versions.

- **Constraints**: Do not change normal supported Conan workflows. The intended incompatibilities are limited to removing unsupported internal access paths and enforcing the newer minimum Python version.


### Task 24 Migrate Conan API consumers to ListAPI.select and immutable home folder
Ensure that upgrading to Conan 2.20.0 preserves recipe and package discovery through the supported public API, prevents workflows from mutating ConanAPI.home_folder after initialization, and only runs on supported Python runtimes.

- **Expectation**: After the upgrade, recipe and package lookup should still be available, but only through the consolidated listing API. Users should be able to query local or remote data, apply supported filters, and receive deterministic results without relying on a separate search namespace. The configured Conan home location should be fixed at construction time rather than mutable later, and the library should only run on supported Python versions.

- **Constraints**: The upgrade must narrow the public API surface without changing the meaning of supported search and listing operations. Existing integrations should only need to move to the supported entry point and runtime, while keeping the same visible lookup behavior and without regaining the ability to silently repoint the Conan home directory during execution.


### Task 25 Adapt integrations to Conan 2.20.0 API contract changes
Ensure that integrations upgrading to Conan 2.20.0 stop depending on `ConanAPI.search`, treat `ConanAPI.home_folder` as read-only after initialization, and only run `ConanAPI` on supported Python versions while preserving supported package discovery and home-resolution behavior.

- **Expectation**: After the upgrade, callers should use the list-based API for package discovery, the Conan home location should be fixed when the API instance starts instead of being reassigned later, and unsupported Python runtimes should be rejected at startup.

- **Constraints**: The upgrade should narrow the supported public API without removing the ability to discover packages through the official list workflow, and it should harden home-folder handling without breaking supported ways of choosing the Conan home before startup.
