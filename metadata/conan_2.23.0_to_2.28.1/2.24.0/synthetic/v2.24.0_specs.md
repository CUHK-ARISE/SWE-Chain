# Upgrade Specification from 2.23.0 to 2.24.0

## New Features

### Task 1 MesonToolchain aligns exe wrapper usage with runnable cross-builds
Ensure that MesonToolchain only marks cross-builds as needing an executable wrapper when Conan determines the produced binaries cannot run in the current build environment.

- **Expectation**: Meson-based cross-builds should only request an executable wrapper when the generated binaries are actually not runnable on the machine performing the build. Runnable cross-builds should behave like native execution for this setting.

- **Constraints**: Do not require wrappers more broadly than necessary, and do not remove wrappers from environments that still need them. The change should narrow behavior based on real execution capability without altering unrelated toolchain behavior.


### Task 2 Workspace super-install honors layout() source folders
Ensure that `workspace super-install` follows each editable recipe's `layout()` when locating workspace package sources, so workspaces continue to install correctly even when a project stores its build inputs under a custom source subfolder.

- **Expectation**: `workspace super-install` should use the same source location rules that the recipe declares through `layout()`. Users should be able to super-install a workspace successfully whether a package keeps its sources at the project root or inside a declared source subdirectory, and the reported build order should clearly show which folder each package is coming from.

- **Constraints**: The upgrade should only change how workspace editable package source locations are resolved and reported. It must not introduce a different workflow for users beyond honoring declared layouts and surfacing layout-related failures normally.


### Task 3 Non-selectable diff markers in HTML report output
Ensure that HTML reports generated by `conan report diff` let users select and copy diff content without including decorative diff symbols in the copied text, while keeping the rendered diff visually clear and aligned.

- **Expectation**: The HTML diff view should behave like a code review interface where change markers are visual aids only. Users should be able to copy code from the report cleanly, without extra diff prefixes appearing in pasted content, and the diff should remain visually aligned and easy to read.

- **Constraints**: Limit the change to copy/select behavior in the HTML report. The visible diff presentation and meaning of additions, deletions, and unchanged lines should stay the same.


### Task 4 Public Conan Python sub-APIs expanded
Ensure that Python integrations can rely on the additional Conan 2.24.0 sub-APIs as supported public interfaces, with clear contracts for cache archive restore/save, lockfile retrieval, recipe and source diff generation, audit access, and backup-source upload behavior.

- **Expectation**: The library should provide officially supported Python entry points for cache operations, lockfile handling, vulnerability auditing, and version-to-version diff reporting, with stable return contracts that callers can depend on when automating Conan workflows.

- **Constraints**: The upgrade should expand supported Python API coverage without regressing existing cache, lockfile, diff, or backup-source workflows. Default discovery and error behavior should stay consistent, and callers should not need to infer undocumented side effects.


### Task 5 Show missing packages in HTML dependency graphs
Ensure that missing dependencies are represented in `graph.html` output and that missing-package errors indicate which graph node requested the unresolved package.

- **Expectation**: If dependency graph generation fails because a package cannot be resolved, the HTML graph should still show where the failure happened instead of silently omitting it. Users should be able to see both the missing package and which dependency path requested it, and textual error reporting should name the requester.

- **Constraints**: The new behavior should extend error visualization for missing dependencies without regressing other graph error displays or normal graph rendering. It should only appear for actual missing-dependency failures and should keep the rest of the graph behavior consistent.


### Task 6 Add structured JSON results for cache integrity checks
Ensure that `conan cache check-integrity` can expose corrupted cache artifacts in a structured JSON format so users and tooling can identify and act on damaged recipes or packages without losing the command's existing corruption detection behavior.

- **Expectation**: The integrity-check command should provide a machine-readable summary of corrupted cache contents, not just human-readable console logs. Consumers should be able to retrieve the set of corrupted artifacts programmatically, and corruption should still be treated as a failed integrity check. Recipe-level corruption should be reported at the recipe scope, while binary-only corruption should identify the affected packages.

- **Constraints**: The new output must add structured reporting without weakening existing validation semantics. Clean artifacts should not be misreported, corrupted artifacts should still cause the operation to fail, and existing consumers that rely on exception-based failure should continue to behave as before unless they explicitly request structured results.


### Task 7 Add workspace completion for intermediate packages
Ensure that Conan workspaces can be completed automatically when editable packages are separated by intermediate cached packages, so users can turn those intermediate dependencies into workspace entries without manual discovery and receive actionable guidance when an incomplete workspace definition is invalid.

- **Expectation**: Users should be able to run one command to complete a partially opened workspace when intermediate dependencies sit between workspace packages. The command should reuse existing local package checkouts when available, fetch or open missing intermediate packages when needed, and otherwise leave the workspace unchanged if there is nothing to add. If users try to operate on an incomplete workspace that still mixes cached packages above editable workspace packages, Conan should fail clearly and direct them to the workspace completion flow.

- **Constraints**: Workspace completion should be narrowly scoped to the missing packages required to make the workspace graph coherent. It should not pull unrelated dependencies into the workspace, it should not treat no-op situations as errors, and it should surface missing recipe problems as explicit user-facing failures.


### Task 8 Allow hashlib in global.conf templates
Ensure that `global.conf` templates can derive configuration values from hashes by using `hashlib` during Jinja2 rendering, so users can generate deterministic values such as shortened or hashed paths directly in configuration.

- **Expectation**: Users should be able to write dynamic `global.conf` templates that compute hash-based configuration values directly at render time, and those computed values should behave like any other rendered configuration setting.

- **Constraints**: The new hashing capability should extend template expressiveness without changing the behavior of existing configurations or requiring users to rewrite non-hash-based settings.


### Task 9 Declarative Configuration Package Installs
Ensure that `conan config install-pkg` supports a declarative `conanconfig.yml` workflow for installing multiple configuration packages, preserves predictable configuration ordering across repeated installs and updates, and prevents unsafe reordering of already-installed configuration packages unless the user explicitly forces it. Ensure that persisted configuration state and lockfile config requirements are tracked at the recipe-reference level so lockfile-driven and repeated configuration installs remain stable across binary package changes.

- **Expectation**: Users should be able to declare configuration packages in a manifest and install them in a predictable sequence, with optional package source URLs bundled alongside that manifest. Conan should treat repeated installs as no-ops when nothing changed, allow safe version updates and additions that preserve the established order, and require an explicit force action before applying a request that would reorder existing configurations. Persisted config state and lockfiles should identify configuration requirements by recipe rather than by resolved binary package, and config lockfile upgrades should follow a dedicated CLI path.

- **Constraints**: Do not accept non-configuration packages or configuration packages with dependencies as valid config installs. Do not silently reshuffle previously applied configuration layers. Do not let binary package identity differences create duplicate configuration entries for the same recipe. Do not apply package bookkeeping files as if they were user configuration.


### Task 10 Support recipe-based configuration package installs and batch config files
Ensure that `conan config install-pkg` can manage configuration packages as an ordered set of recipe references, including installs declared in `conanconfig.yml`, and that it protects users from unsafe reordering of previously installed configuration layers unless they explicitly force the change.

- **Expectation**: Users should be able to install configuration from either one package reference or a config file that lists multiple packages, and Conan should remember that configuration by recipe identity rather than binary package identity. Safe updates should apply normally, duplicate requests should be ignored unless forced, and disruptive reordering of existing configuration layers should require an explicit override.

- **Constraints**: Do not make installed configuration state depend on a specific binary package instance, do not allow invalid configuration packages, and do not silently reshuffle previously applied configuration layers. Existing remote-based and lockfile-based configuration install workflows should keep working.


### Task 11 Support multi-package config installs with safe ordering
Ensure that `conan config install-pkg` can install configuration packages as an ordered set from `conanconfig.yml`, preserve the installed configuration stack by recipe reference, and reject order-changing updates unless the user explicitly forces the change.

- **Expectation**: Users should be able to declare multiple configuration packages in a config file and install them together. Conan should treat the installed configuration stack as ordered, avoid reinstalling an unchanged stack unless forced, and protect users from accidental precedence changes by requiring explicit confirmation before a reorder is applied.

- **Constraints**: The upgrade must remain idempotent for unchanged configuration requests, additive for safe new entries, and explicit when a change would alter configuration precedence. It should continue to honor the user's normal package resolution context.


## Bug Fixes

### Task 12 Generate CMakeConfigDeps targets for framework-only and define-only dependencies
Ensure that CMakeConfigDeps generates consumable targets for dependencies that expose only compiler definitions and/or frameworks, so downstream CMake projects can depend on them without missing-target failures.

- **Expectation**: Upgrading should let CMake consumers use Conan dependencies that contribute only metadata such as frameworks or compile definitions. Those dependencies should behave like normal generated targets, and any exported definitions should reach downstream builds in a form CMake can apply correctly.

- **Constraints**: The fix should expand support for metadata-only dependencies without changing the behavior of ordinary library dependencies or treating executables as linkable library targets.


### Task 13 Warn on ineffective version ranges in reference patterns
Ensure that reference patterns do not silently accept version-range syntax in contexts where version ranges have no effect, and clearly warn users that only the supported consumer and wildcard forms are meaningful there.

- **Expectation**: If a user writes a package selector with a version range in a place where range matching is not supported, the tool should clearly warn that the range will be ignored. The operation should still continue using the normal selector behavior instead of treating the range as a valid filter.

- **Constraints**: This change is informational, not a new matching capability. Existing selectors should keep behaving the same unless they now surface a warning that previously missing range syntax was being ignored.


### Task 14 Detect Visual Studio 18 during Conan profile auto-detection
Ensure that automatic Conan profile detection recognizes Visual Studio 18 (2026) when detecting MSVC toolchains on Windows.

- **Expectation**: Users with Visual Studio 18 installed should be able to rely on Conan's automatic profile detection to identify that IDE correctly, and systems with multiple supported Visual Studio versions should prefer the newest supported one.

- **Constraints**: Adding support for the new Visual Studio release must not regress profile detection for older supported Visual Studio installations or change behavior on machines where the new version is not installed.


### Task 15 Correct sysroot flags for QNX qcc in GNU toolchains
Ensure that configuring a sysroot through Conan's GNU toolchains works correctly for QNX builds that use the qcc compiler, so generated build flags are accepted by the compiler and existing sysroot behavior remains unchanged for other toolchains.

- **Expectation**: When a user sets a sysroot for GNU-style Conan toolchains, the generated compiler and linker flags should match the selected compiler's expected syntax. QNX builds using `qcc` should receive a compiler-compatible sysroot option, while other compilers should keep the existing GNU sysroot behavior. If no sysroot is configured, no sysroot option should appear.

- **Constraints**: The fix must be narrowly scoped to how sysroot flags are formatted for the chosen compiler. Existing sysroot behavior for non-QNX or non-`qcc` builds must not regress, and builds without a sysroot configuration must continue behaving as before.


### Task 16 Fix option scoping for version-range install requirements
Ensure that `conan install` correctly scopes a user-provided unscoped option to the single requested dependency when that dependency is declared with a version-range pattern such as `name/[*]`, and ensure that matching logic for version-pattern-based scoping recognizes version ranges instead of treating them as plain version strings.

- **Expectation**: If a user installs a single dependency using a version-range requirement and passes an option without an explicit package prefix, the option should still apply to that dependency exactly as it would for a fixed version. Version-range expressions should be interpreted semantically as ranges during option matching, and users should not receive misleading warnings when the dependency actually matches.

- **Constraints**: Existing installs that already work with explicit versions or explicit option scoping should continue to behave the same. The change should only broaden correct matching for range-based dependency expressions and should not introduce new ambiguity in how options are targeted.


### Task 17 Fix optimized compatibility mode across multiple remotes
Ensure that enabling `core.graph:compatibility_mode=optimized` works correctly when multiple remotes are configured, so Conan can resolve compatible binaries across all remotes without failing after the first remote lookup.

- **Expectation**: Optimized compatibility resolution should behave correctly in multi-remote setups: Conan should scan all configured remotes for compatible binaries, combine the results it finds, ignore remotes that simply do not contain the package, and still fail on real remote availability problems.

- **Constraints**: Limit the change to making multi-remote optimized compatibility lookups reliable, without altering normal compatibility behavior or weakening existing remote error handling.


### Task 18 Handle external editables during workspace build
Ensure that `conan workspace build` completes successfully when the workspace depends on editable packages that were added globally but are not included in the current workspace, and that those external editables are handled through the normal external build flow instead of causing a crash.

- **Expectation**: `conan workspace build` should distinguish between editables that belong to the current workspace and editables that are only registered globally. Workspace members should keep their current workspace build behavior, while external editables should be processed as external dependencies so the command finishes normally.

- **Constraints**: The update should remove the crash without changing how normal workspace packages are built. Dependencies that are outside the workspace should be handled safely and consistently, and the command should not rely on workspace-only state for them.


### Task 19 Fix CMakeConfigDeps handling of separator-sensitive flags
Ensure that upgrading to Conan 2.24.0 preserves compile and link flags emitted by CMakeConfigDeps when package metadata contains generator-expression-sensitive values, including separator-sensitive and multi-token flag entries, so downstream CMake projects consume the intended options without malformed target properties.

- **Expectation**: CMake dependency files generated after the upgrade should carry compile and link options exactly as package authors declared them, even when an option includes characters or formatting that CMake generator expressions treat specially. Consumers should see the right options applied to the right language or target type, without configuration-time breakage or silently altered flag boundaries.

- **Constraints**: The upgrade should be a compatibility-preserving bugfix: it should only correct how options are encoded and forwarded, not broaden where they apply or require users to redefine package flags that were already supported.


### Task 20 Distinguish empty and unset EnvVars in generated shell scripts
Ensure that EnvVars-generated `.sh` and `.ps1` activation scripts distinguish between environment variables that are explicitly defined as empty and variables that are defined as unset, so upgrades preserve the intended shell environment state.

- **Expectation**: Shell activation scripts should preserve the semantic difference between setting a variable to an empty value and removing the variable from the environment. Users should see empty variables remain present but blank, while unset variables should be absent.

- **Constraints**: Limit the change to fixing the empty-versus-unset distinction without altering normal environment-variable assignment behavior. Both supported shell script formats should behave consistently.


### Task 21 Prevent Workspace crashes when using per-package configuration
Ensure that `Workspace` operations do not crash when users pass per-package configuration, including configuration scoped to selected packages by pattern.

- **Expectation**: Workspace installs should support the same per-package configuration behavior users expect from consumer workflows, allowing package-scoped settings without aborting the operation.

- **Constraints**: The upgrade should eliminate the crash without changing the meaning of valid per-package configuration or altering unaffected workspace behavior.


### Task 22 Fix version-range matching in replace_requires
Ensure that replace_requires correctly matches and replaces dependencies when the replacement pattern uses a version range, including dependencies declared with an exact version and dependencies declared with a version range, while leaving incompatible requirements unchanged.

- **Expectation**: Users should be able to define replace_requires rules with version ranges and have those rules reliably affect all compatible dependencies, regardless of whether the dependency was declared as a single version or as a version range. Incompatible dependencies should remain untouched.

- **Constraints**: The fix should be limited to correct matching semantics for range-based replacement rules. It must preserve existing replacement behavior outside this case and avoid applying replacements to incompatible dependencies.


## Documentation

### Task 23 Clarify MSBuildToolchain compile_options contract
Ensure that `MSBuildToolchain` documentation correctly describes `compile_options` as compiler options applied to MSBuild `ClCompile` settings, and clearly communicates how configuration-provided compile options participate in the generated toolchain behavior.

- **Expectation**: Users should understand that `compile_options` controls MSBuild compiler options, not preprocessor definitions, and that options supplied through the MSBuild toolchain configuration are combined with the toolchain's compile option mapping.

- **Constraints**: The update should remove ambiguity without altering existing toolchain behavior. It should clarify the boundary between compiler options and preprocessor definitions and keep configuration-based compile options additive.
