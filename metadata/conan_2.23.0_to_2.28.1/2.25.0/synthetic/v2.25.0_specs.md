# Upgrade Specification from 2.24.0 to 2.25.0

## New Features

### Task 1 Make Package Binary Downloads Atomic
Ensure that downloading a package binary from a remote only makes the package visible in the local cache after the full download has completed, so cancellations or interruptions do not leave a partially installed package behind.

- **Expectation**: A downloaded binary package should appear in the cache only when it is complete. Interrupted downloads must not leave broken cache entries, and benign races during finalization should degrade to a warning rather than a corrupted or half-visible package.

- **Constraints**: The change should improve interruption safety without changing the expected result of successful downloads. Users should keep getting the same completed package in cache, but they should no longer see incomplete package state if a download stops midway.


### Task 2 Allow `conan new` to generate a default CMake recipe without a template argument
Ensure that `conan new` can be invoked without a positional template argument and that it generates a default CMake-oriented recipe scaffold suitable for a basic consumer project.

- **Expectation**: Users should be able to run `conan new` with no template name and receive a ready-to-edit default recipe for a simple CMake consumer project. The generated scaffold should already reflect the standard Conan+CMake workflow, including layout setup, dependency/toolchain generation, and build orchestration.

- **Constraints**: The new convenience path must not break current template-based usage. Calling the command without a template should behave like a sensible default choice rather than altering other template selection behavior.


### Task 3 Document CacheAPI and ConfigAPI public contracts and cache archive handling
Ensure that upgrading users have a documented and reliable public contract for CacheAPI and ConfigAPI, including which cache locations are read-only versus metadata-only exceptions, how configuration installation affects ConanAPI state, and how cache archives are saved and restored based on the requested archive format.

- **Expectation**: The upgrade should give users a clear, supported contract for inspecting the Conan cache and managing Conan configuration. Cache access APIs should clearly distinguish read-only inspection paths from the limited metadata locations that are safe to update, configuration installation APIs should warn that they refresh the active Conan state, and cache export/import should behave predictably based on the archive format named by the user.

- **Constraints**: The public contract should stay conservative: users may inspect cache contents but should not modify cache artifacts except where metadata is explicitly allowed, unsupported archive formats should fail clearly instead of guessing, configuration downloads should remain separate from configuration installation, and only supported entry points should be presented as part of the public API.


### Task 4 Deprecate MesonToolchain preprocessor_definitions in favor of extra_defines
Ensure that Meson toolchain users are informed that `MesonToolchain.preprocessor_definitions` is deprecated and should be replaced with `extra_defines`, without breaking builds that still rely on the deprecated attribute.

- **Expectation**: Users who still configure Meson preprocessor definitions through the old attribute should receive a clear deprecation notice telling them to migrate to `extra_defines`, while their current builds continue to work during the transition period.

- **Constraints**: The upgrade must be backward compatible for existing users and should add guidance rather than breaking established Meson build configurations.


### Task 5 Add local dependency management with conan require
Ensure that users can add or remove `requires`, `tool_requires`, and `test_requires` entries in a local `conanfile.py` through a dedicated `conan require` CLI, with automatic dependency version selection, safe duplicate handling, and clear behavior when a dependency cannot be found or is not already declared.

- **Expectation**: Users should be able to manage local recipe dependencies from the Conan CLI instead of editing the recipe by hand. Adding a dependency should normally choose the latest available compatible starting point and store it in a forward-compatible range, while removal should cleanly drop the selected dependency kind. The command should be predictable when dependencies already exist, are missing from the recipe, or cannot be resolved from the configured sources.

- **Constraints**: The upgrade should stay limited to managing local dependency declarations, preserve the distinction between normal, tool, and test dependencies, and avoid surprising edits such as duplicate entries or fabricated versions when lookup fails.


### Task 6 Preserve CPS component requires in CMake round trips
Ensure that CMake CPS round trips preserve component dependency relationships and link metadata so packages with components and `requires` remain consumable after CPS export and re-import.

- **Expectation**: A package exported to CPS and then reconstructed from CPS should behave like the original package from a consumer perspective. Component dependencies, link targets, system libraries, and language-specific link metadata should survive the round trip, including packages with multiple components and transitive component relationships.

- **Constraints**: The new round-trip support should extend CPS interoperability without breaking simpler CPS packages or changing how normal package-level requirements are modeled. Missing optional CPS metadata should degrade gracefully instead of producing broken package information.


### Task 7 Add link feature support to CMakeConfigDeps
Ensure that CMakeConfigDeps allows package authors to declare CMake link features for dependency and component links, and that generated consumer targets apply those features only for real link relationships with clear version-gated behavior.

- **Expectation**: Users should be able to mark selected Conan dependencies with a CMake link feature and have generated CMake package configuration files carry that feature into downstream linking. The feature should only affect dependencies that are actually linked, unsupported CMake versions should fail explicitly instead of degrading silently, and non-link relationships should keep their previous compile-only behavior.

- **Constraints**: This must be an opt-in extension of existing dependency generation, not a rewrite of general linking semantics. Feature-aware linking should be limited to cases where the dependency is actually part of the link interface, and obviously nonsensical feature choices should remain the caller's responsibility rather than being silently rewritten.


### Task 8 Add Apple platform 26.2 settings support
Ensure that upgrading to Conan 2.25.0 allows users to target the newly supported Apple platform release level 26.2 in standard settings, so package profiles and configurations using those values are accepted instead of being treated as invalid.

- **Expectation**: Users should be able to declare Apple platform version 26.2 and matching SDK version 26.2 in normal Conan settings for the supported Apple operating systems, and Conan should treat those configurations as supported.

- **Constraints**: The upgrade should expand compatibility for newer Apple target versions without changing how users specify those settings or breaking existing Apple configurations.


### Task 9 Add CPS component round-trip support for Conan and CMake
Ensure that CPS package metadata generated by CMake can be round-tripped through Conan for packages with components, without losing component dependency relationships, linked library information, or shared-library runtime versus link locations.

- **Expectation**: Loading a CPS package with components into Conan should preserve each component's consumable metadata, including headers, compile definitions, linked library artifacts, system libraries, and declared dependencies. Exporting Conan metadata back to CPS should retain the same component-level linkage information, including separate link-time and runtime locations for shared libraries when available.

- **Constraints**: The feature should add component support without making sparse CPS metadata invalid, without confusing runtime and link locations for shared libraries, and without changing normal package-level dependency behavior for non-component or single-component consumption.


### Task 10 Promote CMakeConfigDeps to an experimental standalone CMake generator
Ensure that consumers can use `CMakeConfigDeps` directly as an experimental generator without enabling the previous incubating configuration gate, while preserving clear migration warnings and consistent generated CMake package behavior.

- **Expectation**: Users should be able to adopt `CMakeConfigDeps` directly as an experimental generator, receive warnings that reflect its stability level, and get predictable config-package generation even when older module-oriented settings are present. Existing recipes that still touch obsolete compatibility knobs should continue to run, but those knobs should be treated as deprecated no-ops. Generated CMake package metadata should preserve compile definitions needed by consumers.

- **Constraints**: The upgrade should broaden availability of the new generator without introducing hard failures for existing consumers. Backward-compatibility shims may remain, but unsupported legacy behaviors should degrade with warnings rather than silently changing output shape or stopping installs.


### Task 11 Support CMake CPS shared-library metadata
Ensure that Conan can consume CMake-generated CPS metadata for shared libraries, including componentized packages, so CPS-loaded packages expose correct link-time, runtime, and dependency information to consumers.

- **Expectation**: Loading a package from CPS should work for shared libraries exported by CMake, not just static ones. Consumers should link against the correct library artifact, receive any runtime binary path information needed for shared libraries, and keep component dependency and system library metadata intact even when the CPS data omits optional arrays.

- **Constraints**: The new shared-library support must preserve existing static-library behavior, remain tolerant of partial CPS metadata, and avoid introducing duplicate dependency wiring for simple non-component packages.


### Task 12 Add CPS package discovery support to CMakeConfigDeps
Ensure that CMakeConfigDeps supports full CPS-based CMake round trips for Conan packages that ship packaged `.cps` metadata, so consumers can resolve those dependencies through CMake package discovery even when the dependency is configured not to generate the standard Conan CMake config package files.

- **Expectation**: Consumers using CMake CPS package discovery should be able to round-trip package metadata from a Conan-produced package into a Conan-generated consumer project without requiring a traditional generated config package from Conan. If CPS metadata is present, the consumer should locate the package through that metadata transparently; otherwise, existing behavior should remain intact.

- **Constraints**: The new CPS support should extend dependency discovery without breaking existing consumers, and packages that do not participate in CPS-based metadata should keep working as they did before.


### Task 13 Expose root profile name in Conan profile templates
Ensure that Conan profile templates can identify the top-level profile that initiated rendering, even when configuration is defined inside profiles included by another profile.

- **Expectation**: Profile templates should be able to distinguish between the profile currently being evaluated and the top-level profile that started the include chain. Shared included profiles should be able to tailor behavior based on the root profile without losing awareness of their own local profile identity.

- **Constraints**: Existing profile templates should keep working as before. The only new behavior is that templates can also access the original root profile name consistently, including from nested included profiles.


### Task 14 Add PyEnv with selectable Python version support
Ensure that Conan recipes can create managed Python virtual environments with an explicitly requested Python version, while keeping existing PipEnv-based recipes operational during the migration to the new PyEnv API.

- **Expectation**: Users should be able to ask Conan for a Python virtual environment bound to a specific Python version, and existing recipes that still use the older PipEnv entry point should continue to work while clearly signaling that they should migrate.

- **Constraints**: The upgrade must preserve current recipe behavior for creating, activating, and using Conan-managed Python virtual environments unless a project opts into explicit Python-version selection. Backward compatibility should remain in place, but migration to the new API should be clearly signaled.


### Task 15 Add built-in xz and zstd compression support for Conan artifacts
Ensure that Conan supports built-in `gz`, `xz`, and `zst` compression for uploaded and cache-saved artifacts, and that consumers receive clear compatibility failures or warnings when a selected format is experimental, unsupported by their Python runtime, or stored ambiguously on a remote.

- **Expectation**: Users should be able to choose a built-in compression format for Conan artifacts and cache archives without external tooling, continue consuming those artifacts transparently when their environment supports the format, and receive explicit warnings or errors when the chosen format is experimental, incompatible, or the remote artifact set is inconsistent.

- **Constraints**: The new compression support must preserve backward-compatible defaults, avoid guessing between conflicting artifact variants, and prevent users from producing or consuming formats their runtime cannot safely handle.


## Bug Fixes

### Task 16 Fail fast for unsupported PyEnv version selection
Ensure that requesting a specific Python version through PyEnv only proceeds when the running Conan interpreter supports that workflow. Ensure that unsupported host Python versions fail immediately and clearly instead of failing later during virtual-environment creation.

- **Expectation**: Users can request a specific Python version for an isolated Conan-managed environment only when the current Conan runtime supports that capability. If the current runtime is too old, the operation should stop at setup time with a clear error, while ordinary environment creation without version selection should keep working as before.

- **Constraints**: The fix must be narrowly scoped to compatibility validation for version-selected Python environments. Existing non-versioned environment workflows and supported version-selection flows should remain behaviorally consistent.


### Task 17 Restore legacy CMake definition variables in CMakeConfigDeps
Ensure that upgrading to Conan 2.25.0 preserves compatibility for CMake consumers that rely on legacy `<library>_DEFINITIONS` variables, so packages declaring preprocessor defines continue to work with older symbol checks and similar CMake logic.

- **Expectation**: Generated CMake package files should continue to support both modern target-based consumers and older CMake code that reads package definition variables directly. Any preprocessor definitions declared by the package should be visible to legacy symbol-detection and compatibility logic after the upgrade.

- **Constraints**: The upgrade should add missing compatibility data without changing the normal dependency consumption model. Existing consumers should keep working, and legacy consumers should gain the missing definition visibility rather than needing a different integration pattern.


### Task 18 Default to dnf on AlmaLinux, Rocky, and Oracle Linux
Ensure that automatic system package manager selection uses `dnf` by default on AlmaLinux, Rocky Linux, and Oracle Linux instead of `yum`.

- **Expectation**: Users on AlmaLinux, Rocky Linux, and Oracle Linux should see Conan choose the modern default package manager automatically. Package installation flows that depend on automatic manager detection should invoke `dnf` on those platforms instead of falling back to the older `yum` behavior.

- **Constraints**: Only the affected Linux distributions should change behavior. Other operating systems and Linux distributions should continue using their current default package manager selection without regression.


### Task 19 Preserve package names in no-op system package install output
Ensure that system package manager installs still report the requested package names when Conan skips the install as already satisfied, so users can see which system requirements were evaluated even when no package manager action is taken.

- **Expectation**: If Conan determines that a system requirement install does not need to run, it should still clearly tell the user which packages were considered already satisfied rather than emitting an empty or unclear result.

- **Constraints**: Keep the existing install and error behavior intact. Only improve the accuracy of the user-visible status reported for skipped system package installs.


### Task 20 Align workspace lockfile generation with supported commands
Ensure that Conan workspace commands only expose lockfile behaviors they can actually perform. Orchestrated workspace install/build/complete/create flows must accept an existing lockfile for dependency resolution but must not offer lockfile generation output options, and workspace super-install must be the command that writes any updated lockfile state.

- **Expectation**: Workspace commands that only orchestrate installs and builds should behave as consumers of an existing lockfile, not producers of a new one. Users should only be able to generate or refresh a workspace lockfile through the dedicated workspace command that resolves the full graph and persists the result.

- **Constraints**: Keep existing lockfile consumption behavior intact while removing misleading output-generation options from commands that cannot produce a lockfile. Lockfile creation or refresh must remain available only where the CLI can actually save a resolved result.


### Task 21 Reduce Conan sqlite cache lock contention
Ensure that Conan cache reads against the sqlite metadata database do not keep database connections open while callers consume recipe and package results, so concurrent operations are less likely to hit locking or operational failures. Ensure that lock acquisition timeouts are reported as a ConanException rather than as an assertion failure.

- **Expectation**: Cache metadata reads should release sqlite resources as soon as the rows have been fetched, instead of keeping the database tied up while results are iterated or converted. Users should see the same successful lookup results and missing-item behavior as before, but with fewer lock-related operational issues and with a normal Conan error when lock contention exceeds the timeout.

- **Constraints**: The upgrade should improve robustness under sqlite contention without changing what valid cache queries return or how missing records are represented. Only the connection lifetime and timeout error reporting should change from a user-visible behavior standpoint.


### Task 22 Fix cpp_info deduction for mixed component types
Ensure that C/C++ package metadata deduction works for multi-component packages when some components define a type and others leave the type unspecified, without failing during dependency generation or explicit cpp_info deduction.

- **Expectation**: Upgrading should prevent crashes when package components omit their type. Metadata deduction should succeed for valid packages that mix typed and untyped components, while still rejecting explicitly incompatible component type declarations.

- **Constraints**: Preserve existing valid shared and static library behavior, keep invalid type declarations rejected, and remove only the unintended failure caused by an unspecified type.


### Task 23 Fix Python environment installs for pip version ranges and migrate to PyEnv
Ensure that Conan recipes using the Python virtual environment helper can install pip requirements that include version ranges without command-line parsing failures, while providing a supported upgrade path from PipEnv to PyEnv and preserving compatibility for existing PipEnv consumers through deprecation warnings.

- **Expectation**: The Python environment helper should accept normal pip dependency syntax, including ranged version constraints, without the shell misinterpreting those constraints. Users should be guided toward the new PyEnv name and configuration key, but existing PipEnv-based recipes should continue to work during the deprecation period. When a specific Python version is requested, the helper should either create that environment successfully or fail clearly when the runtime does not support it.

- **Constraints**: The fix must not break ordinary Python environment workflows. Backward compatibility should be preserved for existing recipes, with warnings instead of immediate removal, and interpreter selection should remain predictable when explicit configuration is present.


### Task 24 Fix case-sensitive symlink pattern matching in files.copy
Ensure that `conan.tools.files.copy()` correctly matches symlinked directory paths against the requested glob pattern, including paths with uppercase characters, so matching symlink entries are copied under the same case-sensitivity rules as other copy candidates.

- **Expectation**: Copy operations should treat symlinked directories like other matched inputs: case-sensitive copies should respect exact path casing, and case-insensitive copies should match regardless of letter case. Users should not lose matching symlink entries just because the path or pattern contains uppercase characters.

- **Constraints**: The change should be limited to correcting symlink match behavior without altering how normal file copies, exclusions, or the overall copy interface work.


### Task 25 Fix CMakeConfigDeps transitive libraries in build context
Ensure that CMakeConfigDeps correctly exposes transitive library dependencies when generating build-context dependencies, so a build requirement that depends on libraries can still provide usable CMake library targets to downstream consumers.

- **Expectation**: When a tool or other build-context package depends on a library, that transitive library should appear as a normal CMake dependency that downstream projects can resolve and link. The special treatment of direct build tools should remain unchanged.

- **Constraints**: The fix should be narrowly scoped: it should restore missing transitive library visibility in build context without changing how ordinary host dependencies work or turning every build-only package into a linkable library target.


### Task 26 Fix update to remote revisions already cached locally
Ensure that updating dependencies from a remote can switch to the remote's latest recipe revision even if that revision is already present in the local cache with an older timestamp, and ensure the cache reflects that revision as the current latest local revision instead of failing or keeping a different revision active.

- **Expectation**: An update operation should follow the remote's newest revision, even when that revision was seen before and is already cached locally. If the remote moves back to a previously cached revision, the client should adopt that revision successfully and make it the active latest cached copy.

- **Constraints**: The fix should only change how updates reconcile remote and cached revision metadata. It must not introduce duplicate cached revisions, unnecessary downloads, or changes to cases where no update is needed.


### Task 27 Correct exclusive graph-context package listing
Ensure that `conan list --graph=... --graph-context=build-only|host-only` returns only packages that are exclusive to the requested graph context, and does not surface unintended recipes or binaries when the same dependency appears in both host and build contexts with package binary mismatches or skipped binaries.

- **Expectation**: Exclusive graph-context listing should behave as a true context-only view. If a package is represented in both host and build contexts, it should not appear in `build-only` or `host-only` results just because the binaries differ or one side was skipped; only packages unique to the selected context should remain, and recipes with no remaining packages should disappear.

- **Constraints**: Only the exclusive-context filtering semantics should change. Standard graph listings must stay stable, and genuinely context-specific packages must still be visible.


## Documentation

### Task 28 Document the public InstallAPI sub-API contract
Ensure that Conan 2.25.0 provides a documented public InstallAPI contract so integrators can reliably use the install sub-API with a resolved dependency graph to install binaries and system requirements, download sources, prepare the consumer folder, and perform deployment.

- **Expectation**: Users of the public Conan API should be able to treat `ConanAPI.install` as the supported installation-oriented entry point. Its methods should have clear, stable contracts for installing dependencies from a resolved graph, handling system requirements according to configuration, downloading dependency sources when requested, preparing consumer outputs such as generators and environment files, and running deployers over the resolved graph.

- **Constraints**: This change should clarify and stabilize the supported usage contract without altering the underlying install workflow. Existing configuration-driven behavior, scope of operations, and optional filtering should remain consistent, and consumers should not need to infer unsupported side effects beyond the documented API behavior.


## Performance Improvements

### Task 29 Reduce redundant Conan cache lookups and support configurable upload compression
Ensure that Conan upload, download, metadata retrieval, and package build operations reduce redundant cache or database work without changing the intended recipe and package outcomes. Ensure that upload preparation consistently includes requested metadata, honors the selected compression format and compression level, and makes compatibility limits for experimental compressed package artifacts visible to users.

- **Expectation**: The upgrade should make Conan do less repeated cache or database work during upload, download, metadata refresh, and local package builds while preserving normal package outcomes. Uploads should consistently include selected metadata, respect the configured compression settings, reuse already prepared compressed artifacts when that is unambiguous, warn when users opt into experimental formats, and block unsupported zstd uploads on older Python runtimes.

- **Constraints**: The optimization must stay behaviorally safe: existing valid cached artifacts should continue to work, metadata-only or metadata-inclusive uploads should still transfer the right files, and new failures should be limited to unsupported compression/runtime combinations or ambiguous artifact state.


### Task 30 Optimize dependency graph cache lookups
Ensure that dependency graph construction resolves cached recipes and binaries with fewer local package-cache database accesses while preserving the same latest-revision selection, cache miss handling, and dirty-package cleanup behavior.

- **Expectation**: Building the dependency graph should perform fewer local-cache lookups while keeping the same observable resolution results for latest cached recipes and binaries, including how missing cache entries are handled.

- **Constraints**: This optimization must be behavior-preserving: explicit revisions should continue to resolve as before, missing local cache data should still be handled the same way, and existing package validation or cleanup steps must continue to run against the latest cached binary when one exists.


### Task 31 Batch cache LRU updates for dependency graphs
Ensure that upgrading to Conan 2.25.0 preserves recently-used tracking for cache-backed recipes and package binaries while reducing per-reference cache database work during dependency graph resolution and installation.

- **Expectation**: Dependency resolution and installation should continue to mark the recipes and cached binaries actually used by an operation as recently used, but do so through aggregated cache updates so large graphs avoid unnecessary database overhead.

- **Constraints**: The optimization must be behavior-preserving: it should improve efficiency without changing what gets resolved or installed, and it should only update recently-used state for real cached artifacts that were actually used.


## Additional Changes
