# Upgrade Specification from 2.25.2 to 2.26.0

## New Features

### Task 1 Expose PyEnv virtual environment paths
Ensure that PyEnv exposes the managed virtual environment's root directory, Python executable, and executable directory so recipes and external tools can reference the created environment directly.

- **Expectation**: Users of PyEnv should be able to retrieve the virtual environment location and interpreter path without reconstructing them manually, and those values should be directly usable in build tools and command execution on all supported platforms.

- **Constraints**: The change should add discoverability of the managed environment's paths without changing which environment PyEnv creates or weakening command isolation to that environment.


### Task 2 Add built-in CycloneDX SBOM deployers
Ensure that users upgrading to 2.26.0 can generate CycloneDX SBOM artifacts through built-in deployers, using supported CycloneDX schema versions and receiving predictable output files for the resolved dependency graph without requiring a custom hook or custom deployer for the common case.

- **Expectation**: The upgraded release should let users request SBOM generation as a standard deploy step, choosing either CycloneDX 1.4 or 1.6, and receive a JSON SBOM file in the deploy output location that represents the current resolved dependency graph. For the built-in deployers, advanced inclusion controls for build-only or test-only packages are not part of this feature and remain outside the default workflow.

- **Constraints**: The feature should extend deployment behavior without changing how other deployers are selected or used. Each schema version should produce one clearly named SBOM file, and the built-in option should stay limited to the default SBOM scope rather than introducing new configuration knobs.


### Task 3 Support important configuration precedence for tool requirements
Ensure that configuration values exposed by tool requirements can be marked as explicitly higher priority than profile configuration so consumers receive the tool-provided value when the same `conf` key is defined in both places, without changing the default precedence rules for ordinary `conf` entries.

- **Expectation**: Users should be able to mark selected configuration entries as high priority with an explicit `!` suffix. When such an entry comes from a tool requirement, it should win over the same setting coming from profiles, and composed list or dictionary values should reflect that higher priority. Regular configuration entries should continue to behave as before.

- **Constraints**: This feature should be an opt-in priority override, not a global change to configuration resolution. Existing validation and error behavior should remain intact, and mismatched configuration types should not be silently coerced.


### Task 4 Relax `<host_version>` user/channel matching
Ensure that Conan resolves `<host_version>` from an existing host dependency even when the corresponding build requirement or tool requirement uses different or omitted user/channel values, while still failing when no matching host dependency exists to provide the version.

- **Expectation**: A package that tracks another dependency through `<host_version>` should follow the host package's version based on the dependency relationship, not be blocked just because the package references use different or missing user/channel qualifiers. If there is no corresponding host dependency to follow, resolution should still fail.

- **Constraints**: The change should broaden valid `<host_version>` matches, not turn missing host dependencies into successful resolutions. Resolution should remain strict about requiring an actual host dependency source for the version.


### Task 5 Add Emscripten compiler detection to detect_api
Ensure that Conan exposes a user-facing detect API for EMSDK Emscripten compilers so consumers can identify an `emcc` installation and its compiler version, while safely returning no detection when the executable is missing, unsupported, or not actually Emscripten.

- **Expectation**: Users should be able to ask Conan’s detect API to inspect the default `emcc` command or a custom executable and get back an Emscripten compiler identity plus version when the tool is genuinely present. If the executable cannot be validated as Emscripten or its version cannot be determined, the API should fail gracefully by reporting no detection instead of raising or misclassifying another compiler.

- **Constraints**: The new capability should be conservative: only clear Emscripten installations should be recognized, and ambiguous or failing executions should simply be treated as undetected rather than producing incorrect compiler data.


### Task 6 Harden generated environment scripts for unset variables
Ensure that generated environment activation scripts handle prepend and append operations safely when the target environment variable does not already have a usable value, so scripts do not fail in hardened shells and do not produce extra separators around empty values.

- **Expectation**: Generated activation scripts should adapt to whether an environment variable already has a value. When a prior value exists, prepend and append behavior should preserve it with the correct separator; when no prior value exists, the script should set only the new content without malformed separators or shell failures.

- **Constraints**: Ordinary set and unset behavior should remain unchanged. Only cases that combine new content with an existing variable value should receive the new conditional handling, and separator rules must stay consistent with the variable's normal formatting.


### Task 7 Expose author metadata in ConanFileInterface
Ensure that users and integrations reading recipe metadata through ConanFileInterface can access the recipe's author information as a supported interface attribute.

- **Expectation**: Users should be able to retrieve a recipe's author metadata from the standard Conan file interface without reaching into lower-level objects or custom workarounds.

- **Constraints**: The change should simply expand the available metadata on the public-facing interface, without changing how existing metadata fields behave.


### Task 8 Add opt-in rpath-link support for Conan CMake and Meson toolchains
Ensure that Conan-generated CMake and Meson builds can opt in to supplying link-time search paths for transitive shared libraries from host dependencies, particularly when building with a non-root sysroot, so executables and related link steps can resolve indirect shared-library dependencies without depending only on runtime rpath behavior.

- **Expectation**: Users upgrading to Conan 2.26.0 should be able to turn on a single option that makes Conan-generated CMake and Meson builds pass link-time shared-library lookup paths for host dependencies. With that option enabled, cross-builds and sysroot-based builds should be able to link against transitive or private shared libraries that the GNU linker needs to see at link time, without changing default behavior for users who do not opt in.

- **Constraints**: The new behavior should be narrowly scoped to Conan's generated CMake and Meson toolchains and should only affect builds that explicitly request it. It should not change unrelated dependency resolution rules, pull in build-tool dependencies, or alter default linking behavior for existing projects that do not enable the feature.


### Task 9 Support case-only CMake package name variants in CMakeConfigDeps
Ensure that CMakeConfigDeps lets packages expose additional case-only CMake package name variants so consumers can call find_package with supported capitalization variants, and ensure that invalid or conflicting variant declarations are handled predictably.

- **Expectation**: Packages should be able to advertise approved capitalization variants of the same CMake package name, and consumers should be able to resolve the package with any of those variants. Configuration that changes the package name rather than its casing should not be silently accepted; it should either fail clearly or be ignored with a warning when an explicit package name override already controls lookup.

- **Constraints**: This feature is limited to capitalization aliases, not arbitrary alternate names. A user-selected package name remains authoritative, and the new behavior must preserve existing package discovery for the canonical name.


### Task 10 Add function-style deactivation support for Windows batch env scripts
Ensure that Windows users who enable `tools.env:deactivation_mode=function` can use Conan-generated `.bat` environment scripts with the same function-style activation and deactivation workflow available for shell and PowerShell scripts, including correct restoration or removal of environment variables after deactivation.

- **Expectation**: With function-style deactivation enabled, Windows command prompt users should be able to activate a Conan environment and then deactivate it from the same session through a generated deactivation command, with the shell state returning to what it was before activation. This should work both for individual environment scripts and for aggregated Conan activation scripts.

- **Constraints**: Default upgrade behavior must remain backward compatible, and the new Windows function-mode support must not leave residual helper state behind after deactivation. The feature should align Windows behavior with the established cross-shell activation/deactivation model rather than introducing a separate contract.


### Task 11 Support ABI-sensitive dependency options in consumer package IDs
Ensure that Conan recipes can declare dependency options that must affect a consumer's `package_id` when dependency headers can change the consumer binary ABI, including non-embed relationships.

- **Expectation**: Consumers that build binary artifacts should get distinct package IDs when a dependency explicitly marks ABI-relevant options and those dependency headers can alter the consumer binary. This should work even when the dependency is not embedded, and it should also apply through transitive header exposure. Dependencies that do not opt in, or whose headers do not reach the consumer, should not change the consumer package ID through this feature.

- **Constraints**: Keep the scope narrow: only explicitly opted-in ABI-sensitive dependency options should alter downstream binary identity, and only when those dependency headers can actually affect the consumer artifact. Consumers outside binary-producing package types, or dependency relationships without header influence, should behave as before.


### Task 12 Add explicit cache signing and verification for packages
Ensure that package signing and verification can be performed explicitly from the local cache, that signed recipes and packages expose standardized signature metadata, and that users receive clear per-item errors when integrity or signature validation fails instead of relying on implicit signing during upload.

- **Expectation**: Users should be able to explicitly sign and verify cached packages and recipes before distribution, with a consistent metadata format that describes what was signed and how it was signed. Verification should check both artifact integrity and plugin-defined signature rules, report failures per affected item, and treat signing as a separate step from upload. Older signing plugins may still run temporarily, but users should be warned when they do not provide the new metadata expected by the upgraded workflow.

- **Constraints**: The upgrade must not hide signing work inside unrelated commands, must fail clearly when users provide invalid or empty target selections, and must keep integrity checks focused on real distributable artifacts rather than internal metadata. Verification should be strict about changed files, but compatible with older signed content through warnings instead of silent false success.


## Bug Fixes

### Task 13 Fix PyInstaller Conan system tools packaging and env script behavior
Ensure that Conan standalone binaries built with PyInstaller can use recipes that rely on `conan.tools.system.package_manager` without missing-module failures, and ensure that generated environment activation/deactivation scripts correctly handle function-based deactivation and previously unset variables across supported shells.

- **Expectation**: A packaged Conan executable should behave like a normal install for recipes that use system package manager tooling. Its generated environment scripts should activate and deactivate cleanly, including when deactivation is exposed as callable shell functions and when affected environment variables start out unset.

- **Constraints**: The fix must preserve existing environment generator workflows while making packaged binaries reliable. Activation and deactivation must remain reversible, shell-appropriate, and free of leftover state or malformed variable values.


### Task 14 Restore legacy CMakeConfigDeps definitions formatting
Ensure that upgrading to Conan 2.26.0 restores legacy CMakeConfigDeps compatibility by generating package definition variables in a format that downstream CMake projects can pass directly to legacy definition-consuming APIs, including definitions with assigned values.

- **Expectation**: Generated dependency definition variables should behave like ready-to-use CMake compile-definition arguments. Consumers should be able to reuse them directly in older CMake integration flows without manually adding -D prefixes, splitting strings, or repairing definitions that include values.

- **Constraints**: The upgrade should correct malformed legacy definition output without changing the source of package metadata or altering unrelated CMake dependency information.


### Task 15 Expose .txz and .tzst support in conan cache save help
Ensure that `conan cache save` clearly communicates the supported output archive formats for `--file`, including the availability of `.txz` and `.tzst`, the experimental status of those formats, and the Python version requirement for `.tzst`.

- **Expectation**: Users invoking help for `conan cache save` should see an accurate description of which archive formats they can request for `--file`, along with any format maturity or runtime-version limitation that affects whether a format can be used.

- **Constraints**: The command documentation should remain backward compatible for existing archive usage, avoid overstating support in unsupported environments, and present format limitations clearly enough that users can choose a valid output format.


### Task 16 Generate CMakeConfigDeps targets for requires-only components
Ensure that `CMakeConfigDeps` generates a component target when a package component exists only to require other components, so consumers can still resolve and link that component through generated CMake dependency files.

- **Expectation**: Dependency-only components should remain visible in generated CMake package metadata. If a component exists purely as an aggregation or forwarding target for other components, consumers should still be able to reference it and obtain the expected transitive linkage.

- **Constraints**: Only components that carry meaningful dependency relationships should gain new generated targets. The change should be additive for dependency-only components and should not alter unrelated component generation behavior.


### Task 17 Fix MSBuildDeps build-context component transitives
Ensure that `MSBuildDeps` correctly resolves transitive dependencies referenced by components of build requirements, so generated MSBuild property sheets use the build-context dependency graph instead of host-context imports when tool requirements expose components.

- **Expectation**: `MSBuildDeps` should keep build-time dependencies internally consistent: if a tool requirement component depends on another build requirement or one of its components, the generated MSBuild props should continue following the build dependency graph all the way through.

- **Constraints**: The fix should be limited to correcting incorrect context selection for generated MSBuild dependency imports. Existing valid dependency wiring should remain stable, and missing or skipped transitive entries should not turn generation into an error.


### Task 18 Abstract the CMakeToolchain fallback toolchain-file tip
Ensure that the CMakeToolchain generator presents a portable fallback command for older CMake versions by abstracting the displayed toolchain-file location to an output-folder placeholder instead of a concrete generated path.

- **Expectation**: Users who rely on Conan's printed CMake invocation guidance should see a generic, reusable toolchain-file reference for older CMake versions rather than a concrete build-output path. The guidance should stay complete and should not repeat a toolchain-file argument if the user already defined one.

- **Constraints**: This is an informational compatibility fix, not a change to how builds are configured or generated. Existing explicit toolchain overrides and the rest of the printed CMake guidance should keep behaving the same way.


### Task 19 Preserve CPS package preprocessor definitions across Conan import/export
Ensure that CPS package preprocessor definitions are parsed and preserved correctly when Conan exports package metadata to CPS and when Conan reads CPS metadata back into dependency information, including definitions with assigned values and definitions without values.

- **Expectation**: Conan should reliably preserve compile definitions when exchanging package metadata through CPS files. Consumers should receive the same effective preprocessor definitions regardless of whether a package was described directly in Conan metadata or reconstructed from CPS metadata, and language-specific CPS definitions should override generic ones in a predictable way.

- **Constraints**: The change should be limited to correcting preprocessor-definition handling. Existing package structure, dependency linkage, and library metadata should remain stable, and packages that do not use compile definitions should be unaffected.


### Task 20 Warn Conan users that Python 3.7 support is deprecated
Ensure that Conan informs users when they run the CLI on Python 3.7, because that interpreter version is deprecated and future Conan releases will remove support for it.

- **Expectation**: Users running Conan on Python 3.7 should be clearly warned that their interpreter is deprecated and will stop being supported in a future release, while Conan continues to behave normally. Users on supported Python versions should not see this warning.

- **Constraints**: The deprecation handling must remain informational only, must not disrupt normal CLI behavior, and must only appear for the deprecated interpreter version.


### Task 21 Use hash terminology for checksum verification
Ensure that checksum verification features consistently describe MD5, SHA-1, and SHA-256 values as hashes rather than signatures, so users see accurate terminology in the API documentation and in checksum mismatch failures.

- **Expectation**: Checksum validation should use correct hashing terminology everywhere users interact with it. If a file's expected checksum does not match its actual checksum, the failure should clearly indicate that the hash check failed and show both the expected and actual hash values.

- **Constraints**: The update should improve wording without changing how checksum verification works. Existing workflows should continue to validate files the same way, with only the user-visible language becoming more accurate.


### Task 22 Honor CMake filename variants for packaged config discovery
Ensure that `CMakeConfigDeps` honors declared `cmake_file_name_variants` when exposing package discovery paths, including packages that ship their own CMake config files, so consumers can locate the same dependency through any supported variant name.

- **Expectation**: Packages that intentionally support multiple CMake file-name variants should behave the same regardless of which supported variant a consumer uses. If the package ships its own CMake config files, those files should still be found through the declared variants; if Conan generates the config files, the generated package directory should also be available through those same variants.

- **Constraints**: The fix should expand supported discovery aliases without changing what package is resolved or disrupting the default CMake naming flow. Supported variants should map to the same package location consistently and without duplicate search entries.


### Task 23 Fix context-only graph listing for unnamed consumer recipes
Ensure that `conan list` can process dependency graphs generated from consumer recipes without a name when `--graph-context=build-only` or `--graph-context=host-only` is used, and that context-only results are calculated only from actual package entries.

- **Expectation**: Context-only graph listing should ignore synthetic root or virtual nodes and consider only real packages. Users should be able to run build-only or host-only listing against graphs from unnamed consumer recipes without failures and without seeing packages that are shared across both contexts.

- **Constraints**: Keep normal package listing behavior unchanged for real dependencies. The fix should only make context-only filtering robust and accurate by preventing non-package nodes from affecting the result.


### Task 24 Preserve version-like conf values as strings
Ensure that built-in configuration values that represent version or update identifiers are preserved exactly as user-provided strings so numeric-like inputs do not lose trailing zeroes or other formatting during configuration parsing.

- **Expectation**: Version-like configuration settings should keep the exact value the user typed, even if the value looks like a number. This prevents configuration-driven behavior from changing because the parser normalized or truncated part of the value.

- **Constraints**: The fix should be narrowly scoped to settings whose value format must remain literal, while ordinary configuration values should continue behaving as they did before the upgrade.


### Task 25 Avoid redundant rebuilds for existing compatible binaries
Ensure that using `--build=compatible` does not rebuild a package when an already compatible binary exists. Ensure that repeated resolution of the same package reference reuses the existing binary decision instead of triggering duplicate compatible-build work.

- **Expectation**: Compatible-build mode should prefer reuse over rebuild. If a suitable compatible package is already available, the package manager should consume that existing artifact and keep graph resolution stable, only building a compatible package when no existing compatible binary can satisfy the request.

- **Constraints**: The change should only eliminate unnecessary rebuilds. Existing behavior for selecting cached versus newer remote artifacts should remain intact, and compatible builds should still occur when reuse is not possible.


### Task 26 Correct CMakeToolchain variable escaping for CMake syntax
Ensure that Conan 2.26.0 generates valid CMake toolchain variable definitions when `CMakeToolchain.variables` contains string values with backslashes, double quotes, or dollar signs, including configuration-specific variables, without corrupting values that are already escaped.

- **Expectation**: Projects that define toolchain variables with Windows-style paths, quoted text, or dollar-prefixed content should get usable CMake definitions after upgrade. The generated toolchain should preserve the intended value semantics for normal and per-configuration variables, and repeated processing should not progressively alter already escaped values.

- **Constraints**: The change should be limited to making generated CMake variable values syntactically correct and stable. Existing valid non-string values should behave as before, and upgrading should not unexpectedly rewrite values that were already properly escaped.


### Task 27 Fix cpp_info type serialization round-trip
Ensure that `cpp_info` metadata using the `type` field can be serialized and deserialized correctly, preserving declared package and component types and safely handling unset types during persistence and reload.

- **Expectation**: Persisted `cpp_info` data should round-trip cleanly when a package or component declares a type. Saving and loading the metadata should preserve the visible type information, and components without a type should stay unset.

- **Constraints**: The change should be limited to correcting persistence behavior for typed `cpp_info` data without regressing other metadata fields or forcing type information where none was provided.


### Task 28 Preserve CPS component CMake target naming and metadata
Ensure that CPS-derived package metadata preserves expected CMake package and component target naming, including for single-component CPS packages, and retains the component's compile definitions, dependencies, system libraries, and default component mapping during Conan consumption.

- **Expectation**: Loading package metadata from CPS should yield Conan/CMake integration that matches the CPS package name and component names. Consumers should be able to discover the package by its CPS name and link the expected component-qualified target, while compile definitions and dependency metadata remain intact for both single-component and multi-component packages.

- **Constraints**: Correct the exposed naming and metadata preservation without changing unrelated package discovery behavior or losing component boundaries. The upgrade should maintain existing component semantics while making single-component CPS packages behave consistently with the documented target naming pattern.


### Task 29 Prevent [buildenv] pattern leakage across packages
Ensure that per-package [buildenv] definitions are isolated per package when multiple packages are processed, so package-specific build environment values do not corrupt or leak into other packages' build environments.

- **Expectation**: Build environment configuration should be evaluated independently for each package. Shared baseline environment settings may apply broadly, but package-specific additions must only affect the packages they target and must not alter the environment seen by other packages.

- **Constraints**: Keep current environment features and matching rules intact while eliminating state leakage between packages. The change should improve isolation, not redefine how environment variables are declared or matched.


### Task 30 Default platform revision for lockable platform requirements
Ensure that dependencies resolved through `platform_requires` and `platform_tool_requires` get a stable revision identity by default so platform-provided dependencies can be locked, distinguished from regular package references, and optionally overridden with an explicit revision.

- **Expectation**: Platform dependencies should no longer behave like revisionless references. By default they should resolve as a distinct `platform` revision so lockfiles can capture and replay them consistently, while still allowing users to choose a different revision when the underlying system dependency meaningfully changes.

- **Constraints**: The change should be limited to the identity of platform dependencies. Regular dependency resolution should keep working as before, and explicitly revisioned platform dependencies should not lose their intended identity.


### Task 31 Add riscv64 support to apt and yum system package mapping
Ensure that Conan system package installation supports `arch=riscv64` for Linux environments that use `apt` or `yum`, so recipes can resolve and install architecture-qualified system dependencies correctly.

- **Expectation**: Users targeting riscv64 Linux systems should be able to install system dependencies through Conan with apt- or yum-based package managers without the architecture being treated as unsupported or translated to an incorrect package architecture.

- **Constraints**: The fix should add riscv64 compatibility without changing behavior for other architectures or overriding explicit user customizations.


## Documentation

### Task 32 Publicly document LocalAPI local workflow contracts
Ensure that `ConanAPI.local` is treated as an officially supported local-development API and that its contract is clearly defined for conanfile discovery, editable package management, and local `source()`, `build()`, and `test()` execution.

- **Expectation**: Users should be able to rely on `ConanAPI.local` as a documented public API for local recipe workflows. The documented contract should explain how recipe paths are resolved, how editable packages are added or removed, when remotes are consulted, what operations return, and which local actions can run directly versus which require a prior install that has already prepared dependencies.

- **Constraints**: The upgrade should clarify and stabilize the public contract without changing how existing local workflows behave. It should preserve current failure conditions for invalid recipe selection and keep dependency prerequisites explicit for operations that need an installed graph.


## Performance Improvements

### Task 33 Use filesystem mtimes for cache LRU tracking
Ensure that upgrading to Conan 2.26.0 preserves correct least-recently-used tracking for cached recipes and binaries while reducing the overhead of repeated warm-cache operations by using cache folder modification times as the recency signal.

- **Expectation**: When Conan reuses recipes or binaries that are already in cache, they should still be treated as recently used, but recency should come from normal filesystem metadata rather than extra database bookkeeping. The upgrade should improve warm-cache performance while preserving visible cache reuse behavior.

- **Constraints**: Do not regress cache correctness, cache reuse, or compatibility with existing local cache data. Recency tracking should remain available anywhere Conan relies on LRU ordering, and users should not need to rebuild or migrate their cache to benefit from the change.


## Additional Changes
- Ensure that recipes can explicitly disable generation of virtual environment scripts so installs do not emit unwanted build or run environment activation artifacts when the recipe opts out.
- Ensure that generated `meson_lib` recipes can consume template-declared Conan requirements without manual recipe edits, and that Meson projects receive the dependency metadata they need to discover those packages during configuration.
