# Upgrade Specification from 2.26.2 to 2.27.0

## New Features

### Task 1 Support grouped negated profile tool-requires patterns
Ensure that profile [tool_requires] rules can exclude multiple reference patterns with a single negated OR expression so tool requirements can be applied to all other packages while avoiding build-context dependency cycles.

- **Expectation**: Users should be able to declare one profile tool-requirement rule that applies everywhere except a specified set of package patterns. Packages that match any excluded branch should not receive that tool requirement from the profile, while all other packages should. Invalid grouped exclusion syntax should fail clearly instead of producing ambiguous behavior.

- **Constraints**: The new exclusion syntax should extend current matching behavior without changing unrelated profile rules or introducing new self-dependency behavior. Existing ordinary patterns and normal tool-requirement resolution should continue to work as before.


### Task 2 Add CVSS version details to conan audit results
Ensure that `conan audit` shows richer CVSS information in vulnerability results so users can see the preferred score and any available CVSS version-specific scores without breaking existing audit output for older vulnerability data.

- **Expectation**: Audit results should show more complete CVSS scoring details. Users should see the main score directly with the vulnerability severity, plus version-specific CVSS v3 and v4 scores when the provider knows them, across the supported audit result views.

- **Constraints**: Older vulnerability records must still work, and extra CVSS details should appear only when real version-specific score data is available. The upgrade should extend audit output without removing existing vulnerability information.


### Task 3 Disable CMake package registry exports by default
Ensure that projects using Conan's CMakeToolchain do not write package entries into the CMake user package registry by default, while still allowing consumers to keep an explicit registry export configuration if they already set one.

- **Expectation**: Using Conan's CMake integration should no longer pollute the developer's global CMake package registry unless the project intentionally opts in. The default should be safe, predictable, and effective across supported CMake policy configurations, while respecting any explicit registry export choice already made by the consuming project.

- **Constraints**: Keep explicit user configuration authoritative, and only change the default behavior for projects that did not already choose a package-registry export setting. Prevent new unintended global side effects without removing the ability to opt in deliberately.


### Task 4 Align PyEnv pip and uv output with Conan verbosity
Ensure that PyEnv respects the active Conan verbosity level when invoking pip and uv so users get appropriately quiet or detailed command output without changing virtual-environment creation or package-install behavior.

- **Expectation**: When users choose a Conan verbosity level, PyEnv should make its Python package installation and virtual-environment setup output match that choice. Lower verbosity should suppress nonessential noise, higher verbosity should expose more command detail, and ordinary default usage should behave as before while still reporting failures clearly.

- **Constraints**: The upgrade should change output volume only. It must not change what PyEnv installs, how environments are created, or whether operations succeed or fail, and it must not make default logging noisier or quieter than before unless the user explicitly selects another verbosity level.


### Task 5 Add transitive requirement visibility to HTML dependency graphs
Ensure that the HTML dependency graph can show transitive requirements on demand so users can inspect indirect dependency relationships without cluttering the default view.

- **Expectation**: Users viewing the generated HTML dependency graph should be able to opt into seeing indirect dependencies. The graph should stay readable by default, then reveal transitive relationships in a clearly differentiated way when requested, while preserving the rest of the interactive graph behavior.

- **Constraints**: Keep the default HTML graph focused on the same primary relationships users already see today. Adding optional indirect links must not break or reinterpret existing graph controls, diagnostics, or direct dependency visibility.


### Task 6 Add support for Clang 22 compiler settings
Ensure that users can target Clang 22 through the standard compiler settings model and that configurations using `compiler=clang` with version `22` are accepted as supported.

- **Expectation**: Users should be able to declare Clang 22 the same way they declare other supported Clang versions. The system should recognize that compiler version as valid and allow normal processing to continue instead of rejecting the configuration.

- **Constraints**: Adding support for the new compiler release must not break existing compiler configurations or change behavior outside the intended Clang 22 support.


### Task 7 Visualize dependency loops in HTML graph output
Ensure that `conan graph info --format=html` visibly identifies dependency cycles in the rendered graph so users can immediately see which dependency closes the loop when graph resolution fails due to a cycle.

- **Expectation**: If the dependency graph contains a cycle, the HTML graph view should make the loop obvious by visually highlighting the relationship that creates the cycle, instead of leaving users to infer it from a generic failure.

- **Constraints**: Regular graphs should continue to render normally, and non-loop failures should continue to be represented in their usual way. The loop marker should add clarity without changing the fact that a cyclic graph is invalid.


### Task 8 Support resource compiler flags via Conan build configuration
Ensure that Conan users can declare extra resource compiler flags through a dedicated `tools.build:rcflags` configuration and have those flags propagated consistently to supported generated toolchains and profiles.

- **Expectation**: Users should be able to define resource compiler flags once in Conan configuration and have generated build integrations carry those flags into resource compilation in the same way existing compile and link flag settings already work.

- **Constraints**: The added RC flag support must be additive and non-breaking: existing flag handling should keep working as before, empty RC flag configuration should have no effect, and any per-configuration behavior already present in generated outputs should remain intact.


### Task 9 Add Apple OS 26.3 settings support
Ensure that projects targeting Apple OS 26.3 releases can declare those platform versions in library settings and profiles without being rejected as unsupported.

- **Expectation**: Users should be able to target Apple 26.3 platform releases across the supported Apple operating systems using normal configuration flows, and the library should recognize those version identifiers as supported settings.

- **Constraints**: The upgrade should expand compatibility for the new Apple OS patch release without altering existing behavior for other platforms or changing unrelated configuration rules.


### Task 10 Support extra arguments for CMake.configure()
Ensure that Conan users can supply additional command-line arguments to the CMake configure step through configuration, so `CMake.configure()` can receive extra CMake variables and flags such as `--fresh` without altering existing recipe behavior.

- **Expectation**: Users should be able to configure extra arguments for the CMake configure phase through Conan configuration, and those arguments should be forwarded as part of the configure invocation in the order supplied.

- **Constraints**: Existing consumers should see no behavior change unless they opt into the new setting. Extra arguments should affect only the configure step and should pass through transparently rather than being reformatted or repurposed.


## Bug Fixes

### Task 11 Preserve hexadecimal NMake defines as numeric macros
Ensure that NMake integrations treat hexadecimal assigned defines such as `WINVER=0x0601` as numeric macros rather than string-valued macros, and ensure the same define-formatting behavior is applied whether the define comes from project toolchain settings or dependency metadata.

- **Expectation**: After upgrading, NMake-based builds should preserve hexadecimal macro values as numbers so code that relies on numeric preprocessor comparisons continues to work correctly. Textual macro values should still behave as text, and users should see the same behavior regardless of whether a define is declared locally or supplied by a dependency.

- **Constraints**: The fix should be narrowly scoped to incorrect hexadecimal-value handling and should not change unrelated define semantics. Existing valid numeric and textual macro definitions should continue to work the same way across all NMake-generated compiler flags.


### Task 12 Fix CMakeConfigDeps build-context property overrides
Ensure that CMakeConfigDeps applies set_property() overrides correctly for dependencies consumed in the build context, so custom CMake package metadata for build requirements is honored during generation.

- **Expectation**: Users should be able to customize CMakeConfigDeps output for tool or build dependencies the same way they can for regular dependencies. If they rename or override a build requirement's CMake-facing metadata, the generated CMake files should consistently use that customized value.

- **Constraints**: Customizations should apply only to the dependency instance and context they were defined for. The fix must not change how unrelated dependencies or existing host-side configurations behave.


### Task 13 Validate exact versions in platform requirement profiles
Ensure that Conan profiles reject `[platform_requires]` and `[platform_tool_requires]` entries that use version ranges, and report a clear user-facing error that these sections only accept exact versions.

- **Expectation**: Users upgrading to Conan 2.27.0 should get an immediate, clear configuration error if they place version ranges in platform replacement requirement sections. These profile sections are for pinned platform recipes only, while the deprecated legacy alias should still behave compatibly apart from warning the user.

- **Constraints**: Only invalid platform replacement declarations should be blocked. Valid pinned platform requirements should keep working, and existing legacy profile usage should not silently change behavior beyond producing a deprecation warning and clearer validation errors.


### Task 14 Separate build and host package grouping in HTML graph output
Ensure that `conan graph info .. -f=html` groups repeated packages only within the same dependency context, so packages that appear in both build and host graphs remain separately visible and keep their correct dependency relationships.

- **Expectation**: The HTML dependency graph should no longer merge build-time and host-time packages just because they have the same package label. Users should be able to see separate package instances per context, with each one connected to the dependencies that actually belong to it.

- **Constraints**: Keep the graph compact where duplicates are truly equivalent, but do not sacrifice correctness by combining nodes that represent different dependency roles. Existing filtering behavior should remain intact.


### Task 15 Make lockfile overrides context-aware
Ensure that lockfile-based overrides are applied only within the dependency context they were locked for, so installs and graph resolution do not fail or silently rewrite dependencies when host and build requirements coexist.

- **Expectation**: Lockfile overrides should behave predictably in mixed host/build dependency graphs. An override captured for one side of the graph must not leak into the other side, and upgrades should continue to honor overrides that belong to the current dependency context.

- **Constraints**: The fix should be limited to preventing cross-context override leakage. Legitimate overrides must still work, and unrelated lockfile behavior should remain unchanged.


### Task 16 Clarify source backup authentication failures
Ensure that authentication failures against source backup servers during backup source download or upload are reported as clear credential failures and direct users to verify their source credentials configuration.

- **Expectation**: If a configured source backup server rejects access during source retrieval or source backup upload, users should see a clear error explaining that authentication to that server failed and that their source credentials configuration should be reviewed.

- **Constraints**: Only the clarity of credential-related failure reporting should change. Successful source backup operations and unrelated source backup error handling should continue to behave as before.


### Task 17 Complete legacy CMakeConfigDeps library variables for component packages
Ensure that `CMakeConfigDeps` generates a complete legacy `<packagename>_LIBRARIES` variable for componentized packages so consumers using legacy CMake variables receive every relevant library target instead of an incomplete list.

- **Expectation**: Legacy CMake consumers should see a complete list of linkable targets in `<packagename>_LIBRARIES`. Multi-component packages should expose all component targets there, while single-target packages should keep the existing single entry behavior.

- **Constraints**: The fix should be backward compatible. It should add missing library targets for legacy consumers without changing how non-component packages are represented or breaking custom target naming.


### Task 18 Relax implicit language validation in CMakeConfigDeps
Ensure that CMakeConfigDeps-generated package configuration files do not fail valid CMake consumer projects when dependency link languages are already implicitly supported by the consumer project's enabled languages.

- **Expectation**: Generated CMake dependency configs should follow CMake's own implicit language rules. Valid consumer projects must configure successfully without redundant language declarations, while truly incompatible language requirements should still be blocked.

- **Constraints**: Keep protection against invalid language mismatches, but eliminate false failures caused by requiring users to restate language support that CMake already provides implicitly.


### Task 19 Fix Conan user preset stubs for custom user_presets_path
Ensure that when `CMakeToolchain.user_presets_path` is specified, Conan generates valid user CMake preset stubs for inherited Conan presets so user-defined configure, build, and test presets continue to work even if some inherited Conan presets are not currently present as real presets in the included Conan preset files.

- **Expectation**: Using a custom Conan-generated user presets file should produce a complete and valid preset graph for any user preset that inherits Conan presets. Missing inherited presets should be represented by safe placeholder entries, while real presets from included files should be used directly without duplication.

- **Constraints**: The fix should be limited to keeping custom user preset generation valid and non-destructive. It must not introduce duplicate preset definitions, break existing includes, or overwrite user-owned preset files that Conan does not manage.


### Task 20 Handle editable builds safely when source download is forced
Ensure that Conan operations using `--build=editable` remain stable when `tools.build:download_source=True` is enabled, and that editable dependencies do not trigger source-download processing or crash during the install/build flow.

- **Expectation**: Conan should recognize all editable dependency states as non-cache-backed editables when forced source download is enabled. Users who opt into `--build=editable` should see normal command execution instead of a crash, and editable packages should not run source acquisition as part of that flow.

- **Constraints**: The update should only remove the invalid handling of editable packages under forced source download, without changing how regular packages download sources or how editable mode otherwise behaves.


### Task 21 Fix Emscripten compiler auto-detection on first run and Windows
Ensure that Emscripten compiler auto-detection succeeds on first run and on Windows even when `emcc --version` prints extra lines before the version banner, while still rejecting outputs that are not valid Emscripten version reports.

- **Expectation**: Automatic Emscripten detection should work reliably across platforms and fresh environments, including cases where the compiler prints setup or sanity-check information before its actual version line. Detection should only succeed for genuine Emscripten output with a valid version and otherwise behave as a clean no-match.

- **Constraints**: The fix must broaden compatibility with real `emcc` output formats without making compiler detection looser for unrelated or malformed outputs. Failed detection should remain non-destructive and should not create a false positive compiler identification.


### Task 22 Honor run-scope Windows bash settings in ConanFile.run
Ensure that Windows recipes using `win_bash_run=True` can execute `self.run(..., scope="run")` through the configured bash environment with the correct run-scope behavior.

- **Expectation**: When a recipe opts into Windows bash for run-time commands, run-scoped shell invocations should execute in that bash environment as configured, without silently behaving like build-scoped commands.

- **Constraints**: The fix should preserve current build-time bash behavior while making run-time bash opt-in work independently and predictably.


### Task 23 Fix custom make program paths in Windows subsystem Autotools builds
Ensure that Conan Autotools builds running inside a Windows subsystem correctly honor `tools.gnu:make_program` when the make executable is configured using a native Windows path, so users can override the make binary without path-format-related build failures.

- **Expectation**: If a user selects a custom make executable for an Autotools build running under a Windows Unix-like subsystem, Conan should run that tool successfully even when the configured path is written in normal Windows form.

- **Constraints**: The change should only make custom make-path handling more robust in subsystem-based Windows builds and should not alter unrelated build semantics or break existing configurations that already work.


## Breaking Changes

### Task 24 Remove legacy Conan 1.x alias requirement support
Ensure that upgrading to Conan 2.27.0 no longer relies on legacy Conan 1.x alias requirements, because alias-based dependencies are removed and should fail by default unless an explicit temporary compatibility override is enabled.

- **Expectation**: Alias recipes from Conan 1.x are no longer a supported dependency mechanism. Operations that encounter an alias should stop with an error by default rather than transparently redirecting to another package, while a temporary opt-in compatibility switch may still allow old alias-based graphs to resolve.

- **Constraints**: Normal dependency resolution should remain unchanged for direct dependencies. Only legacy alias indirection should be blocked by default, and any short-term compatibility path should require an explicit user opt-in.


## Additional Changes
- Ensure that operations talking to Conan remotes fail cleanly when the server returns an HTTP status code that is not mapped to one of Conan's known remote exception types.
