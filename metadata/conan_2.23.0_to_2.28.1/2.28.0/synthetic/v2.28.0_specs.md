# Upgrade Specification from 2.27.1 to 2.28.0

## New Features

### Task 1 Allow Uploads to Disabled Remotes
Ensure that users can intentionally run `conan upload` against a disabled remote by passing an explicit command-line option, while preserving the existing behavior that disabled remotes block uploads by default.

- **Expectation**: Uploading to a disabled remote should be possible only through an explicit user override. The override should allow the upload workflow to run normally for that invocation, without changing the default safety behavior for disabled remotes or altering unrelated upload rules.

- **Constraints**: The feature should be an opt-in exception, not a broad change to remote management. Disabled remotes should remain protected by default, and enabling this upload path should not weaken other upload safeguards or unrelated command semantics.


### Task 2 OR policy for required Conan version
Ensure that Conan treats a configured core:policies required_conan_version policy and a recipe-level required_conan_version declaration as independent opt-ins for version-gated behavior, so either one can activate the Conan 2.28 behavior gates.

- **Expectation**: Users should be able to opt into new Conan behavior either once in global configuration or directly in an individual recipe. A positive opt-in from either place should enable the new behavior, and older projects should keep legacy-compatible behavior when they have not opted in.

- **Constraints**: The change should be additive and opt-in. Global and per-recipe policy declarations should cooperate instead of overriding each other, and existing configurations without the new opt-in should continue to behave as before.


### Task 3 Support insecure config package installs
Ensure that users can install Conan configuration packages from HTTPS repositories that require insecure SSL handling, while keeping SSL verification enabled by default and requiring the insecure opt-out to be explicit.

- **Expectation**: Configuration package installation should allow an explicit insecure connection mode for repositories whose SSL certificates cannot be verified, but it should never silently weaken security. Command-line installs may opt out only when the repository URL is supplied on the command line, while configuration-file installs must define the SSL policy alongside each URL in the file.

- **Constraints**: Preserve backward compatibility and secure defaults. Disabling SSL verification must be scoped to the specific repository source where the user explicitly requested it, and it must not change unrelated remotes or package installation behavior.


### Task 4 Add Conan policy controls for deprecated behavior
Ensure that Conan exposes policy-based controls for deprecated behaviors while enforcing the new default semantics for graph build-order ordering and empty version ranges.

- **Expectation**: Users should get stricter, clearer defaults in Conan 2.28 while still having an explicit, temporary compatibility switch for specific deprecated workflows. Global policy configuration should also let users opt into version-gated behavior consistently across recipes.

- **Constraints**: Compatibility should require explicit opt-in, be narrowly scoped, and remain temporary. Modern command usage and supported dependency declarations should continue to behave as before.


### Task 5 Colorize Conan config command output
Ensure that `conan config list` and `conan config show` make their human-readable output easier to read by visually distinguishing configuration names from their values.

- **Expectation**: When users inspect Conan configuration from the terminal, configuration names should be highlighted while the actual configuration values remain unchanged and readable as ordinary text.

- **Constraints**: This is a presentation-only enhancement. It must not affect configuration contents, command behavior, machine-readable output, or unrelated configuration workflows.


### Task 6 Show transitive requires in graph info HTML
Ensure that users viewing `conan graph info ... -f=html` output can inspect the transitive requirements of an individual package as an interactive node subgraph without changing the underlying dependency graph.

- **Expectation**: The HTML graph viewer should let a user focus on one package and see the full set of packages it requires, including indirect requirements, as a highlighted subgraph. This should be a viewing aid only: it should not alter the graph contents or dependency relationships.

- **Constraints**: The new subgraph view must be additive and non-disruptive. Existing graph filters, collapsed views, node and edge selection, and informational display behavior should continue to work, and the visualization should not misrepresent hidden or collapsed packages.


### Task 7 Improve Conan HTML report inspection
Ensure that generated HTML reports make dependency and diff inspection easier: graph info HTML output should let users focus on a selected package's transitive dependency subgraph in the browser, and report diff HTML output should support narrowing results by file extension while keeping diff context visually aligned.

- **Expectation**: Users opening generated HTML reports should be able to narrow what they are looking at without changing the underlying report. In graph reports, selecting a package should be able to reveal the dependency subset it brings in. In diff reports, users should be able to focus on relevant file types and scan context consistently.

- **Constraints**: The report should remain a faithful view of the same data while adding better ways to inspect it. Existing report controls and information should keep working, and the focused subgraph view should not imply relationships that are not present in the graph.


### Task 8 Filter HTML report diffs by extension
Ensure that users viewing `conan report diff ... -f=html` can filter the displayed file tree and diff content by file extension, including files without an extension, while preserving existing report-diff filters and aligned diff rendering.

- **Expectation**: The HTML report diff should let users interactively narrow a large diff to relevant file types without regenerating the report. Extension filtering should feel additive to the existing search and status filters, and users should remain able to restore or clear extension selections from the page.

- **Constraints**: The change should be an additive HTML viewing feature: it should help users hide or reveal groups of changed files without removing report content, weakening existing filters, or making extensionless files impossible to inspect.


### Task 9 Add compiler flags mapping plugin
Ensure that consumers can customize compiler and linker flags exposed by dependencies, especially compatible binaries built under a different compiler or platform, by providing a flags_map plugin that adapts those flags to the consuming Conan context.

- **Expectation**: Users should be able to configure Conan so dependency flags are adapted to the current consuming build environment at consumption time. Incompatible flags can be removed or translated before recipe code or build-system generators use them, while projects without custom configuration behave as before.

- **Constraints**: Only the consumed view of compiler and linker flags should change. Package creation, dependency resolution, and projects without an installed mapping plugin should remain stable and backward compatible.


### Task 10 Allow install_strip to target build systems
Ensure that users can configure install-time binary stripping for only the build system integrations that support or require it, while preserving the previous all-or-nothing boolean behavior.

- **Expectation**: Users can choose whether binary stripping during install applies globally or only to selected build-system backends. Existing boolean configuration remains valid, and unsupported configuration shapes are not silently accepted.

- **Constraints**: The feature must be backward compatible for existing users and must avoid forcing stripping in build systems that were not selected by the user.


### Task 11 Add certified and safe OS setting variants
Ensure that Conan's built-in settings accept the newly supported VxWorks certified variant and Neutrino safe variant, while also recognizing Neutrino 8.0 as a valid Neutrino version.

- **Expectation**: Users should be able to describe certified VxWorks builds and safe Neutrino builds using standard Conan settings, and existing VxWorks and Neutrino profiles that do not specify a variant should continue to work.

- **Constraints**: The update should be additive and backward compatible: it should recognize the new OS configurations without invalidating established profiles or broadening unrelated settings.


### Task 12 Support recipe-name patterns in --update
Allow users to selectively update cached recipes by passing recipe-name patterns to -u/--update, while preserving existing exact-name and update-all behavior.

- **Expectation**: Users can update all recipes whose names match a simple wildcard pattern, such as a shared prefix, without listing each recipe. The matching scope is recipe names only, not complete references.

- **Constraints**: The feature should broaden selective update targeting without changing what versions are chosen, without changing update-all behavior, and without treating full reference strings as valid pattern targets.


### Task 13 Add strict remote authentication mode
Ensure that `conan remote auth` can be run in a strict mode that fails the command when authentication fails for any matched remote, while keeping the existing successful exit behavior for non-strict invocations.

- **Expectation**: Users can opt into CI-friendly remote authentication where any failed remote authentication makes the command fail. Users who do not opt in continue to get the legacy behavior where partial authentication failures are reported but do not make the command unsuccessful.

- **Constraints**: Strict mode should only affect the overall success or failure of the command after authentication has been attempted; it should not alter how remotes are selected, how credentials are requested, or how normal non-strict usage behaves.


### Task 14 Honor configured system package manager before default detection
Ensure that an explicit `tools.system.package_manager:tool` configuration override is honored immediately and does not trigger default system package manager detection.

- **Expectation**: If a user configures which system package manager Conan should use, Conan should trust that choice and avoid auto-detecting another package manager. Automatic detection should remain available only as the fallback for users who did not configure a package manager tool.

- **Constraints**: The change should be limited to avoiding unnecessary default detection when the package manager has already been selected. Existing behavior for unconfigured users and unrelated package manager options should remain stable.


### Task 15 Scoped output for conan export
Ensure that `conan export` presents recipe-scoped output in a compact contextual form by printing the package reference once for a contiguous scoped block instead of repeating it on every output line.

- **Expectation**: Export output should group messages by recipe context so users can identify the package reference once and read the related lines beneath it without repetitive prefixes. Output outside this export-specific contextual mode should continue to look and behave as before.

- **Constraints**: The compact formatting must improve readability without changing command results, package export semantics, or the formatting contract for unrelated commands and ordinary output.


### Task 16 Default pacman support for CachyOS
Ensure that Conan recognizes CachyOS as a distribution whose default system package manager is pacman.

- **Expectation**: Users running Conan on CachyOS should get automatic pacman-based system package manager behavior without needing to manually configure or override the package manager.

- **Constraints**: The upgrade should add CachyOS support without disrupting package-manager detection or system package installation behavior for existing platforms.


### Task 17 Add consistent requirement trait
Ensure that Conan requirements support a `consistent` trait so `visible=False` host requirements can participate in version consistency and conflict resolution in diamond dependency graphs without having to become visible to downstream consumers.

- **Expectation**: Users can keep dependencies hidden from consumers while still asking Conan to enforce a single consistent dependency version across the graph. Hidden host requirements should behave like normal consistency participants by default for recipes opting into Conan 2.28 behavior, while explicitly inconsistent hidden requirements remain isolated.

- **Constraints**: The change must add graph consistency control without changing visibility semantics. Existing recipes that do not opt into the new Conan 2.28 policy should keep their previous default behavior unless they explicitly set the new trait.


## Bug Fixes

### Task 18 Expose bumped development version for TestPyPI publishing
Ensure that the development wheel publishing workflow can obtain the exact timestamped Conan development version produced during version bumping.

- **Expectation**: Version bump automation should not only update the package version, but also expose the final generated version in a machine-readable way so publishing steps can use the same value.

- **Constraints**: The publishing fix should be limited to release automation and must not change how users interact with Conan during normal operation.


### Task 19 Fix workspace lockfile handling
Ensure that `conan workspace install` and `conan workspace build` consistently honor a single workspace-level lockfile, support partial lockfile mode without crashing, and ignore lockfiles located inside individual workspace package folders unless the user explicitly selects such a lockfile.

- **Expectation**: Workspace install and build should have deterministic, workspace-wide lockfile behavior: an explicit or root-level lockfile applies uniformly to the whole workspace, partial mode works with that lockfile, and unrelated lockfiles inside package directories do not change the dependency graph.

- **Constraints**: Keep workspace operations predictable and backward compatible except for removing the unintended influence of local package lockfiles and the crash around explicit partial lockfile usage.


### Task 20 Require explicit build-order ordering
Ensure that `conan graph build-order` no longer silently relies on the deprecated implicit ordering behavior, while still offering a temporary policy-controlled compatibility path for users who need the old behavior during migration.

- **Expectation**: Users must make build-order sorting behavior explicit by selecting an ordering mode. Projects that temporarily need the old implicit behavior can opt into it through configuration and should receive a clear deprecation signal.

- **Constraints**: The change should make ambiguous command usage fail fast by default, while keeping an explicit, temporary migration path and avoiding regressions for users who already provide the required option.


### Task 21 Remove Deprecated Deploy Folder Fallback
Ensure that Conan no longer supports the deprecated deployer extension folder named deploy in Conan home, and instead consistently uses the current deployers folder for cache deployers.

- **Expectation**: Users who provide deployer extensions through Conan home must use the current deployers location. The legacy deploy location is no longer treated as a supported compatibility alias.

- **Constraints**: The upgrade should remove only the deprecated compatibility path while keeping normal deployer discovery through the supported location intact.


### Task 22 Retire CMake interface link directory property
Ensure that the deprecated CMake interface link directory opt-in is fully retired from generated CMake dependency files, so recipes that still declare it no longer receive legacy handling and supported package metadata remains the source of link information.

- **Expectation**: The old CMake link-directory compatibility flag should be treated as removed. Users should see normal CMake dependency generation without legacy warnings or hidden output changes from that flag, and packages should express required link behavior through supported metadata.

- **Constraints**: Keep ordinary CMake dependency generation stable and limit the behavioral change to retiring the deprecated flag.


### Task 23 Warn when remote auth ignores environment credentials
Ensure that `conan remote auth` warns users when credential environment variables are set but the remote accepts anonymous access, causing those credentials to be ignored.

- **Expectation**: When a remote allows anonymous access and Conan therefore does not consume configured credentials, users should receive a clear warning instead of having their login-related environment variables silently ignored. The warning should make it apparent which credentials were ignored and how to request authentication explicitly.

- **Constraints**: The fix must improve visibility without forcing login, breaking anonymous access, or adding noise when no credentials were supplied. Users who explicitly force authentication should continue through the existing authenticated flow without receiving an ignored-credentials warning.


### Task 24 Preserve error-like option names in conan list
Ensure that conan list preserves user-defined option names containing the word error and displays them as normal option data instead of converting them into error entries.

- **Expectation**: Listing package data should distinguish real error indicators from ordinary user-defined names. A user option should not be reported as an error just because its name includes the word error.

- **Constraints**: The fix must be limited to correcting false error classification without weakening real error reporting or changing unrelated list output semantics.


### Task 25 Forward system package manager errors
Ensure that Conan system package manager operations surface underlying package manager failures, including missing tools and command execution errors, instead of reporting only a generic command failure.

- **Expectation**: When Conan cannot use the operating system package manager, users should immediately see why it failed, including relevant diagnostics from the external tool, without successful package-manager checks becoming noisier.

- **Constraints**: Improve failure visibility without changing which package-manager outcomes count as success, without adding noise to normal successful runs, and without overriding user configuration.


### Task 26 Deprecate build_requires in favor of tool_requires
Ensure that users relying on the deprecated build_requires recipe API are warned to migrate to tool_requires with appropriate traits, without breaking existing build requirement declarations.

- **Expectation**: Recipes using the legacy build requirement mechanism should still work, but users should receive a clear migration signal toward the supported tool requirement model. Build environment executable paths should only be propagated when the dependency is intended to be runnable.

- **Constraints**: The upgrade should be advisory and backward compatible for existing recipes, while avoiding false deprecation warnings for recipes that have already migrated.


### Task 27 Inline XcodeDeps transitive metadata
Ensure that XcodeDeps generated xcconfig files for direct dependencies contain all required transitive dependency settings without relying on inter-package include chains, so projects with deep or component-heavy dependency graphs do not crash Xcode.

- **Expectation**: Consumers using XcodeDeps should receive self-contained direct dependency configuration files: all build settings needed from reachable transitive dependencies are already present, while unrelated components and skipped dependencies are not leaked. Xcode should no longer need to evaluate deep nested include chains for transitive packages.

- **Constraints**: Keep generated Xcode configuration complete for compilation and linking, but flatten the dependency structure and avoid introducing settings from dependencies the consumer did not actually require.


### Task 28 Deduplicate finalize folder output
Ensure that Conan reports a recipe's finalized output folder only once when finalize() is involved, avoiding duplicate finalized-folder notifications when the same finalized package is encountered more than once.

- **Expectation**: Users should see one finalized-folder report for each actual package finalization, with no repeated folder lines caused by repeated graph references or already-handled finalization.

- **Constraints**: The fix should remove redundant status output while preserving package finalization semantics and all non-duplicate user-visible behavior.


### Task 29 Default download retry wait
Ensure that Conan package downloads no longer retry immediately by default after a failed remote download, and ensure that retry configuration defaults are visible to users inspecting Conan configuration options.

- **Expectation**: Failed remote package downloads should pause briefly before retrying by default, while users can discover the default retry counts and wait times from Conan's configuration listing.

- **Constraints**: The change should only alter the default delay for remote package download retries and improve configuration discoverability; existing user overrides and other retry defaults should remain stable.


### Task 30 Use User Locale in HTML List Dates
Ensure that dates rendered by `conan list ... -f=html` respect the user's locale instead of always appearing in an English locale format.

- **Expectation**: HTML list reports should feel localized to the person viewing them: date values should follow the user's environment locale while keeping the same information and level of detail as before.

- **Constraints**: Only the locale used to present dates should change; the report contents, available fields, and other formats should continue to behave as they did previously.


### Task 31 Make recipe reference resolution case-sensitive
Ensure that Conan treats package reference casing as significant during requirement resolution, especially when resolving version ranges, so a requirement with incorrect package-name casing does not match an existing recipe with different casing.

- **Expectation**: Dependency resolution must respect the exact spelling of package names. A package name that differs only by uppercase or lowercase letters is a different reference for resolution purposes and must not be accepted as a match.

- **Constraints**: The fix should prevent false positive matches caused by casing mistakes without changing successful resolution for correctly spelled package references or broadening the set of acceptable package names.


### Task 32 Support Xcode 26.4 and Apple Clang 21
Ensure that Conan accepts and models Apple toolchains from Xcode 26.4, including Apple Clang 21, across the supported Apple platform settings.

- **Expectation**: Users working with current Apple developer tools should be able to configure Conan profiles for Xcode 26.4 without encountering unsupported compiler, OS version, or SDK version validation failures for the newly supported values.

- **Constraints**: The update should preserve compatibility with existing Apple profiles while allowing users to adopt the newer Xcode release and compiler version.


### Task 33 Add short aliases for lock upgrade update options
Ensure that `conan lock upgrade` supports concise short options for updating normal requirements, build requirements, and Python requirements while preserving the existing long options.

- **Expectation**: Users should be able to use shorter option names when requesting dependency updates during a lockfile upgrade, with no behavioral difference from using the established long option names.

- **Constraints**: The change must be backward-compatible and limited to command-line option spelling; dependency selection and lockfile update results should remain consistent.


### Task 34 Preserve run trait for build requirements
Ensure that build or tool requirements declared with run=false do not cause their upstream shared-library dependencies to be treated as runnable runtime dependencies in downstream dependency graphs.

- **Expectation**: A dependency used only as a non-runnable build tool should not make that tool's own shared-library dependencies behave like runtime dependencies of the consumer. Runtime propagation should occur only when the originating build requirement is actually runnable.

- **Constraints**: Preserve existing dependency graph behavior except for removing the incorrect runtime marking from non-runnable build dependency chains. Build-only dependencies should remain isolated from normal consumer link and include semantics.


### Task 35 Full-link same-package CMake components
Ensure that CMakeConfigDeps generates complete public link relationships for components that depend on other components from the same Conan package.

- **Expectation**: A consumer linking to one exported CMake component should also receive the component dependencies that the package author declared inside the same package, including shared library component dependencies, so normal CMake usage resolves includes and symbols without extra manual links.

- **Constraints**: Do not change how unrelated package dependencies are discovered or linked, and do not remove existing customization behavior for generated CMake targets.


### Task 36 Fix workspace lockfile handling
Ensure that `conan workspace install` and `conan workspace build` use workspace-level lockfile semantics consistently, do not crash when an explicit partial lockfile is provided, and do not accidentally consume lockfiles from individual workspace packages.

- **Expectation**: Workspace install and build should be deterministic: they should use one intended workspace lockfile, support partial lockfile workflows without crashing, and remain unaffected by stale or unrelated lockfiles inside member packages.

- **Constraints**: The fix should make workspace lockfile behavior predictable while preserving existing supported workflows and avoiding unrelated changes to normal install or build behavior.


### Task 37 Validate Config Packages in Lockfiles
Ensure that lockfile-based Conan operations reject configuration-package drift when a lockfile contains config_requires, instead of proceeding with installed configuration packages that are not aligned with the lockfile.

- **Expectation**: A Conan command that relies on a lockfile with configuration package requirements should only proceed when the user's installed configuration packages satisfy the lockfile. If the local configuration state is missing a required package or contains a conflicting package, the command should fail clearly before continuing.

- **Constraints**: Projects without locked configuration packages should continue to work as before. The new validation should enforce reproducibility for locked configuration packages without making unrelated lockfile workflows stricter.


### Task 38 Respect run trait in VirtualBuildEnv bindirs
Ensure that VirtualBuildEnv no longer exposes executable bindirs from build requirements whose effective run trait is disabled when the Conan 2.28 policy is active, while preserving legacy behavior for projects that have not opted into the new policy and guiding users away from deprecated build_requires usage.

- **Expectation**: Projects that opt into Conan 2.28 behavior should only receive executable paths from tools they actually declare as runnable. Tools marked as not runnable must not silently become available through the generated build environment, while existing projects that have not opted in keep their previous behavior.

- **Constraints**: The fix must be backward compatible by default, limit the behavior change to the documented opt-in policy, and avoid blocking users who still rely on older recipe declarations.


### Task 39 Respect unset PowerShell virtualenv configuration
Ensure that explicitly unsetting the PowerShell virtual environment configuration disables PowerShell script generation instead of being interpreted as a usable PowerShell setting.

- **Expectation**: Disabling the PowerShell environment integration should behave as a real opt-out: no PowerShell activation artifacts should appear just because the setting was unset, while normal defaults should continue to apply where PowerShell execution is actually needed.

- **Constraints**: The fix must only change the disabled-setting behavior and must not break existing explicit PowerShell configurations or the default command used when PowerShell launchers are intentionally present.


### Task 40 Honor transitive libs in CMakeConfigDeps for shared libraries
Ensure that CMakeConfigDeps honors transitive_libs=True for shared-library dependency chains so consumers receive the required transitive link libraries instead of losing them when intermediate dependencies are shared libraries.

- **Expectation**: A package that intentionally exposes another package's libraries to its consumers should have that relationship represented in generated CMake targets regardless of whether the packages are built as shared libraries. Non-library dependencies should remain excluded from link interfaces, and existing CMake naming and link-feature customization should keep working.

- **Constraints**: The fix should only restore intended library propagation and must not broaden link interfaces to non-library artifacts or ignore existing user-provided CMake target configuration.


### Task 41 Opt-in package ID fix for transitive static libraries
Ensure that static-library package_id computation can opt into the Conan 2.28 behavior where transitive static library dependencies that do not expose headers stop contributing to the consuming package's package_id, while preserving legacy behavior for users who have not opted in.

- **Expectation**: Projects that explicitly opt into Conan 2.28 compatibility should get cleaner, more stable package IDs for static libraries by ignoring transitive library dependencies that do not affect the package's headers. Projects that do not opt in should continue to receive the old package IDs and a warning that the old behavior is suboptimal.

- **Constraints**: The fix must be opt-in to avoid invalidating existing binary package IDs. Only dependencies that are irrelevant to the static library's public headers should be removed from the package identity calculation; explicitly requested dependency identity behavior and existing non-static behavior must remain stable.


## Breaking Changes

### Task 42 Disallow empty version ranges by default
Ensure that package requirements using an empty version range are rejected by default, while providing a documented temporary compatibility policy for users who still rely on the deprecated behavior.

- **Expectation**: Empty version ranges should no longer be accepted silently or treated as ordinary deprecated usage. They should fail by default, with an explicit opt-in compatibility switch that keeps existing projects working temporarily while warning users to migrate.

- **Constraints**: The change should be narrow: valid version range usage must keep working, deprecated compatibility must require explicit user choice, and the compatibility mode must clearly remain temporary.


### Task 43 Remove deprecated system_tools profile support
Ensure that Conan profiles no longer support the deprecated [system_tools] section and require users to declare platform tool requirements with [platform_tool_requires].

- **Expectation**: Deprecated profile configuration for system tools is fully removed. Users who need platform-level tool dependencies must use the current supported profile section, and obsolete profile syntax should fail instead of continuing through a compatibility path.

- **Constraints**: Supported profile functionality should remain stable. The only intended compatibility removal is the old system tools profile section, and users should receive normal invalid-profile handling rather than a silent migration or legacy warning path.


### Task 44 Remove Deprecated Detect Compiler API
Ensure that the deprecated `detect_compiler` entry point is no longer available in the detect API, and that users obtain default compiler information through the supported replacement API.

- **Expectation**: The deprecated compiler-detection shortcut should no longer be part of the library surface. Users should use the current compiler detection API and adapt to its supported return contract.

- **Constraints**: The upgrade should remove only the obsolete compatibility path while keeping supported compiler detection behavior stable.


### Task 45 Remove Deprecated PackagesList Helpers
Ensure that deprecated, non-public PackagesList helper methods are no longer available, and that users interact with package lists through the supported APIs for adding references, iterating revision-backed entries, and reading serialized list data.

- **Expectation**: Deprecated package-list shortcuts are removed from the usable API. Users should add package-list entries through the supported single-entry methods, iterate only fully revision-backed artifacts through items(), and use serialization when they need the raw list structure or broad search results that do not include revisions.

- **Constraints**: Removing the deprecated shortcuts must not alter the supported package-list operations or make broad serialized results inaccessible. Existing supported APIs should continue to represent recipe and package revisions consistently.


### Task 46 Remove deprecated Node dependencies alias
Ensure that the deprecated Node.dependencies graph API is no longer available after upgrading, and that dependency relationships are represented through the supported node edge API.

- **Expectation**: The upgrade should stop supporting the deprecated dependency alias and keep the supported graph relationship API as the source of truth. Existing graph node state unrelated to the deprecated alias should remain initialized normally.

- **Constraints**: Only the deprecated alias should disappear; supported graph behavior and normal node state should continue to work as before.


## Documentation

### Task 47 Document Command and Profiles APIs
Ensure that Conan's public API clearly documents how to use the command and profile sub-APIs, while preserving the documented profile composition behavior and avoiding unrelated eager global configuration validation during profile loading.

- **Expectation**: Users of the Conan Python API should be able to understand from the public API surface how to invoke Conan commands programmatically and how profiles are loaded, combined, listed, and detected. Loading a profile should focus on composing the requested profile data and command-line overrides, rather than failing early because of unrelated global configuration validation.

- **Constraints**: The documentation improvements must not change how commands are executed or how profiles are composed, listed, or detected, except that profile loading should no longer be blocked by an eager validation step unrelated to the requested profile composition.


## Additional Changes
- Ensure that Conan can be installed and used with patch-ng 1.19.x so users receive upstream patch-ng fixes without losing compatibility with the existing supported 1.18.x dependency line.
- Ensure checksum-backed source downloads handle `core.sources:download_cache` and `core.sources:download_urls` consistently across local cache hits, recipe-origin URLs, and configured source backup servers.
- Ensure GCC standard-library detection can determine the libstdc++ ABI without mutating the caller's working directory or relying on temporary source files.
- Ensure profile setting update code accepts normal `dict` mappings while preserving the established order-sensitive profile composition behavior.
