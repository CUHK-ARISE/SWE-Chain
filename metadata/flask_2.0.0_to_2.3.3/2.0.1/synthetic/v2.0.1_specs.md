# Upgrade Specification from 2.0.0 to 2.0.1

## Bug Fixes

### Task 1 Restore deprecated filename support in send_from_directory
Ensure that upgrading to 2.0.1 does not break existing `send_from_directory` calls that still pass `filename`, while keeping `path` as the preferred argument name and signaling that the old name is deprecated.

- **Expectation**: Applications using the old argument name should keep working after the upgrade, but they should receive a deprecation signal telling them to move to the new argument name. Applications already using the new name should see no behavior change.

- **Constraints**: The fix must be backward compatible for older callers without regressing the renamed API. It should add a temporary compatibility layer rather than changing the expected file-serving behavior.


### Task 2 Restore Python 3.6.0 typing compatibility
Ensure that Flask 2.0.1 remains usable on Python 3.6.0 by avoiding newer standard-library typing symbols that are unavailable on that interpreter, without changing the observable behavior of the affected APIs.

- **Expectation**: Type annotations and exported typing helpers should stay compatible with Python 3.6.0. Users on that interpreter should be able to import and use Flask normally, and developers using type checking should still see the same intent and contracts.

- **Constraints**: This compatibility fix must not alter how the affected APIs behave at runtime. It should only remove interpreter-version-specific typing breakage while keeping the same user-visible outcomes and type meaning.


### Task 3 Reject dotted blueprint identifiers
Ensure that blueprint configuration rejects dot-containing names and route identifiers so nested blueprint endpoint resolution remains unambiguous, and invalid blueprint registrations fail with explicit runtime errors instead of being silently accepted or relying on assertion behavior.

- **Expectation**: Blueprint APIs should reserve dots for Flask's own nested blueprint and endpoint naming scheme. If an application tries to use a dot inside a blueprint name, custom endpoint name, or inferred view name for a blueprint route, Flask should reject it immediately with a clear value error. Blueprint route registration should still expose the same observable OPTIONS-handling control that application route registration provides.

- **Constraints**: Existing valid blueprint setups should keep working unchanged. Only configurations that misuse dot-separated identifiers should now fail early. The fix must preserve normal URL generation and route registration behavior for valid blueprints while keeping explicit OPTIONS handling available.


### Task 4 Fix nested blueprint prefix composition
Ensure that nested blueprints preserve and combine parent and child URL prefixes correctly, including when a prefix is declared on a Blueprint instance instead of only being passed during registration. Ensure that nested registrations also use the effective registered blueprint name for derived nested namespaces.

- **Expectation**: Nested blueprints should mount child routes under the full expected path instead of dropping configured prefixes. Renaming a blueprint at registration time should stay consistent for nested endpoint and default CLI namespaces.

- **Constraints**: Existing single-blueprint usage should continue to work, and nested prefix handling should be additive and non-destructive. The update should only change cases where nesting previously ignored effective prefixes or inherited names.


### Task 5 Restore session availability in custom URL converters
Ensure that requests using custom URL converters can safely access the active session and session-backed user state during route matching, including converters that consult authentication state.

- **Expectation**: Route matching should run only after per-request session state is ready so custom converters can use session-dependent logic consistently and authenticated requests do not break during parameter conversion.

- **Constraints**: Keep session initialization behavior intact while ensuring converter code can rely on session state. At the same time, avoid assuming that route-resolution details already exist before session setup has finished.


### Task 6 Restore deprecated Config.from_json compatibility
Ensure that applications upgrading to 2.0.1 can still call the deprecated `Config.from_json()` / `app.config.from_json()` API without runtime breakage, and that its continued availability clearly signals that callers should migrate to `Config.from_file()` rather than treating the API as fully supported again.

- **Expectation**: The JSON config helper should remain usable for one more release as a deprecated compatibility API. Existing code that still loads configuration from JSON through `from_json()` should work again, but callers should receive a deprecation warning and be guided toward `from_file()`.

- **Constraints**: The fix should restore compatibility without reversing the deprecation decision. It should behave like the existing file-based JSON configuration flow, preserve expected handling of missing files when silence is requested, and avoid new behavior differences beyond re-enabling the deprecated entry point.


### Task 7 Preserve decorator typing and validate blueprint route registration
Ensure that Flask's decorator-based registration APIs preserve the decorated function's type information for strict static analysis, and ensure that blueprint route registration exposes consistent runtime validation and option forwarding for invalid endpoint names and automatic OPTIONS handling.

- **Expectation**: Applications upgrading to 2.0.1 should get accurate typing from Flask's decorator APIs so registered handlers, filters, tests, and globals remain statically typed after decoration. Blueprint route registration should also fail predictably for invalid dotted names and continue to honor explicit automatic OPTIONS configuration.

- **Constraints**: Existing valid decorator usage should keep working the same way while becoming better typed. Valid blueprint routes must continue to register unchanged, and only invalid dotted names should be rejected with a regular runtime validation error. Any explicit automatic OPTIONS setting supplied during blueprint registration must still take effect.


### Task 8 Fix nested blueprint naming and registration collisions
Ensure that nested blueprints are registered and resolved by their full dotted registration name so applications can nest blueprints with the same local name in different places without collisions. Ensure that blueprint registrations can be given a unique registration name when mounted multiple times, while invalid self-registration and ambiguous name conflicts are surfaced predictably.

- **Expectation**: Applications should be able to mount nested blueprints with duplicate local names as long as their full registration paths are different. When a blueprint is mounted multiple times, callers should be able to assign distinct registration names so routing and URL generation remain unambiguous. Blueprint-specific request hooks, error handling, URL generation helpers, and request metadata should follow the active registered blueprint hierarchy, and invalid naming conflicts should be rejected or warned about in a consistent way.

- **Constraints**: The update must preserve normal blueprint behavior for existing non-conflicting registrations while removing ambiguity from nested and repeated registrations. Nested routes should still appear at the expected combined URL prefixes, and applications should not silently end up with conflicting blueprint namespaces.


### Task 9 Support unique names for repeated blueprint registration
Ensure that blueprint registration supports mounting the same blueprint more than once with distinct names so endpoint resolution and relative url generation target the correct mount. Ensure that blueprint name collisions are handled explicitly instead of silently reusing the wrong registration. Ensure that nested blueprints keep distinct dotted endpoint names and correct URL prefixes when registered through parent blueprints.

- **Expectation**: Applications should be able to mount one blueprint in more than one place as long as each mount has its own public registration name. URL generation and endpoint identity should follow the mount that handled the request, including for nested blueprints. Name conflicts should fail fast, repeated reuse of the same name for the same blueprint should be flagged as deprecated, and invalid self-nesting should be rejected.

- **Constraints**: The fix must isolate blueprint mounts by name without changing their route definitions beyond public endpoint naming. Nested registrations must remain stable and predictable across parent-child combinations, and the update must avoid introducing duplicate-name ambiguity or accidental recursive blueprint registration.


## Typing Updates

### Task 10 Explicitly export top-level Flask symbols for type checking
Ensure that public APIs imported from the top-level `flask` package are recognized as explicitly exported by static type checkers, so typed applications can continue using `from flask import ...` without spurious export errors after upgrading.

- **Expectation**: Applications should be able to import Flask's documented top-level APIs directly from `flask` and have those imports type-check cleanly with the package's own typing information enabled.

- **Constraints**: This should fix typing/export visibility only, without changing how application code imports or uses the library at runtime.


### Task 11 Correct `flask.g` typing for arbitrary attributes
Ensure that upgrading to Flask 2.0.1 preserves the documented ability to store arbitrary per-context attributes on `flask.g` and eliminates incorrect type-checker or linter complaints about normal `g.some_attribute` usage.

- **Expectation**: Applications should be able to keep using `flask.g` as a dynamic namespace for request or app-context data, and tooling should understand that this is a supported pattern instead of treating `g` like a fixed-attribute context object.

- **Constraints**: The fix should remove false developer-tooling errors without changing how existing applications interact with `flask.g` at runtime.


### Task 12 Improve typing for Flask file-serving helpers
Ensure that Flask's file-serving APIs expose accurate public typing for supported inputs and optional values so upgrading to 2.0.1 removes false type mismatches around file paths, file objects, cache-age resolution, and optional filename handling.

- **Expectation**: Typed callers should be able to use Flask's file download helpers with the same supported argument forms that the APIs expose at runtime, especially for path-like inputs, binary streams, optional filenames, timestamp values, and computed cache lifetimes.

- **Constraints**: The upgrade must preserve existing file-serving behavior and only clarify the supported API surface for typed consumers; it should not change how downloads, caching, or responses work in normal execution.


### Task 13 Broaden and refine stream_with_context type hints
Ensure that `stream_with_context` accepts standard iterators used for streaming responses, including iterators yielding bytes or text, without static type errors, while preserving the streamed item type in its public API contract.

- **Expectation**: `stream_with_context` should be typed to work with normal streaming iterators, not only generator objects, so developers can pass existing byte or text iterators to response streaming APIs without type-checking friction.

- **Constraints**: The change should improve compatibility with static typing tools without changing how streaming works at runtime or narrowing the kinds of stream sources developers can already use.
