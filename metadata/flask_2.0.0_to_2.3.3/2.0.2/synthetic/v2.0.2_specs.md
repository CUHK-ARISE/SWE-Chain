# Upgrade Specification from 2.0.1 to 2.0.2

## Bug Fixes

### Task 1 Enable async class-based view handlers
Ensure that routes created from class-based views support async handlers so applications can use async `View` and `MethodView` methods without failing at request time.

- **Expectation**: Class-based views should support async request handlers just like regular Flask view functions. If a `View` or `MethodView` handler is declared with `async def`, requests should complete normally and produce the handler's response rather than failing because a coroutine object was returned.

- **Constraints**: Async support for class-based views must be additive and must not regress existing synchronous class-based views or normal HTTP method dispatch behavior.


### Task 2 Preserve blueprint-local behavior across renamed registrations
Ensure that registering the same Blueprint multiple times with different names keeps every named registration fully functional, including blueprint-scoped request preprocessing and error handling, rather than only applying that behavior to the first registration.

- **Expectation**: Mounting one blueprint in more than one place should behave consistently for every mount. Later named registrations should not silently lose the blueprint's request lifecycle behavior or its custom error handling.

- **Constraints**: This should be a non-breaking consistency fix: keep the existing multi-mount pattern, and make each named mount honor the same blueprint-local behavior instead of only the first one.


### Task 3 Restore Decimal JSON serialization
Ensure that Flask JSON serialization accepts decimal.Decimal values in application payloads and encodes them safely instead of failing when Decimal objects appear in JSON output.

- **Expectation**: Applications should be able to include Decimal values in JSON responses and serialized payloads without extra configuration. Decimal content should remain representable without loss from forced numeric conversion, and the rest of Flask's normal JSON behavior should stay unchanged.

- **Constraints**: The fix should expand default JSON compatibility for Decimal values without regressing other supported serialized types or changing how existing JSON APIs are used.


### Task 4 Preserve original CLI loading errors during lazy app startup
Ensure that Flask CLI preserves the original exception when application loading is deferred under lazy loading, and ensure that CLI app discovery failures are reported as consistent `NoAppException` errors instead of being obscured by misleading exception handling.

- **Expectation**: Lazy CLI startup should expose the real application error that occurred, not a secondary framework error. When the CLI cannot locate, parse, import, or invoke the target app or factory, it should fail with a consistent app-loading error that points to the actual category of problem without leaking misleading exception context.

- **Constraints**: Normal startup must continue to work unchanged. The fix is limited to making failure reporting accurate and stable: genuine app-loading errors should stay genuine, and CLI lookup failures should remain clean, consistent, and non-misleading.


### Task 5 Fix CLI app factory loading for create_app(**kwargs)
Ensure that the CLI can load an application factory such as create_app that accepts only optional variable keyword arguments, without incorrectly treating it as a factory that requires an explicit positional argument.

- **Expectation**: Application factories that are designed to accept injected keyword-only dependencies through arbitrary keyword arguments should continue to load normally from the CLI. The CLI should only use its legacy single-argument compatibility behavior for factories that truly define one required positional-compatible parameter.

- **Constraints**: The fix must be narrowly scoped: restore support for flexible keyword-accepting factories without changing how genuinely single-parameter factories are handled. Signature inspection should not cause the CLI to invent unsupported positional calls.


### Task 6 Fix Nested Blueprint Callback Ordering
Ensure that nested blueprint lifecycle callbacks execute in a consistent hierarchy order so the most specific blueprint can reliably override parent and app behavior during request handling, template rendering, and URL generation.

- **Expectation**: Nested blueprint hooks should behave like hierarchical scoping: setup and preprocessing flow from the app into parent and then child blueprints, and post-response cleanup flows back out. The most specific blueprint should be the final authority for request-time overrides before the view runs.

- **Constraints**: The fix should only correct hierarchy resolution, not break existing callback registration order or override explicit caller-provided values. Non-request usage of templating and URL generation should continue to work.


## Typing Updates

### Task 7 Correct typing for teardown and related callback decorators
Ensure that Flask's callback-based decorators and registrations are typed to match documented and existing runtime behavior, especially that `teardown_*` hooks are not required to return a response and other supported callback forms are accepted by static typing.

- **Expectation**: Users should be able to annotate Flask lifecycle hooks, template helpers, and error handlers in the same way those callbacks already behave at runtime. Teardown hooks should not be modeled as response-producing callbacks, request hooks should support their normal short-circuiting behavior, template helpers should not be restricted to a single fixed signature, and exception handlers should work with specific exception types.

- **Constraints**: This update should only align typing with existing supported behavior. It must not alter how hooks execute, when request processing stops, what error handlers return, or how template helpers are called at runtime.


### Task 8 Correct callback type annotations for request hooks and related APIs
Ensure that Flask's public typing for request lifecycle decorators and related callback APIs matches their documented behavior, especially so that `before_request` and `before_app_request` handlers may legally return a response-like value to stop further request handling while first-request hooks remain return-ignored.

- **Expectation**: Applications using Flask 2.0.2 should see static type hints that match actual framework contracts for hooks and callback registration. Request-preprocessing hooks can either continue normally or return a response to end processing, while callbacks whose return values are ignored should be typed that way instead of implying unsupported behavior.

- **Constraints**: The upgrade is a typing-contract correction, not a behavioral redesign. Existing hook execution rules should stay the same, and only the public developer-facing type expectations should be brought into line with what the framework already documents and supports.


### Task 9 Correct Flask callback typing contracts
Ensure that upgrading to Flask 2.0.2 fixes inaccurate typing for template globals and related callback hooks so valid application callables are accepted by static type checkers and the exposed typing contracts match documented Flask behavior.

- **Expectation**: The public typing surface should reflect how Flask hooks and template helpers actually behave. Template helpers must be free to accept the arguments they are invoked with, request hooks may either continue processing or short-circuit with a response, teardown handlers are cleanup-only, and error handlers should type-check when written for specific exception types.

- **Constraints**: The change should improve static typing accuracy without altering how applications run. Valid existing hook and template-helper patterns should continue to work, and the revised contracts should narrow only behavior that is not actually part of the public callback semantics.


### Task 10 Preserve specific exception typing in error handlers
Ensure that registering an error handler for a specific exception class preserves that same exception type in the handler signature, instead of requiring a generic `Exception` parameter, while keeping existing error-handler registration and resolution behavior intact.

- **Expectation**: When a developer registers a handler for a custom exception type, the framework should treat the handler as receiving that exact exception type rather than a generic one. Existing handler behavior for status-code-based registrations and normal Flask response returns should remain stable, and invalid error-code registrations should still fail clearly.

- **Constraints**: Keep current error-handling behavior stable apart from the stronger typing contract. The update must not alter which handler is selected for a given error, what kinds of responses handlers may return, or the fact that unsupported HTTP error-code registrations are rejected.


### Task 11 Accept PathLike values for static_folder
Ensure that `static_folder` accepts `pathlib.Path` and other path-like values anywhere users configure static file directories, without creating type incompatibilities or changing the existing static file behavior for equivalent paths.

- **Expectation**: Users should be able to configure static file folders with either strings or standard Python path objects in the same places they already configure `static_folder`. Using a path object should behave the same as using the equivalent string path, while also being recognized as valid by typed code.

- **Constraints**: Existing applications that pass string paths or disable static files must continue to work unchanged. Accepting path objects should add compatibility, not alter how static folders are resolved for equivalent inputs.
