# Upgrade Specification from 2.0.2 to 2.0.3

## Bug Fixes

### Task 1 Deprecate Flask test client as_tuple usage
Ensure that Flask's test client continues to work for applications upgrading to 2.0.3 while phasing out the deprecated `as_tuple` usage, and ensure callers can access request environment data through the response object instead of relying on tuple returns.

- **Expectation**: After upgrading to Flask 2.0.3, existing test client code that still passes `as_tuple` should keep working temporarily, but it should clearly warn that this pattern is deprecated and scheduled for removal. Normal test client calls should behave as standard response-returning calls, and code that needs request environment details should read them from the response object.

- **Constraints**: The upgrade should be backward-compatible for current users during the 2.0.x line, while only warning on deprecated usage and leaving unrelated test client behavior unchanged.


### Task 2 Restore Flask CLI ImportError Tracebacks During App Loading
Ensure that the Flask CLI shows actionable import failure details when loading an application raises an ImportError from inside the application or one of its dependencies, while continuing to distinguish that case from a missing application module.

- **Expectation**: Using the Flask CLI to load an app should expose enough traceback information to identify the real missing or broken import inside the app startup path. A genuinely missing app module should still produce the normal module-not-found style failure instead of being reported as an internal app import traceback.

- **Constraints**: Keep current successful CLI loading behavior unchanged, and only expand error detail for the specific regression where internal import failures became opaque. Distinct categories of import failure should remain distinguishable to the user.


### Task 3 Clarify request-context misuse errors for request decorators
Ensure that request-scoped decorators report a clear runtime error when they are used without an active request context.

- **Expectation**: If a developer accidentally uses request-only decorators outside a live request, the library should fail with a clear, actionable runtime error that explains the misuse and the valid context for using it.

- **Constraints**: Correct in-request usage should continue to behave as before. The update should only improve the clarity and consistency of failure behavior for out-of-context calls.


## Typing Updates

### Task 4 Fix error handler typing compatibility
Ensure that registering an error handler for exceptions is accepted by static type checkers when the handler takes the declared exception type and returns a valid Flask response value.

- **Expectation**: Applications should be able to declare error handlers in the normal Flask style and have valid signatures pass type checking. A handler that receives the exception object and returns a standard Flask response should be recognized as compatible when registered for that exception type.

- **Constraints**: This update should improve developer tooling compatibility without changing how error handlers behave at runtime. Existing correctly written handlers should continue to work, and broader exception handlers should not lose compatibility.


## Performance Improvements

### Task 5 Avoid no-op JSON hook overrides in default Flask JSON handling
Ensure that Flask's default JSON serialization and deserialization path does not pay extra overhead for encoder or decoder hook classes when no custom JSON behavior has been configured, while still honoring custom JSON handling defined by the application or blueprint.

- **Expectation**: Flask JSON helpers should use the normal fast path when the application has not customized JSON encoding or decoding, and should only activate custom JSON class behavior when the application explicitly provides it.

- **Constraints**: Keep existing customized JSON behavior intact, and do not change normal JSON results other than removing avoidable overhead from the default configuration.


## Additional Changes
- Ensure that `get_root_path(import_name)` does not crash with `TypeError` when the target module is already present in `sys.modules`, has a `__file__` attribute, but that attribute is `None`. Previously, Flask treated the mere presence of `__file__` as sufficient and attempted to normalize it as a filesystem path.
