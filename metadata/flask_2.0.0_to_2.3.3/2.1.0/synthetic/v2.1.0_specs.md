# Upgrade Specification from 2.0.3 to 2.1.0

## New Features

### Task 1 Support async callables in copy_current_request_context
Ensure that functions decorated with `copy_current_request_context` work for both synchronous and asynchronous callables, preserving access to the current request context and returning normal application results when invoked.

- **Expectation**: Applications should be able to use `copy_current_request_context` with async helpers the same way they use it with sync helpers. Calling the decorated function should execute it under the captured request context and produce the expected application value, regardless of whether the original function is synchronous or asynchronous.

- **Constraints**: The upgrade must add async compatibility without breaking current synchronous usage or changing how developers apply and call the decorator.


### Task 2 Add reloader exclude patterns to flask run
Ensure that `flask run` allows developers to provide file-pattern exclusions for the development reloader so changes to matching files do not restart the local server.

- **Expectation**: Users starting the Flask development server should be able to declare ignore patterns for auto-reload. File changes that match those patterns should be skipped by the reloader, while ordinary watched files should still trigger reloads as usual.

- **Constraints**: This addition should extend the development server configuration without altering existing startup options or default behavior. Ignoring files must be narrowly scoped to the patterns the user explicitly provides.


### Task 3 Add prefixed environment config loading
Ensure that applications can load configuration from environment variables that use a dedicated prefix, with automatic structured value parsing and support for nested configuration keys.

- **Expectation**: Applications should be able to initialize configuration directly from namespaced environment variables instead of only from files or manual string handling. Matching values should load as structured data when possible, nested settings should be expressible through the variable name, and malformed structured input should degrade to plain strings instead of breaking configuration loading.

- **Constraints**: The feature should be isolated to an explicit environment-variable namespace, avoid surprising failures on ordinary string values, and preserve unrelated configuration state while applying only the settings that were explicitly provided through the chosen prefix.


## Bug Fixes

### Task 4 Restore Flask CLI plugin discovery without setuptools
Ensure that the Flask CLI continues to discover and expose plugin-provided subcommands during upgrade to 2.1.0 even when setuptools or pkg_resources is not installed, while keeping plugin command registration behavior consistent across supported Python versions.

- **Expectation**: Users upgrading to Flask 2.1.0 should still see third-party CLI extension commands available in the `flask` command, including in stripped-down environments that do not bundle setuptools. The upgrade should preserve normal plugin command discovery behavior across supported Python versions.

- **Constraints**: The upgrade should change the dependency contract behind command discovery without changing how users register or invoke Flask CLI plugins. Existing working plugin commands should continue to behave the same, and environments that previously lost plugin commands due to missing setuptools should now work.


### Task 5 Preserve Custom FlaskClient Redirect Handling
Ensure that a custom `FlaskClient` subclass can override `open` to apply request defaults while `follow_redirects=True` continues to work without errors, including across internally generated redirect requests.

- **Expectation**: Custom test clients should be able to centralize request customization in `open` without breaking redirect-following behavior. Redirected requests should behave like normal client requests and preserve the client's default request environment and context handling.

- **Constraints**: Existing ways of issuing test-client requests should keep working. The fix should remove the redirect failure without changing the expected request API or forcing users to rewrite custom client subclasses.


### Task 6 Preserve Click context across Flask debug reloads
Ensure that applications started through `flask run` keep the active CLI Click context available during lazy-loaded debug reloads so app-factory logic can continue reading command-scoped state after the reloader restarts.

- **Expectation**: Starting an app from the Flask CLI should behave consistently before and after an automatic debug reload. If application startup reads CLI context or values attached to it, those values should still be available after the process reloads.

- **Constraints**: The upgrade should restore lost CLI state during reloads without changing how applications start in normal cases or forcing a different integration pattern.


### Task 7 Preserve HttpOnly When Clearing Session Cookies
Ensure that clearing a modified Flask session that becomes empty deletes the session cookie with the configured HttpOnly protection still applied.

- **Expectation**: When an application clears its session, the browser should receive a deletion cookie that keeps the same HttpOnly security contract as the configured session cookie instead of dropping that protection during removal.

- **Constraints**: The fix should be limited to preserving security metadata when removing a session cookie and should not otherwise alter when session cookies are created, skipped, or removed.


## Dependency Updates

### Task 8 Require Click 8 for Flask CLI
Ensure that upgrading to Flask 2.1.0 requires a Click 8.x-compatible CLI environment so Flask command-line usage works without legacy compatibility warnings or fallback behavior.

- **Expectation**: After the upgrade, the command-line interface should only run in supported dependency environments and should behave according to the current supported Click runtime rather than maintaining backward-compatibility behavior for an older deprecated Click release.

- **Constraints**: The upgrade should establish a clear supported CLI baseline instead of silently accommodating outdated dependencies. Users on unsupported dependency versions should be required to upgrade rather than relying on deprecated behavior.


### Task 9 Extend deprecated Flask file-send parameter compatibility to 2.2
Ensure that upgrading to Flask 2.1.0 preserves compatibility for applications still using the old `send_file` and `send_from_directory` parameter names introduced before Flask 2.0, while continuing to signal that these names are deprecated and scheduled for removal in a later release.

- **Expectation**: Applications upgrading to Flask 2.1.0 should still work if they have not yet migrated to the renamed file-serving arguments, but the framework should clearly warn that the old argument names are transitional and will be removed in a future release.

- **Constraints**: The upgrade should preserve existing file-serving behavior and only relax the migration deadline. Backward compatibility should be temporary, not a reversal of the deprecation.


### Task 10 Deprecate RequestContext.g access
Ensure that applications upgrading to Flask 2.1.0 no longer rely on `RequestContext.g` as a supported way to read or replace request-scoped global state, while preserving the existing `g` behavior during the deprecation period.

- **Expectation**: The upgrade should preserve observable `g` state behavior for compatibility, but request-context access to that state must be treated as deprecated. Users should move to the supported `g` access paths and see a clear runtime deprecation signal if older request-context access is still used.

- **Constraints**: The upgrade must not break current `g`-based behavior in this release, but it must clearly mark the request-context property as a temporary compatibility path rather than a supported long-term API.


## Breaking Changes

### Task 11 Raise the supported runtime baseline to Python 3.7+ and align async and JSON behavior with that baseline
Ensure that upgrading to 2.1.0 treats Python 3.6 as unsupported, assumes Python 3.7+ standard-library capabilities for JSON serialization, and runs async features only within the supported greenlet or PyPy runtime matrix.

- **Expectation**: After the upgrade, the library should target modern Python only. Dataclass-aware JSON behavior should be available as standard behavior on supported runtimes, and async features should work when the environment meets the supported async and greenlet requirements instead of depending on legacy compatibility shims.

- **Constraints**: The upgrade must narrow the supported runtime matrix without changing the intended public behavior on supported environments. It should remove obsolete backward-compatibility handling while preserving normal JSON and async behavior for users on supported platforms.


### Task 12 Remove reliance on Flask 2.0 deprecated APIs deleted in 2.1
Ensure that the application and its supporting code are compatible with Flask 2.1.0 by removing reliance on deprecated APIs that were deleted, by making CLI app factories callable without implicit Flask-provided script context unless explicit factory arguments are supplied, and by preventing duplicate blueprint-name registration behavior that now fails instead of warning.

- **Expectation**: The upgrade should preserve normal application behavior on Flask 2.1 while removing dependencies on APIs and compatibility shims that were only kept for older code. App loading, configuration loading, JSON handling, helper imports, blueprint registration, and client-side request inspection should all work through the supported 2.1 interfaces and fail early if old deprecated entry points are still used.

- **Constraints**: Keep existing supported usage working, but remove dependence on compatibility-only behavior. The change should tighten invalid cases without breaking correctly named blueprint reuse or correctly declared app factories.


### Task 13 Preserve relative redirect Location headers by default
Ensure that after upgrading to Flask 2.1.0, redirect responses expose relative Location header values by default rather than automatically converting them into absolute URLs with scheme and domain.

- **Expectation**: Redirects should now point to relative destinations by default. Callers that inspect redirect responses should see the same path the app intended to redirect to, without Flask adding the current scheme and host.

- **Constraints**: The upgrade should only change how redirect destinations are represented, not whether a redirect happens or where it ultimately leads. Existing explicit absolute redirects should continue to behave as explicit absolute redirects.


## Typing Updates

### Task 14 Relax error handler typing for precise exception annotations
Ensure that Flask error handler registration supports handlers typed to the specific exception they handle, and allows the same handler function to be registered for multiple exceptions without type-checking conflicts.

- **Expectation**: Applications should be able to declare error handlers using precise exception annotations instead of falling back to a generic `Exception` parameter, and they should be able to reuse one handler across multiple error registrations without typing friction. This should improve editor and type-checker support while preserving existing runtime behavior.

- **Constraints**: The upgrade should broaden what is accepted by static typing, not change how error handlers behave in production. Existing error handler registration patterns and response behavior must remain compatible.


### Task 15 Align Flask context manager exit typing with ExitStack
Ensure that Flask context manager objects expose `__exit__` typing that allows normal context exits with no exception and can be used with standard context manager helpers such as `ExitStack` without type-checking incompatibilities.

- **Expectation**: Flask context managers should be typed the same way Python context managers actually behave: on a clean exit, no exception information is present, and standard context-manager utilities should recognize these objects as compatible.

- **Constraints**: This upgrade must improve type compatibility without altering how Flask contexts enter, clean up, or propagate exceptions at runtime.


## Additional Changes
- Ensure that upgrading to Flask 2.1.0 does not raise the debug-only `FormDataRoutingRedirect` assertion for routing redirects that use HTTP 307 or 308, since those status codes preserve the request method and body.
