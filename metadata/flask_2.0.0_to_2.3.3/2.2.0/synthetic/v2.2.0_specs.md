# Upgrade Specification from 2.1.3 to 2.2.0

## New Features

### Task 1 Adopt Flask 2.2 app-scoped helper and JSON provider customization
Ensure that a Flask 2.2 application can customize URL building, redirects, abort handling, and JSON behavior at the app level, and that the public Flask helpers consistently delegate to those app-scoped customization points while preserving documented fallback and deprecation behavior.

- **Expectation**: Applications should be able to override core helper behavior from the Flask app instance instead of relying on fixed global helper implementations. JSON handling should be centralized behind a per-application provider so serialization, deserialization, and JSON response generation all follow the active app's configured behavior consistently.

- **Constraints**: The new extension points must not remove default helper behavior when no application override is active. Error handling and fallback behavior should remain predictable, and deprecated JSON customization options should remain transitional compatibility features rather than required contracts for all JSON implementations.


### Task 2 Add reusable class-based view instances
Ensure that class-based views can opt out of per-request instantiation so expensive setup can run once per generated view, while preserving the existing default behavior and making the reuse semantics safe and explicit.

- **Expectation**: Class-based views should support an opt-in performance mode that reuses one view object across requests. By default, views should keep their current request-isolated lifecycle. Reused views must still handle routed parameters and HTTP method dispatch normally.

- **Constraints**: The optimization must be opt-in and non-breaking by default. Enabling reuse must not change route matching or supported HTTP methods, and it must not encourage cross-request leakage of request-local state.


### Task 3 Support nested FlaskGroup CLIs
Ensure that a `flask.cli.FlaskGroup` can be used as a subcommand inside a larger Click-based CLI while still loading the configured Flask application, exposing Flask and app-defined commands, and providing the expected Flask CLI runtime context.

- **Expectation**: A Flask application's CLI should behave the same whether it is the main command or a nested subcommand in a larger Click CLI: it should still find and create the app, expose the app's commands, respect normal Flask CLI environment configuration, and run nested commands with the active Flask application context available.

- **Constraints**: Add nesting support without changing the established behavior of the Flask CLI. Users should not need a separate standalone entry point, extra manual context setup, or different environment configuration to keep existing CLI workflows working.


### Task 4 Expose explicit Flask CLI app, debug, and env-file options
Ensure that the `flask` CLI lets users choose the application and debug mode directly from command-line options, and optionally load environment variables from a specific env file early enough for app discovery, help output, and command execution, without requiring environment-variable-only setup.

- **Expectation**: Users should be able to run Flask CLI commands by naming the app and debug mode directly on the command line, and they should be able to point the CLI at a specific env file when startup configuration lives outside the default environment. The CLI should resolve that configuration early enough that command help, app loading, and error reporting all reflect the chosen app and debug settings.

- **Constraints**: The new CLI flags should extend startup configuration without removing the old ways of configuring Flask. Explicit command-line choices should take precedence when provided, but the CLI should continue to behave like earlier versions when users rely on environment variables or default app discovery.


### Task 5 Support explicit dotenv files in the Flask CLI
Ensure that the `flask` CLI allows users to provide an explicit environment file to load at startup, so applications can be configured from a chosen dotenv file in addition to the default dotenv loading behavior.

- **Expectation**: Users should be able to launch Flask commands with a specific dotenv file and have those values available immediately during startup. The explicitly selected file should complement the usual dotenv sources, and unsupported usage should be rejected as an invalid CLI parameter.

- **Constraints**: The new CLI capability should be additive and non-breaking: existing startup flows must keep working, while explicit env-file loading is validated and applied predictably before the app begins loading.


### Task 6 Support direct streaming returns from view functions
Ensure that upgrading to Flask 2.2.0 enables first-class streaming responses by allowing view functions to return iterators or generators directly, while also exposing helper APIs for progressively rendering templates without requiring manual response wrapping.

- **Expectation**: Applications should be able to stream response content by returning a generator or iterator from a view, without having to manually construct a Response first. Template output should also be streamable through dedicated helper functions that preserve normal Flask rendering context.

- **Constraints**: The new streaming capability should extend existing response behavior rather than replace it. Non-streaming return types must keep working as before, and streamed responses should follow the same default HTTP behavior users already expect from Flask.


### Task 7 Add streaming template rendering helpers
Ensure that applications can render Jinja templates incrementally for streaming HTTP responses through supported Flask helper APIs, while preserving the same template context behavior developers expect from normal template rendering.

- **Expectation**: Developers should be able to choose between full template rendering and streaming template rendering using official Flask helpers. Streaming should emit the response piece by piece, preserve normal template context behavior, and keep request-bound data available until the streamed output finishes.

- **Constraints**: The upgrade must add incremental template rendering without regressing existing non-streaming rendering behavior. Streamed templates should behave like normal templating from the caller's perspective, except that output is produced lazily and remains safe to use in request-driven responses.


## Bug Fixes

### Task 8 Align error handler registration with Flask 2.2 validation behavior
Ensure that application error handler registration follows Flask 2.2.0 validation rules so invalid handler targets are rejected consistently and valid exception classes or recognized HTTP error codes continue to register normally.

- **Expectation**: The error-handler registration API should only accept valid exception classes or known HTTP error codes. Invalid inputs should be rejected deterministically with user-visible errors that reflect whether the caller passed an instance, an unsupported class, or an unknown status code.

- **Constraints**: This update should tighten input validation without regressing normal error handling. Existing valid handlers should behave the same after registration, and only unsupported registration inputs should change outcome.


### Task 9 Provide app context automatically for Flask CLI callbacks
Ensure that custom Flask CLI commands have an active application context for the full command lifecycle, including parameter callback evaluation, so application-scoped objects can be used without extra context decorators.

- **Expectation**: Invoking a Flask CLI command should make application-scoped state available consistently from argument parsing through command execution. Users should no longer need extra decorator boilerplate just to access app configuration, database-backed helpers, or other app-bound objects inside CLI callbacks.

- **Constraints**: The upgrade should remove unnecessary context setup for supported Flask CLI commands without breaking existing commands that already opt into explicit app-context handling. It should keep command execution tied to the same application instance and should not mask failures to load the application.


## Dependency Updates

### Task 10 Require Werkzeug 2.2.0 or newer
Ensure that upgrading to version 2.2.0 also upgrades the application's Werkzeug dependency to version 2.2.0 or newer so the library is installed and run only with the supported Werkzeug release line.

- **Expectation**: The 2.2.0 upgrade should move consumers onto a newer supported Werkzeug baseline. After upgrading, the package should only be used in environments that provide a compatible Werkzeug version from 2.2 onward.

- **Constraints**: Treat this as a dependency support-floor update only. The requirement should not imply any separate end-user feature beyond requiring a newer compatible Werkzeug version.


### Task 11 Migrate Flask context access to the 2.2 ContextVar model
Ensure that applications and extensions upgrading to Flask 2.2 no longer depend on `_app_ctx_stack.top` or `_request_ctx_stack.top` as the primary way to read or store per-context state, and instead use `g`, `current_app`, `request`, `session`, `app_ctx`, or `request_ctx` so request and application context behavior remains correct under the new context management model.

- **Expectation**: After upgrading, context-aware code should continue to work through Flask’s normal context proxies, but code that treats the old context stacks as stable public storage should be considered deprecated and migrated to the supported context APIs.

- **Constraints**: The upgrade should preserve existing request and application context behavior for supported APIs, while surfacing deprecations instead of silently breaking current-context access. Any migration away from the old stack objects must keep nested, copied, and streamed request flows behaving consistently.


### Task 12 Migrate deprecated Flask app config proxy attributes
Ensure that applications upgrading to Flask 2.2.0 stop depending on deprecated Flask app shortcut attributes and instead rely on the corresponding configuration entries, without changing observable session, file-serving, template reload, or exception propagation behavior.

- **Expectation**: Treat these Flask settings as configuration values rather than stable app attributes. Deprecated attribute access may still function during the 2.2 transition, but the application should behave the same while using the config-based interface that will continue to work in later releases.

- **Constraints**: The upgrade must not change user-visible request handling, caching behavior, cookie naming, or template reload behavior. Only the supported configuration surface is changing; the runtime contract should remain stable.


### Task 13 Adopt Flask 2.2 JSON provider customization
Ensure that the application remains compatible with Flask 2.2.0 by migrating JSON customization to the new provider-based API, preserving expected JSON serialization and parsing behavior, and handling deprecated JSON configuration and encoder or decoder hooks without breaking existing runtime behavior.

- **Expectation**: JSON behavior should be customizable through a single application-level provider object so that serialization, deserialization, JSON responses, and related framework features stay consistent. Existing legacy JSON settings should continue to work during upgrade, but the supported long-term contract is to configure JSON behavior through the provider rather than through legacy config flags or encoder and decoder hooks.

- **Constraints**: The upgrade should not silently change how normal JSON payloads are produced or parsed unless an application explicitly opts into different provider behavior. Compatibility with older JSON customization paths should remain transitional rather than breaking immediately, and custom provider implementations should only be expected to honor the core provider contract, not legacy default-provider-specific knobs.


### Task 14 Adopt Flask's app-level JSON provider interface
Ensure that upgrading to Flask 2.2.0 uses the new app-level JSON provider model for JSON customization, while preserving existing JSON serialization, deserialization, and `jsonify` behavior and treating older encoder, decoder, and JSON config hooks as deprecated compatibility paths.

- **Expectation**: Applications should be able to replace or extend Flask's JSON behavior from one app-level integration point, and all standard JSON entry points should honor that customization consistently. Existing applications should keep working during the upgrade, but older JSON customization mechanisms should clearly signal that they are transitional and should be migrated away from.

- **Constraints**: The upgrade should not silently change JSON payload semantics for applications staying on Flask's default JSON implementation. JSON customization should be consistent at the application level, backward compatibility should remain available during the transition, and deprecated settings should not be treated as the long-term contract.


### Task 15 Adopt Flask 2.2 JSON provider behavior
Ensure that applications upgrading from Flask 2.1.3 to 2.2.0 use the new app-level JSON provider contract for JSON serialization, deserialization, and JSON responses, while avoiding newly deprecated JSON helper and encoder or decoder customization APIs.

- **Expectation**: After the upgrade, JSON behavior should be configurable at the application level through a dedicated provider object. JSON serialization, parsing, and JSON response generation should consistently follow that provider so apps can replace or optimize JSON handling without relying on legacy encoder or decoder hooks. Deprecated HTML-safe JSON helper APIs should no longer be the supported integration point.

- **Constraints**: The change should not remove normal JSON response behavior for applications that do not customize JSON handling, and it should not require consumers to depend on internal implementation details. Custom JSON behavior should be centralized at the app level and remain compatible with standard request and response flows.


### Task 16 Adopt Flask 2.2 context preservation semantics
Ensure that upgrading to Flask 2.2 preserves `request`, `g`, and related context-local objects with the correct request-specific data in the interactive debugger and test client, while still running request teardown at the end of every request and cleaning up streamed contexts only when the streamed response is consumed or closed. Ensure that code relying on `Flask.propagate_exceptions` accounts for its deprecation.

- **Expectation**: After the upgrade, preserved request state should still be available in debugging and client-inspection flows, but request teardown should no longer be delayed just because that state remains inspectable. Streamed responses should keep their own context alive only until the stream is consumed or explicitly closed. Any use of the exception-propagation convenience accessor should be treated as deprecated.

- **Constraints**: The upgrade must avoid leaking request context or cleanup work across requests, must keep independently preserved contexts isolated from one another, and must not change exception propagation behavior except for surfacing deprecation on the legacy accessor.


### Task 17 Support direct JSON array responses from Flask view functions
Ensure that applications upgrading to Flask 2.2.0 can return JSON array payloads directly from view functions, with the same automatic JSON response handling previously available for dictionary return values, while preserving the existing tuple-based status and header shortcuts.

- **Expectation**: A Flask endpoint may return a plain Python list to produce a JSON array response, and this should behave consistently with the framework's existing automatic JSON handling for object-like payloads. Returning a list should no longer be treated as an invalid response, and combining that payload with normal status or header shortcuts should continue to work.

- **Constraints**: Existing valid response forms must keep their current behavior. The new support should add JSON array returns without changing the meaning of tuple response shortcuts or widening runtime acceptance beyond the response shapes the framework already documents.


## Breaking Changes

### Task 18 Update removed deprecated Flask file-serving and context APIs
Ensure that application code upgrading to Flask 2.2.0 no longer uses removed deprecated argument names in file-serving helpers and no longer depends on RequestContext.g as a proxy for application context state.

- **Expectation**: The upgrade should preserve normal file download, caching, and ETag behavior when using the current public API names, while treating the old deprecated names as unsupported. Request-scoped shared state should be accessed through the standard g object only, not through a request-context proxy.

- **Constraints**: Keep existing supported file-serving behavior unchanged for valid modern API usage. The change should only remove deprecated compatibility paths and require callers to use the current supported interfaces.


### Task 19 Deprecate FLASK_ENV and app.env in favor of explicit debug control
Ensure that application debug behavior is controlled explicitly rather than by environment naming, and that legacy FLASK_ENV or app.env usage is treated as deprecated compatibility behavior with clear migration signals.

- **Expectation**: The upgrade should remove the idea that selecting an application environment is how users turn on development behavior. Users should enable debug mode directly, while any continued use of older environment-based switches should still work temporarily but clearly warn that they are deprecated and will be removed.

- **Constraints**: The migration must preserve current ways to explicitly enable or disable debug mode, keep older environment-based usage temporarily compatible, and avoid overriding separate template reload settings that were intentionally configured by the user.


### Task 20 Enforce setup before first request or blueprint registration
Ensure that all application and blueprint routes, handlers, template helpers, and other setup-time registrations are completed before the app serves its first request or a blueprint is registered, and stop relying on deprecated blueprint first-request setup behavior.

- **Expectation**: After upgrading, application configuration is only valid during startup, not after requests begin. Blueprint configuration is only valid before registration; if code tries to mutate a blueprint later, Flask should warn immediately that the change is too late and may not apply consistently. Blueprint-specific first-request setup should be considered deprecated and avoided.

- **Constraints**: Do not regress valid startup configuration flows. Only setup attempted too late in the lifecycle should be rejected or warned, and already-established application or blueprint behavior should remain stable instead of changing unpredictably.


### Task 21 Migrate away from deprecated first-request setup hooks
Ensure that application and blueprint initialization no longer depends on first-request hooks, and that setup logic runs during application creation or blueprint registration instead of waiting for the first incoming request.

- **Expectation**: Applications upgrading to 2.2 should stop using first-request decorators for setup. Initialization should happen when the app is created, and blueprint-specific setup should happen when the blueprint is registered. Deprecated hooks may still work temporarily, but they should no longer be the supported way to initialize application state.

- **Constraints**: The upgrade should preserve legacy behavior only long enough to support migration, without allowing setup to remain request-triggered as the recommended pattern. Existing apps should continue to behave consistently while being guided toward setup-time initialization.


### Task 22 Adopt timezone-aware session expiration timestamps
Ensure that permanent session expiration values are exposed as timezone-aware UTC datetimes instead of naive UTC datetimes, while preserving the same expiration timing semantics and continuing to report no expiration for non-permanent sessions.

- **Expectation**: After upgrading, permanent-session expiration timestamps should carry explicit UTC timezone information rather than being timezone-naive. The expiration deadline itself should remain the same logical UTC-based moment, and sessions without permanence should continue to have no expiration timestamp.

- **Constraints**: The upgrade should change timezone metadata, not the intended lifespan of a permanent session. Existing session expiration behavior should remain stable except that the exposed timestamp is now explicitly UTC-aware.


### Task 23 Remove flask run eager/lazy loading toggle and standardize app loading
Ensure that `flask run` no longer exposes a lazy-versus-eager loading toggle. Ensure that the first application load happens immediately when the command starts so startup failures are reported at launch time. Ensure that reloads still recover from application import or factory errors without terminating the reloader. Ensure that invoking `app.run()` from code while the app is already being run through the Flask CLI does not start a second blocking server.

- **Expectation**: Users should no longer choose between eager and lazy loading for `flask run`; the command should behave consistently by loading the app up front on startup. Startup errors should appear as soon as the command is run. During automatic reloads, load errors should still be surfaced immediately without killing the reloader, so fixing the code and saving should allow the app to recover. If application code calls `app.run()` while the Flask CLI is already managing the server, Flask should ignore that nested server start rather than blocking or creating duplicate servers.

- **Constraints**: Do not leave multiple supported startup modes for the development server. Keep immediate failure reporting for normal startup, but keep reload resilience for edit-and-refresh workflows. Avoid breaking direct programmatic server startup outside the CLI-managed case.


## Typing Updates

### Task 24 Broaden Flask view return type annotations
Ensure that Flask view functions can declare runtime-supported response return types, including TypedDict-based JSON objects, without being rejected by the framework's public typing contract after upgrading from 2.1.3.

- **Expectation**: Applications should be able to use precise type annotations for valid Flask responses, including structured JSON objects and streamed content, without having to widen those annotations just to satisfy static type checking.

- **Constraints**: Keep current response behavior intact while making the declared type surface accurately reflect supported response forms. Previously valid annotations must continue to work.

- Ensure that the startup banner shown by `flask run` consistently warns users that the built-in server is only for development use, regardless of environment mode. Ensure that obsolete banner details tied to environment reporting and lazy-loading state are no longer displayed.
