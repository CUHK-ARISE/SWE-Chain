# Upgrade Specification from 2.2.5 to 2.3.0

## New Features

### Task 1 Support async Flask signal subscribers
Ensure that built-in Flask signals support asynchronous subscriber functions across request, app-context, template-rendering, flashing, teardown, and exception events without changing the user-visible event payloads exposed by those signals.

- **Expectation**: Applications should be able to register either synchronous or asynchronous handlers for Flask lifecycle signals and have both kinds of handlers run correctly when those events occur, without losing the data normally delivered with those signals.

- **Constraints**: The upgrade should add async compatibility to Flask signals without changing what those signals mean or breaking existing synchronous integrations.


### Task 2 Support binary loaders in Config.from_file
Ensure that `Config.from_file()` can load configuration data with parsers that require a binary-readable file object, while continuing to support existing text-based loaders and the current silent missing-file behavior.

- **Expectation**: Applications should be able to load configuration files through `Config.from_file()` regardless of whether the selected parser expects text input or binary input. By default nothing should change for current JSON-style usage, and binary-only formats such as TOML should work through the same API when requested.

- **Constraints**: The new capability must be additive. Existing configuration loading flows should keep working as before, error handling should remain consistent with prior behavior, and the method should still report success or failure the same way.


### Task 3 Expose route host and subdomain details in flask routes
Ensure that the `flask routes` command shows which host or subdomain each registered route belongs to when domain-based routing is configured, and allow the route list to be sorted by that domain information.

- **Expectation**: Route inspection should make domain-based routing visible. When an application uses subdomains or explicit hosts, the CLI route listing should show that association directly and let users order the list by domain, while preserving the existing route summary and method-filtering behavior.

- **Constraints**: The enhancement must be additive: apps that do not use domain-based routing should continue to see the familiar route listing, and mixed route sets should remain readable even if some entries do not specify a host or subdomain.


## Bug Fixes

### Task 4 Respect subdomains for nested blueprints
Ensure that nested blueprints remain reachable when a parent blueprint is mounted on a subdomain, and that child blueprints with their own subdomain are registered under the correct combined host rather than being ignored or exposed on the wrong host.

- **Expectation**: Applications using nested blueprints should get consistent subdomain behavior: child routes inherit the parent blueprint's subdomain when appropriate, and nested subdomains stack in the expected order so URLs resolve on the intended host.

- **Constraints**: The fix should be limited to correcting nested subdomain resolution without changing unrelated routing behavior, and it should avoid making routes available on hosts where they should not exist.


## Dependency Updates

### Task 5 Raise dependency minimums and align Flask test client cookie handling with Werkzeug 2.3
Ensure that upgrading to 2.3.0 requires Werkzeug 2.3.0 or newer, Jinja2 newer than 3.1.2, itsdangerous 2.1.2 or newer, and click 8.1.3 or newer, and ensure that Flask's test client continues to persist response cookies correctly under the supported Werkzeug 2.3 API.

- **Expectation**: The 2.3.0 release should only support the newer dependency baseline and should keep the test client behaving consistently for applications that rely on cookies or sessions. After a response sets cookies, subsequent client requests should observe those cookies under the supported Werkzeug versions.

- **Constraints**: The upgrade should narrow support to the new dependency floor without changing the expected cookie and session behavior that users see from the client. Applications on supported versions should not lose previously working cookie persistence across requests.


### Task 6 Deprecate Flask namespace exports for MarkupSafe helpers
Ensure that upgrading to Flask 2.3 keeps legacy `flask` namespace access for `escape` and `Markup` working temporarily, while clearly marking those imports as deprecated and preserving consistent deprecation behavior for related legacy attributes.

- **Expectation**: Applications should continue to run after the upgrade if they still use older Flask namespace imports, but the runtime should make it clear that these are transitional compatibility paths and that consumers should move to the new import locations before the next removal window.

- **Constraints**: Existing applications should receive compatibility-first behavior during the upgrade: same functional results for legacy access, explicit warnings about deprecation, and no sudden disappearance of supported compatibility shims in the 2.3 line.


### Task 7 Deprecate locked_cached_property
Ensure that application code no longer depends on `locked_cached_property` as a supported long-term API, while preserving correct cached-property behavior for properties that still need synchronization.

- **Expectation**: The upgrade should keep existing cached property access working in the short term while clearly signaling that the old locking decorator is deprecated. Applications should transition to standard cached-property behavior and perform synchronization explicitly inside the property computation when needed.

- **Constraints**: This upgrade should warn about deprecated usage without immediately breaking working code. Existing behavior should continue for this release, but code should no longer rely on the deprecated decorator as a future-safe API.


### Task 8 Require Blinker for Always-Available Flask Signals
Ensure that upgrading from Flask 2.2.5 to 2.3.0 treats framework signals as always available by requiring a compatible Blinker installation, and stop relying on `signals_available` to decide whether signal features can be used.

- **Expectation**: After upgrading, applications should be able to use Flask signals without conditional setup for optional signal support. Older availability checks may still run for compatibility, but they should only warn that the check is obsolete and should no longer influence behavior.

- **Constraints**: The upgrade should remove uncertainty around whether signals work, while avoiding an immediate hard break for existing code that still reads the old availability flag.


## Breaking Changes

### Task 9 Drop Python 3.7 support in Flask 2.3.0
Ensure that upgrading from Flask 2.2.5 to 2.3.0 is treated as a supported-runtime boundary change: applications must run on Python 3.8 or newer, and async callable handling should follow the supported interpreter's native behavior instead of relying on Flask's legacy Python 3.7 compatibility path.

- **Expectation**: After the upgrade, the library should only be expected to run on currently supported Python versions, and async-related behavior should match the standard behavior of those runtimes rather than preserving special handling for Python 3.7.

- **Constraints**: This is a support-policy and runtime-semantics change, not a new feature workflow. Existing behavior on supported Python versions should remain stable except where the library now intentionally follows the interpreter's native async detection rules.


### Task 10 Adapt application code to Flask 2.3 removed deprecated APIs
Ensure that the application and any Flask extensions remain compatible with Flask 2.3.0 by eliminating reliance on deprecated APIs that were removed, preserving equivalent runtime behavior through supported configuration and JSON provider interfaces, and preventing blueprint setup from occurring after registration.

- **Expectation**: After upgrading to Flask 2.3, one-time initialization must happen during application setup rather than on the first request, debug and environment behavior must no longer depend on old environment aliases, and JSON behavior must come from the active JSON provider rather than deprecated compatibility hooks. Blueprint definitions must be fully configured before registration because late mutation is now a hard error.

- **Constraints**: Preserve existing production behavior through the supported public APIs, keep transitional read-only context access that still exists, and only break code paths that depend on APIs explicitly removed in Flask 2.3 or on mutating a blueprint after it has already been registered.


### Task 11 Adapt to Flask 2.3 first-request and blueprint setup changes
Ensure that applications upgrading to Flask 2.3.0 do not rely on `app.got_first_request` as a supported runtime check and do not call blueprint setup methods after a blueprint has already been registered.

- **Expectation**: After upgrading, the application should continue to behave correctly without depending on deprecated first-request introspection, and any blueprint configuration that must happen during setup should be completed before registration because late blueprint setup is no longer tolerated.

- **Constraints**: The upgrade should keep normal request handling and valid startup configuration behavior unchanged, while surfacing deprecated or too-late configuration patterns as explicit upgrade issues instead of silently accepting them.


### Task 12 Adopt pyproject-based packaging metadata
Ensure that upgrading to Flask 2.3.0 supports modern pyproject-based packaging for the library and bundled examples, and that users can build or install from source without depending on legacy setup.py commands.

- **Expectation**: Upgrading users should interact with Flask through modern Python packaging workflows. Building or installing the library from source, including optional extras and bundled examples, should continue to work without relying on legacy setup scripts.

- **Constraints**: Preserve existing install capabilities while modernizing the packaging metadata. The upgrade should change packaging expectations, not the library's runtime behavior.


### Task 13 Enforce valid blueprint names and forbid late blueprint setup
Ensure that Flask blueprints cannot be created with an empty name, and ensure that blueprint setup is finalized before first registration so late setup calls fail instead of being allowed with only a warning.

- **Expectation**: Blueprint definitions must be valid at construction time and stable once registered. Unnamed blueprints should be rejected immediately, and any attempt to mutate blueprint setup after first registration should fail fast with an exception instead of continuing with a warning.

- **Constraints**: Normal blueprint creation and setup should keep working for valid inputs. The change should only block invalid blueprint identities and unsafe post-registration modifications, without altering the expected workflow before registration.


### Task 14 Make session cookies host-only unless explicitly shared
Ensure that session cookies are restricted to the exact host by default and are only shared across subdomains when `SESSION_COOKIE_DOMAIN` is explicitly configured. Ensure that applications upgrading from Flask 2.2.5 no longer rely on `SERVER_NAME` to populate the session cookie domain, no longer expect legacy localhost or IP cookie-domain warnings, and treat `flask.helpers.is_ip` as deprecated.

- **Expectation**: Flask sessions should stay bound to the exact host that set them unless the application explicitly opts into broader cookie scope with `SESSION_COOKIE_DOMAIN`. Upgrading applications should not receive the old cookie-domain warnings for localhost or IP-based hosts, and any continued use of `flask.helpers.is_ip` should be treated as deprecated.

- **Constraints**: Explicit cookie-domain configuration must keep working, while the default behavior becomes safer and narrower in scope. The change should affect cookie domain semantics only, without changing unrelated session cookie behavior.


### Task 15 Adapt Flask integrations to 2.3.0 removed APIs and stricter defaults
Ensure that applications and extensions upgrading from Flask 2.2.5 to 2.3.0 remain compatible without relying on removed 2.2-era deprecations, and continue to behave correctly under the new blueprint validation, JSON configuration, signal dispatch, and session cookie domain rules.

- **Expectation**: After upgrading to Flask 2.3.0, annotation changes should not alter normal app behavior, but deprecated compatibility shims from 2.2 should be treated as removed. Applications should configure JSON behavior, send-file caching, and X-Sendfile through the current configuration and JSON provider interfaces; blueprint definitions must be valid before registration and cannot be mutated after registration; session cookies should only receive a domain when one is explicitly configured; and signal integrations should assume real Blinker-backed signal delivery.

- **Constraints**: The migration must keep externally visible app behavior stable for supported configurations, while eliminating dependence on legacy fallbacks and warning-based compatibility paths that no longer exist in 2.3.0.


## Performance Improvements

### Task 16 Remove Lock Contention From Cached Flask Properties
Ensure that lazily initialized Flask and Blueprint properties remain cached while no longer causing concurrent requests to briefly block each other when those properties are accessed.

- **Expectation**: Applications upgrading to 2.3.0 should still see the same lazily created app and template-related objects, but repeated access to those properties should no longer introduce brief cross-request blocking under concurrency.

- **Constraints**: Keep the same outward-facing app and blueprint behavior while improving concurrency characteristics. The update must not alter what these properties represent or require callers to use a different API.


## Additional Changes
- Ensure that Flask only adds `Vary: Cookie` to a response when the request handler actually accessed the session data. Responses that merely cause the session cookie to be written, refreshed, or deleted without reading session contents should no longer automatically advertise variation on the `Cookie` request header.
