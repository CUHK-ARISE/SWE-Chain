# Upgrade Specification from 2.3.2 to 2.3.3

## Bug Fixes

### Task 1 Restore Flask compatibility with Python 3.12
Ensure that Flask remains compatible with Python 3.12 by continuing to resolve application and package root paths correctly, reporting installed Flask and Werkzeug versions through the CLI, and providing Werkzeug-version-based defaults in the Flask test client without relying on removed or legacy Python import/version mechanisms.

- **Expectation**: Upgrading to 2.3.3 should let Flask applications and tools behave normally on Python 3.12. Version output, app/package location detection, and default client metadata should continue to work based on the installed packages rather than older Python or dependency internals.

- **Constraints**: The compatibility fix must preserve existing app discovery behavior across supported import styles, degrade safely when package metadata is unavailable, and avoid overriding values the user has already set.


### Task 2 Restore Flask path auto-discovery for direct script apps
Ensure that Flask applications created with `Flask(__name__)` continue to determine their root and instance paths correctly when run directly as scripts, including `app.run()` entrypoints, and that config path APIs accept standard filesystem path objects as well as strings.

- **Expectation**: Running an app directly from a Python script should not break Flask's automatic root or instance path detection. If package metadata cannot be resolved for the app import name, Flask should choose a sensible local path and continue starting normally, while still locating installed and namespace-based apps correctly. Config-related path arguments should work with standard path objects as well as strings.

- **Constraints**: Keep automatic path detection stable for supported app layouts, and prefer safe fallback behavior over startup errors when import metadata is unavailable. Broaden path input compatibility without changing expected config-loading behavior.


## Additional Changes
- Ensure that upgrading to version 2.3.3 uses a supported Werkzeug version by requiring Werkzeug 2.3.7 or newer and no longer treating older Werkzeug releases as compatible.
- Ensure that the library's source distribution and build metadata use flit_core instead of setuptools as the build backend, so consumers can build or install the package through standard Python packaging workflows without relying on setuptools-specific backend behavior.
