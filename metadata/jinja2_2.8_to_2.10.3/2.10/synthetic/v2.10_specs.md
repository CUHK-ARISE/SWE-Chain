# Upgrade Specification from 2.9.6 to 2.10

## New Features

### Task 1 Add OverlayScope support for extension-defined overlay contexts
Ensure that extensions can create an overlay scope that injects arbitrary variables for a section of template output while preserving lookup of variables from the surrounding derived context.

- **Expectation**: Extension authors should be able to wrap part of a template in a special scope backed by a dynamic mapping. Inside that scope, template code should see the injected variables first, while still being able to access other variables that were already available outside the scope, including inside nested scoped constructs.

- **Constraints**: The new scope must accept mapping-like overlay data, allow dynamic names without relying on compile-time declarations, and avoid changing normal rendering behavior for templates that do not use the feature.


### Task 2 Add builtin membership and comparison template tests
Ensure that templates can perform membership checks through a builtin `in` test and can rely on builtin comparison tests being available through standard operator-style aliases when upgrading to 2.10.

- **Expectation**: After the upgrade, template authors should be able to express membership checks directly with a builtin `in` test and use standard equality and ordering test names interchangeably. These tests should behave predictably for normal rendering and for expressions composed entirely of constant values.

- **Constraints**: Do not change the meaning of membership or comparison checks beyond aligning them with normal template and Python expectations. Equivalent test names should stay interchangeable, and unsupported or non-resolvable cases should fail in the existing safe way rather than silently changing meaning.


### Task 3 Add adjacent-item access in loop contexts
Ensure that loop contexts expose adjacent items during iteration so templates can read the previous and next element from the current loop. Ensure that boundary cases behave safely by returning an undefined value when no previous or next element exists. Ensure that this behavior is consistent for standard loops, recursive loops, and asynchronous loops.

- **Expectation**: Templates should be able to look one item backward or forward within a loop by reading `loop.previtem` and `loop.nextitem`. These properties should behave predictably at the start and end of the loop by appearing undefined instead of failing, and they should work the same way regardless of whether the loop is normal, recursive, or async.

- **Constraints**: Adding adjacent-item access must not alter how loops iterate today. Existing loop ordering and nesting behavior should stay intact, and neighbor lookups should stay local to the current loop level while treating missing neighbors as ordinary undefined values.


### Task 4 Add loop.changed value-change detection
Ensure that template loop contexts provide a built-in way to detect whether one or more observed values have changed since the previous `loop.changed(...)` check, so templates can react to group boundaries or repeated values without manual bookkeeping.

- **Expectation**: Templates should be able to ask the loop whether the currently observed value set is different from the last observed value set, and receive a simple true/false answer that can drive rendering decisions.

- **Constraints**: This should work as a self-contained loop helper that does not alter normal loop semantics or require users to manually store previous values.


### Task 5 Support namespace state and filtered block set assignments
Ensure that templates can create mutable namespace state, assign to namespace attributes with the `set` tag so values can survive inner scopes such as loops and macros, and apply filters to block-captured `set` content before the result is stored.

- **Expectation**: Template authors should be able to keep mutable state in a dedicated namespace object, update it from nested scopes, and read the final attributes later in the template. Block `set` assignments should support filter pipelines on captured content, and invalid dotted assignment on ordinary values should fail clearly at runtime.

- **Constraints**: The feature should add safe mutable cross-scope state without changing normal attribute lookup semantics, and existing templates should behave the same unless they opt into namespace assignment or filtered block capture.


### Task 6 Add whitespace trimming controls for trans blocks
Ensure that `{% trans %}` blocks support an opt-in whitespace-trimming mode, and that applications can enable that behavior by default across translation blocks while preserving a way to keep original whitespace for specific blocks.

- **Expectation**: Users should be able to write multi-line translation blocks without leaking template indentation and line breaks into translated message strings. They should be able to turn this on for one block or configure it as the default for all translation blocks, while retaining an explicit opt-out for blocks that need exact whitespace.

- **Constraints**: The upgrade must improve whitespace handling for translation content without changing unrelated translation semantics. Existing templates should continue to behave the same unless trimming is explicitly requested or globally enabled, and explicit block-level intent should override the default.


### Task 7 Add a unique filter and align sequence comparison behavior
Ensure that templates can remove duplicate items with a `unique` filter while preserving the first occurrence of each item, and ensure that sequence comparison filters apply consistent attribute-aware and case-handling semantics across `unique`, `sort`, `min`, and `max`.

- **Expectation**: Template authors should be able to deduplicate lists directly in templates, including lists of objects, without losing the original order of the first matching entries. Sequence filters that compare values should behave consistently: they should optionally compare object attributes, treat string case insensitively by default unless requested otherwise, and handle empty input without crashing.

- **Constraints**: The upgrade should add deduplication and comparison flexibility without changing the basic shape of existing template pipelines. It must preserve stable ordering, avoid surprising case transformations on non-string data, and degrade safely on empty sequences.


### Task 8 Add built-in min and max template filters
Ensure that upgrading to Jinja 2.10 exposes built-in `min` and `max` template filters for sequences, and that these filters behave consistently for strings and object collections without requiring application-defined replacements.

- **Expectation**: Templates should be able to ask for the smallest or largest item directly with `min` and `max`. These filters should work predictably for plain values and collections of objects, compare strings case-insensitively unless explicitly told otherwise, and fail gracefully on empty input.

- **Constraints**: The new filters should fit the library's existing template behavior: they should select from the input data itself, honor the same attribute-selection rules users already expect, and avoid introducing surprising case-ordering changes unless requested.


### Task 9 Support comparison operator tests by alias and symbol
Ensure that templates can use comparison operator tests through both symbolic and short-name forms, and that these test names behave consistently anywhere Jinja resolves tests, without breaking existing long-form aliases.

- **Expectation**: Users upgrading to 2.10 should be able to write Jinja tests with familiar comparison operator names or symbols, and those forms should work the same way in normal template conditions and in filter-based selection. Existing comparison test names must keep working, and membership checks through a test-style `in` form should be available.

- **Constraints**: The upgrade must be additive: new comparison spellings should expand what template authors can write, not alter how previous templates behave. Equivalent comparison forms should stay semantically aligned, and invalid test usage should still surface as an error instead of producing misleading results.


### Task 10 Add reverse ordering support to the dictsort filter
Ensure that the `dictsort` filter can return dictionary items in descending order when requested, while preserving its existing ascending default, key-or-value sort selection, case-sensitivity behavior, and invalid sort-mode handling.

- **Expectation**: Templates should be able to ask `dictsort` for either ascending or descending dictionary item order without changing how the filter otherwise works. Users should still be able to choose whether sorting is based on keys or values, and unsupported sort modes should remain explicit errors.

- **Constraints**: Adding descending sorting must not regress existing ascending behavior, alter established case-sensitivity semantics, or broaden accepted sort-mode inputs beyond the documented choices.


### Task 11 Add opt-in native Python type rendering
Ensure that applications upgrading to 2.10 can opt into a template environment that preserves native Python result types during rendering instead of always returning text, so templated values such as numbers, booleans, containers, `None`, and other Python objects can remain usable as native values when the rendered output represents them.

- **Expectation**: The upgrade should introduce an explicit native-rendering mode for Jinja templates. In that mode, rendering should preserve real Python value types whenever the template output naturally represents a single value or a parseable Python literal, while still falling back to a string for outputs that are genuinely textual.

- **Constraints**: Existing text-based template rendering should remain unchanged unless the application explicitly selects the new native mode. Native conversion should be best-effort and safe: preserve normal rendering semantics, keep failures attributable to template evaluation, and treat non-native-looking output as plain text.


### Task 12 Support filtered block set assignments
Ensure that block-form `set` assignments can apply standard Jinja filters to captured content before storing the result, while preserving normal escaping behavior and supporting namespace-qualified `set` targets.

- **Expectation**: Users upgrading to 2.10 should be able to write a block `set` that transforms its captured content with normal Jinja filters before the value is stored. The resulting assigned value should behave like normal rendered template content with respect to escaping, and namespace-style `set` targets should be accepted where `set` assignments are supported.

- **Constraints**: Templates that do not use this new syntax should continue to behave the same. The new capability should only add filtered block assignment behavior and broader supported target syntax without introducing escaping regressions.


## Bug Fixes

### Task 13 Preserve runtime randomness for the Jinja random filter
Ensure that templates using the `random` filter produce a fresh random selection each time they are rendered, rather than reusing a value that was fixed when the template was compiled.

- **Expectation**: Templates that use `|random` should behave as dynamic content. Re-rendering the same compiled template should be able to return different items from the same input, while empty inputs should still behave like an undefined value instead of causing a crash.

- **Constraints**: The upgrade should be narrowly scoped to restoring true runtime randomness and keeping existing error semantics for empty inputs. Users should not need to rewrite templates that already use `|random`.


### Task 14 Mark `tojson` output as safe markup
Ensure that the `tojson` filter produces JSON that is treated as safe template output, so embedding serialized data in autoescaped templates preserves valid JSON syntax while remaining safe for HTML contexts.

- **Expectation**: Serialized JSON produced by `tojson` should behave as already-safe template content. Users should be able to embed JSON in autoescaped templates without the serializer output being transformed into HTML-escaped text, and without losing the safety protections needed for HTML embedding.

- **Constraints**: The upgrade should only change how `tojson` is treated by template escaping, not what data gets serialized or how custom JSON serialization behavior is selected. Safety protections for HTML embedding must remain in place.


### Task 15 Prevent traceback debug locals from mutating Jinja template context
Ensure that retrieving traceback debug locals in Jinja does not modify the active template context while still exposing the current template variables for debugging.

- **Expectation**: Debugging a template failure should never change the template's own variable state. The locals shown for a traceback should reflect the template context at the moment of failure, but they must be detached from the live context so inspection remains side-effect free.

- **Constraints**: Keep traceback debugging behavior compatible for callers while removing unintended side effects. Debug information should still be available, and absence of template context should continue to be handled safely.


### Task 16 Support large Jinja elif chains without compilation failure
Ensure that templates containing large numbers of `{% elif %}` branches compile and render successfully without failing due to generated indentation depth, while preserving the normal ordered behavior of `if` / `elif` / `else` branch evaluation.

- **Expectation**: A template author should be able to write long `if` / `elif` chains without hitting an internal compiler limit. The engine should treat each `elif` as part of the same decision chain, choose the first matching branch in order, and fall back to `else` only when nothing matches.

- **Constraints**: The fix should remove the failure mode for deep conditional chains without changing which content renders for existing templates or altering how ordinary `if` / `else` blocks behave.


## Breaking Changes

### Task 17 Reject malformed from-import template syntax
Ensure that malformed `{% from ... import ... %}` statements are rejected consistently. Ensure that the import list always contains valid imported names, and that empty imports, trailing commas, repeated commas, or comma-separated gaps no longer compile silently.

- **Expectation**: Users should only be able to import explicitly named symbols in `{% from ... import ... %}` statements. If the import clause is incomplete or contains stray commas, template compilation should fail consistently instead of accepting invalid syntax in some forms.

- **Constraints**: Correct import statements must keep working as before, including the context-carrying form. The upgrade should only remove accidental acceptance of invalid template syntax and should not change the meaning of valid imports.


### Task 18 Align indent filter behavior with Jinja 2.10
Ensure that upgrading to Jinja 2.10 preserves expected template output for the `indent` filter by accounting for the new default of not indenting blank lines, supporting the `first` option for first-line indentation, and handling the deprecated `indentfirst` alias without breaking existing templates.

- **Expectation**: After the upgrade, templates using the `indent` filter should produce output that skips indentation on empty lines unless explicitly requested, continue to support optional first-line indentation through the current API, and warn when older argument naming is used so callers can migrate safely.

- **Constraints**: Keep existing indentation behavior stable for normal text lines, avoid silently breaking older call sites that still use the previous option name, and make blank-line indentation opt-in rather than the default.


## Additional Changes
- Ensure that template variable and expression names are lexed according to the host Python runtime's identifier rules, especially for Unicode identifiers. Valid Unicode identifiers should compile when supported, and invalid characters should not be accepted merely because they match a broad regex.
- Ensure that `TemplateRuntimeError` is part of Jinja's public top-level API so callers can import it directly from the `jinja2` package.
