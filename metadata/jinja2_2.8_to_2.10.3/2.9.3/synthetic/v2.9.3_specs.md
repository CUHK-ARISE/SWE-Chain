# Upgrade Specification from 2.9.2 to 2.9.3

## Bug Fixes

### Task 1 Restore block rendering inside macros
Ensure that templates render block content correctly when blocks are used inside macros or similar buffered rendering contexts, so Python 3 output shows the intended rendered text rather than an internal generator representation.

- **Expectation**: Templates that combine macros and blocks should render the same human-readable output that the block defines. If block scope affects which values are visible, the rendered result should still reflect the correct in-scope data.

- **Constraints**: The upgrade should remove the broken output without changing unrelated template behavior. Existing rendering modes and context rules should continue to behave as before except for the corrected block output.


### Task 2 Fix inconsistent inner-scope variable reads
Ensure that when a template reads a variable inside an inner scope and later assigns to that same variable name within the inner scope, the pre-assignment read consistently uses the nearest outer value when one exists, instead of behaving as undefined. Ensure that this fix does not restore legacy behavior where inner-scope assignments could mutate or leak into the outer scope.

- **Expectation**: Nested template scopes should consistently inherit an existing variable value for reads that happen before a same-named local assignment, while still keeping the assignment local to that nested scope. If no outer value exists, the read should stay undefined until the variable is assigned locally.

- **Constraints**: The fix must improve read consistency without changing scope isolation rules. Local assignments inside nested scopes must remain local, and missing outer values must not be replaced with invented defaults.


### Task 3 Preserve full visible scope for derived block rendering
Ensure that block rendering in Jinja uses the full currently visible template scope when a derived context is created, so scoped blocks and similar block evaluations do not lose variables that were overridden in a local scope.

- **Expectation**: Blocks that render in nested or independent template contexts should behave as if they were executed with the same visible data the template had at that point. If a value was overridden in a nearer scope, the block should use that value instead of acting as though the override never happened.

- **Constraints**: The fix should broaden block visibility to match the caller's actual scope without changing unrelated rendering semantics. Existing block execution should keep working, but variables that are already visible where the block is entered must remain visible inside it.


### Task 4 Correct `with` block scoping semantics
Ensure that `with` statements follow the updated scoping model so values declared in a `with` header are computed from the enclosing context, then exposed only as temporary names inside the block, avoiding edge-case misresolution between sibling assignments.

- **Expectation**: A `with` block should behave like creating a temporary local scope from a snapshot of expressions in the current context. Names introduced by the block should be visible inside the block, but earlier names in the same `with` declaration must not influence how later declarations are computed.

- **Constraints**: Keep `with` blocks temporary and predictable. The update should correct expression scoping at block entry without changing normal visibility inside the block or leaking temporary names after the block ends.
