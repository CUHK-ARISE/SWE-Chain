# Upgrade Specification from 2.9.3 to 2.9.4

## Bug Fixes

### Task 1 Eliminate invalid escape sequence warnings in Jinja2 2.9.4
Ensure that upgrading from 2.9.3 to 2.9.4 no longer emits library-originated invalid escape sequence deprecation warnings during normal Jinja2 import and template-processing usage, without changing existing lexer, token stream, or raw/block/variable parsing behavior.

- **Expectation**: The upgrade should make Jinja2 clean to use in warning-sensitive environments by removing deprecation warnings caused by the library's own string literals, while leaving template parsing and extension-facing token behavior functionally the same.

- **Constraints**: The fix must be non-breaking: it should only remove spurious warnings from the library itself and must not alter how templates are interpreted or how existing integrations interact with Jinja2.


### Task 2 Invalidate stale bytecode caches after upgrading to 2.9.4
Ensure that upgrading to Jinja2 2.9.4 invalidates previously persisted bytecode cache entries from the older cache generation so stale compiled templates are not reused.

- **Expectation**: After the upgrade, old on-disk or external template bytecode caches should no longer be trusted automatically. The template engine should discard outdated cached bytecode and rebuild it transparently, while continuing to use caching normally for newly generated entries.

- **Constraints**: Treat this as a compatibility-preserving cache reset rather than a rendering feature change. Existing applications should continue to work without configuration changes, apart from a one-time rebuild of stale cached templates.


### Task 3 Fix filtered loop scoping regression in Jinja2 templates
Ensure that templates using filtered for-loops continue to render correctly when the filter expression references values from the surrounding template scope, including recursive loops.

- **Expectation**: Filtered loops should behave as normal iteration with a condition: items that satisfy the condition are rendered, items that do not are skipped, and variables from the surrounding template remain available while the condition is evaluated.

- **Constraints**: The update should be limited to correcting filtered-loop behavior without changing unrelated template rendering, iteration order, recursion behavior, or fallback behavior.


### Task 4 Fix conditional template compilation after known extends blocks
Ensure that templates using conditional branches around top-level content that becomes silent after a known `{% extends %}` block still compile and load successfully, instead of failing during template compilation.

- **Expectation**: Conditional template branches that effectively render nothing because template inheritance suppresses top-level output should still be accepted as valid empty branches. After upgrading, affected templates should compile and render normally instead of failing before render.

- **Constraints**: The change should remove erroneous compilation failures without altering normal conditional behavior, template inheritance behavior, or rendered output for templates that were already valid.


### Task 5 Make truncate default leeway configurable
Ensure that applications can globally configure the default `truncate` filter leeway so templates remain compatible across versions without requiring every `truncate` call site to pass `leeway` explicitly.

- **Expectation**: Templates that use `truncate` without specifying `leeway` should follow an application-level default rather than a fixed built-in value. Upgrading applications should be able to keep the newer truncation tolerance or globally restore legacy stricter truncation behavior through configuration alone.

- **Constraints**: Only the source of the default `leeway` should change. Explicit per-call settings and the rest of the filter's truncation rules should continue to behave the same, and invalid negative defaults should still be rejected.
