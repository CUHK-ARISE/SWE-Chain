# Upgrade Specification from 2.9.4 to 2.9.5

## Bug Fixes

### Task 1 Restore tuple-style representation for groupby results
Ensure that values returned by the `groupby` filter are represented to users and downstream consumers like plain tuples again, so upgrades from versions before 2.9 do not break integrations that rely on tuple-style output.

- **Expectation**: Grouped values from `groupby` should still behave as two-part group records, while their displayed form should look the same as it did before the 2.9 series. Users and integrations should see tuple-style output rather than an implementation-specific namedtuple display.

- **Constraints**: The fix should preserve existing grouping behavior and data shape while narrowing the change to how grouped results are presented externally. Upgrading should improve compatibility without changing how callers iterate over or access grouped data.


### Task 2 Restore compatibility for custom Context.resolve overrides
Ensure that upgrading to 2.9.5 preserves expected template variable lookup for custom Jinja2 context classes that override the legacy resolve() method, so existing integrations do not regress when resolving provided values, inherited context values, or missing names.

- **Expectation**: Custom context classes that rely on the older variable-resolution hook should keep working after the upgrade. Template rendering should still see custom-resolved values, ordinary context values should still be found normally, and missing names should still be treated as missing rather than as successful resolutions.

- **Constraints**: The fix must preserve backward compatibility for older custom context integrations, keep missing-value semantics stable, and avoid changing normal variable lookup behavior for users who are not customizing context resolution.


### Task 3 Fix recursive for-else template rendering regression
Ensure that recursive template for-loops with an else clause compile and render correctly, so empty iterables produce the fallback output instead of causing syntax failures or incorrect rendered results.

- **Expectation**: Recursive loop templates should handle `else` the same way users expect from normal loop constructs: if there are no items, the fallback content renders normally, and the template remains valid to compile and render across supported runtimes.

- **Constraints**: Correct the broken fallback behavior without changing output for loop scenarios that already work.


### Task 4 Fix async template inheritance for extends
Ensure that templates using `{% extends %}` can be loaded, compiled, and rendered in async-enabled environments without failing because of async-incompatible inheritance handling.

- **Expectation**: Template inheritance should work in async mode the same way users expect it to work in normal mode: extending a parent template should succeed and produce inherited output without async-specific compilation failures.

- **Constraints**: The fix should remove the async-mode failure while preserving existing inheritance behavior and rendered results for non-async usage.


### Task 5 Fix async macro autoescaping in Jinja2 2.9.5
Ensure that template macros render correctly during asynchronous execution when autoescaping is enabled, so users receive the macro's rendered output with normal escaping behavior instead of coroutine-like output or incomplete async execution.

- **Expectation**: In asynchronous template rendering, calling a macro should behave the same as normal rendering from the user's perspective: the macro should finish executing, produce its rendered value, and honor autoescaping consistently.

- **Constraints**: The update should only correct broken async macro behavior and should not change how macros work in regular rendering or when escaping settings are unchanged.


## Performance Improvements

### Task 6 Reduce Unicode Identifier Matching Memory Use
Ensure that upgrading to Jinja 2.9.5 reduces the memory footprint of Unicode identifier handling on Python 3 without changing which template identifiers are recognized or regressing ASCII-only fallback behavior on runtimes that do not support Unicode identifiers.

- **Expectation**: The upgrade should lower memory retained for identifier parsing, especially on Python 3, while preserving the same observable identifier acceptance rules for valid Unicode names and keeping the existing ASCII-only fallback on interpreters that cannot use Unicode identifiers.

- **Constraints**: Template authors should not need to rename identifiers or change templates because of this upgrade. The change must act as a transparent optimization and preserve compatibility across both Unicode-capable and ASCII-only interpreter behavior.
