# Upgrade Specification from 2.8.1 to 2.9

## New Features

### Task 1 Enable generator-stop semantics in compiled templates
Ensure that templates compiled and rendered on supported Python versions use generator-stop semantics so unexpected StopIteration raised by application code during template execution is surfaced as an error instead of silently terminating template generation.

- **Expectation**: On Python runtimes that support generator-stop behavior, template rendering should no longer treat an unexpected StopIteration from application code as a normal end of template generation. Instead, rendering should fail clearly with the runtime error Python uses for that situation, while older runtimes continue to render templates without requiring unsupported syntax.

- **Constraints**: The change must preserve compatibility with older Python versions and avoid altering normal template output when no unexpected StopIteration is raised.


### Task 2 Add opt-in async template execution support
Ensure that templates support an opt-in async execution mode so applications can render against async iterables and awaitable helpers on supported Python runtimes, while keeping async-only limitations explicit and predictable.

- **Expectation**: When async mode is enabled, users should be able to render templates against asynchronous data sources and awaitable helper results using normal template syntax. The library should offer explicit async APIs for full rendering, streaming, and module creation, while preserving synchronous rendering entry points where feasible. Async mode should also expose clear failure behavior for capabilities that cannot be represented safely in synchronous form.

- **Constraints**: The new async feature must be opt-in, must not regress existing synchronous template behavior, and must fail clearly where synchronous assumptions no longer hold. The library should not invent metadata such as collection length when asynchronous iteration cannot provide it reliably.


### Task 3 Add configurable environment policies for filter defaults and safe JSON output
Ensure that upgrading to Jinja2 2.9 adds environment-level policies for filter defaults and related rendering behavior, so applications can centrally control safer `urlize` output, built-in JSON serialization through `tojson`, and compatibility-sensitive string handling where supported.

- **Expectation**: The upgraded library should let users configure rendering defaults once at the environment level instead of hardcoding them in every template call. URL auto-linking should apply safer default link metadata and allow centralized overrides, templates should gain a built-in JSON serialization filter suitable for HTML output, and compatibility-related string behavior should remain configurable through policies.

- **Constraints**: The new policy system should refine default rendering behavior without removing normal template customization. Explicit caller choices should override environment defaults, disabling a default should stop that output from appearing, and JSON output should stay safely embeddable in HTML-oriented template contexts.


### Task 4 Support top-level set statements in extended templates
Ensure that templates using `{% extends %}` can define top-level variables with `{% set %}` statements, including block capture form, and have those assignments available during rendering just like other top-level template state.

- **Expectation**: A child template should be able to define top-level variables, including captured block values, before or alongside inheritance logic. Those variables should behave like normal top-level template assignments: available where rendering needs them, exported when public, and handled with the same escaping semantics users see elsewhere.

- **Constraints**: Inheritance support for top-level assignments must not leak private variables, must not turn captured assignments into rendered output, and must keep assignment visibility consistent whether one or many variables are defined.


### Task 5 Update truncate filter tolerance behavior
Ensure that upgrading to 2.9 preserves and documents the new `truncate` filter behavior so content that only barely exceeds the configured length is left intact by default, while callers can still force truncation when needed.

- **Expectation**: The truncation API should treat near-boundary values more leniently by default: text that only slightly exceeds the target length should remain unmodified, but callers must be able to opt into stricter truncation and still choose whether truncation preserves whole words or cuts mid-word.

- **Constraints**: The upgrade must remain backward-compatible for normal `truncate` usage while adding stricter validation around nonsensical argument values. Any custom suffix should continue to count toward the visible truncation limit, and the new tolerance should not alter strings that already fit comfortably within the configured threshold.


### Task 6 Add configurable HTML-safe JSON rendering with `tojson`
Ensure that templates can serialize values through a built-in `tojson` filter, and allow applications to configure how that JSON is produced through environment-level policies while keeping the rendered output safe for HTML embedding.

- **Expectation**: Applications should be able to render JSON directly from templates with `|tojson`, optionally pretty-printed, and centrally control the serializer and its default options through environment configuration. The rendered JSON should be safe to embed in HTML and script contexts.

- **Constraints**: Configuration should remain centralized and reusable across templates, while one-off pretty-printing remains possible at the usage site. The feature should improve safe HTML embedding without changing the need for context-appropriate escaping in placements that remain unsafe, such as double-quoted attributes.


### Task 7 Make Python 2 ASCII literal coercion configurable
Ensure that on Python 2, applications can disable automatic ASCII-byte coercion for ASCII-only template string literals through the compiler policy system, while preserving the previous compatibility behavior by default and leaving non-ASCII text unaffected.

- **Expectation**: Upgrading to 2.9 should let Python 2 users opt out of legacy ASCII coercion for template literals. With the default setting, existing templates should keep their prior byte-string-compatible behavior for ASCII-only literals. When the option is turned off, those literals should stay as text/unicode, and literals containing non-ASCII characters should continue to stay as text regardless of the setting.

- **Constraints**: The new option should narrowly affect legacy Python 2 string typing behavior for ASCII-only template literals. It should not create regressions in other runtimes, other data types, or text that contains non-ASCII characters.


### Task 8 Make with and autoescape tags built in
Ensure that templates can use the `with` and `autoescape` block tags by default in 2.9, without requiring opt-in extension setup, while preserving the same scoped variable-binding and scoped autoescaping behavior users expect from those tags.

- **Expectation**: Users upgrading to 2.9 should be able to write `with` and `autoescape` blocks in templates out of the box. Those blocks should behave the same as before from a template author’s perspective: `with` provides temporary scoped variables, and `autoescape` temporarily changes escaping rules only for the enclosed content.

- **Constraints**: The upgrade should remove configuration overhead without changing how template authors use these tags or weakening their scope boundaries. Temporary assignments and temporary escaping settings must stay local to the block that declared them.


### Task 9 Add built-in autoescape selection helper
Ensure that applications upgrading to Jinja2 2.9 can use a built-in helper to configure `Environment` autoescaping based on template name and extension, with safe defaults for common markup templates and predictable fallback behavior for string templates and unmatched filenames.

- **Expectation**: The library should provide a first-class way to turn autoescaping on or off from template naming conventions instead of requiring every application to implement its own callback. Using the helper should produce consistent, case-insensitive decisions for common markup templates, sensible behavior for templates created from strings, and an explicit fallback for filenames that do not match configured rules.

- **Constraints**: The new helper should be predictable and safe: common web template types should autoescape by default, opt-out extensions should remain opt-out, and anything not explicitly matched should follow the caller's chosen fallback instead of changing behavior implicitly.


## Bug Fixes

### Task 10 Scope template cache entries to the active loader
Ensure that `Environment` template caching remains performant and returns the correct template for the currently configured loader, including when loaders do not expose file-backed sources and when the loader is replaced at runtime.

- **Expectation**: Template caching should be keyed by which loader is serving the template, not by a resolved file path. After upgrading, applications should see the same fast cache reuse for repeated lookups from one loader, and they should get fresh content when the environment switches to a different loader that serves the same template name.

- **Constraints**: Keep current caching behavior intact aside from the cache identity fix. Cache disablement, cache size limits, and reload checks should continue to behave as before, and loaders should not need filesystem-style metadata in order to participate in caching.


### Task 11 Fix template arithmetic operator precedence
Ensure that arithmetic expressions in templates produce the mathematically expected result when combining addition, subtraction, multiplication, division, floor division, modulo, and comparisons in a single expression.

- **Expectation**: Mixed math in template expressions should behave like normal arithmetic: multiplicative operators are resolved before additive operators, operators at the same level are evaluated from left to right, and any comparison should use those corrected numeric results.

- **Constraints**: The upgrade should only correct arithmetic interpretation errors without changing unrelated expression capabilities or forcing template authors to rewrite ordinary math expressions.


### Task 12 Support attribute fallback for legacy Python 2 classes
Ensure that item-preferred lookups still fall back to object attributes for old-style Python 2 class instances when item access fails with an attribute-related error, so existing templates and callers can resolve available attributes instead of failing the lookup early.

- **Expectation**: Lookups that normally try subscript access first should remain compatible with legacy Python 2 objects whose failed item access surfaces as an attribute error. If the requested name exists as an attribute, users should see that value resolved instead of an unexpected failed lookup.

- **Constraints**: Do not change normal lookup precedence or general mapping behavior. The update should only broaden fallback compatibility for affected legacy objects without altering successful existing resolutions.


### Task 13 Restore Cycler.next compatibility on Python 3
Ensure that upgrading to 2.9 restores Python 3 compatibility for `Cycler` by making the helper expose a callable `next()` method again, without changing its existing cycling semantics.

- **Expectation**: Users should be able to advance a `Cycler` with either its explicit `next()` method or normal iterator usage, and both forms should produce the same sequence and state transitions.

- **Constraints**: The compatibility fix should add back the missing public method without altering how cycling, rewinding, or iterator consumption already works.


### Task 14 Align undefined subtraction with standard undefined operator behavior
Ensure that subtraction expressions involving undefined template values behave consistently with other operations on undefined values and report the framework's standard undefined-value failure instead of inconsistent operator behavior.

- **Expectation**: When a template performs subtraction and either side is undefined, the operation should fail in the same predictable way as other invalid uses of undefined values, using the template engine's undefined-value error semantics.

- **Constraints**: The upgrade should only remove the inconsistency around subtraction on undefined values and should not alter unrelated undefined-value behaviors that users already rely on.


### Task 15 Improve errors for unquoted callable names in sequence filters
Ensure that `map` and related sequence-selection filters report actionable runtime errors when a filter or test name is passed without quotes, so template authors can distinguish a missing callable from an accidentally undefined template variable.

- **Expectation**: If a template uses a filter or test name dynamically in a sequence helper but forgets to quote it, rendering should fail with a clearer error that points to the unquoted-name mistake rather than only saying the callable was missing.

- **Constraints**: The upgrade should only improve error reporting for the unquoted-callable case. Normal filter and test execution, attribute-based mapping, and default truthiness-based selection behavior should continue to work as before.


### Task 16 Use call-time autoescape for macros
Ensure that macros honor the active autoescaping mode at the point they are invoked, and that omitted macro parameters are resolved during macro execution so returned output and defaulted values reflect the caller's current rendering context.

- **Expectation**: A macro should be escaped based on where it is used, not where it was declared. When callers omit macro arguments, defaults should be applied when the macro runs so the macro sees the current rendering context for those values.

- **Constraints**: The upgrade should preserve existing macro calling compatibility and validation rules while changing only when escaping and default values are decided.


### Task 17 Mark block set assignments safe under autoescape
Ensure that content captured with block-form `set` is treated as safe by default in autoescaped templates so reusable template fragments are not double-escaped, while unsafe values rendered inside the block remain escaped appropriately and top-level block assignments continue to work consistently.

- **Expectation**: Captured template fragments assigned with block-style `set` should behave like already-safe rendered content in autoescaped environments. Users should see untrusted values sanitized inside the captured fragment, but should not see the entire fragment escaped again when the variable is rendered later. The same construct should work reliably even when used at the top level of a template.

- **Constraints**: Only the safety status of captured block assignments should change in autoescaped rendering. Existing assignment behavior outside that case should remain stable, and the update must not weaken escaping of untrusted content inserted into the captured block.


### Task 18 Fix sandbox handling of async generator attributes
Ensure that accessing attributes of async generator objects in the sandbox does not raise an unexpected runtime error and instead follows the sandbox's normal attribute-safety behavior.

- **Expectation**: When sandboxed code inspects an async generator, attribute access should behave like other supported object types: unsafe async-generator attributes remain blocked by the sandbox, and supported attributes are processed normally without an unexpected runtime exception.

- **Constraints**: The fix should remove the crash without broadening sandbox access. Existing security boundaries for unsafe attributes and internal attributes must remain intact.


## Dependency Updates

### Task 19 Require MarkupSafe 0.23+ for sandboxed format handling
Ensure that upgrading to 2.9 requires MarkupSafe 0.23 or later and that sandboxed template formatting through `format` continues to work safely and consistently for plain text and markup-aware values.

- **Expectation**: After the upgrade, installations should fail fast on unsupported MarkupSafe versions, and applications using sandboxed templates should be able to rely on `format`-based interpolation remaining available without bypassing sandbox protections or markup escaping behavior.

- **Constraints**: The dependency floor can increase, but the upgrade must not relax security boundaries or change unrelated template behavior.


## Breaking Changes

### Task 20 Harden urlize links with default noopener rel
Ensure that URL auto-linking through `urlize` produces opener-safe links by default while remaining configurable for relationship and target attributes through the supported public API.

- **Expectation**: Auto-linked URLs should become safer by default by adding opener protection to generated links. Callers should still be able to control link relationship tokens and target behavior explicitly or through environment-level defaults, and `nofollow` should continue to affect the rendered relationship attribute rather than being dropped.

- **Constraints**: The upgrade should not change what text is recognized as a link or how links are escaped and shortened, beyond adding the new relationship metadata and policy-driven target defaults. Consumers must be able to disable the default relationship metadata or override it without causing duplicate or conflicting link attributes.


### Task 21 Refine `is` test argument parsing for boolean test expressions
Ensure that template `is` test expressions can be combined with boolean operators such as `and` and `or` without requiring extra parentheses, while restricting the first argument passed to a test so it is not interpreted as an arbitrary expression.

- **Expectation**: Template authors should be able to write multiple `is` checks in one boolean expression and have each check evaluated independently. A test's first argument should behave like a single direct value, not like an unrestricted inline expression that can absorb later boolean logic.

- **Constraints**: Fix the parsing ambiguity without changing unrelated expression behavior. Existing straightforward test usage should keep working, but overly broad first-argument syntax should no longer be accepted.


### Task 22 Normalize Context Propagation for Includes and Imports
Ensure that template inclusion and import operations propagate context consistently so included templates and imported macros or modules observe the same active caller data whenever context sharing is enabled, while explicit context isolation continues to work predictably.

- **Expectation**: Included templates and imported macros should either see the caller's live template data consistently or stay isolated from it, depending only on the explicit context modifier or the construct's documented default.

- **Constraints**: Keep existing template syntax and default behavior intact, but remove inconsistent scope visibility between the different include and import forms. Explicit isolation must still isolate.


## Additional Changes
- Ensure that a `for` loop with an `else` branch does not hide an outer variable that uses the same name as the loop target when the loop body never runs.
- Ensure that the `title` filter capitalizes words that begin immediately after common opening punctuation, not only words separated by whitespace or hyphens.
- Ensure that templates can express greater-than and less-than comparisons through named built-in tests in addition to the existing comparison operators.
- Ensure that callers working with Jinja's parsed AST can obtain a readable serialized representation of node trees without building their own traversal logic.
