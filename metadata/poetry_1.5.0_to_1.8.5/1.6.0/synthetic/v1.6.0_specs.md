# Upgrade Specification from 1.5.1 to 1.6.0

## New Features

### Task 1 Support non-default repository hash algorithms for package selection
Ensure that packages can be discovered and installed from repositories that publish artifact hashes with algorithms other than the preferred SHA-256, SHA-384, or SHA-512 set, while continuing to reject artifacts whose published hash cannot be validated.

- **Expectation**: When a repository publishes package checksums in a different algorithm, Poetry should still be able to recognize and install the correct artifact by validating the published checksum and matching the artifact through an internally derived SHA-256 checksum.

- **Constraints**: Do not relax checksum safety. Repositories that already use the standard hash formats should behave exactly as before, and artifacts with mismatched or unverifiable published hashes must continue to be treated as invalid.


### Task 2 Support duplicate dependencies with overlapping markers
Ensure that duplicate declarations of the same dependency remain fully resolvable when their environment markers overlap, including Python-version, platform, direct-origin, and named-source cases, and that genuinely incompatible overlaps fail with a clear incompatibility error.

- **Expectation**: The upgrade should let projects with repeated dependency declarations across partially overlapping environments install or lock correctly by computing the right requirement for each environment segment. If two declarations disagree for the same real environment, resolution should stop with a clear incompatibility signal instead of producing an unrelated solver failure or silently dropping coverage.

- **Constraints**: Keep source distinctions intact, only evaluate environment slices that can actually occur, and do not widen, remove, or duplicate requirements outside the environments where they apply.


### Task 3 Expand `poetry check` to validate README declarations and lock state
Ensure that `poetry check` reports missing README files declared in project metadata and surfaces `poetry.lock` consistency problems during validation so configuration mistakes are caught before later install or release workflows.

- **Expectation**: The project validation command should fail fast on broken README metadata and dependency lock drift. Users should be told when declared README files are missing, when an explicitly requested lock file is absent, and when an existing lock file is out of date with the project configuration.

- **Constraints**: The stronger validation should preserve current checks and report all relevant issues in one run. It should not treat an optional missing lock file as an error unless the user explicitly asks for that check, but it should always flag an out-of-date lock file when one is present.


### Task 4 Support xonsh environment activation through vox
Ensure that Poetry can activate a project's virtual environment correctly when the user is running the `xonsh` shell, so entering a Poetry-managed shell works in xonsh the same way it already does in other supported shells.

- **Expectation**: Users who launch a Poetry-managed shell from xonsh should enter the correct project virtual environment successfully, using xonsh's native activation behavior instead of a generic shell script activation approach.

- **Constraints**: The new xonsh support should be additive only: it should fix xonsh activation without changing how existing supported shells behave, and it should activate the intended project environment rather than a different or fallback environment.


### Task 5 Move lock-file validation to poetry check --lock
Ensure that project validation is centered on `poetry check`, so users can verify metadata, README references, and lock-file consistency through `poetry check --lock`, while legacy `poetry lock --check` invocations continue to work with a deprecation notice.

- **Expectation**: Users should use `poetry check` as the main validation command, with `--lock` enabling strict lock-file presence checking. Validation should surface missing README files and stale lock files as user-visible errors, and the old lock-check entry point should remain temporarily usable but clearly marked as deprecated.

- **Constraints**: The upgrade should steer users to the new validation workflow without abruptly removing the old one. Strict lock-file existence checks should only happen when explicitly requested, while stale existing lock files should never pass validation.


## Bug Fixes

### Task 6 Differentiate downgrade operations from upgrades in package output
Ensure that package operation output clearly identifies when a dependency change installs an older version, instead of presenting every version change as a generic update.

- **Expectation**: Users should be able to tell from standard package operation output whether a dependency is moving to a newer version or being rolled back to an older one. Backward version moves should be surfaced as downgrades, while forward version moves should remain ordinary updates.

- **Constraints**: Do not change unrelated package operation behavior. The update should only make older-version moves explicitly recognizable without altering how other actions are reported.


### Task 7 Support git+http Git dependency URLs
Ensure that dependency requirement strings using the `git+http://` scheme are accepted and interpreted as Git dependencies rather than ordinary URL dependencies.

- **Expectation**: Users should be able to declare Git-hosted dependencies with `git+http://...` and have them behave like other supported Git dependency URLs. The dependency should be recognized as coming from a Git repository, while normal HTTP(S) dependency URLs without the Git prefix should keep their existing behavior.

- **Constraints**: The update should extend supported Git URL schemes without changing existing supported Git behavior or collapsing the distinction between Git sources and ordinary downloadable URLs.


### Task 8 Respect build-system requirements during editable installs
Ensure that `poetry install` respects a project's declared `build-system.requires` during editable installation, including for projects that use build scripts, so required build-time dependencies are available and installs do not fail because those requirements were ignored.

- **Expectation**: Editable installs should honor the project's declared build requirements just like other install metadata. If a project needs extra build-time dependencies for its build script, Poetry should make sure they are taken into account automatically.

- **Constraints**: The fix should be narrowly scoped to build dependency handling. Existing editable install workflows that already work should keep working, without requiring version-specific workarounds.


### Task 9 Handle subprocess text encoding in environment and git operations
Ensure that subprocess-backed Poetry operations correctly handle text input and output, including project, interpreter, and environment paths that contain accented or Cyrillic characters.

- **Expectation**: Poetry should behave correctly when it shells out to Python, pip, or git, even if command input, command output, or filesystem paths contain non-ASCII characters. Users should continue to see normal string results and normal command failures instead of encoding-related breakage.

- **Constraints**: Expand character-encoding compatibility without changing how command execution normally succeeds or fails, and without requiring callers to manually encode input or decode output.


### Task 10 Fix top-level dependency display for extras in poetry show
Ensure that `poetry show --top-level` lists direct project dependencies even when those dependencies are declared with extras, so the command accurately reflects the packages the user explicitly added and does not hide them because extras were requested.

- **Expectation**: The top-level dependency view should show every package the project directly depends on, regardless of whether that dependency was requested with extras. Selecting extras must not make the direct package itself disappear from the top-level list.

- **Constraints**: Keep the fix scoped to correctly identifying direct dependencies in the top-level view. The command should remain focused on user-declared packages and should not change unrelated listing modes or start treating transitives as direct dependencies.


### Task 11 Correct `poetry init` package metadata for normalized module names
Ensure that `poetry init` generates package metadata that works for existing single-package projects, including projects arranged with a `src` layout, and does not emit redundant package inclusion configuration when the package name already matches the normalized project name.

- **Expectation**: `poetry init` should produce a `pyproject.toml` that installs and resolves the project's main package correctly without requiring users to manually remove unnecessary package metadata, especially for existing projects whose source code lives under `src`.

- **Constraints**: Only remove package configuration when it adds no information. Projects that rely on explicit package selection or a non-default source location should continue to receive explicit metadata.


### Task 12 Use locale-aware encoding for editable install .pth files
Ensure that Poetry editable installs write generated .pth files using the target environment's expected text encoding so editable packages work correctly on locale-specific systems, without changing the paths registered by the editable install.

- **Expectation**: Editable installs should produce .pth files in the encoding the target environment expects, so users on non-UTF-8 locales do not get broken or unreadable editable-install metadata. Re-running the install should remain robust and should not depend on a stale .pth file already existing.

- **Constraints**: The update should improve encoding compatibility only; it should not change what the editable install exposes or require users to change their workflow.


### Task 13 Respect locked package sources during install
Ensure that lockfile-based resolution respects the locked source for a dependency when multiple packages with the same name and version are present from different sources, so installs and other lockfile-backed resolution do not select the wrong distribution.

- **Expectation**: If a lock file contains identical package versions from different package sources, source-qualified dependencies must stay distinguishable. User-facing commands that resolve from the lock file should install or display the package from the declared source instead of treating all locked copies as interchangeable.

- **Constraints**: The fix must preserve normal behavior for packages that do not declare a source, while preventing URL or other direct-origin packages from being mistaken for packages from a named index. Source selection should only become stricter where the lock file already distinguishes identical packages by origin.


## Dependency Updates

### Task 14 Adapt PyPI source warning semantics for Poetry 1.6.0
Ensure that the forward-compatibility warning about PyPI being disabled automatically is shown only for configurations that define at least one custom primary package source without explicitly adding PyPI, and not for configurations that use only supplemental or explicit custom sources.

- **Expectation**: The upgrade should treat supplemental and explicit sources as additions that do not, by themselves, trigger a warning about losing the default PyPI source. Only configurations that promote another source to primary should receive guidance that PyPI may need to be declared explicitly for forward compatibility.

- **Constraints**: Keep package source behavior unchanged except for narrowing when the compatibility warning appears. Users who add non-primary custom sources should not be told to change configuration unless their setup would actually be affected by future primary-source behavior.


## Breaking Changes

### Task 15 Raise the minimum Python version to 3.8 and preserve packaging behavior
Ensure that upgrading to 1.6.0 only targets Python 3.8 or newer and that package discovery and editable install behavior remain correct on supported runtimes.

- **Expectation**: Users should run the upgraded library only on Python 3.8 or later. Package repositories should still produce correct download links, including pages that define a base URL, and editable installs should remain readable on systems whose default text encoding is not UTF-8.

- **Constraints**: Do not regress normal package link discovery or standard editable installs on supported runtimes; the intended compatibility break is the new Python 3.8 minimum.


## Performance Improvements

### Task 16 Prioritize high-version dependencies during locking
Ensure that `poetry lock` handles edge-case dependency graphs more efficiently by choosing the next dependency to resolve in a way that avoids unnecessary backtracking, especially when some packages have many more available versions than others.

- **Expectation**: Locking should complete faster on difficult dependency graphs by exploring the most branching dependencies earlier, while continuing to honor direct-origin requirements, locked selections, update preferences, and all declared version constraints.

- **Constraints**: This is a performance-focused solver change, not a change to dependency semantics. Resolution may proceed in a different order, but the resulting lock outcome must remain valid and consistent with the project's dependency rules.


### Task 17 Speed up repository package lookup during install
Ensure that upgrading to Poetry 1.6.0 improves `poetry install` performance without changing dependency resolution outcomes, and ensure any integration that retrieves packages from a repository does not rely on receiving a separate mutable clone.

- **Expectation**: Package retrieval during installation should avoid unnecessary object copying so installs resolve faster without changing which dependencies are selected. Consumers should treat repository lookup results as shared read-only package data, and missing packages should still fail with the existing not-found behavior.

- **Constraints**: The upgrade must improve performance without altering dependency selection or missing-package handling, and it must remain safe for callers that only read package metadata rather than mutating lookup results as private copies.


## Additional Changes
- Ensure that Poetry's bundled pre-commit hooks support projects whose `pyproject.toml` and `poetry.lock` live below the repository root, trigger only for relevant Poetry file changes, and avoid failing or running unnecessarily when unrelated files change or no applicable Poetry files are present.
- Ensure that version 1.6.0 documents the official Poetry badge so users can identify the supported Poetry badge representation without any change to runtime behavior.
- Ensure that macOS users are directed to the updated Poetry configuration folder path when upgrading from 1.5.1 to 1.6.0, so configuration discovery and related guidance remain accurate.
- Ensure that application developers are explicitly warned that using pip to install a Poetry-managed project does not honor the project's lock file, so relying on pip for deployment can silently resolve newer dependency versions than the ones locked by Poetry.
- Ensure that the `virtualenvs.in-project` setting is documented clearly enough that users can predict whether Poetry will use a cached virtual environment or a project-local `.venv`, especially when the setting is changed after an environment already exists.
- Ensure that Poetry's published pre-commit configuration examples use the canonical pre-commit YAML style so users can copy examples that match upstream pre-commit conventions without changing hook behavior.
- Ensure that users are given the correct command for listing installed plugins so upgrade guidance in 1.6.0 no longer points to an incorrect or misleading plugin-listing action.
- Ensure that Nox users are told about a supported documented workflow for reusing dependency versions from poetry.lock in Nox sessions via the nox-poetry package.
- Ensure that users upgrading from 1.5.1 to 1.6.0 can understand how to configure PyPI as a supplemental source in pyproject.toml when using a private primary repository, and ensure that the documentation clearly states that a PyPI source entry cannot define a custom URL.
- Ensure that user-facing guidance for defining scripts uses `reference` instead of the deprecated `callable` field so users are directed to the current supported configuration style.
- Ensure that cached marker and generic-constraint handling preserves operand order for composite expressions, so normalization, union, and intersection remain correct, deterministic, and free of recursion failures when equivalent subexpressions appear in different orders.
- Ensure that dependency and environment marker parsing accepts `|` as a separator in `in` and `not in` marker expressions, so packages using pipe-delimited marker values can be parsed and resolved the same way as existing space- or comma-delimited markers.
- Ensure that building or publishing a package preserves the project's declared pretty name in generated metadata while keeping distribution filenames normalized to packaging standards.
- Ensure that upgrading to poetry-core 1.6.0 uses the refreshed supported SPDX license catalog so declared package licenses resolve against the current upstream license data and produce correct observable license metadata.
- Ensure that PEP 508 dependency specifications whose package name starts with a digit are accepted as valid requirements so dependent packages are not rejected or dropped during dependency parsing.
- Ensure that building a package does not treat ignore rules from an unrelated parent Git repository as project exclusions when the project directory itself is under a Git-ignored path, so generated artifacts are not empty.
- Ensure that exported dependency files generate correct markers for packages required by a selected extra, so transitive dependencies are exported as actual resolved requirements instead of remaining incorrectly gated by extra-specific conditions.
- Ensure that PyPI search results are parsed correctly from the current `pypi.org/search` HTML so package lookup features continue to return usable package names, versions, and descriptions instead of silently missing results because the page markup no longer matches the old scraper.
