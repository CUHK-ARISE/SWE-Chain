# Upgrade Specification from 1.6.0 to 1.7.0

## New Features

### Task 1 Official Python 3.12 compatibility for build and environment workflows
Ensure that Poetry officially supports Python 3.12 for project installation and package inspection workflows. Ensure that virtual environment creation, isolated PEP 517 builds, source archive extraction, and cleanup behavior continue to work correctly when Python 3.12 changes default packaging tool availability and standard-library APIs.

- **Expectation**: Running Poetry on Python 3.12 should be fully supported across environment creation, source installs, and metadata/build preparation. Build environments should initialize correctly, package metadata generation should succeed, archive-based packages should still unpack normally, and explicit requests for packaging tools such as `setuptools` and `wheel` should continue to work even though newer Python environments no longer assume those tools are preinstalled.

- **Constraints**: Existing installation and inspection flows must keep working for supported archive formats and previously supported Python runtimes. Cleanup must remain safe, and the upgrade must not silently change packaging-tool availability beyond making explicit provisioning work correctly on Python 3.12.


### Task 2 Add prerelease phase advancement to `poetry version`
Ensure that `poetry version` lets users advance an existing prerelease to its next phase with `--next-phase` when running the `prerelease` update rule, including progressing from alpha to beta, beta to release candidate, and release candidate to the final release.

- **Expectation**: Users should be able to choose between continuing the current prerelease series and promoting the version to the next prerelease stage. Promotion should follow the normal prerelease lifecycle and produce a final stable version when promoting a release candidate.

- **Constraints**: The new flag should be additive and narrowly scoped. It should only affect prerelease promotion semantics, preserve existing behavior in all other versioning cases, and avoid changing how the command otherwise reports or applies version updates.


### Task 3 Support dynamically generated packages during root install
Ensure that `poetry install` can install projects whose package is created dynamically by a custom build script, and that projects with no installable root package are skipped with a clear warning instead of failing or being silently ignored.

- **Expectation**: Installing a project that generates its package at build time should work the same as installing a normal packaged project. If the current project is not installable as a package, the install should remain non-fatal and clearly tell the user how to skip root installation.

- **Constraints**: Keep the opt-out behavior unchanged, avoid breaking projects that are not meant to be installed as packages, and do not regress normal root-package installation flows.


## Bug Fixes

### Task 4 Warn on non-fatal file overwrites during wheel installation
Ensure that installing a wheel no longer silently overwrites an existing installed file, that the overwrite is surfaced as a warning without turning compatible namespace-package installs into failures, and that each wheel installation uses its own distribution-specific installation context.

- **Expectation**: When a package install would replace an existing file, the package manager should warn the user instead of silently proceeding with no signal. That warning should be non-fatal so installs that depend on shared namespace-package files still work, and each wheel should be installed with its own package-specific destination so headers and optional bytecode compilation are handled consistently.

- **Constraints**: Increase visibility into file conflicts without making previously valid namespace-package installations fail. Repeated installs in one session should not reuse another package's output paths or drop the currently selected compilation behavior.


### Task 5 Warn when the current project cannot be installed during poetry install
Ensure that `poetry install` informs users when the current project cannot be installed as part of the install flow, instead of silently succeeding without installing the project itself.

- **Expectation**: Running the install command without opting out should tell users when only the dependencies were installed and the project itself could not be installed. This should be communicated as a warning, not as a hard failure, and users should be reminded that skipping project installation intentionally is supported.

- **Constraints**: Intentional dependency-only installs must remain unaffected, successful installs must stay quiet, and the new visibility for root-install problems must not break existing automation that depends on a successful install command.


### Task 6 Expose underlying build-backend errors in Poetry output
Ensure that Poetry surfaces the underlying cause of package build-backend failures so users can diagnose installation errors without losing the original backend exception context.

- **Expectation**: Users should see the real reason a dependency build backend failed, whether the backend failed through a subprocess or by raising a normal Python exception directly. Poetry should continue to present the failure as a backend-originated problem while giving users an updated pip command they can run to reproduce the issue outside Poetry.

- **Constraints**: This update should only make backend build failures more informative. It should not change how successful installs behave, and it should not reclassify backend problems as Poetry-internal errors.


### Task 7 Use a Poetry-specific User-Agent for repository HTTP requests
Ensure that Poetry's HTTP requests to package repositories identify themselves as Poetry rather than the default generic requests client so dependency operations are not incorrectly blocked as bot traffic.

- **Expectation**: Repository and package-download requests should clearly identify the client as Poetry so servers can distinguish normal package-manager traffic from generic automated traffic.

- **Constraints**: Only the client identity presented to servers should change; normal repository access behavior should remain compatible with prior versions.


### Task 8 Sync should remove unmanaged setuptools and wheel
Ensure that `poetry install --sync` fully synchronizes an environment by removing installed `setuptools` and `wheel` when they are not required by the project, instead of preserving them as special cases.

- **Expectation**: `poetry install --sync` should leave the environment matching the project's actual dependencies. Extra copies of `setuptools` and `wheel` should be cleaned up unless the project depends on them, while unmanaged `pip` should continue to be left alone.

- **Constraints**: Synchronization must not delete dependencies the project actually needs, and it must keep the existing exception that avoids stripping an unmanaged `pip` from the environment.


### Task 9 Gracefully handle locked and failing keyring credential lookups
Ensure that keyring-backed credential lookup does not raise user-visible failures when secure storage is locked or the keyring backend errors, and instead continues as if no stored credential was available unless another lookup succeeds.

- **Expectation**: Credential retrieval through the keyring should degrade gracefully when the backend is temporarily locked or otherwise fails during access. Instead of terminating the operation, the application should treat that lookup as unavailable, continue any remaining credential search, and keep successful credential-based authentication behavior unchanged.

- **Constraints**: The fix must preserve normal authentication behavior when credentials are present and should only suppress recoverable keyring-read failures, not hide unrelated problems or alter successful lookups.


### Task 10 Preserve descriptions for setup-based packages
Ensure that packages whose metadata is read from setup.py or setup.cfg keep their declared description, so setup-based dependencies do not end up with blank or missing descriptions during dependency resolution and lock updates.

- **Expectation**: When the library reads dependency metadata from setup-based packages, it should preserve the package description if one is declared and expose it consistently to downstream consumers such as lock generation.

- **Constraints**: Projects that do not declare a description must continue to work normally, and existing dependency and version parsing behavior must not change as a side effect of adding description support.


### Task 11 Ignore inactive extras during dependency resolution
Ensure that dependency resolution, locking, and installation ignore dependencies that are only activated by extras that were not requested, so inactive extras do not constrain chosen versions or cause additional packages to be installed.

- **Expectation**: Selecting a package without an optional extra should behave as if that extra's dependencies do not exist. Selecting a package with one or more extras should activate only the dependencies for those extras, and unrelated extras must not affect which versions are chosen or which packages are installed.

- **Constraints**: The fix should be limited to removing the effect of inactive extras. It must preserve normal resolution for active extras and continue honoring Python and environment conditions for dependencies that are actually in scope.


### Task 12 Prevent artifact cache races during package downloads
Ensure that concurrent installs and source builds do not miss build requirements or consume corrupted cache entries when multiple operations request the same artifact at the same time.

- **Expectation**: Artifact downloads should behave as one coordinated cache operation. If several install or package-origin flows need the same archive at once, Poetry should end up with one complete cached artifact that all callers can use, and failed downloads should not leave corrupt cache state that can break later installs.

- **Constraints**: The fix should remove the race without changing normal cache reuse, dependency selection, or error reporting. Successful cached artifacts should keep working as before, and unsuccessful downloads should fail cleanly instead of poisoning the cache.


### Task 13 Respect inherited system site-packages in virtualenv installs
Ensure that when a virtual environment is configured to include system site-packages, compatible dependencies already available from those inherited system packages are treated as installed instead of being installed again into the virtual environment.

- **Expectation**: Virtual environments that are allowed to see system packages should reuse compatible inherited dependencies instead of duplicating them. Installation should only add a package when it is missing or the inherited version does not satisfy the requirement.

- **Constraints**: Do not change how fully isolated virtual environments work, do not treat unrelated filesystem locations as installed packages, and do not skip required installs when the available inherited package version is not acceptable.


### Task 14 Fix relative git submodule URL resolution
Ensure that installing a git dependency correctly resolves and clones submodules declared with relative URLs, including when the parent repository uses SSH or other non-HTTP git URL schemes.

- **Expectation**: Installing a git dependency should recurse into submodules reliably even when those submodules are referenced relative to the parent repository. Users should get the correct submodule repositories and revisions whether the dependency is fetched over HTTPS, SSH, or another supported git transport.

- **Constraints**: The fix should be limited to incorrect relative submodule resolution and should not regress normal git dependency installs. Existing repositories without affected relative submodule links should continue to behave as before, and missing submodule metadata should not turn into a hard failure.


### Task 15 Detect failed build dependency installs
Ensure that package installation stops immediately when required build dependencies cannot be installed for an isolated build environment, and report that failure as the direct cause instead of allowing it to appear later as a generic backend or build problem.

- **Expectation**: When Poetry cannot install a package's declared build dependencies, it should fail fast and tell the user that the build dependencies could not be installed, along with useful diagnostics from that failed install attempt.

- **Constraints**: Do not change successful builds or collapse different failure modes into one. Resolution issues, build-dependency installation issues, and other install failures should remain clearly differentiated.


### Task 16 Fix `poetry shell` behavior in Nushell
Ensure that `poetry shell` works correctly in Nushell by activating the project virtual environment immediately on shell startup and preserving normal interactive terminal input behavior.

- **Expectation**: Starting `poetry shell` from Nushell should place the user directly into an active project environment, and interactive programs in that shell should behave like a normal terminal with visible typed input.

- **Constraints**: The upgrade should correct Nushell-specific shell startup behavior without altering the expected experience in other shells.


### Task 17 Clarify missing-value errors for sensitive poetry config settings
Ensure that invoking `poetry config` for sensitive credential-style settings without supplying a value produces a clear missing-value error instead of a confusing or unrelated failure.

- **Expectation**: When a user runs `poetry config` for a credential setting like `pypi-token.pypi` without a new value, the CLI should clearly state that the command is incomplete and needs a value, rather than surfacing a misleading error.

- **Constraints**: Normal configuration reads and explicit unsets should continue to work as before. Only incomplete attempts to configure sensitive settings should be rejected with the clearer error behavior.


### Task 18 Handle lockfiles missing metadata gracefully
Ensure that reading a lock file with no metadata section fails with a clear, actionable error instead of a cryptic failure, so users know the lock file must be regenerated.

- **Expectation**: If a lock file is empty or otherwise missing required metadata, Poetry should stop with a clear error that explains the lock file is incomplete and needs to be rebuilt, rather than surfacing an unhelpful internal failure.

- **Constraints**: Do not change how valid lock files behave or how syntax or read errors are reported. Only improve the failure mode for parsed lock files that are structurally missing their metadata section.


### Task 19 Support special-character virtualenv paths
Ensure that Poetry can execute its internal Python helper scripts when a virtualenv path contains special or non-ASCII characters, so environment inspection and package metadata extraction do not fail because of script encoding or delivery issues.

- **Expectation**: Operations that depend on running small Python helpers inside a virtual environment should work regardless of special characters in the environment path. Metadata discovery should remain functional, and failures should still be reported as environment command errors with actionable subprocess output.

- **Constraints**: The update should eliminate path-related encoding failures without changing the normal success and failure contract of environment command execution. Standard workflows should behave the same aside from no longer breaking on special-character virtualenv paths and no longer echoing the helper script text in command errors.


### Task 20 Align repository connection pools with installer worker limits
Ensure that configuring installer worker concurrency also adjusts the HTTP connection pool used for package source and repository requests, so parallel dependency operations do not run with a smaller or mismatched pool than their effective worker count.

- **Expectation**: The configured installer worker limit should consistently govern both parallel work scheduling and the number of HTTP connections available to package sources, including default PyPI access and configured repositories.

- **Constraints**: This change should only synchronize concurrency-related limits. It must not remove existing worker caps, change fallback behavior on unusual platforms, or alter the single-worker behavior of non-parallel installs.


### Task 21 Clarify root project Python range in incompatibility errors
Ensure that Python dependency compatibility errors explain conflicts in terms of the project's supported Python range so users understand the issue is evaluated across the full set of Python versions the project declares, not only the current interpreter.

- **Expectation**: Python version conflict errors should clearly tell users that the problem is with the full Python versions their project claims to support. Any existing remediation or guidance tied to that conflict should still appear after the wording change.

- **Constraints**: Keep dependency resolution behavior the same. Only clarify the wording of this class of Python incompatibility error and preserve the same user guidance behavior around it.


## Dependency Updates

### Task 22 Warn that export plugin will need explicit installation
Ensure that running `poetry export` warns users that `poetry-plugin-export` will no longer be bundled by default in a future Poetry release, while still allowing the warning to be disabled without changing export behavior.

- **Expectation**: Using the export command should proactively notify users about the upcoming change to plugin bundling, while preserving the current export workflow. Teams that do not want the advisory should be able to turn it off through normal configuration without affecting the command itself.

- **Constraints**: This change must remain advisory only. It should not break existing automation, change export results, or surface the notice outside the export flow, and opting out should only suppress the warning.


## Breaking Changes

### Task 23 Make setuptools and wheel opt-in for Poetry virtual environments
Ensure that upgrading from 1.6.0 to 1.7.0 no longer relies on Poetry-created environments containing setuptools by default on Python 3.12, and ensure that packaging-related workflows still receive setuptools and wheel only when those tools are explicitly required.

- **Expectation**: After the upgrade, Poetry-managed environments should not silently include legacy packaging helpers by default. Users should only get setuptools or wheel when a workflow explicitly asks for them, while package metadata and build-related operations continue to work without extra manual intervention.

- **Constraints**: Keep default environments minimal without breaking workflows that intentionally request packaging tools or depend on Poetry's package inspection behavior.


### Task 24 Stop seeding wheel by default in Poetry environments
Ensure that upgrading to Poetry 1.7.0 does not assume `wheel` is present in newly created Poetry-managed virtual environments by default, while still allowing explicit opt-in for `wheel` and `setuptools` and preserving metadata/build workflows that require those tools.

- **Expectation**: After the upgrade, a new Poetry environment should be leaner by default and should not include `wheel` unless it is explicitly requested. If `wheel` or `setuptools` is requested, the environment should still provide them, and packaging metadata workflows should continue to work without extra user intervention.

- **Constraints**: The change should only alter the default presence of helper packages. Explicit opt-in or opt-out behavior for environment seed packages should remain predictable, and upgrade-related packaging workflows should keep working.


## Additional Changes
- Ensure that Poetry exposes a `poetry-install` pre-commit hook that users can enable to refresh installed dependencies after checkout and merge events so branch changes do not leave the environment out of sync with the lock file.
- Ensure that users who hit a package build failure related to PEP 517 support are told to verify the package with pip caching disabled, so cached artifacts do not make an unsupported package appear to work.
- Ensure that Poetry installation guidance presents pipx as the preferred installation method, clearly emphasizes using an isolated environment regardless of installation method, and highlights version pinning for CI usage.
- Ensure that the 1.7.0 upgrade guidance clearly recommends the preferred Poetry installation workflow, warns Windows users about `poetry self`, and more prominently communicates the need for isolated environments and CI version pinning, without implying a runtime behavior change.
- Ensure that guidance for adding a Git-hosted dependency with `poetry add` uses the correct `git+https` URL form so users are not shown a misleading HTTPS-only example.
- Ensure that users upgrading to 1.7.0 understand that `poetry build` automatically includes certain standard files in wheel metadata and in the root of source distributions, so they can reason correctly about build outputs without assuming those files must be added manually.
- Ensure that the documentation for configuring custom repositories via environment variables uses the correct `POETRY_REPOSITORIES_<NAME>_URL` naming pattern so users can set repository URLs without being misled.
- Ensure that the project provides standard citation metadata so users and external tools can discover how to cite the library correctly.
- Ensure that dependency markers using `extra` are evaluated correctly when multiple extras can be active at the same time, so optional dependency conditions are not incorrectly simplified, rejected, or mismatched because of extra-name normalization.
- Ensure that newly added SPDX license and exception identifiers are recognized as supported licenses, and that projects declaring those licenses are normalized consistently in parsed license data and generated package metadata.
- Ensure that projects with extension modules can be installed in editable mode without losing access to the compiled extension or packaging a duplicate copy of the project into the editable wheel.
- Ensure that wheel builds include files from the correct build output directory so packages do not ship the wrong files, or miss generated files entirely, when the build process produces either pure-Python or platform-specific library output.
- Ensure that `poetry export` can include dependencies from every declared extra without requiring users to enumerate each extra manually, and reject conflicting requests that try to combine automatic all-extra export with explicit extra selection.
- Ensure that exporting dependencies produces Git-based requirements pinned to the exact resolved commit recorded in the lock data, rather than a branch name or other unresolved reference.
- Ensure that publish/upload failures surfaced as `HTTPError` still produce a usable user-facing upload error even when the exception has no `response` object attached.
- Ensure that invalid `tool.poetry` configuration is validated through the new fastjsonschema-backed validator and that the resulting user-visible diagnostics reflect that validator's error format.
