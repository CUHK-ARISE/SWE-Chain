# Upgrade Specification from 1.7.1 to 1.8.0

## New Features

### Task 1 Support dependency-only projects with Poetry non-package mode
Ensure that projects using Poetry only for dependency management can opt out of package semantics, so they are not required to provide package metadata, do not install the root project during dependency installation, and cannot accidentally run packaging-only workflows.

- **Expectation**: Users should be able to configure Poetry for dependency management only. In that mode, dependency installation should still work, the local project itself should not be installed, and packaging commands should be unavailable because the project is not being treated as a distributable package.

- **Constraints**: The new capability must be opt-in, preserve existing package-oriented behavior by default, and only relax rules that are irrelevant for dependency-only workflows.


### Task 2 Support PEP 658 metadata from simple package indexes
Ensure that packages published on PEP 503 simple repositories that expose PEP 658 core metadata can be resolved without downloading the full wheel or source distribution, while still returning correct dependency metadata, Python version constraints, summary information, and release file data when sidecar metadata is missing, invalid, or unavailable.

- **Expectation**: When a package index publishes sidecar core metadata for a release file, the client should use that metadata directly to resolve package information instead of requiring a full archive download. This should work with both current and older metadata markers used by simple indexes. If the sidecar cannot be fetched or does not validate, users should still get the same resolved package information through the normal archive inspection fallback.

- **Constraints**: The upgrade must improve repository compatibility and reduce unnecessary downloads without changing successful resolution outcomes for repositories that already worked. Repositories that do not provide usable sidecar metadata should continue to behave as before, and invalid sidecar metadata must not become the source of truth.


### Task 3 Enable lazy wheel metadata retrieval for dependency resolution
Ensure that dependency resolution reduces unnecessary wheel downloads by default while still resolving package metadata correctly across repositories that expose metadata directly, support HTTP byte ranges, or require full archive downloads.

- **Expectation**: Poetry should minimize network transfer during dependency resolution by using published metadata when possible and by lazily reading only the metadata portion of remote wheels when needed. This optimization should be enabled by default, configurable by the user, and transparent: unsupported or unreliable repositories should still resolve successfully through the existing full-download path.

- **Constraints**: The optimization must never change the resolved metadata contract or make repository compatibility worse. Correctness and compatibility take precedence over bandwidth savings, and users must be able to turn the optimization off to restore eager downloads.


### Task 4 Validate dependency source references during `poetry check`
Ensure that `poetry check` reports an error whenever any dependency references a package source that is not declared in the project's configured sources, including dependencies defined in the main dependency section, dependency groups, and alternative or list-based declarations.

- **Expectation**: Running `poetry check` should catch undefined dependency source references up front. If a dependency points to a repository or source name the project has not declared, the command should fail validation and surface that configuration problem to the user.

- **Constraints**: The new validation should stay narrow and non-disruptive: it should flag only truly unknown source names, while leaving valid dependency configurations unchanged.


### Task 5 Allow disabling keyring integration via configuration
Ensure that users can disable keyring completely through configuration so Poetry does not probe, read from, or write to keyring when that integration is causing problems, while still supporting repository credentials from environment variables or configuration files.

- **Expectation**: Users should be able to switch keyring off completely with `keyring.enabled`. After that, Poetry should behave as if keyring is unavailable: it should not inspect the system keyring, should not store or retrieve repository secrets there, should continue using environment/config-based credentials, should warn when it stores secrets in plaintext configuration, and should only report keyring access as unavailable if something explicitly asks for it.

- **Constraints**: The new opt-out must not change normal credential handling for users with a working keyring, and it must not silently fall back to broken or insecure keyring backends. Disabling keyring must prevent side effects from keyring access without blocking non-keyring credential sources.


### Task 6 Support synchronized updates in Poetry
Ensure that `poetry update` provides an opt-in synchronization mode so users can update dependencies while also aligning the installed environment with the lock file for the selected dependency groups.

- **Expectation**: Users should be able to ask an update to also clean up the environment so only packages that belong to the updated locked dependency set for the chosen groups remain installed.

- **Constraints**: Existing update workflows should behave the same unless synchronization is explicitly requested, and synchronization should only apply within the dependency scope the user selected.


### Task 7 Support custom artifact output directories for build and publish
Ensure that package build and publish workflows can target a user-selected artifact directory instead of always using the default distribution folder, while preserving existing build format validation and package-mode restrictions.

- **Expectation**: Users should be able to choose where build artifacts are created, and publish should use the same chosen artifact location whenever it builds packages on the user's behalf. The default behavior should remain unchanged for existing workflows, and invalid build modes or unsupported formats should still be rejected.

- **Constraints**: Existing users who do not opt into a custom artifact directory should see no change in where packages are created. Choosing a different destination should only redirect artifact placement, not alter package contents, format selection, or whether the project is buildable. Build and publish should stay consistent about where artifacts live.


### Task 8 Support configurable artifact directories in poetry publish
Ensure that `poetry publish` can publish distributions from a user-specified artifact directory, that `--build` writes artifacts to and publishes from that same directory, and that publishing is rejected when the project is not operating in package mode.

- **Expectation**: Users should be able to keep build artifacts outside the default folder and still publish them with `poetry publish`. The publish flow should treat the chosen artifact directory as the single source of truth for both existing artifacts and artifacts created during a build-then-publish run. Projects that are not publishable packages should fail fast instead of attempting any publishing work.

- **Constraints**: Existing users should see no behavior change unless they opt into a custom artifact directory. Custom directory support should be additive and consistent, without changing what counts as a publishable artifact or how publish behaves apart from where artifacts are read from and written to.


## Bug Fixes

### Task 9 Support archive validation with all supported hash algorithms
Ensure that package installation and artifact selection validate archives against recorded hashes using any digest algorithm supported by the runtime, instead of assuming SHA-256, and reject artifacts whose hashes cannot be matched or verified from the available metadata.

- **Expectation**: Installing from locked or repository-provided archives should verify the downloaded file against a supported recorded digest even when that digest is not SHA-256. When multiple digests exist, the installer should use a preferred supported one, accept artifacts whose published hashes agree with the lock data, and fail clearly instead of proceeding when validation is impossible or every available digest disagrees.

- **Constraints**: The upgrade should add support for more digest algorithms without weakening integrity checks for existing workflows. It must not broaden acceptance of mismatched archives, and the same package file should be handled consistently wherever Poetry resolves, validates, or caches it.


### Task 10 Improve interactive virtualenv activation for fish shells
Ensure that `poetry shell` opens a clean, already-activated interactive shell for `fish` users and preserves reliable activation behavior across other supported shells.

- **Expectation**: Starting a Poetry-managed shell should immediately place the user in an activated environment without showing a typed activation command in the session, while keeping shell activation dependable across supported shell types.

- **Constraints**: Keep current shell support intact, avoid duplicate activation side effects, and ensure activation remains safe and reliable even when environment paths are not simple.


### Task 11 Rename `poetry env info` parent interpreter output from System to Base
Ensure that `poetry env info` describes the interpreter underlying the active virtual environment as `Base` instead of `System`, so the output does not imply that this interpreter is always the operating system's system Python.

- **Expectation**: Users inspecting an environment should see the underlying interpreter described as the base Python for that environment, while the same interpreter metadata remains available.

- **Constraints**: This should be a terminology correction for the secondary interpreter section only; the rest of the environment report and the interpreter facts it shows should stay the same.


### Task 12 Preserve declared package name in `poetry version` output
Ensure that `poetry version` displays the project name in its user-facing form when reporting the current package version, so command-line users and automation receive the declared package name instead of a normalized variant.

- **Expectation**: The default `poetry version` command output should show the package name exactly as users define it in project metadata, alongside the current version. Short output should remain a version-only view.

- **Constraints**: This update should adjust name presentation without changing how the version itself is reported or altering the compact version-only mode.


### Task 13 Improve invalid Poetry script entry errors
Ensure that malformed `tool.poetry.scripts` entries fail with actionable validation errors during editable build or install, so users can identify whether a console script is missing its callable separator or contains too many separators.

- **Expectation**: Editable installs should validate script definitions in `tool.poetry.scripts` and report configuration mistakes clearly. A script entry should reference a callable inside a module. If the callable separator is missing, users should be told that the script points to a module instead of a function and be given actionable guidance. If multiple separators are present, users should be told that the format is invalid because the script target is ambiguous.

- **Constraints**: Correctly defined scripts should behave as before. The change should only make invalid script configuration failures clearer, without changing successful script generation or broadening the accepted format beyond a single callable target inside a module.


### Task 14 Preserve extras in verbose dependency resolution output
Ensure that verbose dependency-resolution output preserves extras on declared dependencies, so commands such as `poetry lock -vv` identify `foo[bar]` as an extra-enabled requirement instead of collapsing it to the base package name.

- **Expectation**: When verbose dependency resolution explains why one package depends on another, the output should reflect the exact dependency the user asked for, including extras. Internally equivalent lookups for the same package should not lose that extra-qualified identity in the user-visible explanation.

- **Constraints**: Improve identification of extra-enabled dependencies without changing dependency-selection outcomes or regressing the existing output format for plain dependencies and direct-source dependencies.


### Task 15 Fix poetry shell activation for MSYS2 Python on Windows
Ensure that `poetry shell` can activate virtual environments on Windows when the interpreter was installed via MSYS2 and the environment uses a POSIX-style layout instead of the usual Windows `Scripts` directory.

- **Expectation**: `poetry shell` should work on Windows for both standard Windows virtual environments and MSYS2-style environments by finding the activation script in the layout the environment actually uses.

- **Constraints**: The update should add compatibility for the alternate virtual-environment layout without breaking activation for existing environments on Windows or other platforms.


### Task 16 Prevent CLI output encoding failures in non-UTF-8 terminals
Ensure that Poetry commands which print package-operation or plugin-list entries do not fail in terminals using a non-UTF-8 encoding, while preserving the same visible progress, status, and package information.

- **Expectation**: When Poetry prints list-like status lines, it should use terminal-safe text so the command output remains readable and the command completes normally even on non-UTF-8 terminals. Users should see the same operational information as before, with only the list marker style changing from a special symbol to a plain ASCII character.

- **Constraints**: Keep the behavior and meaning of command output the same apart from using a more compatible list marker. The fix should improve terminal compatibility without altering the underlying package actions or reducing the detail shown to users.


### Task 17 Handle missing project names without confusing validation failures
Ensure that Poetry handles project configurations with a missing `name` by surfacing a clear invalid-configuration error, while preserving the existing validation that rejects a project name that duplicates one of its dependencies.

- **Expectation**: Users who omit the project name should see a normal, understandable configuration error about the missing required field. Users who do define a project name should continue to be prevented from using the same name as one of their dependencies.

- **Constraints**: The upgrade should improve error clarity for incomplete project metadata without weakening existing validation rules or changing outcomes for named projects whose metadata is otherwise valid.


### Task 18 Support installing local sdist path dependencies
Ensure that adding or installing a dependency from a local source distribution archive path works reliably and is handled the same way as the same archive provided by URL, without failing because the package is treated as a directory source.

- **Expectation**: A dependency supplied as a local source archive should behave like a file dependency, not like a directory dependency. Users should be able to add the archive from disk and get the same successful install behavior they would get from the same archive hosted at a URL.

- **Constraints**: Only local source archives should change behavior. Real directory dependencies and other source types should keep their existing semantics, and archive inspection should remain transparent to the user.


### Task 19 Remove unrequested extras during synchronized installs
Ensure that `poetry install --sync` removes previously installed packages that belong only to extras that are not requested for the current install, so synchronized installs do not leave stale extra dependencies behind.

- **Expectation**: A synchronized install should fully match the extras the user asks for. If an optional extra is no longer requested, its packages should be removed instead of remaining in the environment.

- **Constraints**: Only stale optional extra dependencies should be cleaned up. Packages that are still required by the current project configuration must remain installed, and ordinary install behavior should not regress.


### Task 20 Accept Unicode author names in poetry init
Ensure that `poetry init` accepts author entries containing accented or other Unicode characters, including canonically equivalent combining-character forms, whenever the entry otherwise matches the existing author-field format.

- **Expectation**: Users should be able to enter author names with accented and other Unicode characters in `poetry init` without false validation failures. Different Unicode encodings of the same visible name should behave identically, while genuinely malformed author entries should still be rejected.

- **Constraints**: Improve character handling without loosening the overall author-field contract or changing how users skip the prompt.


### Task 21 Support build-requirement CLIs during sdist metadata inspection
Ensure that Poetry can determine metadata for source distributions when the package's metadata generation step invokes CLI tools provided by its declared build requirements.

- **Expectation**: Packages that need build-time command-line tools to compute their metadata should install and resolve normally as long as those tools are declared as build requirements. Poetry should treat those tools as available during metadata extraction and should no longer fail just because they are not on the user's ambient shell PATH.

- **Constraints**: The change should only remove the false failure caused by missing access to declared build-time tools. It should not relax isolation, invent undeclared tool dependencies, or alter successful metadata results for unaffected packages.


### Task 22 Clear stale environment state after `poetry env remove --all`
Ensure that `poetry env remove --all` also clears Poetry's remembered environment selection for the current project, so stale metadata from deleted or manually removed virtual environments does not prevent Poetry from using the currently activated environment.

- **Expectation**: Removing all project environments should also reset Poetry's saved environment choice for that project. Once the old environments are gone, Poetry should not keep behaving as if a deleted environment is still selected, and an already activated environment should be usable again.

- **Constraints**: The reset should only affect the project whose environments are being removed, must not fail when there is no saved environment state, and must handle previously deleted environments without leaving stale selection data behind.


### Task 23 Fix poetry shell activation for zsh virtualenv paths with spaces
Ensure that `poetry shell` reliably opens an activated shell session when the virtual environment path contains spaces, especially for `zsh`, without changing expected activation behavior for other supported shells.

- **Expectation**: `poetry shell` should work the same for users regardless of whether their project or virtual environment lives in a path with spaces. Opening a shell should result in an active environment, and shell-specific startup flows should not trigger duplicate or broken activation steps.

- **Constraints**: The fix should be limited to making shell activation robust and should not alter the expected startup experience for unaffected shells or normal path layouts. Users who already had working shell activation should continue to see the same outcome.


### Task 24 Fix console script installation for scripts with extras
Ensure that console scripts declared with extras install successfully and invoke the intended callable. Ensure that malformed script declarations are rejected clearly instead of producing unusable installed commands.

- **Expectation**: When a package defines a CLI script with optional extras, installing the project should still create a working command that runs the same function as the script definition without extras. If the script target format itself is invalid, installation should stop with a clear error rather than create a broken command.

- **Constraints**: Keep existing working script installation behavior intact, ignore extras for command target resolution, and prefer an explicit install-time failure over silently generating an unusable executable.


### Task 25 Preserve explicit sources across dependency extras
Ensure that dependency resolution preserves an explicitly configured source for a package even when the same package is encountered transitively with no extras or with a different set of extras, so installs and updates continue to pull that package from the intended repository.

- **Expectation**: If a project pins a package to an explicit repository, that repository choice should remain in effect for every resolved occurrence of the package, even when some dependency paths request the package without extras or with different extras. The selected extras should still be honored.

- **Constraints**: The change must prevent loss of repository selection without merging unrelated sources or changing which extras are active for the resolved package.


### Task 26 Restore debug logging for builds that use a custom build script
Ensure that builds using a custom build script no longer lose verbose or debug diagnostic output while Poetry prepares the build environment, and that third-party log output remains readable and attributable during those builds.

- **Expectation**: Verbose builds that rely on a custom build script should keep producing diagnostic output throughout build-environment setup. In debug mode, users should see the underlying build-system installation output, and third-party multiline logs should be clearly labeled so their origin is obvious instead of disappearing or becoming ambiguous.

- **Constraints**: The change should improve diagnostics without making normal builds unexpectedly noisy, without altering the caller's chosen logging level, and without reformatting first-party Poetry logs as if they came from external packages.


### Task 27 Preserve explicit sources for locked dependencies
Ensure that dependencies declared with an explicit source keep that source association when Poetry resolves them from locked packages, so installs and updates do not lose the intended repository for direct or transitively reached dependencies.

- **Expectation**: A package already pinned in the lock should still be treated as coming from the repository the user explicitly selected. Reusing locked dependency data must not strip away repository intent or cause later resolution steps to behave as if the package came from the default source.

- **Constraints**: The fix should stay limited to preserving explicit repository selection. It should not change compatibility matching, alter behavior for dependencies that do not name a source, or carry stale source choices into a different resolution context.


### Task 28 Correct Poetry self-environment detection
Ensure that Poetry does not falsely identify the interpreter running Poetry itself as the system environment when resolving environments, including installs where Poetry runs inside an ordinary virtual environment.

- **Expectation**: When Poetry inspects the Python interpreter it is running under, it should distinguish Poetry's own virtual environment from the real base or system interpreter instead of classifying that runtime as the system environment.

- **Constraints**: The change should remove false positives in system-environment detection without altering the explicit raw-system lookup mode or breaking standard interpreter discovery.


### Task 29 Stop Silently Dropping setup.py Dependencies
Ensure that Poetry does not silently ignore dependencies declared in a package's setup.py, and that unreadable dependency declarations are recognized as an inspection failure rather than being treated as missing dependencies.

- **Expectation**: When Poetry inspects a legacy setup.py-based project, it should either recover the project's declared dependencies accurately or recognize that static parsing was unreliable and switch to a safer metadata source. It must never behave as though unreadable dependencies simply do not exist.

- **Constraints**: Simple, statically declared dependencies should continue to work as before, and packages that truly declare no dependencies should still be treated as dependency-free. The change should only remove silent data loss from unreadable declarations.


### Task 30 Honor environment overrides for virtualenv options
Ensure that environment-variable overrides for virtual environment creation options are honored when Poetry resolves and applies virtualenv option settings, so created environments reflect the user's exported configuration instead of defaulting to stored values.

- **Expectation**: Poetry should treat virtual environment option values supplied through environment variables the same way it treats equivalent configured values. Reading or using the virtualenv options as a group must preserve nested overrides so the created environment matches the user's requested behavior.

- **Constraints**: The fix should be limited to honoring exported overrides without changing defaults for options the user did not set. Nested settings should behave consistently whether users access one option directly or rely on the full options group during normal Poetry operations.


### Task 31 Honor boolean Poetry env vars for virtualenv options
Ensure that supported boolean Poetry configuration options provided through `POETRY_*` environment variables are interpreted correctly and actually affect runtime behavior, especially virtual environment creation flags such as system site packages, pip, and setuptools handling.

- **Expectation**: Boolean configuration flags set via environment variables should behave the same way as the equivalent settings in Poetry's normal configuration sources. Users should be able to turn supported features on or off with `POETRY_*` variables and see those choices reflected in actual Poetry behavior.

- **Constraints**: Fix the boolean env var handling without changing unrelated configuration semantics. The update should only make supported boolean overrides reliable and consistent.


### Task 32 Allow Path Dependencies Without a Declared Build System
Ensure that local path dependencies are accepted and resolved even when their pyproject.toml omits a [build-system] section, as long as the project metadata is otherwise valid.

- **Expectation**: A package referenced by local path should work the same whether or not it explicitly declares a build system in pyproject.toml, provided the project metadata itself is valid. The upgrade should remove failures caused only by the missing build-system table and let dependency metadata be read normally.

- **Constraints**: Missing build-system configuration alone must no longer block local dependency usage, but the upgrade should not mask unrelated project metadata errors or change behavior for projects that were already valid.


### Task 33 Silence benign git output outside repositories
Ensure that git-backed operations no longer print insignificant git errors when the current working directory is not inside a git repository, while still failing normally for real git command errors.

- **Expectation**: When the library interacts with git, users should not see irrelevant console noise just because their current directory is outside a repository. Successful operations should be silent, and genuine git failures should still stop the operation and surface as errors.

- **Constraints**: Keep normal git-driven features working the same way from a user perspective, except that benign git noise should disappear. Real failures must still be visible as failures.


## Breaking Changes

### Task 34 Require explicit PyPI with primary sources
Ensure that projects upgrading to Poetry 1.8.0 do not rely on PyPI remaining implicitly available once any primary package source is configured, and that automatic PyPI fallback uses the new primary-source semantics.

- **Expectation**: Upgrading to 1.8.0 should make repository selection explicit: once a project chooses a primary source, Poetry should only use the sources the project names unless PyPI is also named. Projects with no primary or default source should still get PyPI automatically, and that automatic PyPI source should behave like a normal primary source.

- **Constraints**: Keep PyPI as the default fallback only for projects that have not selected another primary or default source. Do not silently continue querying PyPI for projects that have already opted into explicit primary sources.


### Task 35 Deprecate default source priority and require explicit PyPI with primary sources
Ensure that upgrading to Poetry 1.8.0 no longer relies on the deprecated `default` source priority or on implicit PyPI remaining active when a custom primary source is configured.

- **Expectation**: After the upgrade, source configuration should express preferred indexes with ordered primary sources instead of a special default priority. Users must explicitly add PyPI if they want it searched alongside a custom primary index, while existing deprecated configurations should still work with warnings rather than immediate failure.

- **Constraints**: The change should steer users toward the new source model without silently removing plain PyPI access from configurations that still depend on it, and it should not turn these deprecations into hard failures in this release.


### Task 36 Fail Fast on Inconsistent Poetry Lockfiles
Ensure that dependency installation aborts when `poetry.lock` is inconsistent with `pyproject.toml`, instead of warning and continuing with stale lock data that can produce confusing dependency resolution failures.

- **Expectation**: If the project definition has diverged from the lockfile, Poetry should fail fast with a clear error that tells the user the lockfile must be refreshed, rather than attempting to install from outdated pins.

- **Constraints**: Reject only the inconsistent lockfile state, preserve normal behavior for valid lockfiles, and surface the problem at the point it is detected instead of allowing later, less accurate dependency errors to appear first.


### Task 37 Remove legacy pip<19 installation compatibility
Ensure that upgrading to Poetry 1.8.0 no longer supports `pip` versions below 19, and that installation behavior consistently uses the modern build-system-aware flow for Poetry-managed packages unless a package explicitly requires the legacy build-script fallback.

- **Expectation**: The upgrade should require a modern pip and remove special handling for very old pip releases. Normal packages should install through the standard modern workflow, editable installs should keep working, and only packages that explicitly depend on a legacy build script should still use the older fallback behavior.

- **Constraints**: Keep behavior stable for supported modern environments, preserve compatibility for packages that explicitly need legacy script-based builds, and avoid retaining support guarantees for outdated pip versions.


### Task 38 Fail fast on outdated lockfiles with clearer guidance
Ensure that a significantly outdated `poetry.lock` is treated as an actionable error, not a soft warning, and that lockfile-related commands consistently explain that the lock file must be regenerated after meaningful `pyproject.toml` changes.

- **Expectation**: If the project metadata has changed enough that the lockfile is no longer current, Poetry should clearly tell users that the lockfile is outdated and stop any workflow that depends on that stale lockfile until it is regenerated.

- **Constraints**: Only the outdated-lockfile scenario should become stricter. Valid lockfiles should continue to work normally, and users should not be allowed to proceed on a dependency state that Poetry already knows is out of sync.


## Documentation

### Task 39 Clarify `poetry show --why` dependency-origin semantics
Ensure that `poetry show --why` is presented as showing how a package is included in the dependency graph, so users do not interpret it as giving a narrative reason for why the package was added.

- **Expectation**: Users should understand that `poetry show --why` explains a package's dependency origin within the project, distinguishing direct dependencies from transitive ones rather than providing a human explanation for the package's inclusion.

- **Constraints**: This change should clarify what the existing flag means without altering which packages are shown or how dependency relationships are determined.


## Performance Improvements

### Task 40 Treat package extras as immutable for shallow-copy resolution
Ensure that dependency resolution can use shallow package copies without changing how extras and duplicate conditional dependencies are interpreted, including when package data comes from published metadata or an existing lock file.

- **Expectation**: The 1.8.0 upgrade should make dependency resolution faster while preserving the same observable extras behavior. Package variants created during solving must not share mutable optional-dependency or override state with each other.

- **Constraints**: Keep dependency and extras semantics stable while improving performance. Independent resolution branches must remain isolated, and lock-backed package reconstruction must behave the same as metadata-backed reconstruction.


## Others

### Task 41 Deprecate legacy installer opt-out
Ensure that users who still configure `installer.modern-installation` as `false` are explicitly warned that this legacy installer mode is deprecated and will be removed in a future release, while current installation behavior continues to work for now.

- **Expectation**: Users who opt out of the modern installer should be clearly informed at runtime that they are on a deprecated path and need to migrate away from it, without breaking their current install flow immediately.

- **Constraints**: Maintain backward compatibility for existing users in this version. Only users who rely on the deprecated legacy mode should see the new notice, and the notice must not turn the configuration into an immediate error.


## Additional Changes
- Ensure that `tool.poetry.packages` can declare a custom destination path so included packages or modules may be installed under a different relative location in generated wheel distributions.
- Ensure that upgrading to 1.8.0 requires a requests-toolbelt release that is compatible with urllib3, so users do not end up with unsupported 0.x dependency combinations that can break HTTP-related behavior.
- Ensure that Poetry can be installed and used when its environment resolves platformdirs 4.x, while preserving compatibility with supported 3.x releases and avoiding user-visible regressions in Poetry behavior.
- Ensure that macOS installations and upgrades use a supported `xattr` 1.x dependency so users do not hit failures caused by the missing `xattr/lib_build.h` file.
- Ensure that `poetry install` does not fail solely because an optional file or directory dependency belongs to an unrequested extra and is unavailable, while still failing when that extra is explicitly selected.
- Ensure that Poetry can download and install source distributions from package servers that are misconfigured to send archive responses with HTTP gzip content encoding, without corrupting the saved archive or failing package validation because the downloaded bytes were transformed in transit.
- Ensure that user-facing guidance for installing without development dependencies uses the supported `--without dev` option instead of the deprecated `--no-dev` flag.
- Ensure that projects upgrading to Poetry 1.8.0 use `poetry-check` as the recommended pre-commit hook and stop relying on the deprecated `poetry-lock` hook in user-facing guidance and configuration expectations.
- Ensure that configuring repository credentials through environment variables is unambiguous so users know that the variable names must include the target repository name in uppercase, including `PYPI` for the default repository, for both token-based and HTTP basic authentication.
- Ensure that the 1.8.0 upgrade guidance explains how users can install and keep multiple Poetry versions in parallel instead of assuming only a single active installation.
- Ensure that users upgrading to 1.8.0 receive clearer and more complete documentation for `poetry update`, so they can better understand the command's purpose and expected usage without any change to how the command behaves.
- Ensure that the upgrade warns users that values passed to `poetry config` on the command line may fail when a value starts with `-`, and that users are shown the supported way to disambiguate such values from command options.
- Ensure that user-facing upgrade and environment guidance clearly states that the virtual environment in which Poetry itself is installed should not be activated.
- Ensure that the 1.8.0 upgrade clearly explains how `poetry run` should be interpreted when a project uses an externally managed environment, and make clear that this item resolves confusion rather than introducing new runtime behavior.
- Ensure that the documented `tox` integration guidance matches `tox` 4 behavior, so users are not told to configure isolated builds explicitly when using `tox` 4, while still preserving the required compatibility guidance for `tox` 3 users.
- Ensure that the documented behavior for package include and exclude entries correctly describes the default format handling, including directory include scenarios, without changing existing packaging behavior for users upgrading from 1.7.1.
- Ensure that the 1.8.0 upgrade guidance clearly warns users that running Poetry inside tox can break installation of dependencies from private repositories when the required credentials are not forwarded into the tox environment.
- Ensure that Poetry's installation guidance explains how users can install `pipx` before following the `pipx`-based installation path.
- Ensure that the documented `poetry add` examples for git dependencies accessed over SSH show the correct supported command usage, so users can add SSH-hosted repositories without being misled by invalid example syntax.
- Ensure that Poetry 1.8.0 no longer presents extras-dependent console script declarations as a supported or recommended `tool.poetry.scripts` configuration, while continuing to document the standard script entry format.
- Ensure that guidance for installing only runtime dependencies consistently recommends the main-only install flow, and ensure that container build examples exclude development dependencies in every install step intended to produce a production dependency set.
- Ensure that upgrade guidance makes clear that the `develop` attribute is only meaningful within Poetry and must not be relied on as a cross-tool dependency setting.
- Ensure that upgrade guidance for adding supplemental and secondary package sources clearly states that users must provide both a source name and a source URL.
- Ensure that the upgrade documents how to use PyTorch with an explicit package source so users can understand this supported dependency source configuration.
- Ensure that script entry points that depend on extras are treated as deprecated, with clear warnings during project validation and package build operations, while script entries that name undefined extras continue to be rejected as invalid configuration.
- Ensure that license declarations are evaluated against the updated set of supported licenses so users can rely on current license support without false rejections caused by the older 1.7.1 catalog.
- Ensure that package builds automatically include well-known legal files in both wheel and source distribution outputs, including common license, notice, copying, and authors files.
- Ensure that packaging workflows still recognize a Windows project as being inside a Git repository even when the repository path contains non-ASCII characters, and that build-time subprocess output is decoded consistently so encoding-related warnings or path corruption do not interfere with packaging behavior.
