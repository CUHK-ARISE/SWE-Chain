# Upgrade Specification from 1.8.1 to 1.8.2

## Bug Fixes

### Task 1 Harden lazy-wheel fallback for misbehaving package indexes
Ensure that lazy-wheel metadata retrieval gracefully falls back when a package index mishandles ranged wheel requests, including missing range metadata and other unexpected lazy-wheel failures, so package metadata resolution does not fail simply because lazy-wheel was attempted.

- **Expectation**: When a package index does not correctly support byte-range access for wheel files, Poetry should treat lazy-wheel as unavailable for that source and continue through a safe fallback path. Users should see controlled fallback behavior instead of an unexpected failure caused by malformed, incomplete, or inconsistent range responses.

- **Constraints**: Do not change behavior for indexes that already behave correctly. Apply fallback conservatively: only disable lazy-wheel when the server response is incomplete, contradictory, or otherwise unsuitable, and do not let one failure broadly regress sources that have already proven compatible.


### Task 2 Harden lazy-wheel against broken negative range responses
Ensure that lazy wheel metadata inspection continues to work when an index server incorrectly handles HTTP range requests with negative offsets, instead of accepting malformed tail responses or failing the inspection flow.

- **Expectation**: If a package index responds incorrectly to suffix range requests, wheel metadata lookup should recover automatically by falling back to a compatible retrieval path and should keep working without exposing protocol quirks to the user.

- **Constraints**: Do not degrade normal lazy metadata fetching for compliant repositories. Only treat obviously broken suffix-range behavior as incompatible, and avoid repeating the same failing request pattern once a repository has been identified as incompatible.


### Task 3 Handle misleading HTTP range support in lazy-wheel
Ensure that lazy wheel metadata retrieval correctly detects package index servers that advertise HTTP byte-range support but do not honor ranged responses, and report that condition as an explicit unsupported lazy-wheel failure instead of surfacing an internal assertion-style crash.

- **Expectation**: When Poetry lazily reads wheel metadata over HTTP, a server that falsely claims byte-range support should be detected and treated as an unsupported lazy-fetch scenario. Users should receive a deliberate lazy-wheel error classification for that condition rather than an unexpected internal failure.

- **Constraints**: Keep correct range-based metadata reads working as before, and only flag servers that return the wrong amount of data for a ranged request. Do not blur malformed wheel content errors with HTTP range-behavior problems.


### Task 4 Support redirected HEAD requests in lazy-wheel
Ensure that lazy-wheel can inspect wheel metadata when the wheel URL redirects on the initial HEAD request instead of failing before reaching the actual artifact location.

- **Expectation**: Wheel metadata lookup should work for redirected artifact URLs the same way it works for direct URLs, provided the resolved download endpoint is valid for lazy inspection.

- **Constraints**: Following redirects should only remove redirect-related failures. All existing eligibility checks for lazily reading a remote wheel must still apply after the redirect is resolved.


### Task 5 Improve lazy-wheel fallback diagnostics
Ensure that when wheel metadata cannot be retrieved through Poetry's lazy-wheel optimization, the affected repository host falls back cleanly and the reason is visible in debug output instead of only handling a narrow subset of lazy-wheel failure conditions.

- **Expectation**: Any repository-specific lazy-wheel failure should degrade gracefully. Poetry should stop using the lazy-wheel optimization for the affected host, log enough debug information to explain why it was disabled, and continue resolving package metadata through the regular wheel download flow.

- **Constraints**: Keep lazy-wheel opportunistic: working hosts should continue to benefit from it, unsupported cases should fall back safely, and one unsupported response should not unnecessarily degrade known-good host behavior.


### Task 6 Correct metadata hash validation for charset-ambiguous responses
Ensure that metadata file hash verification uses the exact response payload so metadata served without reliable charset information does not fail validation because of encoding-related byte changes.

- **Expectation**: Metadata integrity checks should reflect the actual file that was downloaded, not a transformed text version of it. Users should be able to install or resolve packages from repositories that omit charset metadata without seeing false metadata hash mismatches caused solely by response decoding.

- **Constraints**: The fix should be limited to preventing encoding-related false mismatches during metadata verification and should not change how other package files are fetched, hashed, or validated.


### Task 7 Allow `poetry add` in unnamed non-package projects
Ensure that `poetry add` works for projects running in non-package mode even when no project name is configured.

- **Expectation**: Users should be able to add dependencies in non-package projects without being forced to define a package name. The add command should accept unnamed project metadata in that mode and behave the same as a normal dependency add operation.

- **Constraints**: The fix should only remove the unnecessary failure caused by an absent project name. It should not change normal add behavior for projects that are already valid and named.


### Task 8 Correct Poetry install guidance for package-mode
Ensure that the install-time guidance for projects that should not be installed as packages points users to the supported `package-mode` configuration instead of obsolete non-package mode terminology.

- **Expectation**: Users who see the install warning should be guided with the current, supported configuration name for dependency-only workflows, so the message is accurate and actionable without relying on outdated terminology.

- **Constraints**: Keep the existing install behavior and warning scenario intact while correcting the configuration advice so it matches the supported product surface.
