# Upgrade Specification from 1.8.2 to 1.8.3

## Bug Fixes

### Task 1 Support untagged CPython builds with trailing plus versions
Ensure that untagged CPython builds whose reported full version ends with a trailing '+' are accepted and interpreted as the corresponding standard Python release when Poetry evaluates environment and dependency markers.

- **Expectation**: Poetry should treat untagged CPython interpreters that append '+' to their version string as the same release without the suffix when determining Python-version-based compatibility.

- **Constraints**: The fix should be limited to smoothing over the special CPython version suffix and should not change how standard Python versions or unrelated environment metadata are interpreted.


### Task 2 Handle FIPS-restricted MD5 dependency hashes
Ensure that dependency downloads remain processable on FIPS-enabled systems when a package link advertises an MD5 hash that the runtime refuses to initialize, instead of failing before SHA256 can be calculated.

- **Expectation**: If the environment blocks a legacy hash algorithm advertised by a package source, dependency resolution and artifact verification should fall back to a supported SHA256 calculation rather than erroring out solely because that legacy hash cannot be created.

- **Constraints**: The fix should be limited to hash-algorithm availability problems and must not change successful hashing flows or the resulting SHA256-based artifact identification.


### Task 3 Raise an error for unsupported wheel metadata versions
Ensure that wheels with unsupported or unrecognized package metadata versions are rejected explicitly instead of being interpreted as having empty dependency metadata.

- **Expectation**: When Poetry reads dependency information from a wheel, unsupported metadata formats should produce a clear failure instead of making the package look dependency-free. Supported wheel metadata should continue to resolve package information normally.

- **Constraints**: Do not hide metadata parsing failures by substituting incomplete package information. Only packages using unsupported metadata formats should fail; valid wheels should remain unaffected.


### Task 4 Handle Trailing Slashes In Git Source URLs
Ensure that git dependency source URLs ending with a trailing slash are handled the same as equivalent URLs without the trailing slash when deriving the repository name.

- **Expectation**: Git-based dependency sources should behave consistently whether or not the configured URL ends with a trailing slash. A valid repository URL must still resolve to the same package or repository name regardless of that formatting difference.

- **Constraints**: This fix should be limited to normalizing trailing slashes and must not alter how other valid git URLs are interpreted.


### Task 5 Remove false installability warnings from poetry self commands
Ensure that poetry self commands do not emit a misleading warning that the current project cannot be installed when operating on Poetry's own managed environment.

- **Expectation**: When users run Poetry's self-management commands, Poetry should recognize that its own maintenance project is configuration-only rather than an installable package, and it should stop showing the erroneous installability warning.

- **Constraints**: The fix should only correct the self-maintenance workflow and should not change how regular Poetry projects are classified or handled outside that workflow.


### Task 6 Prevent sporadic poetry install crashes from progress output races
Ensure that `poetry install` does not sporadically fail with a `KeyError` when concurrent install operations update progress output, and that progress rendering capability is interpreted consistently for the duration of an install run.

- **Expectation**: Install runs should treat rich progress output support as a stable capability of the run, not something that can temporarily change while work is already in progress. Temporary terminal-formatting changes during output updates must not crash installation, and dry runs should continue to avoid rich progress behavior.

- **Constraints**: The fix must remove instability in progress-output detection without changing whether dry runs use rich output, without requiring decorated terminal support, and without altering normal behavior for environments that already use plain output only.


### Task 7 Clarify `poetry add` help to mention installation
Ensure that the `poetry add` command help clearly communicates that adding a dependency also installs it, so the CLI description matches the command's actual behavior.

- **Expectation**: Users should see unambiguous CLI guidance that `poetry add` both registers a dependency in the project configuration and installs it, with consistent wording wherever the command is summarized.

- **Constraints**: This update should improve the accuracy of the command help without changing the workflow or adding new behavior.


### Task 8 Clarify README extension support in poetry new
Ensure that `poetry new --readme` is presented and supported as a general README file extension option with `md` as the default, instead of implying that only `md` and `rst` are valid values.

- **Expectation**: Users creating a new project should be able to choose the README extension they want. The command should communicate that Markdown is the default, while not misleading users into thinking the option only supports two predefined formats.

- **Constraints**: Preserve the existing default behavior while removing misleading restrictions from the user-facing contract. The update should clarify supported input without changing unrelated project creation behavior.


## Documentation

### Task 9 Correct `poetry shell` help for shell detection and fallback
Ensure that `poetry shell` provides accurate user-facing guidance about how it chooses and launches a shell inside the project's virtual environment, including the correct platform-specific fallback environment variable and the creation of a virtual environment when one is missing.

- **Expectation**: Users reading `poetry shell` help should see behavior that matches what the command actually does: Poetry automatically chooses an appropriate shell, only uses the platform shell setting as a fallback, and can create the project environment if needed.

- **Constraints**: This update should remove misleading guidance without altering how the command behaves when users actually run it.


### Task 10 Document git subdirectory support in poetry add help
Ensure that `poetry add` help explains how to add a dependency from a subdirectory within a Git repository so users can discover the supported syntax directly from the CLI.

- **Expectation**: Users viewing `poetry add` help should be able to understand, without consulting external documentation, that dependencies can be added from a package living in a subfolder of a Git repository.

- **Constraints**: The change should improve discoverability only. Existing ways of adding dependencies should continue to behave the same, with no new operational requirements introduced by the upgrade.


## Additional Changes
- Ensure that dependency handling can process packages whose distribution metadata uses version 2.3, instead of failing during package inspection or package creation when those packages are encountered.
- Ensure that users upgrading to 1.8.3 are explicitly informed that credential configuration supports an interactive flow, so authenticated setup is easier to discover and understand.
- Ensure that the 1.8.3 upgrade provides clear guidance for optional advanced installation steps while leaving existing installation and runtime behavior unchanged.
- Ensure that the `poetry publish` documentation clearly points users to the credential configuration guidance needed before publishing to authenticated package repositories.
- Ensure that users can understand how to configure repository access credentials through environment variables, including when repository URL configuration also needs to be supplied through environment variables.
- Ensure that Poetry's user guidance for virtual environments no longer implies that containers are a normal reason to disable Poetry-managed virtual environments, and clearly states when disabling them is appropriate.
- Ensure that the 1.8.3 upgrade no longer instructs users to seed project environments with keyring backend packages as part of normal keyring setup, and clarify that this release is a documentation correction rather than a runtime behavior change.
- Ensure that documentation for dependency extras clearly shows how to declare multiple extras for a single dependency in pyproject.toml, and distinguish that format from the Poetry CLI extras syntax to prevent missing dependencies caused by configuration mistakes.
- Ensure that users publishing to TestPyPI with `poetry publish` can understand how to configure authentication credentials without ambiguity.
- Ensure that Poetry clearly communicates that the project's Python constraint is a compatibility declaration rather than a managed dependency, so users understand they must provide a compatible interpreter themselves.
- Ensure that users managing Poetry plugins through pipx are given the correct uninstall flow for injected plugins, so plugin removal guidance matches the pipx command intended for removing previously injected packages.
