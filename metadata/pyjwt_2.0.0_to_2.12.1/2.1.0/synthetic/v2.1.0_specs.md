# Upgrade Specification from 2.0.1 to 2.1.0

## New Features

### Task 1 Decouple JWT claim validation from signature verification
Ensure that JWT decoding can validate configured standard claims even when signature verification is disabled, without turning claim validation into a mandatory default for unsigned decoding.

- **Expectation**: Applications should be able to inspect a JWT without verifying its signature and still opt into validating specific standard claims. Disabling signature verification should no longer force all claim validation off, but unsigned decoding should remain permissive by default unless the caller asks for a specific claim check.

- **Constraints**: This upgrade should add optional claim enforcement for unsigned decoding without breaking callers that only disable signature verification to read token contents. Existing signed-token decoding behavior should remain consistent, and enabling a claim check should have the same user-visible effect regardless of whether signature verification is on.


### Task 2 Support JWKs without alg while requiring kty
Ensure that JWK loading accepts supported keys that omit `alg` by deriving the algorithm from the key metadata, and ensure that JWKs without `kty` or with unsupported key type or curve values are rejected as invalid.

- **Expectation**: Applications should be able to load common JWKs from providers that omit `alg` and still get the correct signing algorithm automatically, while malformed or ambiguous keys fail fast with a key validation error instead of being accepted without a determinable algorithm.

- **Constraints**: The upgrade should expand compatibility for valid alg-less JWKs without weakening input validation. Keys that clearly identify a supported algorithm should continue to load, and keys that do not provide enough valid metadata should be rejected rather than guessed.


### Task 3 Default signing-key caching for PyJWKClient
Ensure that repeated PyJWKClient signing-key lookups for the same key ID are cached by default to reduce unnecessary JWKS network requests, while still allowing applications to disable caching or limit cache size when they need different runtime behavior.

- **Expectation**: By default, signing-key resolution should behave like a per-client cache keyed by key ID so repeated lookups avoid another remote JWKS retrieval. Applications that require fresh lookups every time must be able to opt out, and applications that want bounded memory use must be able to set the cache capacity.

- **Constraints**: Caching should improve repeated lookup performance without changing which signing key is chosen for a given key ID. Consumers must keep control over whether lookups are cached and how large the cache may grow.


### Task 4 Add ES256K support and infer algorithms for JWKs without alg
Ensure that the library supports ES256K-backed elliptic-curve keys and can load supported JWKs without an explicit alg by deriving the correct default algorithm from the key metadata, while rejecting missing or unsupported key type and curve combinations.

- **Expectation**: Users should be able to use secp256k1 keys with ES256K and supply common JWKs without needing to repeat alg when the key itself already determines the algorithm. The library should choose the expected default algorithm for supported key types and fail clearly when the key metadata is incomplete or unsupported.

- **Constraints**: The new behavior must extend supported key loading without weakening validation. Adding convenience for omitted alg must not guess across unsupported key formats or accept malformed curve parameters.


### Task 5 Support Ed25519 JWK loading and JWK algorithm inference without alg
Ensure that Ed25519-based JWKs can be consumed through the library's JWK loading flow for EdDSA usage, and ensure that supported JWKs without an explicit algorithm can still be interpreted from their key type and curve instead of failing solely because alg is absent.

- **Expectation**: The library should accept standard Ed25519 JWKs for EdDSA signing and verification workflows, and it should be able to choose the correct algorithm for supported JWKs even when the JWK does not declare alg explicitly. Invalid or unsupported JWK structures should still fail clearly rather than being silently accepted.

- **Constraints**: Keep backward-compatible behavior for valid existing inputs while broadening support for standards-compliant JWKs that omit alg. Reject ambiguous, malformed, or unsupported key descriptions instead of guessing.


### Task 6 Add Ed25519 JWK import and export support
Ensure that Ed25519Algorithm supports JWK interoperability for Ed25519 keys, including exporting supported Ed25519 public and private keys to JWK form and loading valid Ed25519 OKP JWK inputs back into usable key objects, while rejecting invalid or incompatible JWK data with key validation errors.

- **Expectation**: Users should be able to round-trip Ed25519 keys through JWKs with Ed25519Algorithm. Public keys should export and import as public JWKs, private keys should export and import as private JWKs, and malformed or unsupported inputs should fail with a key validation error instead of producing a usable key.

- **Constraints**: The new capability is limited to valid Ed25519 JWK interoperability. It must preserve the distinction between public-only and private keys, avoid leaking private data when exporting a public key, and consistently reject malformed or non-Ed25519 key descriptions.


### Task 7 Expose PyJWK and PyJWKSet in the top-level jwt API
Ensure that applications upgrading to 2.1.0 can access JWK model types directly from the public `jwt` package so they can import and use `PyJWK` and `PyJWKSet` without relying on non-top-level module imports.

- **Expectation**: The library should treat `PyJWK` and `PyJWKSet` as first-class public API types that users can import directly from `jwt`, just like other documented top-level JWT helpers and classes.

- **Constraints**: The upgrade should be additive and backward-compatible: existing public imports should continue to work, while the new JWK types become directly available through the main package entry point.


## Bug Fixes

### Task 8 Support JWKs That Omit alg
Ensure that JWK loading accepts valid keys that omit the `alg` field, derives a usable algorithm from the key's declared type metadata, and rejects malformed or unsupported key descriptions with key-validation errors instead of failing solely because `alg` is absent.

- **Expectation**: Loading a JWK should work even if the key does not name an algorithm, as long as the key metadata clearly identifies one. The library should infer the expected algorithm from the key type information, honor an algorithm explicitly provided by the caller, and reject incomplete or unsupported key metadata with a validation error.

- **Constraints**: Keep existing valid key-loading flows working, but add compatibility for algorithm-less JWKs only when their metadata is sufficient to identify a safe default. Reject keys whose type information is absent or unsupported instead of guessing beyond the documented mappings.


### Task 9 Allow EC verification with private keys
Ensure that ECDSA token verification accepts an elliptic-curve private key as a valid verification input, so applications can verify signatures with the same key object they already hold and get behavior consistent with other asymmetric algorithms that already allow this.

- **Expectation**: JWT verification for EC-based algorithms should work whether the caller provides the public key directly or the matching private key object. A valid signature should still verify successfully, and invalid signatures should still be rejected.

- **Constraints**: The upgrade should broaden accepted verification inputs without changing normal verification behavior. Existing successful verification flows must continue to work, and the library should not weaken signature rejection rules.


### Task 10 Expose InvalidKeyError from the top-level jwt API
Ensure that the JWT package exposes the missing InvalidKeyError exception from its top-level public API so callers can import and handle invalid-key failures consistently with other JWT exception classes.

- **Expectation**: After upgrading, applications should be able to access the invalid-key exception from the main JWT package without reaching into a submodule, and it should behave like the rest of the package's public error types.

- **Constraints**: The update should expand the public error surface without changing how existing JWT exceptions are imported or how invalid-key failures are otherwise interpreted.


## Additional Changes
- Ensure JWK-related usage guidance reflects canonical unpadded Base64URL member values, while preserving the same runtime behavior for consumers upgrading from 2.0.1 to 2.1.0.
