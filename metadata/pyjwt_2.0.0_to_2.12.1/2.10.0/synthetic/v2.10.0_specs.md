# Upgrade Specification from 2.9.0 to 2.10.0

## New Features

### Task 1 Support PyJWK inputs for JWT and JWS encoding
Ensure that JWT and JWS encoding accepts JWK-based keys directly and selects an appropriate default signing algorithm when callers do not pass one.

- **Expectation**: Applications upgrading to 2.10.0 should be able to pass a JWK object directly to JWT or JWS encoding APIs. If they do not specify an algorithm, encoding should automatically use the algorithm declared by the JWK when available and otherwise preserve the standard HS256 default.

- **Constraints**: This upgrade should broaden the accepted key input format without changing established encode behavior for existing callers that already pass raw keys or explicitly choose an algorithm.


## Bug Fixes

### Task 2 Improve warning attribution and error surfaces in JWT decoding and JWK handling
Ensure that upgrading to PyJWT 2.10.0 gives applications clearer caller-facing warnings and more consistent public exception behavior for JWT decoding, claim validation, JWK parsing, JWKS retrieval, and signature verification inputs without changing normal token-processing behavior.

- **Expectation**: Warnings raised by deprecated decode-time arguments should clearly point to the application code that triggered them. Invalid JWT payloads, time claims, algorithm headers, and JWK inputs should fail through the library's documented exception types with predictable causes instead of exposing confusing low-level parser details. Network failures during JWKS retrieval should remain wrapped in the client error type while retaining the underlying network error, and callers should be able to provide allowed algorithms using common sequence types.

- **Constraints**: Keep normal token handling and existing public APIs stable. The upgrade should improve diagnostics and input compatibility only, without changing what valid tokens do or reclassifying established failure cases into different kinds of public errors.


### Task 3 Fix EC JWK export to use fixed-width values
Ensure that elliptic-curve keys exported as JWK use fixed-length base64url-encoded values for their key material so generated EC JWKs are accepted by consumers that enforce the JWK field width required by the selected curve.

- **Expectation**: Exporting an EC key to JWK should always produce curve-sized coordinate and private-value fields, including any required leading zero bytes, so the output is interoperable with strict JWK validators. Integer encoding utilities should optionally support fixed-width output without altering normal minimal-width encoding for existing callers.

- **Constraints**: The fix should be backward-compatible for callers that do not request fixed-width encoding, should keep existing invalid-input handling intact, and should not change unrelated key formats or serialization flows.


## Dependency Updates

### Task 4 Relax JWT decode algorithm enforcement
Ensure that JWT decoding no longer fails solely because the caller omitted a non-empty algorithms list at the JWT API layer, and ensure that turning off signature verification also leaves subject and JWT ID validation off by default unless explicitly requested.

- **Expectation**: JWT decoding should follow one source of truth for algorithm validation instead of rejecting requests early in a separate layer. If signature verification is disabled, claim validation that depends on trusted token contents should stay disabled by default unless the caller deliberately turns it on.

- **Constraints**: Avoid duplicate validation rules between decoding layers, and do not leave extra claim checks unexpectedly active when signature verification has been disabled. Explicit caller choices should continue to take precedence over defaults.


### Task 5 Broaden JWT decode inputs for algorithms and issuers
Ensure that JWT decode and verification APIs accept broader collection types for allowed algorithms and issuers, and that decode calls continue to expose issuer, subject, and algorithm validation through the public API with stable observable error behavior.

- **Expectation**: Callers should be able to pass broader sequence-based collections when declaring accepted algorithms or issuers during JWT decoding, while continuing to rely on the same public decode flow for issuer and subject validation. Invalid or missing issuer and algorithm conditions should still surface as the library's normal decode errors.

- **Constraints**: Existing decode callers should keep working, and the upgrade should expand accepted inputs rather than forcing API rewrites. Validation outcomes should remain consistent from a user perspective even as input flexibility increases.


## Breaking Changes

### Task 6 Require explicit none algorithm for unsecured JWT encoding
Ensure that applications using the library no longer rely on `algorithm=None` to create unsecured JWTs, and instead explicitly request the `none` algorithm when an unsigned token is intended.

- **Expectation**: Unsigned JWTs should only be produced through an explicit opt-in. If the caller does not choose an algorithm, the library should behave like a normal signed-token workflow instead of silently creating an unsecured token.

- **Constraints**: The upgrade must close the ambiguity between no algorithm and the none algorithm without removing supported explicit unsecured-token behavior or breaking normal key-based algorithm selection.


### Task 7 Validate JWT subject and ID claims on decode
Ensure that JWT decoding enforces valid `sub` (subject) and `jti` (JWT ID) claim semantics, supports subject-based matching during decode, and preserves compatibility for tokens that omit these optional claims unless the caller explicitly requires or verifies them.

- **Expectation**: Decoding a JWT should now reject malformed subject or JWT ID claims and optionally enforce that the token subject matches an expected subject provided by the caller. Tokens that carry valid values should continue to decode normally, and tokens that simply omit these optional claims should remain acceptable unless the application explicitly requires them.

- **Constraints**: The upgrade should be strict about malformed or mismatched values without turning optional claims into mandatory ones. Applications must be able to keep or relax the new validations through decode options, and disabling signature verification should not automatically force these additional claim checks to run.


### Task 8 Adopt pyproject-based packaging and remove setup.py
Ensure that the library can be built and installed using modern PEP 517/518 tooling with project metadata defined through `pyproject.toml`, without relying on a legacy `setup.py` entrypoint.

- **Expectation**: The release should modernize packaging so the library works with current Python build and install tools without changing the produced package contents or requiring legacy packaging commands.

- **Constraints**: The update should be limited to packaging behavior, keep normal installation outcomes stable, and not change how the library behaves at runtime.


## Additional Changes
- Ensure that version 2.10.0 is treated as a breaking compatibility update that no longer supports Python 3.8 and is used only on Python 3.9 or newer.
- Ensure that upgrading to 2.10.0 restores successful hosted documentation builds by providing the required Read the Docs project configuration, without changing runtime JWT behavior.
- Ensure that the upgrade to PyJWT 2.10.0 reflects the correct user-facing behavior for `iat` claim validation so consumers can rely on the documented exception types when decoding tokens.
- Ensure that the documented OIDC login flow uses decode_complete() in the correct scope and requires an explicit algorithms argument so integrators follow the intended decoding contract.
- Ensure that the official PyJWT usage documentation presents working, up-to-date examples so users can follow documented JWT usage patterns without encountering broken or misleading guidance after upgrading to 2.10.0.
- Ensure that the library's integer-to-base64url encoding behavior is understood as rejecting invalid negative integer input, and that upgrading does not imply any new runtime behavior beyond clarifying this existing contract.
- Ensure that the `jwt.decode` API documentation accurately describes the accepted `audience` parameter so users can understand the supported input contract without ambiguity.
- Ensure that the library officially supports Python 3.13 so users can upgrade their interpreter to Python 3.13 and continue using the library without losing existing functionality.
- Ensure that the project publishes a dedicated security policy so library users can identify the official security guidance and vulnerability reporting path, without changing existing runtime behavior.
- Ensure that the library documentation clearly explains how users can encode and decode JWTs with the PS256 algorithm, so supported PS256 usage is discoverable during upgrade to 2.10.0.
- Ensure that the library clearly documents PyJWK as a supported public API, including how PyJWK instances can be used with JWT encoding and decoding and which PyJWK metadata is available to callers.
- Ensure that the 2.10.0 upgrade clearly documents EdDSA as a supported algorithm choice for JWT encoding and decoding, so users can discover and apply EdDSA usage through the public library guidance.
- Ensure that the development workflow validates `pyproject.toml` and related YAML configuration files during pre-commit so packaging metadata remains compliant and configuration issues are caught before changes are committed.
- Ensure that the library's upgrade guidance and public usage documentation clearly cover how to decode JWTs signed with the ES256 algorithm using compatible EC key material.
- Ensure that the `decode_complete` helper is part of the public top-level `jwt` package API so callers can access it directly from `jwt` without reaching into `jwt.api_jwt`.
