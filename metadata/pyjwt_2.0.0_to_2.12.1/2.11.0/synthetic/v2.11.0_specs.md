# Upgrade Specification from 2.10.1 to 2.11.0

## New Features

### Task 1 Make PyJWKSet directly iterable
Ensure that JWK sets can be consumed as standard iterables so application code can loop over their keys directly without depending on internal collection access.

- **Expectation**: Users should be able to treat a JWK set like a normal collection of keys and iterate over it directly, with each iteration item being one key object from the set.

- **Constraints**: The new iterable behavior should be additive only: it should make key sets easier to consume without changing how key lookup or missing-key failures behave.


## Bug Fixes

### Task 2 Reject mismatched asymmetric key families during JWT verification
Ensure that JWT operations reject asymmetric keys that do not belong to the selected algorithm family, so using RSA, ECDSA, or EdDSA algorithms with incompatible key material fails as an invalid-key condition instead of surfacing low-level cryptography type errors.

- **Expectation**: JWT signing and verification should confirm that the provided asymmetric key matches the selected algorithm type before using it. Incompatible RSA, elliptic-curve, and EdDSA keys should be rejected immediately with a clear invalid-key failure, and any explicit elliptic-curve restriction should be enforced when applicable.

- **Constraints**: Keys that already match the selected algorithm should continue to work unchanged. The update should only make incompatible or unsupported asymmetric keys fail earlier and more clearly, without changing non-cryptography algorithm behavior.


### Task 3 Make Decode Options Typed and Consistent
Ensure that JWT decoding exposes a clear, supported options contract and applies decode options consistently across `jwt.decode`, `jwt.decode_complete`, and `PyJWT` instances, especially when `verify_signature` is disabled or custom verification options are supplied.

- **Expectation**: Decoding APIs should have a well-defined options schema that users can rely on. Turning off signature verification should also turn off dependent claim validation by default unless the caller explicitly re-enables a specific check, and custom defaults should merge predictably with per-call options.

- **Constraints**: Default decoding behavior should stay secure and backward compatible. Relaxed validation should only happen when a caller opts into it, and existing warning behavior for deprecated decode arguments should not be removed.


### Task 4 Remove invalid-escape warnings from JWT decode APIs
Ensure that importing the JWT decoding APIs does not emit invalid-escape SyntaxWarning or DeprecationWarning noise, and ensure that the public decode contract clearly reflects the supported issuer input form and the dictionary-shaped return values of decode-related APIs.

- **Expectation**: Upgrading users should be able to import and use the JWT decoding APIs without spurious interpreter warnings, and the published API surface should accurately describe what issuer values are accepted and what decoded data is returned.

- **Constraints**: The upgrade should be non-breaking for normal JWT decoding. It should eliminate warning noise and improve API clarity without changing how tokens are validated or the structure of successful decode results.


### Task 5 Normalize PyJWT decode options and expose typed option contracts
Ensure that upgrading to PyJWT 2.11.0 provides a consistent, documented `options` contract for `jwt.decode()`, `jwt.decode_complete()`, and `PyJWT(options=...)`, especially when signature verification is disabled and when applications rely on static typing for JWT options and key aliases.

- **Expectation**: The library should present one clear, supported configuration model for JWT decoding and signature handling. Callers should be able to understand which options exist, type-check them reliably, and expect disabled signature verification to turn off related claim validation unless those checks are explicitly turned back on.

- **Constraints**: The upgrade should refine configuration behavior and documentation without changing the basic JWT API shape. Existing successful decode flows should continue to work unless they depended on ambiguous or inconsistent option handling.


## Dependency Updates

### Task 6 Enforce string issuer claim validation in JWT encode and decode flows
Ensure that JWT issuer handling enforces the `iss` claim as a string and that issuer verification during decode fails predictably when the token issuer claim or supplied issuer value is invalid.

- **Expectation**: JWT issuer values must be treated as textual identifiers. Encoding should fail fast if a token payload uses a non-text issuer, and decoding with issuer verification should only accept tokens whose issuer is a string that matches the expected issuer or one of the allowed issuers. Invalid issuer inputs should produce issuer-related validation errors rather than undefined type-driven failures.

- **Constraints**: The upgrade should narrow invalid issuer handling without changing unrelated JWT behavior. Existing valid string-based issuer workflows must keep working, missing issuer claims should still be reported through the established required-claim path, and multi-issuer allowlists should remain supported.


### Task 7 Add configurable minimum key length validation for HMAC and RSA JWT operations
Ensure that JWT signing and signature verification detect insecure HMAC and RSA key sizes, warn by default for backward compatibility, and support opt-in strict rejection of undersized keys.

- **Expectation**: JWT operations should surface insecure signing material to callers. By default, existing flows should remain compatible but emit a dedicated warning when an HMAC secret or RSA key is below the library's minimum recommendation. Applications that require strict enforcement should be able to opt in so the operation fails with an invalid-key error rather than proceeding.

- **Constraints**: Only undersized HMAC and RSA keys should be affected. Existing callers should not be forced into failures unless they explicitly enable strict enforcement, and keys that satisfy the minimum recommendation should continue to work without new warnings or errors.


### Task 8 Isolate PyJWT JWS state and tighten issuer validation
Ensure that upgrading to PyJWT 2.11.0 preserves expected JWT encode and decode usage while making `PyJWT` instance options apply consistently to signing and verification, and ensure issuer claims are validated strictly as strings during both token creation and issuer matching.

- **Expectation**: Each JWT handler should behave as if it owns its own signing and verification configuration, so instance-level options work predictably and do not depend on shared global state. Token creation should only accept string issuer claims, and issuer-constrained decoding should only succeed when the token issuer is a valid string that matches the configured allowed issuer or issuer set.

- **Constraints**: The upgrade should improve option isolation and issuer validation without removing the existing top-level JWT API or changing unrelated claim-validation rules. Runtime behavior should remain backward-compatible except where stricter issuer type handling and correctly applied instance options are now enforced.


## Breaking Changes

### Task 9 Enforce RFC-compliant ECDSA curve validation
Ensure that ECDSA JWT operations reject elliptic-curve keys that do not match the selected ES algorithm's required curve, while continuing to accept correctly matched keys.

- **Expectation**: Using an ECDSA JWT algorithm with the wrong elliptic-curve key should fail immediately instead of producing or accepting a token. Correctly matched keys should continue to work for signing and verification.

- **Constraints**: The change should tighten security for standard ES algorithms without breaking valid same-curve usage or removing intentionally unrestricted ECAlgorithm behavior for advanced callers.


## Typing Updates

### Task 10 Support fractional JWK cache lifespan and timeout values
Ensure that JWK client timeout and cache lifespan parameters are supported as floating-point durations so users can supply fractional values, while keeping existing integer-based usage valid and unchanged.

- **Expectation**: Users should be able to configure JWK retrieval timeouts and cache lifetimes with fractional durations, and those values should be recognized as part of the supported public API rather than as type mismatches.

- **Constraints**: The upgrade must be backward compatible for existing duration settings and should only expand the accepted contract to include fractional values, without introducing unrelated behavior changes.


### Task 11 Refine PyJWT public typing contracts for supported Python versions
Ensure that upgrading to 2.11.0 provides complete, Python-version-compatible public typing for PyJWT APIs, including key, token, option, and JWK-related interfaces, without changing normal JWT signing, verification, serialization, or decode behavior.

- **Expectation**: The upgrade should make the library's public typing accurate and complete for supported Python versions so that IDEs, static analyzers, and generated documentation correctly describe supported key types, token inputs, options, and decoded JWT/JWS object shapes, while the runtime behavior users already depend on stays the same.

- **Constraints**: This upgrade is a typing-contract refinement, not a cryptographic or serialization behavior change. Existing JWT encode/decode flows, JWK serialization modes, supported key categories, and current error conditions must remain stable.


### Task 12 Stabilize PyJWT key typing and documentation builds
Ensure that upgrading to PyJWT 2.11.0 preserves a usable public key-type and option surface for API documentation builds, while keeping `PyJWT` encode/decode behavior consistent when JWT options are merged and delegated to internal JWS processing.

- **Expectation**: The library should keep its documented key aliases visible to documentation tooling, and JWT operations should continue to accept the documented key forms while applying JWT and JWS options consistently through a single configured object model.

- **Constraints**: Documentation-only environments should not fail because optional crypto types are missing, and existing token verification defaults should remain stable apart from the clarified accepted input shapes and internal option propagation.


## Additional Changes
- Ensure upgrading to 2.11.0 removes package build warnings caused by deprecated license metadata and requires a compatible setuptools version so builds succeed cleanly under current packaging standards.
- Ensure that upgrading to 2.11.0 remains behaviorally transparent for application runtime usage while improving contributor and CI workflow efficiency by avoiding redundant package builds during multi-environment test setup.
- Ensure that the library officially supports CPython 3.14 and PyPy 3.10 and 3.11 while preserving existing user-facing JWT behavior for already supported runtimes.
- Ensure that upgrading to 2.11.0 replaces deprecated `pep517`-based package build validation with the supported `build` tooling, while preserving existing runtime library behavior for consumers.
- Ensure that upgrading from 2.10.1 to 2.11.0 for this release item introduces no user-visible runtime or public API behavior changes, because the documented update is limited to development tooling, coverage reporting, and test suite maintenance.
- Ensure that changelog entries in the 2.11.0 release documentation render pull request references consistently as proper links rather than malformed or ambiguous link text.
- Ensure that users understand that configuring decode-time leeway also affects validation of the `nbf` claim, so JWTs can tolerate expected clock skew around their not-before time.
- Ensure that the library documentation fully describes the registered JWT claims by explicitly documenting the `sub` and `jti` claims, clarifying their intended purpose and preserving existing runtime behavior.
- Ensure that upgrading to 2.11.0 preserves existing runtime behavior while reflecting the library's modernized typing surface, including replacement of deprecated `typing` collection aliases and use of standard built-in generic annotations where applicable.
