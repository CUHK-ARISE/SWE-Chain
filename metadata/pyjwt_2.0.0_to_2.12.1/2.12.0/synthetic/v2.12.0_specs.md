# Upgrade Specification from 2.11.0 to 2.12.0

## Bug Fixes

### Task 1 Close JWKS HTTP error responses during connection failures
Ensure that JWKS fetch failures caused by HTTP response errors do not leave open response resources, while callers still receive the same PyJWKClientConnectionError failure signal from PyJWKClient operations.

- **Expectation**: If the JWKS endpoint returns an HTTP error, the client should clean up the failed response object and still report the problem as the library's normal JWKS connection error. Upgrading should remove leaked-resource warnings during failed JWKS fetches without changing how applications detect the failure.

- **Constraints**: The fix must only improve cleanup on failed HTTP fetches. It must not alter normal successful JWKS retrieval behavior or require callers to handle a different outward-facing error type for connection failures.


### Task 2 Validate JWT critical header extensions on decode
Ensure that token-reading behavior enforces RFC 7515 critical-header rules so JWTs/JWSs with malformed, unsupported, or inconsistent `crit` declarations are rejected, while correctly declared supported critical extensions continue to be accepted.

- **Expectation**: Token decoding must honor JWT critical-header semantics. If a token declares critical extensions that the library does not understand, declares them in an invalid format, or marks an extension as critical without actually providing it, the token should be treated as invalid. Tokens that use the supported critical extension correctly should continue to decode normally.

- **Constraints**: Keep existing valid token flows working. The upgrade should harden token consumption without changing unrelated header validation behavior or breaking tokens that do not rely on unsupported critical extensions.


### Task 3 Honor PyJWK algorithms when encoding without an explicit algorithm
Ensure that encoding with a PyJWK-backed key honors the key's declared signing algorithm when the caller does not explicitly provide an algorithm, so generated JWS/JWT tokens use the expected algorithm instead of silently defaulting to HS256.

- **Expectation**: If a caller supplies a JWK that already declares its algorithm, encoding should automatically use that algorithm whenever the caller leaves the algorithm unspecified. Existing behavior for callers that explicitly choose an algorithm, explicitly pass `None`, or use non-JWK keys should remain consistent.

- **Constraints**: Limit the fix to the missing-algorithm case for JWK-based encoding. Other encoding flows should keep their prior defaults and override rules.


## Typing Updates

### Task 4 Type PyJWKSet.keys as PyJWK instances
Ensure that `PyJWKSet.keys` is exposed as a concretely typed collection of parsed JWK objects so downstream consumers do not see unknown member types when using static analysis.

- **Expectation**: Applications upgrading to 2.12.0 should receive accurate type information for the keys exposed by a JWK set, improving IDE and type-checker support without changing JWK set runtime behavior.

- **Constraints**: The upgrade should only improve developer tooling and type visibility. Existing runtime behavior for valid, invalid, empty, or unsupported JWK sets should remain the same.


## Documentation

### Task 5 Document PyJWKClient caching and key lookup semantics
Ensure that `PyJWKClient` is documented as a supported public API with clear guidance for its two-tier caching model, JWKS retrieval flow, signing-key lookup behavior, and the observable errors callers may receive.

- **Expectation**: `PyJWKClient` should be documented so consumers understand what is cached by default, how long cached JWKS data remains valid, when optional signing-key caching applies, when the client refreshes data from the endpoint, and how signing-key lookup behaves when a key is missing or the endpoint cannot be reached.

- **Constraints**: Clarify the existing behavior without implying a functional redesign. The documentation must not suggest that signing keys are cached by default, that all lookups always hit the network, or that network and missing-key failures are hidden from callers.


## Performance Improvements

### Task 6 Reduce PyJWK per-instance memory usage
Ensure that creating a PyJWK does not keep an unnecessary copy or reference of the full default algorithms registry on each instance, while preserving existing algorithm selection and failure behavior.

- **Expectation**: Creating a JWK object should use only the algorithm implementation needed for that key instead of storing the whole algorithm registry on the object. From a caller perspective, supported keys should continue to load normally and unsupported keys should still fail with the documented JWK error type.

- **Constraints**: The optimization must be behavior-preserving for normal consumers: valid keys should behave the same, invalid or unsupported keys should still fail in the same way, and the API surface should remain unchanged.
