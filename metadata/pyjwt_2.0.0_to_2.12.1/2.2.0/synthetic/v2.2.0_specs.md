# Upgrade Specification from 2.1.0 to 2.2.0

## New Features

### Task 1 Expand EdDSA support to Ed448 and OKP keys
Ensure that EdDSA supports both Ed25519 and Ed448 Octet Key Pair keys, and that integrations using the previous Ed25519-specific algorithm class are aligned with the generalized OKP algorithm interface.

- **Expectation**: Users should be able to sign, verify, import, and export EdDSA keys for both Ed25519 and Ed448 through the generalized OKP algorithm interface, while invalid or unsupported OKP key material is still rejected in a consistent way.

- **Constraints**: Do not regress existing Ed25519 EdDSA flows while adding Ed448 support. Keep the verification contract stable, preserve JWK round-tripping for supported OKP keys, and continue rejecting malformed or unsupported keys instead of silently accepting them.


## Bug Fixes

### Task 2 Adopt timezone-aware UTC handling for JWT claim validation
Ensure that upgrading to 2.2.0 preserves JWT decoding behavior while using timezone-aware UTC semantics for time-based claims and relying on the library's explicit decode parameters for audience, issuer, and leeway.

- **Expectation**: JWT decoding should continue to work with the documented claim-validation inputs, but time-based claims must now be interpreted against the current UTC time using timezone-aware semantics. Consumers should call the decode API through its supported audience, issuer, and leeway arguments rather than depending on unspecified extra keyword forwarding.

- **Constraints**: Keep existing JWT validation outcomes stable for supported inputs while modernizing UTC time handling. The upgrade should narrow integrations to the documented decode contract without introducing unrelated behavior changes.


### Task 3 Accept JWKs without a use claim as signing keys
Ensure that JWKS signing-key discovery accepts JWK entries whose `use` claim is omitted, so valid signing keys are not excluded solely because they do not explicitly declare `use: sig`.

- **Expectation**: Signing-key lookup should treat a missing JWK use declaration as compatible with signing, while still returning only keys that are identifiable and still failing clearly when the JWKS does not contain any usable signing keys.

- **Constraints**: The update should expand compatibility for valid JWKS documents without weakening key filtering rules or changing the way missing usable signing keys are reported.


### Task 4 Honor JWT header algorithm during encoding
Ensure that `jwt.encode()` honors a caller-provided JWT header algorithm so applications can control the encoded token's algorithm through the header, including when the `algorithm` argument is omitted or conflicts with the header value.

- **Expectation**: Encoding a JWT should respect the algorithm declared in the supplied headers. A header-specified algorithm should override any separate algorithm argument, while existing behavior should remain unchanged when no usable header algorithm is provided.

- **Constraints**: Only requests that explicitly provide a usable header algorithm should behave differently. All other encoding scenarios should continue to work as before.


### Task 5 Treat null JWT audience claims as absent during decode validation
Ensure that JWT decoding treats a token audience claim of `null` as absent for audience validation, so tokens with `{"aud": null}` can be decoded without supplying `audience`, while still failing appropriately when an audience is explicitly required or when a real audience claim does not match.

- **Expectation**: Decoding should no longer treat `aud: null` as a real audience that forces callers to pass an audience. A null or otherwise unusable audience claim should behave like an absent claim: harmless when no audience check is requested, but rejected as missing when the caller explicitly asks to validate an audience.

- **Constraints**: Only the null or effectively absent audience case should change. Normal audience-enforcement behavior for present audience values must remain intact, including rejection of unexpected or mismatched audiences.


### Task 6 Allow encoding JWTs without a typ header
Ensure that applications can generate JWT/JWS tokens without a `typ` header when needed for standards compliance, while preserving support for explicit custom `typ` header values during encoding.

- **Expectation**: Users should be able to create tokens with either a custom type header or no type header at all. The library should no longer force a `typ` header onto encoded tokens when the caller explicitly clears it.

- **Constraints**: Existing token generation behavior should remain unchanged unless the caller intentionally suppresses the type header. The update should narrow the change to header output semantics rather than altering unrelated encoding behavior.


## Breaking Changes

### Task 7 Reject unsupported keyword arguments in decode APIs
Ensure that JWT and JWS decoding only accept the documented decode parameters and fail fast when callers pass unsupported keyword arguments, instead of silently ignoring those inputs.

- **Expectation**: Decoding should match the documented API exactly: supported validation options remain available, and any unknown decode option should be treated as an error instead of being silently accepted.

- **Constraints**: The upgrade should be strict about invalid inputs without regressing normal decoding behavior for valid, supported arguments.


## Additional Changes
- Ensure that upgrading to 2.2.0 no longer blocks users from installing or resolving the library with newer major versions of `cryptography` solely because of an upper dependency bound.
