# Upgrade Specification from 2.3.0 to 2.4.0

## New Features

### Task 1 Clarify decode optionals and surface deprecated verify mismatches
Ensure that JWT and JWS decode APIs continue to accept omitted decode configuration, support detached-payload JWS decoding through the public API, and surface conflicting use of deprecated verification flags without changing the active verification setting.

- **Expectation**: Decoding entry points should clearly accept omitted configuration, support detached JWS payload workflows, and warn callers when they combine deprecated verification controls inconsistently, while preserving established decode behavior for normal usage.

- **Constraints**: Existing decode call patterns should remain valid. Deprecated verification inputs may warn but should not silently change which verification setting takes effect, and detached-payload handling should only matter for callers that need it.


### Task 2 Add key ID lookup on PyJWKSet
Ensure that applications upgrading to 2.4.0 can look up a JSON Web Key in a JWK set directly by key ID and receive a clear lookup failure when the requested key is not present.

- **Expectation**: A JWK set should behave like a keyed collection for key IDs: consumers can request a key by kid and either receive the matching key object or get a normal missing-key error when that identifier does not exist.

- **Constraints**: The upgrade should add direct key-ID access without changing how JWK sets are otherwise constructed or traversed, and missing keys should fail in a predictable, standard way.


### Task 3 Add detached JWS payload support
Ensure that JWS encoding and decoding support detached, unencoded payloads so applications can generate and verify RFC 7797-style signatures when the payload content is transported or stored separately from the JWS token.

- **Expectation**: Users should be able to create a JWS whose payload is not embedded in the token, then later verify that token by providing the original payload bytes separately. The API should clearly distinguish detached-payload tokens from normal JWS tokens and fail predictably if the detached content required for verification is missing.

- **Constraints**: The new capability must extend existing JWS behavior without regressing standard tokens. Detached payload handling should only activate when explicitly requested or when the token metadata indicates it, and standard signed tokens should continue to behave as before.


## Bug Fixes

### Task 4 Harden HMAC key validation against PEM and SSH key confusion
Ensure that HMAC-based JWT operations do not accept asymmetric key or certificate material in PEM or SSH formats as shared secrets, so applications are protected from key confusion attacks when upgrading to 2.4.0.

- **Expectation**: HMAC JWT flows should only accept real symmetric secrets. If a caller passes public keys, private keys, certificates, or SSH key material, the operation should be rejected with an invalid-key error rather than proceeding. Legitimate asymmetric-key JWT usage should continue to work when the correct algorithm family is used.

- **Constraints**: The safeguard should be broad enough to catch equivalent asymmetric key representations, without rejecting ordinary symmetric secrets or interfering with correct use of asymmetric JWT algorithms.


### Task 5 Reject non-EC keys for ECDSA algorithms with a clear invalid-key error
Ensure that ECDSA JWT operations reject keys that are not elliptic-curve keys with a clear library-level invalid-key failure instead of surfacing a confusing downstream signing error.

- **Expectation**: ECDSA JWT APIs should validate that the supplied key actually belongs to the elliptic-curve family and fail immediately with a clear invalid-key error when it does not.

- **Constraints**: Correct EC-based usage should keep working as before, and only mismatched key types should change behavior by producing a clearer error.


### Task 6 Warn on legacy decode verify mismatch
Ensure that `jwt.decode` surfaces a deprecation warning when callers use the legacy `verify` argument inconsistently with signature-verification options, while preserving existing decode behavior and leaving caller-supplied options unchanged.

- **Expectation**: JWT decoding should warn users when they rely on an obsolete `verify` argument in a way that contradicts the actual verification setting, so ignored security-related arguments are visible during upgrade. Normal decoding behavior should stay the same, and passing an options object should not cause that object to be modified.

- **Constraints**: The upgrade should add visibility into deprecated, contradictory usage without changing how valid decode calls behave. Existing verification defaults must remain intact, and caller-provided configuration objects must remain reusable after decoding.


### Task 7 Preserve decode options and warn on legacy verify mismatches
Ensure that JWT decoding does not mutate a caller-supplied options dictionary when applying default verification behavior, and ensure that contradictory use of the deprecated `verify` argument is surfaced to callers during decode operations.

- **Expectation**: Decoding a token should honor the caller's verification configuration without modifying the configuration object they passed in. If a caller mixes the old `verify` flag with the newer options-based signature verification setting and the two disagree, the library should clearly warn that the legacy flag is deprecated and inconsistent.

- **Constraints**: Keep normal decode results and verification defaults unchanged apart from removing unintended side effects on shared option objects and surfacing the deprecated conflict case. Callers already using the options-based verification settings consistently should not see behavioral regressions.


### Task 8 Correct detached JWS serialization behavior
Ensure that detached JWS encoding produces a compact token with no embedded payload segment when detached mode is requested, while preserving the existing public decoding and key-validation error contracts across JWT and JWK handling.

- **Expectation**: When callers request a detached JWS, the serialized token should omit the payload content from the token body while remaining a valid signed compact representation. Outside that case, the upgrade should keep the library's observable failure modes stable: malformed JSON still fails as decode errors, invalid or unsupported JWK inputs still fail as key-related errors, and missing required claims still report which claim is absent.

- **Constraints**: Limit the behavior change to detached-token serialization only. Existing successful token flows and the categories of user-visible errors for malformed tokens, unsupported algorithms, invalid keys, and missing claims should remain consistent after the upgrade.


## Documentation

### Task 9 Refresh PyJWT package metadata for 2.4.0
Ensure that upgrading to PyJWT 2.4.0 exposes updated package metadata so consumers see the correct library version and current copyright year range without any change to JWT runtime behavior.

- **Expectation**: After the upgrade, applications and tooling that inspect PyJWT package metadata should observe the new release version and refreshed copyright information, while all functional JWT behavior remains unchanged.

- **Constraints**: This upgrade is metadata-only. It must not introduce new user-facing JWT features, regress existing behavior, or remove previously visible package metadata.


## Additional Changes
- Ensure that the API documentation exposes decode_complete() under the correct scope so users can locate and understand the function without having to inspect the library source.
- Ensure that upgrading from 2.3.0 to 2.4.0 allows the library to be used on Python 3.10 while preserving the existing user-facing JWT behavior for current consumers.
- Ensure that upgrading from 2.3.0 to 2.4.0 for this task is handled as a documentation-only usage update, with refreshed user guidance but no new runtime behavior, API changes, or migration requirements.
- Ensure that the upgrade guidance explains that repeated RSA JWT encoding can reuse the same RSAPrivateKey instance for performance, without changing how encoding behaves for callers.
- Ensure that user-facing guidance for creating JWTs uses the correct jwt.encode() parameter name so consumers do not follow an example that fails with an argument error.
- Ensure that the 2.4.0 upgrade guidance clearly explains how users should convert popular PyJWT v1.x syntax to the corresponding v2.x usage so they can complete the upgrade without ambiguity.
- Ensure that EdDSA algorithms validate the resolved key type during key preparation and reject incompatible keys with a clear invalid-key failure.
