# Upgrade Specification from 2.4.0 to 2.5.0

## New Features

### Task 1 Warn on unsupported decode keyword arguments
Ensure that JWT and JWS decode APIs warn callers when they pass unsupported extra keyword arguments, while continuing to accept documented decode and validation parameters without breaking current successful decode behavior in 2.5.0.

- **Expectation**: The library should preserve successful decoding for supported inputs, but it should now clearly warn users when they rely on extra, non-supported keyword arguments so they can remove that usage before the next major release.

- **Constraints**: This upgrade should improve visibility into deprecated API usage without breaking normal decoding, and it should only preserve compatibility for supported public arguments rather than for accidental passthrough of custom extras.


### Task 2 Add EC JWK export support to ECAlgorithm
Ensure that applications upgrading to 2.5.0 can export elliptic-curve keys through the JWT algorithm API as JWKs, including supported public and private EC keys, while rejecting unsupported key objects and unsupported EC curves with a key-related error.

- **Expectation**: Users should be able to serialize supported EC keys into standard JWK form through ECAlgorithm, use the exported value anywhere a JWK is expected, and rely on the result to preserve the original key material needed for later JWK import.

- **Constraints**: The feature should only succeed for supported EC key types and named curves, fail clearly for unsupported inputs, and avoid changing how valid EC JWKs are interpreted on import.


### Task 3 Expose public algorithm lookup for JWT alg values
Ensure that applications can retrieve the Algorithm object for a JWT algorithm name through the public API for advanced token-processing workflows such as OIDC at_hash handling, while signing and signature verification continue to reject missing, unsupported, or disallowed algorithms with the appropriate public error behavior.

- **Expectation**: Users should be able to ask the library for the algorithm object represented by a JWT's `alg` header and use that object in higher-level token validation flows. The library should preserve strict algorithm enforcement during signing and verification: unsupported or disallowed algorithms must fail clearly, and signature failures must remain distinct from algorithm-selection failures.

- **Constraints**: Making algorithm metadata accessible should not relax any security checks. Existing signing and verification behavior should remain strict about which algorithms are permitted, while continuing to report unsupported algorithms differently from bad signatures.


## Bug Fixes

### Task 4 Ignore unusable keys when loading JWK sets
Ensure that loading a JWK Set succeeds when the set contains at least one usable key, even if other entries are incompatible or unusable, and ensure that invalid, empty, or wholly unusable key sets are still rejected.

- **Expectation**: When an application loads a JSON Web Key Set, unsupported or unusable entries should be skipped rather than aborting the whole load, as long as at least one valid key remains. Loading should still fail for invalid inputs, empty key sets, or key sets where none of the keys can be used.

- **Constraints**: Be tolerant of mixed-quality key sets, but keep strict failure behavior for malformed inputs and for key sets that cannot provide any usable key.


### Task 5 Skip unusable keys when loading JWK sets
Ensure that loading a JWK Set does not fail just because some keys in the set are unusable, while still rejecting invalid key-set inputs and key sets that contain no usable keys.

- **Expectation**: Applications should be able to consume real-world JWK Sets that include unsupported or otherwise unusable keys without losing access to the valid keys in the same set. Loading should still fail when the key-set payload itself is malformed or when there are no usable keys to work with.

- **Constraints**: Be more tolerant of mixed-quality key sets, but do not silently accept malformed input or produce an empty usable key set as a successful result.


### Task 6 Clarify JWT decode audience typing and supported kwargs
Ensure that JWT decoding in 2.5.0 exposes a consistent public contract for `audience` and other claim-validation arguments, so callers use explicit supported parameters, receive deprecation warnings for unsupported extra kwargs, and no longer treat bytes as a supported `audience` type.

- **Expectation**: Applications upgrading to 2.5.0 should interact with JWT decoding through a clearer, explicitly supported parameter set. Audience validation should follow a documented string-or-string-list contract, and unsupported keyword passthrough should surface as deprecation warnings instead of remaining an implied feature.

- **Constraints**: Existing supported decode flows should continue to work, but the library should narrow callers onto the documented API surface and avoid silently preserving unsupported keyword behaviors.


### Task 7 Improve PyJWKSet usable-key handling and validation errors
Ensure that `PyJWKSet` accepts JWK sets containing a mix of usable and unusable keys, reports set-level validation failures accurately, and only fails when the input does not provide keys, has an invalid key collection shape, or yields no usable keys.

- **Expectation**: Loading a JWK set should succeed if the set contains at least one valid, usable key, even when some entries are unusable. Failures should clearly distinguish between an absent or empty key set, an invalid key-set shape, and a key set where every entry is unusable.

- **Constraints**: Partial validity should be tolerated, but fully unusable or malformed sets must still fail. The behavior must not collapse different failure modes into the same generic outcome when users need to understand whether no keys were provided, the structure was wrong, or none of the keys could be used.


### Task 8 Deterministic JWT header ordering
Ensure that encoding a JWT with equivalent header content produces a stable result even when header fields are supplied in a different order.

- **Expectation**: Token generation should treat header field ordering as non-semantic. If the header content is the same, the emitted token should not change just because the caller built the header object in a different order.

- **Constraints**: The upgrade should preserve current JWT behavior and only eliminate instability caused by header ordering. Equivalent requests must stay equivalent, and non-order-related behavior must not regress.


## Dependency Updates

### Task 9 Align JWS decoding with PyJWT 2.5.0 API changes
Ensure that upgrading to PyJWT 2.5.0 preserves JWT/JWS decode behavior while adopting the new explicit JWS API: detached payloads must be passed through the supported decode parameter, arbitrary extra decode kwargs must no longer be relied on, and tokens with missing, disallowed, or unsupported algorithms must be rejected consistently.

- **Expectation**: The library upgrade should expose a supported way to verify detached JWS payloads, warn consumers away from deprecated generic decode kwargs, and fail verification predictably whenever a token does not present a valid usable algorithm.

- **Constraints**: The upgrade must preserve valid decoding flows while removing reliance on ambiguous decode inputs. It must remain strict about which algorithms are acceptable and must not silently accept tokens whose algorithm metadata is missing or unsupported.


### Task 10 Add TTL-based JWKS caching and refresh behavior to PyJWKClient
Ensure that PyJWKClient uses a bounded, configurable JWK set cache for signing-key resolution, refreshes the JWK set when a requested kid is missing, and exposes the new cache controls and error behavior introduced in PyJWT 2.5.0.

- **Expectation**: The JWKS client should reuse recently fetched signing-key metadata for a short configurable period, bypass or refresh that cache when asked, and recover from key rotation by refetching once before failing. Fetch failures should be reported consistently through the library's error type, and stale cached JWKS data should not remain after a failed refresh.

- **Constraints**: The upgrade must preserve correct signing-key resolution while preventing indefinite reuse of stale JWKS data. Applications must be able to disable set-level caching or explicitly re-enable key-level caching, and missing-key failures must still be surfaced when a refresh cannot resolve them.


## Typing Updates

### Task 11 Improve strict typing compatibility in jwt.utils
Ensure that upgrading to PyJWT 2.5.0 removes strict-mode type-checking issues in jwt.utils without changing the observable behavior of optional cryptography support or SSH public key format handling.

- **Expectation**: Applications that use strict static type checking should be able to upgrade without adding local suppressions for library code, and existing runtime behavior for optional crypto support and SSH key recognition should remain unchanged.

- **Constraints**: This upgrade should improve developer tooling compatibility only; it must not force new runtime dependencies or alter the key formats that existing consumers already provide.


### Task 12 Complete typing support for jwt.help
Ensure that upgrading to 2.5.0 provides complete type-checker support for the `jwt.help` helper APIs and includes the missing cryptography type information needed to analyze those APIs cleanly in typed projects.

- **Expectation**: The library should present `jwt.help` as a fully typed public helper module. Developers using IDEs and static type checkers should be able to inspect and use its helper functions with accurate signatures and without extra workaround configuration, while the observable runtime output stays the same.

- **Constraints**: This should be a non-breaking typing improvement. Existing consumers should continue to get the same helper behavior and environment reporting, with the only meaningful change being better typing support and dependency completeness for typed development workflows.


## Documentation

### Task 13 Correct EdDSA signing API documentation typo
Ensure that the EdDSA signing documentation correctly describes the accepted private key input types so users are not misled by a typo in the API reference.

- **Expectation**: Users reading the EdDSA signing documentation should see an accurate description of which private key objects are supported, using correct terminology that matches normal Python usage.

- **Constraints**: The change should improve clarity in the docs without altering how the library behaves in production.


## Additional Changes
- Ensure that upgrading to 2.5.0 drops support for Python 3.6 and treats Python 3.7 or newer as the supported interpreter range, without changing the library's user-facing behavior on still-supported Python versions.
- Ensure that upgrading to 2.5.0 no longer requires or advertises `wheel` as an explicit project dependency, while preserving the existing install and build experience.
- Ensure that invalid JWS `options` inputs are treated as caller errors without assuming a single exception type across Python runtimes.
- Ensure that the 2.5.0 upgrade corrects the published typo so documentation reads "prior" instead of the misspelled term, while preserving existing library behavior.
