# Upgrade Specification from 2.5.0 to 2.6.0

## Bug Fixes

### Task 1 Expire JWTs exactly at the exp boundary
Ensure that JWT expiration enforcement invalidates a token at the exact moment its effective expiration time is reached, so a token is no longer accepted when the current time equals its exp value after accounting for leeway.

- **Expectation**: JWTs should stop being accepted exactly when they expire, not after an extra boundary second. If expiration leeway is configured, that grace period should shift the cutoff, but the token should still become invalid immediately once the adjusted cutoff is reached.

- **Constraints**: Preserve normal JWT expiration behavior and only correct the exact cutoff edge case. Valid future-dated tokens should continue to decode normally, while tokens at or past the expiration cutoff should be rejected consistently.


### Task 2 Reject JWTs with future issued-at timestamps
Ensure that JWT decoding rejects tokens whose `iat` claim is set in the future beyond the allowed leeway, so tokens cannot be treated as valid before their effective issued-at time while preserving existing handling for malformed `iat` values.

- **Expectation**: Issued-at should participate in token freshness checks the same way other time-based validity claims do. A token with an issued-at time too far in the future must be rejected as premature, while malformed issued-at values should continue to surface as invalid input.

- **Constraints**: Keep backward-compatible behavior for bad `iat` formats, and only add rejection for tokens that are observably ahead of the allowed clock-skew window. Tokens that are already within the permitted validity window should not start failing solely because they contain `iat`.


## Additional Changes
- Ensure that version 2.6.0 only supports environments using `cryptography` 3.4.0 or newer, so installations and supported usage align with the updated dependency baseline.
- Ensure that upgrading to 2.6.0 no longer requires the `types-cryptography` stub package when users install the library with crypto support enabled, while keeping cryptography-backed JWT functionality available through the existing optional crypto dependency.
- Ensure that the 2.6.0 update corrects the mislabeled 2.5.0 release heading so users reading release information are not misled about the affected version, while preserving all existing library behavior.
