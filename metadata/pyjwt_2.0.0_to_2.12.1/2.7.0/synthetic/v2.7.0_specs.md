# Upgrade Specification from 2.6.0 to 2.7.0

## New Features

### Task 1 Add hash digest support on Algorithm objects
Ensure that applications can compute the hash digest associated with a selected JWT Algorithm instance for arbitrary input bytes, and that algorithms without an associated hash algorithm fail in a predictable way instead of exposing undefined behavior.

- **Expectation**: Callers should be able to ask a JWT algorithm object to hash arbitrary bytes using the same digest family that the algorithm is defined around. If that algorithm does not support hashing, the library should fail explicitly with an unsupported-operation error.

- **Constraints**: The new capability should only add digest access; existing token processing behavior should remain unchanged. Results should be the direct digest output for the requested input, and unsupported algorithms should fail clearly instead of guessing.


### Task 2 Support custom headers and connection-aware failures in PyJWKClient
Ensure that PyJWKClient can be configured for authenticated or customized JWK set fetches by supplying request headers, and that fetch failures caused by connectivity or timeout issues are exposed as a connection-specific error.

- **Expectation**: Users of PyJWKClient should be able to customize how the library contacts the JWK endpoint, including sending extra HTTP headers and controlling request timeout behavior. When the endpoint cannot be reached or the request times out, the failure should be reported as a dedicated connection-related error rather than a generic client failure.

- **Constraints**: This update should add request customization without changing normal successful JWK retrieval behavior. Default usage should continue to work without extra parameters, and only network-style failures should shift to the more specific error category.


### Task 3 Add overridable JWT payload encode/decode hooks to PyJWT
Ensure that `PyJWT` subclasses can customize how JWT payloads are converted to signed bytes and how verified payload bytes are decoded back into application data, so non-standard payload encodings can be supported without breaking the default JWT behavior.

- **Expectation**: Applications that extend `PyJWT` should be able to plug in custom payload formats, such as transformed or compressed payloads, by overriding dedicated payload hooks. Out of the box, standard JWTs should keep working exactly as before: payloads are treated as JSON objects, invalid payload content is rejected with a decode error, and decoded claims remain available through the normal decode APIs.

- **Constraints**: This upgrade should extend PyJWT rather than redefine it. Existing callers using normal JWT payloads should see no behavioral regression, and custom payload support should fit into the same verification and claim-checking flow that the library already exposes.


### Task 4 Expose JWT header ordering control in encode
Ensure that upgrading to PyJWT 2.7.0 lets callers control whether JWT headers are sorted during encoding so existing integrations that depend on header insertion order can opt out of sorting, while preserving the default sorted behavior and enforcing that encoded JWT payloads are JSON-object dictionaries.

- **Expectation**: JWT encoding should allow callers to disable automatic header sorting when they need tokens to preserve the order in which header fields were supplied. Existing callers that do not opt out should keep the current sorted-header behavior, and encoding should continue to accept only plain object-style payloads.

- **Constraints**: The upgrade must remain backward compatible by default, changing header order only when explicitly requested. It must not broaden payload acceptance beyond normal JSON object dictionaries or change how tokens are interpreted when decoded.


### Task 5 Differentiate JWKS connection failures in PyJWKClient
Ensure that JWKS retrieval through PyJWKClient clearly distinguishes connection-related failures from other JWK client failures so applications can detect transient network issues, handle them separately, and safely retry when appropriate.

- **Expectation**: When PyJWKClient cannot reach the JWKS endpoint because of a network or timeout problem, callers should receive a dedicated connection-oriented exception instead of a generic client failure. Existing code that already handles the broader JWK client error family should remain compatible, and outbound JWKS requests should honor the client's configured request settings.

- **Constraints**: The change should narrow error reporting for transport failures without changing unrelated failure semantics or breaking existing consumers that catch the broader client exception type.


### Task 6 Add dictionary output option to JWK serialization
Ensure that applications upgrading to 2.7.0 can obtain JWK data directly as a native mapping from `Algorithm.to_jwk()` without breaking existing code that expects the legacy JSON string output.

- **Expectation**: Users should be able to choose whether JWK export returns JSON text or an already-parsed mapping, while preserving the same key information and keeping existing code paths unchanged by default.

- **Constraints**: This upgrade must add an opt-in output format, not a new serialization format or a breaking API change. Apart from returning a mapping when requested, JWK export should behave the same as before.


## Bug Fixes

### Task 7 Differentiate JWT audience mismatch errors
Ensure that JWT audience validation clearly distinguishes a caller-provided invalid audience configuration from the case where a token's audience claim does not match the expected audience.

- **Expectation**: Audience validation should report a token audience mismatch as a distinct failure condition, so applications can tell the difference between a bad caller configuration and a token that simply targets a different audience.

- **Constraints**: Do not change which requests succeed or fail. Preserve the existing audience-validation contract while making user-visible error reporting specific enough to distinguish the reason for failure.


### Task 8 Clarify JWK errors when cryptography is unavailable
Ensure that JWK and JWK set loading report actionable failures when a selected algorithm depends on the optional cryptography package, while still preserving usable keys from a set whenever possible.

- **Expectation**: Loading a JWK should clearly tell the caller when the requested key algorithm cannot be used because the optional cryptography package is not installed. Loading a JWK set should tolerate unusable keys, keep any valid keys that can still be used, and only fail with a clear explanation if the entire set is unusable.

- **Constraints**: Existing successful JWK flows should keep working. The change is limited to making dependency-related failures clearer and making JWK set parsing more resilient to unusable keys without hiding a total failure.


### Task 9 Ignore invalid keys when loading JWKS
Ensure that loading a JWKS tolerates invalid or unusable key entries so one bad key does not prevent consumers from using other valid keys in the same set.

- **Expectation**: JWKS-loading APIs should accept mixed-quality key sets by skipping entries that cannot be used and continuing with the valid keys that remain. Loading should still fail clearly when the JWKS does not contain any usable keys at all.

- **Constraints**: Partial invalidity in a JWKS must not become a full failure, but a completely unusable JWKS must still surface as an error. Existing successful behavior for valid keys should remain intact.


### Task 10 Fix numeric-string iat validation during JWT decode
Ensure that JWT decoding correctly validates the `iat` claim when it is provided as a numeric string, while preserving existing error behavior for malformed or not-yet-valid tokens.

- **Expectation**: Token decoding should treat integer-like issued-at values consistently, even when the claim is serialized as text. Users should see successful decoding for valid numeric timestamps, a validation error for malformed issued-at values, and a not-yet-valid error for tokens whose issued-at time is still in the future.

- **Constraints**: The update should broaden compatibility for valid issued-at formats without relaxing correctness checks or changing the meaning of future-issued tokens.


### Task 11 Use sub-second UTC time for JWT time-claim validation
Ensure that JWT decoding validates time-based claims against the actual current UTC time, including fractional seconds, so tokens are not accepted or rejected incorrectly near second boundaries.

- **Expectation**: Token validation should honor real wall-clock time rather than rounding down to whole seconds. Around expiration and not-before boundaries, the decode result should change as soon as the actual time crosses the claim threshold after applying any configured leeway.

- **Constraints**: Keep the existing validation feature set intact and limit the change to timing precision. The update should only affect borderline cases where sub-second timing matters.


## Dependency Updates

### Task 12 Add configurable timeout and headers to PyJWKClient JWKS fetches
Ensure that PyJWKClient JWKS retrieval uses a finite default network timeout, allows callers to provide custom HTTP headers and a custom timeout for JWKS requests, and reports network or timeout failures as connection-related fetch errors instead of hanging indefinitely.

- **Expectation**: Applications using PyJWKClient should be able to control request metadata and how long JWKS retrieval waits before failing. If the JWKS endpoint is unreachable or takes too long, the client should fail with a connection-style error rather than block without a timeout.

- **Constraints**: Existing successful JWKS lookups should keep working, while the upgrade adds safer network behavior and configurable request options. The new behavior should only affect request configuration and failure handling for remote JWKS fetches.


### Task 13 Expand key typing and JWK interoperability in PyJWT 2.7.0
Ensure that upgrading to PyJWT 2.7.0 supports all allowed signing and verification key forms across JWT and JWS APIs, allows supported keys to round-trip through JWK APIs as either JSON text or dictionary data, and surfaces clear failures for unsupported payload shapes or unusable JWK inputs.

- **Expectation**: The upgraded library should let callers use any supported key object or encoded key material directly with the public JWT/JWS APIs, should interoperate cleanly with JWK data in either serialized or already-parsed form, and should fail early with explicit JWT/JWK errors when payload content or key material is not usable.

- **Constraints**: Existing valid token workflows must continue to work, invalid signatures must still be treated as verification failures rather than successful decodes, and unsafe or unsupported key types must continue to be rejected instead of being coerced silently.


## Breaking Changes

### Task 14 Enforce the abstract Algorithm contract
Ensure that custom JWT algorithm integrations remain compatible with 2.7.0 by treating Algorithm as an abstract contract rather than an instantiable placeholder, and by providing the full signing, verification, key preparation, and JWK conversion behavior expected by the library.

- **Expectation**: Custom JWT algorithms should be fully defined concrete components. Applications should no longer rely on creating a generic algorithm object and discovering unsupported operations only when methods are called; incomplete algorithms should be rejected up front, while complete algorithms continue to support signing, verification, key normalization, and JWK import/export.

- **Constraints**: Existing working algorithms should keep behaving the same for normal signing, verification, and key conversion flows. The upgrade should tighten the contract for incomplete or placeholder implementations without changing the expected behavior of valid concrete algorithms.


## Typing Updates

### Task 15 Tighten PyJWT public typing contracts
Ensure that upgrading to PyJWT 2.7.0 provides stricter and more accurate typing for public APIs and utility helpers without changing expected JWT processing behavior.

- **Expectation**: The upgrade should make the library safer to use in strictly typed Python projects by publishing clearer input and output types for its public APIs, while keeping the same observable JWT, JWK, and helper behavior for existing callers.

- **Constraints**: The upgrade must remain backward compatible for normal callers: JWT workflows should keep working, helper functions should remain usable with text or byte inputs, and environment introspection should still succeed whether optional crypto support is installed or not.


### Task 16 Expand typed key and JWK support across PyJWT APIs
Ensure that upgrading to PyJWT 2.7.0 provides more accurate support for supported key objects, byte-based JWT inputs, and JWK helper usage so typed applications can use the library without false type conflicts. Ensure that existing token verification, claim validation, and invalid-key handling semantics remain unchanged.

- **Expectation**: The library should accurately advertise the token, key, and helper input forms it supports so typed Python applications can decode and verify JWTs without unnecessary casting or wrapper code. JWK helper APIs should support both serialized and structured forms where applicable, while all existing validation outcomes stay consistent.

- **Constraints**: This upgrade should improve typing precision and helper ergonomics without changing how valid tokens succeed or how invalid tokens, headers, claims, and keys are rejected.


## Additional Changes
- Ensure that the library explicitly advertises Python 3.11 compatibility in its published package metadata so ecosystem tools and users can detect support for that Python version.
- Ensure that the upgrade guidance for PyJWT 2.7.0 accurately describes how legacy `jwt.decode(..., verify=False)` usage maps to the 2.x API, so users are not told to change expiration-verification behavior when they only intend to disable signature verification.
- Ensure that RSA-PSS JWT algorithms compute padding salt length from the active hash algorithm instance so PS* token signing and verification work correctly at runtime.
- Ensure that JWS verification fails with a clear, explicit error when the header omits the required `alg` field, rather than folding that case into the generic 'alg value is not allowed' path.
- Ensure that JWKS client loading validates that fetched JWKS data is a JSON object before passing it to JWK set parsing, so malformed endpoint responses produce a clear client-level failure.
