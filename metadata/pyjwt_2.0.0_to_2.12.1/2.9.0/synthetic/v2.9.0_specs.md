# Upgrade Specification from 2.8.0 to 2.9.0

## New Features

### Task 1 Support multiple allowed JWT issuers during validation
Ensure that JWT issuer validation accepts either one issuer value or multiple allowed issuer values, so tokens with an `iss` claim matching any configured allowed issuer are treated as valid while non-matching or missing issuer claims continue to fail validation appropriately.

- **Expectation**: Issuer validation should allow applications to configure one trusted issuer or several trusted issuers without changing how they call the library. Tokens should be accepted when their issuer matches any configured allowed issuer, rejected when the issuer does not match, and still rejected when issuer validation is required but the issuer claim is absent.

- **Constraints**: The upgrade should add multi-issuer support without changing established behavior for current single-issuer consumers. Error outcomes for missing or invalid issuers must remain consistent, and the new behavior should only expand which issuer configurations are accepted.


### Task 2 Support decoding directly with PyJWK keys
Ensure that decoding accepts a `PyJWK` object as the verification key, automatically uses the JWK's own algorithm when callers do not provide `algorithms`, and preserves safe algorithm validation and dependency-related failures.

- **Expectation**: Callers should be able to pass a JWK wrapper directly into decode without manually unpacking it. If that wrapper already defines the signing algorithm, decode should use that algorithm by default, while still rejecting tokens signed with a different algorithm and reporting missing crypto support through the specific dependency error.

- **Constraints**: Only relax the missing-`algorithms` requirement when the key itself already carries authoritative algorithm metadata. Preserve existing decode safety rules and continue failing closed on mismatched, unsupported, or unverifiable signatures.


### Task 3 Expose the resolved JWK algorithm on PyJWK
Ensure that applications using PyJWK can read the resolved algorithm directly from the parsed JWK object and receive a specific dependency error when constructing a PyJWK for an algorithm that requires cryptography support.

- **Expectation**: Parsed JWK objects should carry their own algorithm identifier so callers can use the same algorithm consistently in later JWT operations. Missing optional crypto support should fail with a dependency-specific error rather than a generic JWK failure.

- **Constraints**: This change should add algorithm introspection and clearer dependency failures without weakening existing validation. Valid JWKs should continue to parse normally, and invalid or unsupported algorithms should still be rejected.


## Bug Fixes

### Task 4 Normalize invalid RSA PEM key parsing errors for cryptography 42 compatibility
Ensure that RSA PEM key parsing remains compatible with newer cryptography releases by surfacing invalid public key input as the library's InvalidKeyError instead of leaking backend parsing exceptions.

- **Expectation**: Applications using RSA key input should receive one consistent library-level invalid-key failure when the supplied PEM data cannot be parsed as a supported RSA key, including under newer cryptography versions. Valid RSA PEM keys should keep working as before.

- **Constraints**: The change should be limited to error normalization for bad RSA PEM input and must not alter normal behavior for valid keys or broaden the visible exception surface for callers.


### Task 5 Expose missing cryptography dependency during JWK loading
Ensure that JWK and JWK set loading surfaces a clear runtime failure when the selected key algorithm requires the optional cryptography dependency and that dependency is missing, rather than hiding the misconfiguration behind a generic JWK error or by skipping the key.

- **Expectation**: If application code loads JWT key material that depends on crypto support not present in the runtime environment, the library should fail immediately with a specific missing-dependency error so the deployment issue is obvious and the key set is not partially accepted.

- **Constraints**: Do not broaden this change beyond the missing dependency case. Normal invalid-key handling should stay consistent, and only absent crypto support should become a hard stop during JWK set loading.


## Dependency Updates

### Task 6 Add Python 3.12 support and drop Python 3.7 support
Ensure that upgrading to version 2.9.0 supports running the library on Python 3.12 while no longer treating Python 3.7 as a supported runtime, without changing the normal user-facing JWT encode, decode, and algorithm usage on supported Python versions.

- **Expectation**: After the upgrade, applications using the library should be able to run on Python 3.12 with the same normal JWT workflows they used before, while environments pinned to Python 3.7 should be considered unsupported and expected to upgrade their interpreter.

- **Constraints**: The upgrade should behave as a compatibility expansion for current supported users, not as a functional redesign. The only breaking boundary exposed to users is the supported Python version range.


## Breaking Changes

### Task 7 Raise the Python baseline to 3.8 and support Python 3.12
Ensure that version 2.9.0 is treated as a runtime-compatibility upgrade: the library must support Python 3.12, stop claiming support for Python 3.7, and preserve the existing JWT API behavior for users on supported Python versions.

- **Expectation**: The upgrade should refresh interpreter compatibility boundaries without changing how users normally call the JWT APIs. Users on current Python releases should be able to adopt 2.9.0, while Python 3.7 users should understand that this version is no longer for their runtime.

- **Constraints**: This change is about supported environments, not a redesign of JWT behavior. Supported users should see continuity in everyday library behavior, and unsupported runtimes should simply fall outside the version's compatibility promise.


## Performance Improvements

### Task 8 Tighten and speed up SSH key detection
Ensure that SSH key detection recognizes only supported SSH public keys whose data begins with a valid SSH key type marker, so key classification is faster and does not misidentify unrelated byte strings that merely contain SSH key text later in the input.

- **Expectation**: SSH key detection should rely on the declared key type at the start of the key data. Supported SSH public keys, including supported certificate-style variants that begin with those key types, should still be recognized, while unrelated data should not be accepted just because it contains similar text somewhere inside.

- **Constraints**: Keep the change limited to stricter and faster recognition of already supported SSH public key formats. Existing valid SSH key inputs should remain accepted, and the upgrade should not require callers to adopt a new interface.


## Refactors

### Task 9 Preserve decode behavior for invalid exp claims during cleanup
Ensure that upgrading to 2.9.0 preserves the existing user-visible behavior for JWT decoding when the `exp` claim is invalid, while incorporating the internal cleanup to the expiration-claim error text construction.

- **Expectation**: JWT decoding should continue to reject tokens whose expiration claim is malformed and continue to reject expired tokens using the same public error behavior as before. The 2.9.0 update should not change how callers experience expiration validation failures.

- **Constraints**: The upgrade should be behaviorally neutral aside from code cleanup. Invalid expiration data must still fail in the same way, and valid expiration checks must behave exactly as before.


## Additional Changes
- Ensure that the documented jwt.decode_complete API includes the strict_aud option so users can rely on the same advertised decoding options across the library's decode entry points.
- Ensure that upgrading from 2.8.0 to 2.9.0 is treated as a documentation-only release and does not imply any runtime, API, or integration behavior change for library consumers.
- Ensure that the published example for retrieving RSA signing keys from a JWKS endpoint only includes variables that are actually used, so users are not misled into thinking an unused `kid` value is required.
