# Upgrade Specification from 7.1.2 to 7.1.3

## Bug Fixes

### Task 1 Fix tearDown execution for class-level skipped unittest.TestCase under --pdb
Ensure that when a unittest.TestCase class is decorated with unittest.skip (or pytest.mark.skip) at the class level and pytest is invoked with --pdb, the tearDown() method is NOT executed for any tests in that class. Previously, only method-level skip decorators were respected in this code path, causing class-level skipped tests to still run tearDown(), leading to unexpected errors and unwanted PDB sessions.

- **Expectation**: When pytest runs in --pdb mode, skipped unittest test classes must be treated identically to skipped individual test methods: their tearDown() must not execute. The skip check must account for skip decorators applied at both the class level and the method level.

- **Constraints**: Normal (non-pdb) test execution behavior must not be affected. Method-level skip handling under --pdb must remain intact. Only the class-level skip gap in --pdb mode needs to be addressed. No other test lifecycle methods (e.g., setUp) should be impacted by this change.


### Task 2 Escape invalid XML characters in setup/teardown error messages for JUnit XML reports
Ensure that JUnit XML reports generated by pytest remain valid XML even when setup or teardown error messages contain characters that are invalid or special in XML (e.g., control characters, null bytes, or reserved XML entities). Previously, such characters in setup/teardown error messages were written unescaped into the report, producing malformed XML that could break downstream consumers such as CI dashboards and XML parsers.

- **Expectation**: When generating JUnit XML reports, any error messages produced during the setup or teardown phases of a test must be sanitized so the output is always well-formed XML. Characters that are not permitted in XML documents should be escaped or replaced, ensuring that any XML parser can successfully consume the report regardless of what characters appear in the original error message.

- **Constraints**: The fix must not alter the semantic content of error messages beyond making them XML-safe. Other parts of the JUnit XML report generation that already handle escaping correctly must remain unchanged. The report must continue to distinguish between setup failures, teardown failures, and test body failures in its structure.


### Task 3 Suppress PytestAssertRewriteWarning for pyproject.toml-based editable installs
Ensure that installing a pytest plugin in editable mode via `pip install -e .` using pyproject.toml-based builds (pip 21.3+) does not produce a spurious `PytestAssertRewriteWarning` about `__editable__` finder modules that cannot be rewritten.

- **Expectation**: When pytest discovers installed plugin packages, it should silently ignore synthetic finder modules created by pip's editable-install mechanism. Users should see a clean test session output with no warnings related to editable installation internals.

- **Constraints**: The fix must be narrowly scoped to editable-install finder modules and must not suppress assertion rewriting for any user-authored or plugin-authored modules. Normal assertion rewriting behavior for all other modules must be preserved.


### Task 4 Doctests now respect the --import-mode flag
Ensure that the --import-mode flag is respected when pytest collects and imports modules for doctest execution. Previously, running --doctest-modules with a non-default --import-mode (such as importlib) had no effect on how doctest modules were imported, causing failures with namespace packages that rely on the importlib import mode for correct module resolution. Modules could be imported under incorrect names or fail to resolve relative imports when the implicit namespace was missing from the import path.

- **Expectation**: Doctest module collection should honor the same --import-mode configuration that governs how all other test modules are imported. When a user sets --import-mode to a specific value, doctest modules must be imported using that same strategy, ensuring consistent module naming and namespace resolution across the entire test suite.

- **Constraints**: The change must not break existing doctest collection for users who do not specify --import-mode. Import error handling and skip behavior for doctests must remain intact. The fix should bring doctest import behavior into alignment with the rest of pytest's module import infrastructure without introducing side effects.


### Task 5 Fix AttributeError in assertion rewrite path handling when os.path is overridden
Ensure that pytest's assertion rewriting hook does not crash with an AttributeError during test collection when os.path has been replaced or overridden by an alternative module that lacks the 'sep' attribute. This occurs in specific environments such as IDE debug mode (PyCharm, VS Code) when third-party libraries trigger nested imports that re-enter the assertion rewriting import hook.

- **Expectation**: The assertion rewriting hook's early bailout path resolution must be robust against environments where the os.path module has been replaced or monkey-patched. Path construction from module name segments should use pathlib's native API to avoid any dependency on os.path attributes. The resulting path must remain functionally equivalent for subsequent filename pattern matching.

- **Constraints**: The fix must preserve the existing pattern-matching behavior for assertion rewrite eligibility. Only the internal path construction mechanism should change; the observable result of which modules get rewritten and which bail out early must remain identical under normal conditions.


### Task 6 Fix pytest.approx string representation for tuple comparisons
Ensure that pytest.approx() correctly produces its string representation when comparing tuples, including tuples of complex numbers. Previously, using pytest.approx() with tuple arguments caused a TypeError during assertion introspection, resulting in a 'faulty __repr__' error message instead of a clear diff of expected vs actual values.

- **Expectation**: When pytest.approx() receives a tuple (or a nested structure containing tuples), it should produce a well-formed, human-readable string representation showing each element with its tolerance. The representation should work identically for tuples and lists, and should preserve the original container type in its output.

- **Constraints**: All existing pytest.approx() use cases involving lists, numpy arrays, and scalar values must continue to work without regressions. The fix must not alter comparison semantics—only the string representation path is affected.


## Dependency Updates

### Task 7 Replace atomicwrites dependency with os.replace for pyc cache writing
Ensure that the atomicwrites third-party dependency is removed and that .pyc assertion-rewrite cache files are still written atomically on all platforms, including Windows, using only standard library facilities. The previous dependency was declared unmaintained and removed from PyPI, making it an unreliable supply-chain component for a critical project like pytest.

- **Expectation**: When pytest rewrites assertion bytecode and caches the compiled .pyc file, the write operation must be atomic on all supported platforms. A temporary file is written first, then atomically moved to the target location. If any filesystem error occurs during writing or moving, the operation fails gracefully without raising exceptions to the caller. No third-party library is required for this functionality.

- **Constraints**: No unmaintained or removed third-party packages may be used for file atomicity. The cache write mechanism must work correctly on all platforms including Windows, must handle concurrent process access safely, and must degrade gracefully on filesystem errors without crashing the test session.


## Typing Updates

### Task 8 Type-annotate FixtureRequest.param as Any for type-checker compatibility
Ensure that accessing `request.param` inside a parametrized fixture no longer triggers a type-checker error claiming 'FixtureRequest has no attribute param'. The `param` attribute is available at runtime for parametrized fixtures but was previously invisible to static analysis tools.

- **Expectation**: When a user type-annotates a fixture's request parameter as `pytest.FixtureRequest` and accesses `request.param`, static type checkers should accept the code without reporting a missing-attribute error. The declared type of `param` should be `Any`, allowing any parameter value without narrowing.

- **Constraints**: This is a stop-gap typing improvement only; it must not alter runtime behavior of fixtures. The typing must be broad enough (Any) to avoid false positive type errors for any parameter type. Non-parametrized fixtures must continue to raise an error at runtime when param is accessed, even though the type annotation now declares the attribute.


## Documentation

### Task 9 Add explicit deprecation notes to tmpdir and tmpdir_factory fixture docstrings
Ensure that the docstrings for the legacy tmpdir fixture and tmpdir_factory (including the TempdirFactory class and its methods mktemp and getbasetemp) contain explicit, prominent notes advising users to prefer tmp_path and tmp_path_factory respectively. Ensure that all type references in these docstrings refer to the public py.path.local type and TempPathFactory class rather than internal module paths.

- **Expectation**: All legacy temporary directory fixtures and their factory class must carry prominent deprecation-style notes directing users to the modern tmp_path and tmp_path_factory equivalents. Method docstrings must reference the public return type and the corresponding modern factory methods rather than internal implementation details.

- **Constraints**: This change must be purely documentation-level with no effect on runtime behavior. The deprecation guidance must be informational (not a warning or error at runtime). Existing fixture functionality must remain fully intact and backward-compatible.
