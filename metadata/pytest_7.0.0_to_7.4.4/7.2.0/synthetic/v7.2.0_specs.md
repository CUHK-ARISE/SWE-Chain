# Upgrade Specification from 7.1.3 to 7.2.0

## New Features

### Task 1 Deprecate legacy attribute/mark-based hook configuration in favor of pytest.hookimpl and pytest.hookspec decorators
Ensure that hook implementation and hook specification functions configured via legacy mechanisms (function attributes or pytest marks such as tryfirst, trylast, optionalhook, hookwrapper, firstresult, historic) emit a PytestDeprecationWarning at runtime, guiding users to migrate to the pytest.hookimpl() and pytest.hookspec() decorator APIs. The legacy configuration must continue to function (the options must still take effect) but must no longer be silently accepted.

- **Expectation**: Any hook function relying on the old attribute-based or mark-based configuration approach must produce a deprecation warning at plugin registration time. The warning must clearly identify the affected function, the legacy options detected, and the recommended decorator replacement. Hooks decorated with the modern pytest.hookimpl or pytest.hookspec APIs must not trigger any deprecation warning. The legacy options must still be honored functionally during the deprecation period.

- **Constraints**: The deprecation must not break existing plugins that use the legacy approach; their hook options must still take effect. Only functions following the pytest_ naming convention should be subject to legacy detection. Modern decorator-based hooks must be completely unaffected. The deprecation messaging must direct users to the official migration documentation.


### Task 2 Deprecation warning for test functions returning non-None values
Ensure that when a test function returns a value other than None, pytest emits a deprecation warning alerting the user that they likely intended to use `assert` instead of `return`. This catches a common mistake where tests silently pass because a boolean expression is returned rather than asserted, producing false positives in test suites.

- **Expectation**: When a test function returns any value other than None, pytest should issue a visible deprecation warning suggesting the user likely meant to assert the expression rather than return it. The warning should clearly identify which test produced it and what value was returned, and should communicate that this behavior will become a hard error in a future major version.

- **Constraints**: Tests that return None (explicitly or by falling through without a return statement) must continue to pass silently with no new warnings. Async test detection must not be disrupted. The warning must be a standard Python deprecation warning so that users can filter, capture, or suppress it using standard warning filter mechanisms.


### Task 3 Add shell-style wildcard (glob) support to testpaths configuration
Ensure that the testpaths configuration option accepts shell-style wildcard patterns (e.g. src/*/tests) and correctly expands them to matching directories during test collection. Ensure that a new public Config.ArgsSource enum and Config.args_source attribute are available to indicate whether test arguments were sourced from the command line, the invocation directory, or the testpaths configuration value. Ensure that the terminal header accurately displays testpaths information by using the new args_source attribute rather than a value-comparison heuristic.

- **Expectation**: Wildcard patterns in the testpaths configuration should be transparently expanded to their matching filesystem paths before test collection begins. The framework should track the origin of test arguments via a public enumeration on the Config object, distinguishing between explicit command-line arguments, the testpaths configuration, and the invocation directory fallback. The terminal session header should reliably report when testpaths are in effect based on the tracked argument source, not by comparing argument values.

- **Constraints**: Backward compatibility with non-wildcard testpaths values must be preserved. Module-style test path resolution (pyargs) must not be affected by glob expansion. The fallback behavior when no test paths are resolved must remain unchanged. The new argument-source tracking must not alter existing test collection semantics beyond enabling wildcard expansion.


### Task 4 Broaden parametrize argnames to accept any Sequence[str]
Ensure that @pytest.mark.parametrize() accepts any Sequence[str] (not just list or tuple) as the argnames parameter, while preserving the existing behavior of treating a plain str as a comma-delimited name list.

- **Expectation**: When a user passes any sequence-like collection of strings (beyond just list or tuple) as argument names to parametrize, the framework should accept it and use those names directly. Only when a bare string is provided should the framework perform comma-based splitting to extract individual argument names. The type annotations should reflect this broader acceptance.

- **Constraints**: Existing tests and user code that pass str, list, or tuple as argnames must not break. The change must not alter how string-based argument names are parsed. Only the dispatch logic (which types trigger comma splitting vs. direct use) changes, and it must correctly distinguish strings from all other sequence types.


### Task 5 Add --no-showlocals flag to override --showlocals from addopts
Ensure that users can override a globally configured --showlocals option on a per-invocation basis. When --showlocals is set in addopts (e.g., in pyproject.toml or pytest.ini), it is currently impossible to disable local variable display for a specific test run without modifying the configuration file. A --no-showlocals flag should be provided so that CLI invocations can negate the global setting.

- **Expectation**: When a user passes --no-showlocals on the command line, local variable display in tracebacks is suppressed, even if --showlocals was previously enabled via addopts or earlier arguments. The two flags (--showlocals and --no-showlocals) act as a toggle pair: whichever appears last in the effective argument list wins.

- **Constraints**: The addition of --no-showlocals must be purely additive and must not alter existing default behavior. Tests that rely on --showlocals being enabled globally should still work unless --no-showlocals is explicitly passed. No other traceback formatting behavior should be affected.


### Task 6 Enhance error messages for pytest.warns() and ExceptionInfo.match() with multiline formatting
Ensure that when pytest.warns() fails to match an expected warning (either by type or by regex), the resulting error message displays emitted warnings in a multiline, pretty-printed format rather than a single condensed line. Ensure that when ExceptionInfo.match() fails because a regex does not match the exception string, the error message presents the regex pattern and the input value on separate labeled lines for easy comparison.

- **Expectation**: Failure messages from pytest.warns() and ExceptionInfo.match() should use structured multiline formatting that clearly separates the expected pattern from the actual values, making it easy for users to visually compare and diagnose mismatches at a glance.

- **Constraints**: No change in when or why failures are triggered. The matching semantics, success return values, and exception types raised must remain identical to the previous version. Only the human-readable content of the error messages changes.


### Task 7 Add coloring to short test summary info
Ensure that the short test summary info section uses colors to visually distinguish between different test result categories (failed, passed, error, skipped, xfailed, xpassed). Previously, the summary lines were uncolored plain text, making it difficult to scan and differentiate statuses at a glance, especially when multiple result types are intermixed.

- **Expectation**: When a test run completes and the short test summary is displayed, each line should use color-coded status labels so users can instantly distinguish failures from skips, expected failures, passes, and errors. The test function name within each entry should be visually emphasized with bold styling. The summary section header should also be visually distinct. Expected-failure reasons should appear inline with their test entry rather than on a separate line.

- **Constraints**: Coloring must not break non-terminal output or alter the informational content of summary lines. The change must not affect test execution behavior, only terminal display. All existing summary entry types must continue to appear correctly. Color styling must degrade gracefully when terminal markup is unavailable.


### Task 8 Display full crash messages in short test summary on CI
Ensure that when pytest runs in a CI environment, the crash messages displayed in the 'short test summary info' section are shown in full without truncation. Previously, these messages were always trimmed to the terminal width, causing important failure context to be lost in CI log output where horizontal space is effectively unlimited.

- **Expectation**: When pytest detects it is running in a CI environment, crash messages in the short test summary section should be displayed in their entirety. When not in CI, crash messages should continue to be truncated to fit the terminal width. This ensures CI logs contain full diagnostic information while interactive terminal output remains readable.

- **Constraints**: The truncation behavior for non-CI environments must not regress. CI detection must rely on the existing CI-detection mechanism used elsewhere in pytest. Only the crash message portion of summary lines should be affected; other summary formatting must remain unchanged.


### Task 9 Support .pytest.ini as a hidden configuration file alternative
Ensure that pytest discovers and loads a hidden configuration file named .pytest.ini as an alternative to pytest.ini. Users should be able to use the Unix dot-file naming convention for their pytest configuration, aligning with the convention used by other development tools (.flake8, .pylintrc, .coveragerc, etc.).

- **Expectation**: When a user places a .pytest.ini file in their project, pytest should automatically discover and load it as configuration. The hidden dot-prefixed variant should behave identically to pytest.ini in terms of configuration parsing and option handling. If both pytest.ini and .pytest.ini exist, pytest.ini takes precedence.

- **Constraints**: The change must be fully backward-compatible. Projects relying on any existing configuration file format must not experience any change in behavior. The hidden config file is purely an additive alternative and must not interfere with existing configuration discovery.


### Task 10 Export DoctestItem as public pytest API and resolve circular imports in doctest module
Ensure that DoctestItem is accessible as a first-class member of the public pytest namespace (pytest.DoctestItem) so that users can reference it for type annotations, isinstance checks, and plugin development without relying on private internal module paths. Ensure that the internal doctest module no longer triggers circular imports by depending on the top-level pytest package.

- **Expectation**: Users should be able to import DoctestItem directly from the public pytest namespace for type checking and runtime inspection purposes. All existing doctest collection, execution, skipping, and fixture behavior must remain unchanged. The internal module structure should avoid circular dependency on the top-level package.

- **Constraints**: All existing doctest functionality—collection, execution, skip handling, fixture injection, and error reporting—must behave identically to prior versions. The promotion of DoctestItem to the public API must be additive and must not break any existing import paths or plugin contracts.


## Bug Fixes

### Task 11 Improve assertion messages for Unicode-normalized string comparisons
Ensure that when an assertion compares two strings that are visually identical but differ in Unicode normalization form (e.g., NFC vs NFD), the assertion failure message clearly reveals the difference rather than displaying two identical-looking strings. Previously, users saw output like `assert 'hyvä' == 'hyvä'` with no visible distinction, making it impossible to diagnose the mismatch from the error output alone.

- **Expectation**: When a string equality assertion fails and both strings normalize to the same Unicode form, the assertion output must use an ASCII-safe representation that makes invisible codepoint-level differences (such as precomposed vs decomposed characters) visible to the user. In all other cases, the existing human-readable representation must be preserved unchanged.

- **Constraints**: The improved representation must only apply to the specific case of Unicode-normalization-equivalent strings. All other assertion failure messages, including those for non-string types and for strings that differ beyond normalization, must remain unchanged. Truncation behavior for long strings in non-verbose mode must be preserved.


### Task 12 Raise clear ValueError when empty tuple or falsy value is passed to pytest.raises()
Ensure that `pytest.raises()` raises a clear, immediate error when the `expected_exception` argument is an empty tuple `()`, `None`, or any other falsy value, instead of producing a confusing error later in execution. The error message should explain why the input is invalid and clarify that raising exceptions is already understood as failing the test, so no special code is needed to say 'this should never raise an exception'.

- **Expectation**: When a user passes an empty or absent exception specification to `pytest.raises()`, the framework should fail fast with a clear, actionable error message rather than proceeding to produce a confusing failure downstream. The message should educate the user that no special assertion is needed to express 'this should never raise'.

- **Constraints**: The change must be purely additive in terms of input validation — all previously valid inputs must remain valid and behave identically. Only previously-broken or nonsensical inputs should now produce a better error. The fix must not alter the behavior of successful exception matching or the structure of the returned exception info.


### Task 13 Display assertion messages without escaped newlines in verbose mode
Ensure that assertion error messages displayed in very verbose mode (-vv) render object representations with actual newlines instead of escaped '\n' characters. Previously, the initial AssertionError line contained escaped newlines when comparing large objects (e.g., dictionaries with many keys), severely degrading readability of failure output.

- **Expectation**: The safe repr subsystem provides control over whether object representations use ASCII-escaped output or standard repr output. An additional unlimited-size variant is available for contexts where truncation is undesirable, such as verbose assertion error display. Assertion failure messages in very verbose mode should render multi-line object representations with real newlines, not escaped newline sequences.

- **Constraints**: Default assertion formatting behavior must not change for standard verbosity levels. Exception safety for objects with broken __repr__ implementations must be preserved across all repr functions. Critical system exceptions must never be silenced.


### Task 14 Improve error message when no collector is found for a file
Ensure that when pytest is invoked with a file argument for which no collector can be found (e.g., an unrecognized file extension), the resulting error message clearly communicates the root cause rather than displaying a confusing internal representation such as an empty list of collectors.

- **Expectation**: When no collectors are available for a given file argument, pytest should display a concise, user-friendly error message indicating that no collectors were found. When collectors do exist but the item is absent from them, the error message should continue to list which collectors were searched.

- **Constraints**: Existing error behavior for files that have matching collectors but are not found within them must not regress. The change must only affect the presentation of the error when there are genuinely no collectors available for the file type.


### Task 15 Complete file-like interface on DontReadFromInput for captured stdin
Ensure that sys.stdin, when replaced by pytest's capture mechanism, implements the complete file-like object interface so that code relying on standard IO methods (such as readable(), seekable(), writable(), flush(), seek(), tell(), truncate(), write(), writelines()) does not raise AttributeError. Previously, wrapping sys.stdin.buffer with io.TextIOWrapper during capture would fail with 'DontReadFromInput object has no attribute readable'.

- **Expectation**: When pytest capture is active, the stdin replacement object must behave as a well-formed file-like object. Introspection methods (readable, seekable, writable) must return False to indicate the stream is non-functional. Mutation and positioning methods (flush, seek, tell, truncate, write, writelines) must raise an appropriate unsupported-operation error rather than an AttributeError. Code that checks for or calls standard IO interface methods on sys.stdin during capture should never encounter a missing-attribute error.

- **Constraints**: All previously existing behaviors of the captured stdin proxy must be preserved. The fix must only add missing interface methods without changing the semantics of existing ones. The proxy must not become readable, writable, or seekable — it must remain an inert placeholder that simply avoids AttributeError on standard method lookups.


### Task 16 Do not break into pdb on unittest.SkipTest during collection
Ensure that when pytest is invoked with the --pdb flag, top-level `raise unittest.SkipTest()` statements in test files do not cause pytest to break into the pdb debugger. Previously, each such skip statement produced an unwanted interactive pdb breakpoint, forcing developers to manually continue past every skipped file. This was especially costly in large projects with many conditionally-skipped test modules.

- **Expectation**: When pytest is run with --pdb and a test file raises unittest.SkipTest at module level, pytest should skip the file silently without entering the debugger. The debugger should still activate for all genuine test failures and errors. Skipped tests should appear in the session summary as skipped, just as they do without the --pdb flag.

- **Constraints**: The fix must be narrowly scoped to unittest.SkipTest exceptions only. It must not suppress the debugger for any legitimate test failures, errors, or internal pytest errors. The overall --pdb experience for non-skip scenarios must be completely unaffected.


### Task 17 Inherit pytest marks from all base classes using full MRO
Ensure that when a test class inherits from multiple base classes, each carrying distinct pytest markers, all markers from every base class in the MRO are collected and applied to the test class. Previously only markers from the first base class in the MRO were effective, causing markers from additional base classes to be silently lost. Ensure that marker ordering places subclass markers before superclass markers in MRO order. Ensure that the pytestmark attribute on a class only reflects marks directly applied to that class, not marks inherited from ancestors.

- **Expectation**: When resolving markers for a test class in a multiple-inheritance hierarchy, the framework must collect markers from all base classes, not just the first one. Markers must be ordered so that the most specific class's markers appear first, followed by ancestor markers in standard Python MRO order. Directly querying a class's marker attribute must return only that class's own markers, while the standard marker iteration API aggregates the full inheritance chain.

- **Constraints**: Non-class objects such as test functions and modules must continue to have their markers resolved exactly as before, with no behavioral change. The default behavior of mark collection must include full MRO traversal so existing call sites are unaffected. Marks must still be normalized and validated. Storing a new mark on a class must not cause inherited marks to be duplicated or incorrectly persisted onto the subclass.


### Task 18 Display inner exceptions of ExceptionGroups in pytest output
Ensure that when a test raises a BaseExceptionGroup (PEP-654), all inner/nested exceptions within the group are fully displayed in the pytest test output, regardless of the active traceback display style (--tb=short, --tb=long, --tb=line, etc.). Previously, inner exceptions were silently omitted or collapsed when a non-native traceback style was selected, causing users to lose critical diagnostic information about multiple simultaneous failures.

- **Expectation**: When a test raises an ExceptionGroup containing multiple nested exceptions, pytest must render the full tree of inner exceptions in the test failure output. This must work consistently across all traceback display modes, not only the native mode. The feature must be compatible with both Python 3.11+ (built-in ExceptionGroup) and earlier Python versions using the exceptiongroup backport.

- **Constraints**: The rendering of standard (non-grouped) exceptions must not be altered. The fallback to native display is a temporary measure and must not preclude a future full implementation of styled exception group rendering. Cross-version compatibility must be maintained without introducing unconditional new dependencies for Python 3.11+ users.


### Task 19 Fix caplog.get_records() returning stale data after caplog.clear()
Ensure that caplog.get_records(when) returns current and correct data after caplog.clear() is invoked. Previously, calling caplog.clear() caused get_records() to become frozen: it neither reflected the cleared state nor captured any subsequently emitted log records. This made it impossible to reliably use get_records() and clear() together within the same test.

- **Expectation**: Calling caplog.clear() must fully reset the capture state such that get_records() and records remain consistent with each other at all times. After clearing, get_records() should return an empty list for the current phase, and any new log messages emitted afterward should appear in both get_records() and records. The when parameter of get_records() should only accept the three valid test phase strings.

- **Constraints**: The fix must not break existing tests that rely on caplog.clear() or caplog.get_records() individually. The internal list identity between records returned by get_records() and the handler's live records must be preserved across any number of clear/log cycles. No existing public API signatures should be removed.


### Task 20 Fix EncodingWarning in cacheprovider by specifying explicit UTF-8 encoding
Ensure that running pytest under Python 3.10+ with the warn_default_encoding interpreter flag does not produce EncodingWarning diagnostics originating from the cache provider. Ensure that all cache file I/O uses a consistent, explicit character encoding so that cache data round-trips correctly regardless of the platform's default locale encoding. Ensure that non-ASCII values stored in the cache are preserved as native UTF-8 characters rather than ASCII-escaped Unicode sequences.

- **Expectation**: The cache provider must perform all file operations with an explicitly declared UTF-8 encoding. Cache values containing non-ASCII text must be stored as native Unicode characters rather than escaped sequences. Running pytest on Python 3.10+ with encoding warnings enabled must produce zero encoding-related warnings from the caching subsystem.

- **Constraints**: The encoding fix must be backward-compatible: previously written cache data must remain readable. The change must not alter the logical content or structure of cached data. The fix must be inert on Python versions that do not support encoding warnings, introducing no regressions on older runtimes.


### Task 21 Improve error message when accessing a torn-down fixture via getfixturevalue
Ensure that when a user calls request.getfixturevalue during fixture teardown for a fixture whose cached result has already been finalized, the resulting error clearly identifies the fixture by name and explains that the value is unavailable because the fixture has been torn down. Additionally, ensure the getfixturevalue docstring documents that fixture values may not be available during the teardown phase.

- **Expectation**: When a user attempts to retrieve a fixture value via request.getfixturevalue for a fixture that has already completed its teardown, the error must be descriptive and actionable, identifying the fixture by name and explaining the teardown-related cause. The method's documentation must warn users that fixture values are reliably available during setup and test execution but may be unavailable during teardown.

- **Constraints**: Normal fixture retrieval behavior during setup and test execution must not be affected. The fix must only improve the diagnostic quality of the error when a fixture is accessed after teardown. No new exception types should be introduced; the existing assertion mechanism is preserved.


## Dependency Updates

### Task 22 Remove py library dependency by vendoring py.path and py.error
Ensure that pytest no longer requires the py library as an install-time dependency. Ensure that vendored copies of py.path and py.error are provided so that existing code referencing these modules continues to work. Ensure that if the py library is separately installed, it takes precedence over the vendored copies. Ensure that LocalPath.sysexec raises RuntimeError instead of the former py.process.cmdexec error when a subprocess exits with a non-zero return code.

- **Expectation**: pytest should install and run without the py library present. All existing uses of py.path and py.error should continue to resolve correctly. The local path object should behave identically to its predecessor for all filesystem, import, and path-manipulation operations. The only observable behavioral change is that sysexec raises a standard RuntimeError instead of a library-specific process execution error.

- **Constraints**: Only py.path and py.error are replaced; other py submodules are not covered. Backward compatibility for py.path and py.error must be maintained without requiring users to change their imports. The vendored modules must coexist gracefully with a fully installed py library when present.


### Task 23 Use stdlib tomllib for TOML parsing on Python 3.11+
Ensure that pytest uses the standard library's tomllib module for TOML parsing when running on Python 3.11 or later, removing the need for the third-party tomli dependency on those versions. On Python versions below 3.11, ensure that the existing tomli dependency continues to be used for TOML parsing with no behavioral change.

- **Expectation**: Pytest should automatically select the appropriate TOML parsing backend based on the Python version at runtime. Users on Python 3.11+ should not need the tomli package installed. Users on earlier Python versions should see no change. TOML parsing errors should continue to be reported as UsageError regardless of the backend.

- **Constraints**: The change must not alter any user-observable TOML parsing behavior, error reporting, or configuration loading outcomes. The only difference is which underlying library provides the TOML parser. Backward compatibility with Python versions below 3.11 must be preserved.


## Breaking Changes

### Task 24 Upgrade PytestUnhandledCoroutineWarning to deprecation warning and introduce PytestReturnNotNoneWarning
Ensure that PytestUnhandledCoroutineWarning is elevated from a general warning to a deprecation warning, signaling to users that unhandled coroutines in test functions will become hard errors in pytest 8. Introduce a new public warning class PytestReturnNotNoneWarning as the common ancestor for warnings about test functions returning non-None values, including unhandled coroutines.

- **Expectation**: When a test function yields an unhandled coroutine, the emitted warning should now be classified as a deprecation warning rather than a general warning. Users should be able to filter or catch this warning using standard Python deprecation warning categories. A new publicly accessible warning class for non-None test returns should serve as the shared base for all related warnings, providing a single filter point.

- **Constraints**: The reclassification must not break existing warning suppression or capture configurations that target the unhandled coroutine warning by its class name. The new warning hierarchy must preserve backward compatibility for users filtering on the general PytestWarning category. The deprecation pathway must clearly signal that these warnings will become errors in the next major version.


### Task 25 Deprecate nose test support with runtime warnings
Ensure that pytest emits deprecation warnings when nose-style test setup and teardown patterns are used, signaling that nose support will be removed in a future release. Specifically:
- Ensure that plain setup() and teardown() functions invoked through the nose plugin trigger a PytestRemovedIn8Warning.
- Ensure that class-level setup(self) and teardown(self) methods (nose idioms) trigger a PytestRemovedIn8Warning advising the user to rename them to setup_method(self) and teardown_method(self).
- Ensure that the @with_setup decorator usage is covered by the deprecation notice.
- Ensure that the deprecation warnings include the node ID of the offending test and the name of the deprecated method, along with a link to the deprecation documentation.

- **Expectation**: When tests rely on nose-specific setup and teardown conventions, pytest must warn users at runtime that this support is deprecated and will be removed in a future version. The warnings must clearly identify which test and which method triggered the deprecation, and must provide actionable guidance for migrating to standard pytest idioms. Tests that already use pytest-native setup/teardown patterns must remain unaffected.

- **Constraints**: Nose-style tests must continue to pass and function correctly during the deprecation period — only warnings are added, not behavioral changes. The deprecation warnings must be filterable so that users can suppress them if needed. No false positives should occur for tests using standard pytest conventions.
