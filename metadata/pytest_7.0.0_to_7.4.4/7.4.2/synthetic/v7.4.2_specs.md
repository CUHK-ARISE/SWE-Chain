# Upgrade Specification from 7.4.1 to 7.4.2

## Bug Fixes

### Task 1 Fix doctest collection for functools.cached_property decorated methods
Ensure that doctests defined inside methods decorated with `functools.cached_property` are collected and executed when running pytest with `--doctest-modules`. Previously, these doctests were silently skipped while doctests in regular `@property` methods were collected normally, leading to undiscovered test gaps.

- **Expectation**: Doctests in `functools.cached_property` methods should be discovered and executed identically to doctests in regular `@property` methods when using `--doctest-modules`. No doctests should be silently dropped due to the descriptor type wrapping the method.

- **Constraints**: The change must be limited to doctest collection behavior for cached_property descriptors. It must not alter collection or execution of any other doctest sources. It must not regress doctest discovery for other descriptor types or plain functions.


### Task 2 Fix duplicate import of package __init__.py under --importmode=importlib
Ensure that when pytest is invoked with --importmode=importlib, package __init__.py files are not imported and executed more than once during test collection. Previously, collecting tests (including doctests) from packages caused __init__.py module code to run twice, which could produce side effects such as duplicated registrations, warnings, or resource allocations.

- **Expectation**: When pytest uses importlib-based importing, each package __init__.py should be imported exactly once during a test session, regardless of how many submodules or doctests are collected from that package. Module-level side effects in __init__.py must execute only once.

- **Constraints**: The fix must not regress module name resolution for non-package modules. Import behavior under the default import mode must remain unchanged. Packages at any nesting depth must be handled correctly without double imports.


### Task 3 Preserve user_properties in JUnit XML when fixture teardown fails
Ensure that properties added via the record_property fixture are always included in the JUnit XML output for a test case, even when a fixture teardown raises an exception. Previously, if a test passed or failed and its teardown also failed, the recorded properties were missing from the resulting JUnit XML testcase element.

- **Expectation**: All properties recorded via record_property during a test's lifecycle must appear in the JUnit XML report for that test case. This must hold true regardless of whether the test itself passes or fails, and regardless of whether any fixture teardown raises an error.

- **Constraints**: The fix must not introduce duplicate properties for tests that do not experience teardown failures. Existing JUnit XML output for all other test outcomes (pass, fail without teardown error, teardown-only error) must remain unchanged. No new public API surface or configuration options should be introduced.


### Task 4 Fix crash when long command-line arguments are interpreted as file paths
Ensure that pytest does not crash with an INTERNALERROR when a user supplies very long command-line arguments (e.g., long comma-separated values for custom options) that exceed the operating system's maximum file name length. Previously, pytest attempted to interpret such arguments as file paths and called Path.exists() without guarding against OSError or ValueError, causing an unrecoverable internal error during collection argument resolution and conftest discovery.

- **Expectation**: When pytest receives a command-line argument that produces a path string exceeding OS limits, all path-existence checks must gracefully treat the path as non-existent rather than raising an unhandled exception. Pytest should continue normal execution, applying its standard error reporting for missing paths or skipping conftest loading as appropriate, instead of terminating with an internal error.

- **Constraints**: The fix must not alter pytest's behavior for normal command-line arguments and file paths. Only arguments that produce paths exceeding OS limits should be affected, and they should be treated as non-existent paths. The solution must be consistent across all platforms (POSIX and Windows) and across all code paths where user-supplied arguments are tested for path existence.


## Documentation

### Task 5 Improve plugin list disclaimer to clarify non-curated, non-endorsed status
Ensure that the pytest plugin reference page prominently disclaims that the auto-generated plugin listing is not curated, not systematically reviewed, and does not constitute an endorsement by the pytest project or its developers. This addresses the risk of users trusting potentially malicious or placeholder packages (e.g., dependency confusion attack placeholders) simply because they appear in the official documentation.

- **Expectation**: The auto-generated plugin reference page should clearly communicate to users that appearing on the list does not imply quality, safety, or endorsement. Users should be warned to independently evaluate any plugin before use. The page title and description should accurately reflect the automated, non-curated nature of the listing.

- **Constraints**: No changes to which plugins are listed or how they are discovered. The disclaimer must be prominent and unambiguous, not buried in fine print. Existing documentation structure and formatting conventions for the rest of the page must be preserved.
