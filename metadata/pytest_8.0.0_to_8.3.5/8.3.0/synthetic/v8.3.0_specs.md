# Upgrade Specification from 8.2.2 to 8.3.0

## New Features

### Task 1 Support Marker Keyword Argument Selection in -m Expressions
Ensure that marker-based test selection supports filtering by marker keyword arguments and values in addition to marker names, so users can target or exclude tests based on custom marker metadata supplied on the marker.

- **Expectation**: Users should be able to select tests with `-m` not only by marker name, but also by specific marker attributes such as IDs, flags, or other marker metadata. Marker filters should behave predictably in combined expressions, and only clearly supported literal value types should be accepted.

- **Constraints**: This enhancement is scoped to marker selection only and must not broaden unrelated expression features. Invalid filter syntax should fail fast instead of being interpreted loosely, and existing name-only marker selection should continue to work unchanged.


### Task 2 Support per-test skipped entries in the short summary
Ensure that users can control whether skipped tests are folded together in the short test summary, so they can either keep the existing grouped output or view each skipped test as an individual summary entry.

- **Expectation**: Users should be able to switch skipped-test reporting in the short summary from grouped output to per-test output. By default the summary should stay compact, and opting out of folding should make every skipped test visible as its own line together with any available reason.

- **Constraints**: Keep existing behavior unless the user explicitly disables skipped-summary folding, and limit the change to skipped-item presentation in the short summary. Other reporting categories and execution behavior should not change.


## Bug Fixes

### Task 3 Improve virtual environment detection during collection
Ensure that pytest reliably recognizes Python virtual environment roots across platform-specific and nonstandard layouts so it does not mistakenly treat virtual environment directories as normal project content during default test discovery.

- **Expectation**: Pytest should identify virtual environments using the standard metadata file that Python environments provide, regardless of whether their folder layout looks Windows-style or Unix-style, and it should avoid surfacing filesystem-detection failures as user-facing errors.

- **Constraints**: Virtual environment recognition should be layout-agnostic, should not depend on activation script conventions, and should fail conservatively instead of disrupting collection.


### Task 4 Show full function arguments in -vvv failure output
Ensure that pytest failure output shown at very high verbosity no longer truncates displayed function arguments in tracebacks, while keeping lower-verbosity failure output safely abbreviated.

- **Expectation**: At very high verbosity, traceback argument displays should show complete values instead of ellipsized ones. Normal verbosity should keep shortening long argument values so failure output remains manageable.

- **Constraints**: Only the visibility of function argument values at high verbosity should change. Other traceback formatting behavior and the default condensed output should continue to behave as before.


### Task 5 Improve bound-method assertion introspection readability
Ensure that failed assertions involving bound instance methods present concise, readable introspection output instead of verbose bound-method object representations.

- **Expectation**: When an assertion fails around a call to an instance method, the failure explanation should show a compact, human-readable method reference so users can understand the failing expression quickly.

- **Constraints**: Improve readability for bound methods without broadly changing how unrelated values are displayed in assertion failure output.


### Task 6 Add timezone-aware JUnit XML suite timestamps
Ensure that JUnit XML reports include timezone information in the testsuite timestamp so downstream CI and reporting systems can interpret the reported suite start time correctly.

- **Expectation**: JUnit XML output should expose the suite start time with an explicit timezone offset, allowing consumers to read the timestamp unambiguously across different environments.

- **Constraints**: Only improve the timestamp's clarity and interoperability; the report should remain compatible with existing JUnit XML consumers aside from now providing the missing timezone context.


### Task 7 Restore reporting of higher-scoped fixture teardown failures on early stop
Ensure that teardown failures from higher-scoped fixtures are still executed and reported when pytest stops a run early because `--maxfail` is reached or `--stepwise` halts progression after a failing test.

- **Expectation**: Early-stop modes should not hide fixture cleanup failures. If a test failure causes the run to stop, pytest should still finish relevant fixture teardown work and surface any teardown failure as an error alongside the original failure.

- **Constraints**: Keep early termination semantics unchanged while making shutdown reporting complete. The fix should add missing teardown error visibility without resuming normal execution of the remaining test suite.


### Task 8 Support sequence-like inputs in pytest.approx
Ensure that `pytest.approx()` supports ordered custom sequence-like values in the same way it supports built-in sequences, including when a comparison fails and pytest needs to show mismatch details.

- **Expectation**: Approximate equality should work for custom ordered sequence containers, and a failing comparison should still produce a normal, user-readable mismatch result instead of failing while formatting the assertion output.

- **Constraints**: Limit the change to ordered sequence-like inputs and keep all other supported and unsupported input categories behaving as they did before.


### Task 9 Stabilize reused setup failure tracebacks
Ensure that repeated test failures caused by a shared higher-scope fixture setup error or collector setup error report a stable traceback for every affected item, while preserving compatibility expectations for plugins that inspect cached setup failures.

- **Expectation**: Repeated failures caused by one shared setup problem should look the same for each affected test item instead of growing noisier over time. Reused setup failures should preserve their original failure context, and plugin integrations should continue to understand the failure metadata exposed by the upgraded version.

- **Constraints**: The change should stabilize how reused setup failures are reported without changing which tests fail, what kind of failure they report, or how successful setup and caching behave. Edge cases around unusual cache-key objects should remain safe and non-disruptive.


### Task 10 Skip abstract test classes during collection
Ensure that abstract test classes are not collected as runnable tests, including abstract unittest.TestCase subclasses, so collection only considers concrete implementations and does not fail when abstract base classes are present.

- **Expectation**: Users should be able to create abstract base classes for shared test behavior without pytest attempting to run those base classes. Only concrete subclasses should be collected and executed, and abstract classes should be skipped cleanly during discovery.

- **Constraints**: Do not broaden or narrow test discovery beyond excluding abstract classes. Projects that already rely on concrete test classes being collected should continue to behave the same, aside from removal of failures caused by abstract bases being considered runnable tests.


### Task 11 Restore package-scoped fixture reuse ordering
Ensure that parametrized package-scoped fixtures are reused across all applicable test modules in the same package before pytest tears them down and switches to the next parameter value.

- **Expectation**: If several test modules in one package use the same parametrized package-scoped fixture, pytest should run every test for one parameter value across that package before moving to the next value, restoring efficient fixture reuse and avoiding unnecessary teardown and recreation between modules.

- **Constraints**: Improve ordering efficiency without changing fixture isolation rules or causing unrelated packages or scopes to share lifecycle state they should not share.


### Task 12 Restore rerun support for unittest.TestCase tests
Ensure that failing tests defined on unittest.TestCase can be re-run by rerun-capable pytest plugins without crashing in pytest internals, and that reruns continue from the test's actual failure state rather than stopping on an internal assertion.

- **Expectation**: Rerunning a unittest-style test should behave like a normal second execution of that test. Users should see the test rerun according to plugin behavior, without pytest crashing internally or replacing the test's real result with a framework error.

- **Constraints**: The change should be narrowly scoped to restoring correct rerun behavior for unittest-based tests, without altering how ordinary test runs behave or requiring users to change plugin usage.


### Task 13 Stabilize custom pytest_report_teststatus verbose markup
Ensure that custom `pytest_report_teststatus` hooks can return a verbose status with explicit markup for reported outcomes, including `failed` and `error`, without crashing terminal output or summary rendering.

- **Expectation**: Plugins that customize test status text should be able to provide styled status labels, and those labels should appear consistently anywhere pytest prints that status. Invalid custom status data should produce a clear plugin-facing failure rather than an internal crash.

- **Constraints**: The upgrade must preserve current behavior for standard custom status labels while extending support for styled labels. It should tighten validation of malformed custom status output without regressing normal reporting.


### Task 14 Handle invalid pytest.raises match patterns cleanly
Ensure that `pytest.raises(..., match=...)` handles invalid regular expression patterns as a user-facing pytest failure instead of exposing an internal regex error or traceback.

- **Expectation**: Users should get a clear and direct failure when they provide an invalid regex to the `match` option of `pytest.raises`. The failure should point to misuse of the `match` argument, and valid matching behavior should continue to work as before.

- **Constraints**: This change should only improve how invalid `match` patterns are reported. It should not alter normal exception assertion behavior for correctly formed patterns.


### Task 15 Prevent Windows cache crashes during concurrent cache directory creation
Ensure that using pytest's cache functionality on Windows does not crash when the cache directory is created concurrently by another process or thread.

- **Expectation**: Cache-related operations should remain stable under normal concurrent use on Windows. If another actor creates the cache directory first, pytest should continue normally instead of failing, while genuine filesystem problems should still be reported.

- **Constraints**: The fix should be narrowly scoped to the harmless race condition. It must not hide real cache filesystem failures or alter normal cache behavior outside that concurrency edge case.


### Task 16 Fix parametrized fixture cache reuse for equal values
Ensure that parametrized fixtures are cached and reused based on parameter value equality rather than only object identity, while still handling parameter types whose equality comparison is unsafe.

- **Expectation**: Pytest should reuse a previously created parametrized fixture whenever a later parameter represents the same value, even if it is a different object instance. For parameter objects that cannot be compared safely with normal equality, pytest should degrade gracefully to identity-based matching. Repeated requests that hit a cached fixture failure should surface the same failure again without rerunning setup.

- **Constraints**: The fix must broaden cache reuse for equivalent parameter values without breaking parameter types that have non-standard equality behavior, and it must not change the fact that both successful and failed fixture outcomes remain reusable from cache.


### Task 17 Fix progress indicator alignment for parallel test runs
Ensure that terminal progress output stays aligned and readable during parallel execution, and that completed progress is not shown before the test run has actually finished.

- **Expectation**: Parallel execution should not cause the progress meter to drift, wrap unpredictably, or reach a completed state too early. Users should see stable incremental progress throughout the run and a single final completion display only when execution is fully done.

- **Constraints**: The change should improve progress display accuracy only. It must not alter which test outcomes are reported or otherwise change the meaning of the test run beyond making progress reporting correct and readable.


## Dependency Updates

### Task 18 Separate XFAIL traceback output from XFAIL summary reporting
Ensure that XFAIL traceback display is controlled independently from XFAIL summary reporting, so users can keep XFAIL entries in terminal summaries without automatically printing traceback details unless they explicitly opt in.

- **Expectation**: Users should be able to see which tests were expected to fail without being forced to view full XFAIL tracebacks. XFAIL tracebacks should appear only when explicitly requested, and they should respect the configured traceback display style.

- **Constraints**: The change should narrow XFAIL output without reducing normal failure diagnostics or removing existing XFAIL summary information. Opt-in traceback behavior for expected failures must remain consistent with the user's overall traceback display preferences.


### Task 19 Adopt generic third-party plugin terminology in pytest plugin reporting
Ensure that pytest's user-facing version and help output refers to distribution-discovered plugins using generic third-party plugin terminology instead of setuptools-specific wording.

- **Expectation**: Pytest should use modern, generic language when showing installed external plugins, so users see them described as third-party plugins without any outdated setuptools-specific wording.

- **Constraints**: The upgrade should rename the plugin category in output without changing which plugins are shown, when they are shown, or the practical meaning of the reported plugin details.


### Task 20 Adopt pytest 8.3.0 typing update and corrected package-scoped fixture ordering
Ensure that upgrading to pytest 8.3.0 preserves compatibility with the library's Python 3.10+ annotation model and correctly groups parametrized package-scoped fixtures across tests in the same package so unnecessary setup and teardown churn does not occur between modules.

- **Expectation**: After the upgrade, the dependency should behave like pytest 8.3.0: typing metadata follows modern Python annotation conventions, and tests that share the same package-level parametrized fixture should execute in a package-consistent grouping that avoids needless fixture recreation across files in the same package.

- **Constraints**: The upgrade should be narrowly compatible: it should improve package-scoped parametrized fixture scheduling without introducing unrelated execution-order changes or altering how other fixture scopes behave.


## Documentation

### Task 21 Expose CI-related environment variables in pytest help
Ensure that `pytest -h` documents the CI-related environment variables that affect pytest's output behavior, so users can discover from the CLI help that `CI` and `BUILD_NUMBER` indicate CI execution and influence summary truncation.

- **Expectation**: Users reading pytest's command-line help should be able to see which environment variables mark the run as occurring in CI, and understand that either variable enables the same CI-oriented summary visibility behavior.

- **Constraints**: The upgrade should improve discoverability of existing CI-related behavior without changing unrelated help output or altering the meaning of other environment variables.


### Task 22 Render changelog drafts directly during Sphinx doc builds
Ensure that Sphinx documentation builds always render the changelog draft preview automatically, without depending on a separately generated temporary draft file, so contributors and hosted doc builders see the same changelog preview behavior.

- **Expectation**: When the docs are built, the pending changelog preview should appear automatically as part of the Sphinx output in all supported build environments. The preview should be generated from the project's release-note fragments directly during the build, even when there are no entries for some sections.

- **Constraints**: The upgrade must remove reliance on temporary generated artifacts and keep the changelog preview consistently available wherever the documentation is built. It should avoid introducing environment-specific behavior or manual setup just to make the draft preview appear.


### Task 23 Adopt the new Sphinx PR role and updated documentation extensions
Ensure that the documentation system and contributor-facing authoring conventions are updated for pytest 8.3.0 so GitHub pull request references use the new `:pr:` role, GitHub issue/PR links continue to resolve correctly, draft changelog content remains available in documentation builds, and release documentation builds preserve release-specific content handling.

- **Expectation**: After upgrading, documentation authors should use the newer, shorter pull request role and expect GitHub references to render correctly without project-specific custom link role wiring. The documentation build should continue to surface draft changelog information and distinguish tagged release builds from non-release builds, while leaving pytest's runtime behavior unchanged.

- **Constraints**: The upgrade should remain backward-safe for pytest users at runtime, with all impact confined to documentation authoring and rendering. Documentation references and release-build content must stay consistent and not lose existing issue, pull request, or changelog visibility.


### Task 24 Remove legacy BPO documentation role support
Ensure that documentation used with pytest 8.3.0 no longer relies on the deprecated `:bpo:` role and instead uses supported GitHub issue cross-references so documentation remains compatible with the updated docs toolchain.

- **Expectation**: Documentation authors should reference migrated Python issues through the supported GitHub issue-linking roles and treat the old Python bug tracker role as removed and unsupported.

- **Constraints**: The upgrade should only change how documentation links are authored and resolved, without affecting normal library usage outside the docs toolchain.


## Additional Changes
- Ensure that code needing to know whether it is running under pytest can use a documented, supported signal to detect that condition.
- Ensure that user-facing guidance for external pytest plugins no longer implies setuptools is required for plugin discovery or installation metadata, and instead describes such plugins in generic installed, external, or third-party package terms while preserving existing plugin behavior.
- Ensure that PyPy-based use of the library runs on PyPy 3.9 instead of PyPy 3.8 so users do not encounter intermittent collection and import failures caused by the PyPy 3.8 runtime bug.
- Ensure that every tox environment exposed by the project is described when contributors list environments, so no supported environment appears undocumented or unclear in purpose.
- Ensure that release note classification no longer relies on the deprecated `trivial` category and instead uses the new audience-specific categories for packaging-related updates, contributor/process updates, and miscellaneous documented changes.
- Ensure that automatically generated plugin list update pull requests use a review-ready workflow that lets maintainers trigger CI by marking the pull request as ready for review, without needing to close and reopen it.
- Ensure that upgrading from 8.2.2 to 8.3.0 preserves existing runtime behavior while adopting the updated coverage-reporting semantics in which tests marked as expected to fail no longer influence the reported coverage level.
- Ensure that contributor validation catches malformed `:user:` RST role usage in change note and release note bylines before documentation changes are accepted.
- Ensure doctest collection and line-number reporting stay correct across supported Python versions without continuing to override private stdlib doctest internals once upstream Python releases have fixed the relevant bugs.
- Ensure that users who misconfigure terminal code-highlighting theme environment variables receive clear, actionable error messages that explain how to correct the setting.
