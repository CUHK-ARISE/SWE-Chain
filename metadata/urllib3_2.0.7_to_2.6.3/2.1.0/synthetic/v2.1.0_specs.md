# Upgrade Specification from 2.0.7 to 2.1.0

## Bug Fixes

### Task 1 Support in-memory CA data for proxies
Ensure that proxy-based urllib3 connections can be configured with CA certificates supplied directly from memory, not only from certificate files.

- **Expectation**: Users should be able to provide trusted CA certificate contents directly when configuring a proxy, and requests through that proxy should use the supplied trust material without rejecting the option.

- **Constraints**: The change should only add support for in-memory CA certificate data in proxy configurations and should not weaken existing certificate validation or alter unrelated SSL options.


### Task 2 Support x-gzip response decoding
Ensure that HTTP responses declaring Content-Encoding as x-gzip are decoded the same way as responses declaring gzip, so users do not need to manually disable decoding and decompress the body themselves.

- **Expectation**: A gzipped response should be transparently decompressed even when the server uses the x-gzip content-encoding label instead of gzip.

- **Constraints**: The change should add compatibility for x-gzip without broadening decoding behavior in unrelated ways or regressing existing supported encodings.


## Breaking Changes

### Task 3 Remove deprecated secure extra support
Ensure that urllib3 2.1.0 treats the deprecated urllib3[secure] extra as removed and no longer presents it as a supported way to obtain TLS-related behavior or dependencies.

- **Expectation**: Users should install and depend on plain urllib3 instead of the old secure extra. The library should not imply that the removed extra provides additional security, and its normal TLS compatibility checks should continue to behave consistently.

- **Constraints**: The upgrade should remove only the obsolete secure-extra contract while preserving existing TLS safety boundaries and unrelated public behavior.


### Task 4 Remove SecureTransport TLS support
Ensure that the deprecated SecureTransport TLS backend is no longer supported as an injectable urllib3 TLS implementation, and that urllib3 behaves only according to supported SSL backends.

- **Expectation**: Users must not be able to opt urllib3 into Apple's SecureTransport TLS implementation. urllib3 should use its supported TLS stack and should not preserve compatibility flags or behavior branches for the removed backend.

- **Constraints**: Removing the deprecated backend must not degrade supported TLS usage for normal HTTPS clients, but code depending on the removed backend should fail clearly through normal missing-API or missing-module behavior rather than silently enabling SecureTransport.


### Task 5 Drop Python 3.7 support
Ensure that urllib3 2.1.0 no longer supports Python 3.7 and that related compatibility paths are removed without regressing SSL and SOCKS behavior on supported Python versions.

- **Expectation**: Users must run urllib3 on supported Python versions, and SSL context setup should only enable TLS post-handshake authentication when certificate verification actually requires it. Supported PyPy runtimes should continue to receive the correct SSL reliability classification, and SOCKS proxy support should remain available on supported runtimes.

- **Constraints**: The upgrade should make the supported runtime boundary explicit while avoiding unrelated behavior changes for supported users. Security-sensitive SSL behavior should remain conservative, and proxy functionality should continue to behave the same on supported platforms.
