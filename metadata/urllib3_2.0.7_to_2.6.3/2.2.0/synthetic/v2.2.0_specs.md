# Upgrade Specification from 2.1.0 to 2.2.0

## New Features

### Task 1 Support urllib3 in Emscripten and Pyodide
Ensure that urllib3 can perform HTTP and HTTPS requests from Emscripten/Pyodide browser runtimes using the standard urllib3 APIs, including incremental response streaming when the browser environment supports it.

- **Expectation**: Users running urllib3 in Pyodide, PyScript, or other Emscripten browser environments should be able to make HTTP and HTTPS requests through familiar urllib3 interfaces. Capable browser worker environments should deliver streamed response bodies incrementally, while unsupported environments should still complete requests through buffered browser APIs and report limitations through warnings and standard Python exceptions.

- **Constraints**: The new browser runtime support should integrate without disrupting existing urllib3 users, should degrade gracefully when streaming or timeout features are unavailable, and should keep browser-specific limitations behind the normal urllib3 API contract.


### Task 2 Add HTTPResponse.read1 support
Ensure that HTTPResponse supports read1-style body consumption for streamed responses, including optional content decoding and consistent end-of-stream handling.

- **Expectation**: Users should be able to read streamed HTTP responses one buffered chunk at a time through HTTPResponse.read1(), with the same decoding controls and error behavior they expect from existing response reads.

- **Constraints**: The new read1 API must be additive and must not change existing response-reading behavior for callers that continue using the established APIs.


### Task 3 Add rudimentary HTTP/2 support
Provide rudimentary opt-in HTTP/2 support for HTTPS requests while preserving the ability to restore the existing HTTP/1.1 HTTPS behavior and clearly rejecting unsupported HTTP/2 scenarios.

- **Expectation**: Users can opt into simple HTTP/2 over HTTPS for requests that do not need request bodies, proxying, streaming, multiplexing, redirects, or connection reuse. Responses should be fully buffered and presented through urllib3 response semantics with the correct protocol version, status, headers, and body. Users can opt back out to normal HTTPS behavior.

- **Constraints**: Do not present this as complete HTTP/2 support. Unsupported features should either remain unavailable or fail explicitly, and enabling HTTP/2 should not permanently alter HTTPS behavior once the user opts back out.


## Bug Fixes

### Task 4 Fix HTTPS proxy handling for trailing-dot hostnames
Ensure that proxied HTTPS requests to hostnames ending in a trailing dot do not fail SSL certificate validation solely because the requested URL uses a fully qualified domain form.

- **Expectation**: A user should be able to access a valid HTTPS site through a proxy whether the hostname is written with or without a final dot, while still receiving accurate security status about what endpoint was actually verified.

- **Constraints**: The fix must remove only the false hostname mismatch caused by fully qualified domain spelling and must preserve strict TLS verification and truthful verification reporting for all proxy modes.


### Task 5 Normalize proxy verification state
Ensure that proxied HTTP and HTTPS connections expose deterministic and truthful verification state after connecting, with proxy verification and destination verification reported separately.

- **Expectation**: Applications should be able to inspect a completed proxied connection and always get clear true-or-false answers for whether the proxy was verified and whether the destination was verified. These states should reflect what the client actually verified, including proxy forwarding scenarios and hostnames written with a trailing dot.

- **Constraints**: Maintain request compatibility while making verification reporting explicit, conservative, and separated between the proxy and the final destination.


### Task 6 Preserve caller headers during JSON and proxy requests
Ensure that request APIs do not mutate caller-provided headers when preparing JSON request bodies or merging proxy headers, while still sending the appropriate headers on the wire.

- **Expectation**: Supplying headers to a request should be side-effect free. urllib3 may add default JSON or proxy-related headers to the request it sends, but those additions must not alter the caller's original header data. Existing user-specified content types must continue to be respected.

- **Constraints**: The fix must avoid new side effects without changing the request that users intended to send. Immutable or reused header mappings should be accepted wherever they were otherwise valid.


### Task 7 Correct HTTPS proxy verification reporting
Ensure that HTTPS proxy connections report proxy TLS verification and target TLS verification independently, so an HTTPS proxy forwarding to an HTTP target does not cause the target-facing HTTPSConnection.is_verified state to appear verified.

- **Expectation**: A secure proxy being verified must not be treated as proof that the destination server was verified. Applications should be able to tell whether the proxy was trusted, whether the destination was trusted, and whether a warning is warranted based on those separate facts.

- **Constraints**: Keep request routing and successful responses unchanged while making the exposed security state accurate. Avoid noisy warnings for a verified secure proxy, but continue to surface genuinely unverified secure connections.


### Task 8 Handle OpenSSL 3.2 proxy TLS mismatch errors
Ensure that HTTP-only proxies mistakenly configured as HTTPS are diagnosed consistently under OpenSSL 3.2.0, and ensure expected platform connection-reset signals in request handling do not cause unnecessary failures.

- **Expectation**: Users who accidentally configure an HTTP proxy as HTTPS should get a clear configuration error instead of an unclear SSL failure, including on newer OpenSSL versions. Connection-pool handling should remain resilient to known platform-level reset signals without hiding unrelated network errors.

- **Constraints**: Do not mask unrelated SSL, proxy, or socket failures, and do not change behavior for correctly configured proxies or ordinary response processing. The compatibility fix should be limited to the newly observed OpenSSL/platform error surfaces.


### Task 9 Restore TLS 1.3 post-handshake authentication without certificate verification
Ensure that TLS 1.3 post-handshake client certificate authentication remains available when urllib3 creates an SSL context with server certificate validation disabled.

- **Expectation**: A caller that disables server certificate verification should still be able to connect to TLS 1.3 services that request a client certificate after the initial handshake. Unsupported SSL context implementations should continue to behave gracefully.

- **Constraints**: The fix should restore client-certificate authentication compatibility without broadening assumptions about SSL backends or changing unrelated certificate verification behavior.


## Additional Changes
- Ensure that downstream distributors can distinguish the default validation workflow from the slower integration validation workflow introduced in 2.2.0, without implying any change to urllib3 runtime behavior.
- Ensure urllib3's stale-system-clock diagnostic uses a current recent-date threshold after upgrading to 2.2.0.
- Ensure the missing-PySocks diagnostic directs users to the current SOCKS proxy documentation.
