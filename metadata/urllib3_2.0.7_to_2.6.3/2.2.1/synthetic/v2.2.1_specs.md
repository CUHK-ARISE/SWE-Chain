# Upgrade Specification from 2.2.0 to 2.2.1

## Bug Fixes

### Task 1 Correct Emscripten HTTPS verification warnings
Ensure that urllib3 running on Emscripten does not warn that HTTPS requests are insecure when those requests are validated by the browser-managed TLS layer.

- **Expectation**: Secure browser-backed HTTPS requests should not be surfaced to users as insecure, while non-secure HTTP requests should continue to be recognized as unverified.

- **Constraints**: Do not hide real insecure-connection warnings or change behavior for unrelated runtimes; only correct the false warning for browser-backed HTTPS.


### Task 2 Preserve request headers in urlopen
Ensure that HTTPConnectionPool.urlopen preserves caller-provided non-proxy request headers without prematurely coercing them into HTTPHeaderDict, so supported header values such as bytes do not fail because of HTTPHeaderDict behavior.

- **Expectation**: Requests should keep accepting header inputs that worked before 2.2.0. Adding proxy headers must not change ordinary request headers into a stricter representation that rejects otherwise usable values.

- **Constraints**: The fix must be limited to avoiding the regression while preserving existing proxy behavior and caller data isolation.


### Task 3 Clarify truncated chunked response errors
Ensure that chunked HTTP responses which terminate before sending the next chunk length are reported as premature protocol termination rather than as malformed chunk-length data.

- **Expectation**: A truncated chunked response should be classified as an incomplete protocol exchange, while an actually malformed chunk-size value should remain classified as invalid chunk metadata.

- **Constraints**: Only the error classification for an absent chunk length at end of stream should change; valid responses and genuinely malformed chunk headers should behave as before.


### Task 4 Clarify ProtocolError for unexpected response bodies
Ensure that HTTP responses expected to be empty but received with body content fail with a clear ProtocolError explaining that content is not allowed, instead of presenting the condition as a generic incomplete read or broken connection.

- **Expectation**: Consumers should get a clear protocol-level error when a server or mock sends a body for a response that must be empty. The error should make the unexpected-content problem apparent without changing the public exception category callers already handle.

- **Constraints**: This is a diagnostic fix only: valid responses should behave as before, and unrelated connection failures should keep their previous meaning.


## Additional Changes
- Ensure urllib3 HTTP/2 response objects can be closed through the normal response interface without raising an unimplemented-method error.
