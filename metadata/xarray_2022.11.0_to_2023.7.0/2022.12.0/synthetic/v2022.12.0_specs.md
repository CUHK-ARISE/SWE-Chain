# Upgrade Specification from 2022.11.0 to 2022.12.0

## New Features

### Task 1 Add origin and offset support to resample
Ensure that time-based resampling supports aligning bins with both an explicit origin and an additional offset so users can control how resample windows are anchored for regular datetime data and CF calendar data.

- **Expectation**: Resampling should let users choose the reference point used to anchor aggregation windows and optionally shift that reference by a time delta. This alignment control should work consistently across normal datetime indexes and CF calendar indexes, including backward-aligned windows based on the end of the series.

- **Constraints**: The new alignment options must not break existing end-of-period resampling defaults or blur the distinction between bin anchoring and label shifting. Invalid combinations or unsupported alignment values should fail clearly instead of being silently accepted.


### Task 2 Add experimental Zarr v3 read/write support
Ensure that xarray can read and write datasets against the experimental Zarr v3 protocol while keeping existing Zarr v2 behavior stable, requiring explicit version intent when the store type does not reveal the protocol version, and preventing unsupported consolidated-metadata usage for Zarr v3.

- **Expectation**: Users should be able to opt into experimental Zarr v3 support through the normal xarray Zarr APIs. If the backing store already identifies its Zarr protocol version, xarray should follow that version automatically; if the store is just a path or URL, xarray should remain on Zarr v2 unless the caller explicitly requests v3. Zarr v3 operations should use non-consolidated metadata only, and unsupported consolidation requests should fail clearly rather than behaving inconsistently.

- **Constraints**: The upgrade must preserve current default behavior for existing users, add v3 only as an explicit or inferable capability, and block unsupported metadata modes instead of silently producing partially supported stores. User-visible metadata should stay clean and reflect data semantics rather than backend internals.


## Bug Fixes

### Task 3 Preserve source attributes in xr.where with keep_attrs
Ensure that `xr.where(..., keep_attrs=True)` preserves the metadata of the `x` input in the returned object, including coordinate attributes, and handles DataArray, Dataset, and scalar combinations without incorrectly copying unrelated attributes.

- **Expectation**: Turning on attribute preservation for `xr.where` should keep metadata aligned with the values selected from the primary `x` input. The returned object should preserve the source metadata that users expect to follow those values, especially coordinate metadata, and should avoid inventing or misassigning attrs when one side is a scalar or when the result is promoted to a Dataset.

- **Constraints**: Attribute preservation should be predictable, source-based, and safe across supported input combinations. The behavior must not regress by attaching metadata from the wrong operand or by failing on scalar cases.


### Task 4 Restore cftime plotting via lazy nc_time_axis import
Ensure that plotting DataArray or coordinate values that use cftime-based datetimes works again when the optional nc_time_axis dependency is installed, and fails with a clear dependency error when cftime plotting is attempted without that package.

- **Expectation**: Plots that use non-standard calendar dates from cftime should work again out of the box whenever the optional nc_time_axis package is installed. If that package is missing, the plotting call should stop with an explicit missing-dependency error instead of an unrelated low-level plotting failure. Plotting behavior for standard supported coordinate types should remain unchanged.

- **Constraints**: The fix must be narrowly scoped to cftime-based plotting. It should not make ordinary plotting depend on extra packages, and it should preserve existing validation rules for supported and unsupported plot input types.


### Task 5 Automatically rewind file-like inputs before engine detection
Ensure that opening a dataset from a reusable file-like object does not fail solely because the stream position is not at the beginning, including when the same fsspec-backed S3 file object is opened multiple times.

- **Expectation**: Opening a dataset from a file object should be resilient to the file pointer already having moved. Users should be able to reuse the same compatible stream object without manually closing and reopening it just to reset its position.

- **Constraints**: The fix should only relax failures caused by stream position, without broadening accepted input categories or leaving streams in an unexpected state after opening logic inspects them.


### Task 6 Preserve existing coordinate indexes during Dataset.assign_coords
Ensure that `Dataset.assign_coords()` preserves the existing indexes of dimension coordinates that are not being updated, and does not reset unaffected or retained coordinates to a default pandas index when coordinates are added or reassigned.

- **Expectation**: Assigning coordinates should only change the coordinates the user is actually assigning. Other dimension indexes should stay the same, including any custom or non-default index behavior, so adding a coordinate does not unexpectedly change how existing dimensions are indexed.

- **Constraints**: The update must avoid regressions where unrelated dimensions change indexing behavior as a side effect of assigning coordinates. Existing indexing behavior should remain stable unless the user explicitly changes that coordinate's index.


## Dependency Updates

### Task 7 Raise minimum dependency support and align NetCDF/HDF5 backend behavior
Ensure that upgrading to 2022.12.0 requires the documented newer minimum dependency versions and that NetCDF/HDF5 backend behavior remains correct with those versions, including native advanced indexing support and consistent acceptance of compression-related encoding options.

- **Expectation**: After upgrading, users should be able to rely on the newer supported dependency stack without legacy compatibility shims. Reading data through the HDF5-backed backend should honor advanced indexers using the backend's native behavior, and writing with compression-related encoding metadata should be accepted consistently when using supported NetCDF functionality.

- **Constraints**: The new version should narrow support only by the published dependency floor changes and should not otherwise change backend behavior in surprising ways. Valid compression settings should work consistently, and invalid metadata should still be treated as invalid.


## Typing Updates

### Task 8 Fix xr.polyval static return type inference
Ensure that xr.polyval exposes accurate static typing so users upgrading to 2022.12.0 get the correct inferred return type based on whether coord and coeffs are DataArray or Dataset inputs, including when degree_dim is not passed.

- **Expectation**: Calling xr.polyval should no longer produce an unnecessarily ambiguous inferred type in static analysis. The reported return type should reflect the kind of xarray objects passed by the user, even in the common case where optional arguments are omitted.

- **Constraints**: The upgrade should improve developer tooling feedback without changing how users normally call the API or introducing new calling requirements.


## Others

### Task 9 Deprecate the PyNIO backend with runtime warnings
Ensure that using the PyNIO backend is treated as deprecated while remaining temporarily usable, so users are explicitly informed that this backend is no longer supported and will be removed in a future release.

- **Expectation**: Users who still rely on the PyNIO engine should see a clear deprecation signal whenever they use it, while existing reads continue to behave the same in this release. The library should communicate that PyNIO support is on a removal path without silently changing successful usage into a failure.

- **Constraints**: The update should warn, not break. Existing PyNIO users must still be able to open supported datasets in the current release, but they should no longer be able to use the backend without being told it is deprecated.

- Ensure that xarray plotting APIs that map data values into marker sizes or line widths still produce usable widths when the mapped data is constant rather than varying.
