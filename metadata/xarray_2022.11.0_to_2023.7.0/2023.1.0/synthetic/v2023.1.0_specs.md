# Upgrade Specification from 2022.12.0 to 2023.1.0

## New Features

### Task 1 Add keep_attrs support to pad operations
Ensure that padding a Dataset, DataArray, or Variable can preserve metadata when requested, and that pad operations no longer silently drop attrs when users rely on `keep_attrs` semantics.

- **Expectation**: Padding APIs should give users explicit, reliable control over whether metadata is preserved. If metadata preservation is enabled directly or through the library's default attribute policy, the padded result should keep its attrs; if disabled, the padded result should omit them. This behavior should be consistent across dataset, array, variable, and padded coordinate outputs.

- **Constraints**: The upgrade must only change observable metadata retention behavior for padding and must not alter the actual padded data result or require callers to change existing pad usage unless they want different metadata handling.


## Bug Fixes

### Task 2 Preserve lazy dask dataframe conversion for large datasets
Ensure that converting large dask-backed datasets to a dask dataframe remains lazy and does not crash or exhaust memory due to eager coordinate broadcasting.

- **Expectation**: Converting a large lazily loaded dataset to a dask dataframe should behave as a lazy operation. Users should be able to continue working with or exporting the resulting dataframe without the conversion step unexpectedly materializing huge intermediate arrays in memory.

- **Constraints**: The upgrade should reduce memory pressure without changing how users invoke the feature or weakening normal dataframe conversion behavior. Existing lazy workflows should continue to work, especially on large datasets that were previously unstable.


### Task 3 Preserve lazy behavior when reading xarray nbytes
Ensure that checking the byte size of an xarray object does not accidentally load its underlying data into memory, especially for lazy, deferred, or otherwise inaccessible array backends.

- **Expectation**: Users should be able to inspect how many bytes an xarray object represents without that inspection causing data access, computation, or materialization. If exact byte metadata is unavailable, the library should still provide a sensible size estimate from known shape and data type information.

- **Constraints**: Byte-size introspection should remain safe in lazy workflows, should not break deferred backends, and should continue to return an accurate or metadata-derived size rather than causing unexpected execution.


### Task 4 Preserve xr.where usability with NumPy inputs when keep_attrs is enabled
Ensure that `xr.where()` works correctly when attribute preservation is enabled, including cases where the operands are plain NumPy scalars or arrays rather than xarray objects.

- **Expectation**: Attribute preservation in `xr.where()` should only affect results that actually support attributes. Calls that operate purely on NumPy data should still succeed and return the expected value, while xarray results should continue to preserve metadata in the same user-visible way as before.

- **Constraints**: The fix must be limited to preventing failures on metadata-free results. It should not alter normal metadata propagation for labeled xarray objects, and it should not introduce new metadata or wrapper objects for plain NumPy outputs.


### Task 5 Preserve coordinate dtypes when accessing stacked MultiIndex levels
Ensure that stacking coordinates into a MultiIndex does not change the user-observed dtype of the original coordinate when that coordinate is accessed afterward.

- **Expectation**: Users should observe the same value type before and after stacking coordinates into a MultiIndex. Creating or reading stacked coordinates should not silently promote numeric types.

- **Constraints**: The upgrade should only remove unintended type changes and must not alter the normal semantics of stacked indexing. Existing workflows that read stacked coordinates should keep working, except that returned dtypes now remain stable.


## Dependency Updates

### Task 6 Normalize xarray package imports to absolute module paths
Ensure that upgrading to 2023.1.0 preserves existing xarray behavior while the package adopts absolute import paths throughout the library and associated test helpers.

- **Expectation**: After the upgrade, users should observe the same importable xarray functionality and package behavior as before. The main change is that the project now consistently resolves modules through full package-qualified imports, improving package consistency without introducing a new user-facing feature.

- **Constraints**: The upgrade should be behavior-preserving. Existing workflows, imports, and runtime results should remain stable, and users should not need to change how they call xarray APIs just because the package's internal import style changed.


## Breaking Changes

### Task 7 Update CFTimeIndex lookup semantics for pandas 2.0 compatibility
Ensure that upgrading to 2023.1.0 preserves exact `CFTimeIndex` key lookup through `get_loc()` while treating inexact matching as a separate indexer operation, so applications depending on nearest or tolerance-based lookup can migrate without ambiguity.

- **Expectation**: Index location lookup should clearly separate exact matching from approximate matching. Exact key resolution should continue to work as before, but any lookup that depends on nearest-match behavior or a tolerance window should be performed through the API intended for indexer-based matching rather than through a single-key location helper.

- **Constraints**: Existing exact lookups and date-string slicing should remain stable, while only the calling convention for approximate lookup changes. The upgrade should not remove the ability to perform tolerant or nearest matching; it should only require those behaviors to be requested through the correct public interface.


## Performance Improvements

### Task 8 Optimize alignment when indexed and non-indexed objects already match
Ensure that alignment-heavy operations such as assigning a DataArray into a Dataset do not incur unnecessary reindexing when indexed and non-indexed inputs already have compatible dimensions and equivalent indexes, while still reindexing whenever indexes or dimension sizes are not truly compatible.

- **Expectation**: Operations that combine labeled and unlabeled data of the same shape should remain fast when no actual alignment work is needed. The library should recognize when coordinates already match or when only compatible dimension lengths need to be checked, and it should preserve existing alignment behavior for mismatched indexes or incompatible sizes.

- **Constraints**: The optimization must not weaken correctness checks. Cases that genuinely need alignment should still be aligned, and only redundant work should be removed.


## Additional Changes
- Ensure that concatenating xarray objects backed by Array API-compatible arrays uses the backend's native concat implementation so the result remains on that backend.
