# Upgrade Specification from 2023.1.0 to 2023.2.0

## New Features

### Task 1 Adopt inclusive boundary control for date range APIs
Ensure that date range creation supports the new `inclusive` boundary-selection behavior while preserving existing `closed` behavior only as a deprecated compatibility path.

- **Expectation**: Range-construction APIs should let users choose whether the start and end boundaries are included using a single modern `inclusive` option. Existing callers using `closed` should continue to get equivalent results for now, but they should receive a deprecation warning and be prevented from combining old and new boundary arguments in the same call.

- **Constraints**: The upgrade must preserve existing default range results, provide a clean migration path from the old option to the new one, and fail clearly on ambiguous or unsupported boundary selections. The same boundary rules should apply regardless of which date range variant a user calls.


### Task 2 Support concatenating datasets with missing data variables
Ensure that concatenating datasets can succeed even when some datasets omit data variables that exist in others, without requiring callers to pre-create placeholder variables, while keeping coordinate consistency checks and predictable output layout.

- **Expectation**: Concatenation should behave like an outer union for data variables: users can combine datasets with non-identical variable sets and still get one result containing all relevant variables, with missing portions represented as missing data. The result should be stable in layout and should continue to fail when coordinate definitions are incomplete for a requested coordinate-aware concat.

- **Constraints**: The change should relax dataset variable matching only where users expect optional data variables, not weaken coordinate integrity checks. Missing values should appear in a type-appropriate way, output ordering should stay predictable, and previously valid empty or partially populated concatenations should remain safe.


## Bug Fixes

### Task 3 Respect keep_attrs in Dataset binary operations
Ensure that Dataset binary operations preserve dataset-level attributes when attribute retention is enabled, so Dataset behavior matches user expectations and remains consistent with other xarray container types.

- **Expectation**: Binary arithmetic on Dataset objects should respect the library's attribute-preservation setting. If attribute retention is enabled, the result should keep the original dataset metadata from the primary input; if it is disabled, the operation should continue to produce a result without preserved metadata.

- **Constraints**: The fix should only affect whether metadata is retained during Dataset-to-Dataset arithmetic. It must not change numerical results or introduce new metadata-combination behavior beyond preserving the source dataset metadata when requested.


### Task 4 Validate missing output_sizes in dask apply_ufunc
Ensure that using xarray.apply_ufunc() with Dask parallelization reports a clear validation error whenever output core dimensions require explicit sizes but output_sizes is not provided.

- **Expectation**: Parallelized ufunc execution should consistently reject underspecified output shapes. If the library cannot infer the size of an output dimension from the usable inputs, the user should get an immediate, explicit error telling them to supply output_sizes.

- **Constraints**: The fix must improve error reporting without breaking calls whose output shapes are already well-defined. It should close gaps where shape validation was skipped because dimension names happened to match, even though the sizes were not actually inferable.


### Task 5 Handle xarray-added encodings in Dataset.to_zarr
Ensure that datasets opened in xarray can be written with Dataset.to_zarr() even when variable encodings copied from the loaded dataset include xarray-added metadata that is not part of the zarr encoding API.

- **Expectation**: Writing an already-opened dataset to zarr should work when callers reuse the dataset's existing variable encodings. Internal metadata added during reading should not be treated as an invalid user encoding option or block the export.

- **Constraints**: The fix should be narrowly scoped to internal read-time metadata and must not weaken normal validation of genuinely unsupported zarr encoding settings.


## Breaking Changes

### Task 6 Raise runtime support floor to Python 3.9 and newer dependency minimums
Ensure that upgrading to 2023.2.0 is treated as a runtime compatibility update: the library should only be used on Python 3.9+ with the documented minimum dependency versions, and users should observe the standardized behavior associated with those supported versions.

- **Expectation**: After upgrading, the package should run only on the newer supported Python and dependency stack. Behavior that previously varied across older dependency versions should become consistent: supported dask installations should allow the documented assignment operations, supported h5netcdf installations should use modern string-decoding behavior, and operations that rely on modern pandas or NumPy behavior should expose the warnings and errors of those supported versions rather than preserving legacy compatibility branches.

- **Constraints**: The upgrade should narrow the supported environment without changing the intended behavior on the newly supported stack. Unsupported old-version fallbacks should not be treated as regressions, but current users should still see stable, predictable results and clear failure modes for unsupported operations.


## Documentation

### Task 7 Document flox support for groupby and resample aggregations
Ensure that users upgrading can discover that groupby and resample aggregations support optional flox acceleration, understand that it is used automatically when available, and know how flox-specific options affect observable aggregation behavior.

- **Expectation**: Users should be told, in the main aggregation method documentation, that an optional acceleration backend is available for grouped and resampled reductions, that it is picked up automatically when present, and that callers can tune its behavior through supported keyword arguments. The guidance should also explain the default recommended method and note when an alternative method may perform better.

- **Constraints**: The change is informational and must not break existing grouped or resampled workflows. Existing behavior descriptions should remain intact, and the new guidance should appear consistently anywhere users would reasonably look for aggregation method documentation.


## Additional Changes
- Ensure that converting a dataset to a dask dataframe does not eagerly materialize large NumPy arrays when a variable must be broadcast over several dimensions during conversion.
