# Upgrade Specification from 2023.2.0 to 2023.3.0

## New Features

### Task 1 Support lazy dask indexers on unindexed dimensions
Ensure that indexing and selection along unindexed dimensions can use dask-backed integer indexers lazily, including scalar results from dask computations, while clearly rejecting unsupported dask indexing patterns that would produce ambiguous shapes or unsupported vectorized behavior.

- **Expectation**: Users should be able to pass lazy dask-based integer selectors into xarray selection operations and get the same result shape and values they would get from equivalent in-memory selectors, without eagerly computing those selectors first. When a lazy selector would make the result shape unknowable or relies on unsupported vectorized dask behavior, the operation should fail immediately with a clear, user-facing error instead of producing a confusing downstream failure.

- **Constraints**: The new lazy indexing capability should extend supported selection behavior without weakening existing input validation or silently changing unsupported cases into partial behavior. Previously supported eager indexing paths should keep working the same way, and unsupported lazy cases should be rejected consistently and predictably.


### Task 2 Add dask support for first and last reductions
Ensure that `first` and `last` reductions work on dask-backed arrays in the same user-visible cases supported for in-memory arrays, including skipping missing values for nullable dtypes and returning lazy reduction results instead of rejecting dask input.

- **Expectation**: Users should be able to call `first` and `last` on lazy dask-backed data and get the first or last non-missing value along the requested dimension, with the same reduction semantics they would expect from eager arrays.

- **Constraints**: The new support should extend existing behavior without changing how non-nullable data or explicit non-skipna reductions behave, and it should remain shape-compatible and lazy for dask workloads.


## Bug Fixes

### Task 3 Support correct complex-valued covariance and correlation in xarray
Ensure that `xr.cov()` and `xr.corr()` correctly support complex-valued `DataArray` inputs so users receive mathematically valid covariance and correlation results, including for autocorrelation and self-comparisons.

- **Expectation**: Complex-valued arrays should behave like first-class inputs to covariance and correlation APIs. Users should be able to compute covariance and correlation on complex data and obtain results consistent with standard complex linear algebra, including stable self-correlation behavior.

- **Constraints**: The fix should be backward-compatible for existing callers, should not change how users invoke the APIs, and should improve complex-number correctness without regressing normal real-number workflows or missing-data handling.


### Task 4 Report missing variable names in Dataset.drop_vars errors
Ensure that when dropping variables from a dataset fails because one or more requested variables are not present, the user is told which variables could not be dropped.

- **Expectation**: When a user tries to drop variables that do not exist, the operation should fail with a clear error that names the missing variables so the user can immediately see what was invalid.

- **Constraints**: Only the clarity of the failure feedback should change. Existing successful drops and optional ignore-missing behavior should continue to work as before.


### Task 5 Avoid scatter warnings for unfilled markers while preserving default marker outlines
Ensure that xarray scatter plots do not raise Matplotlib warnings when users choose unfilled markers, while still keeping the default marker outline behavior that helps overlapping points remain visible.

- **Expectation**: Scatter plots should keep the library's default marker outline styling for normal use, but that default must not trigger warnings for marker types that do not support filled edge coloring. If a caller supplies their own edge color, that explicit styling should take precedence.

- **Constraints**: Preserve existing visible defaults for standard scatter markers, avoid introducing new warnings for unfilled markers, and do not override user-requested marker edge styling or require users to adopt a new API.


### Task 6 Fix multidimensional interpolate_na max_gap handling at boundaries
Ensure that `interpolate_na` respects `max_gap` correctly for multidimensional arrays, including missing-value gaps at array boundaries, so edge interpolation or extrapolation only occurs when the gap length for that slice is within the configured limit.

- **Expectation**: Interpolation over multidimensional data should treat each row, column, or slice independently when enforcing `max_gap`. Missing values at the edges should only be filled if that specific edge gap is small enough; otherwise they should remain missing, even if extrapolation is enabled.

- **Constraints**: The upgrade should tighten incorrect edge-case filling without changing the intended meaning of `max_gap`. Existing valid interpolations should continue to work, while oversized boundary gaps in multidimensional data must no longer be filled accidentally.


### Task 7 Fix pcolormesh for string-valued coordinates
Ensure that DataArray.plot.pcolormesh() works when one of the plotted coordinates uses string labels, instead of failing during automatic plotting setup.

- **Expectation**: Pcolormesh plotting should support mixed coordinate types, including categorical or string axis labels. When a plot uses string labels on either axis, it should render normally and avoid coordinate processing that would distort the expected grid shape.

- **Constraints**: Preserve existing pcolormesh behavior for standard numeric coordinate plots while making string-labeled axes safe to plot. The change should be limited to preventing the string-coordinate failure mode and should not introduce new plotting requirements for unaffected cases.


## Dependency Updates

### Task 8 Restrict pandas support to versions below 2.0
Ensure that upgrading to xarray 2023.3.0 enforces compatibility with pandas versions earlier than 2.0 and preserves the expected behavior of datetime conversion, datetime accessor operations, string formatting, rounding, and CFTime-based resampling when values are temporarily represented through pandas Series.

- **Expectation**: Users upgrading to this release should remain on a pandas version below 2.0, and date/time features should continue to work the same way as before for supported pandas versions, including extracting datetime fields, rounding timestamps, formatting datetimes as strings, and resampling CFTime indexes.

- **Constraints**: The change is a compatibility boundary, not a redesign of date/time APIs. Existing supported workflows should keep the same externally visible behavior, and the release should not imply support for newer major pandas versions.


## Breaking Changes

### Task 9 Deprecate resample base and loffset parameters
Ensure that `xr.DataArray.resample()` and `xr.Dataset.resample()` treat `base` and `loffset` as deprecated arguments while preserving current resampling behavior during the transition, including consistent behavior for datetime-like and CFTime-based indexes.

- **Expectation**: The resample API should keep legacy `base` and `loffset` usage working temporarily, but clearly signal that these parameters are being removed and that users should migrate to newer alternatives. During this transition, resampling results should stay behaviorally consistent, parameter conflicts should be rejected, and unsupported `loffset` inputs should fail clearly.

- **Constraints**: The deprecation path must not change which bins observations belong to except where existing public parameters already define that behavior. Compatibility support should stay limited to valid time-based resampling inputs, and invalid legacy usage should fail explicitly instead of producing ambiguous results.


### Task 10 Require explicit scatter hue and marker-size dimensions
Ensure that upgrading to xarray 2023.3.0 preserves predictable scatter and plot1d behavior by only inferring required axes automatically, requiring optional encodings like hue and marker size to be explicitly requested, and continuing to support coordinate selection even when coordinate names are integers.

- **Expectation**: Scatter and other 1D-style plots should stop guessing extra semantic mappings from whatever coordinates happen to exist. The library should only infer the required axis needed to draw the plot, and it should apply color or size encodings only when the caller explicitly asks for them. Default plotting should therefore stay fast, unsurprising, and consistent with direct matplotlib styling, while coordinate names of any hashable type should still be usable.

- **Constraints**: The upgrade must reduce accidental heavy plotting and nonsensical defaults without removing explicit semantic plotting features. It must not break valid explicit axis, hue, or size selections, and it must continue to accept coordinate names that are not ordinary strings.


## Performance Improvements

### Task 11 Avoid full reads when detecting cftime values in object arrays
Ensure that opening datasets and validating datetime-like inputs remain responsive for large object-dtype arrays by avoiding unnecessary full-array reads when determining whether values are `cftime` datetimes.

- **Expectation**: Datetime-like feature detection should stay behaviorally consistent but become lazy enough that large object arrays do not need to be fully loaded just to decide whether they contain `cftime` timestamps. APIs that accept datetime-like data should continue to accept valid datetime inputs and reject invalid ones with the same kinds of user-visible failures.

- **Constraints**: The optimization must not change the meaning of datetime detection, only how much data is touched to make that decision. Existing datetime-related APIs should keep the same acceptance and rejection boundaries while avoiding avoidable I/O and computation.


## Additional Changes
- Ensure that opening Zarr-backed datasets is standardized around `xarray.open_dataset(..., engine='zarr')`, and that existing users of `xarray.open_zarr` are clearly treated as using a deprecated API that should be migrated without losing the ability to open Zarr data.
- Ensure xarray does not expose NCZarr internal metadata as user attributes merely because the backend stored those metadata keys with lowercase `_nc` prefixes instead of uppercase `_NC`.
