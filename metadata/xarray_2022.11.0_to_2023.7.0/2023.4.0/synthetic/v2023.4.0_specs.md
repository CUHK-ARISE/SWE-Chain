# Upgrade Specification from 2023.3.0 to 2023.4.0

## New Features

### Task 1 Add reset_encoding APIs for xarray objects
Ensure that users can explicitly remove stored encoding metadata from xarray objects after loading or modifying data, so backend-specific encoding does not interfere with later writes, appends, or re-encoding workflows.

- **Expectation**: Users should be able to call a dedicated reset API on loaded xarray objects to drop inherited encoding metadata and continue working with equivalent data using default or newly supplied encoding settings. The reset operation should behave like a non-destructive copy that removes encoding state but does not alter the actual contents of the object.

- **Constraints**: The feature must be safe to use as a metadata cleanup step: it should only remove encoding information, keep the original object intact, and avoid changing values, dimensions, coordinates, or overall dataset meaning.


### Task 2 Refresh backend engine discovery after environment changes
Ensure that backend engine discovery can be refreshed at runtime so datasets using newly installed or newly registered engines are recognized in the current session without requiring a process or kernel restart.

- **Expectation**: Users should be able to install or expose an Xarray backend during an active session, call a refresh operation, and immediately have backend discovery reflect the new environment. After refreshing, operations that depend on backend availability should behave as though Xarray had been imported after the installation.

- **Constraints**: Refreshing should update backend visibility without changing unrelated dataset behavior. The refreshed engine list should match the current environment exactly, drop no-longer-available dynamic engines, preserve normal engine listing behavior, and keep always-supported backends available.


### Task 3 Support saving DataArray objects directly to Zarr
Ensure that users can save an `xarray.DataArray` directly to a Zarr store, with the result remaining readable as the same data array shape, values, dimensions, coordinates, and name semantics after reopening.

- **Expectation**: Users should be able to write a single data array to Zarr directly, without converting it to another container type first. Reopening that store as a data array should reproduce the original array semantics, including edge cases around missing names and name conflicts. Deferred execution should also be available so writes can be scheduled and computed later.

- **Constraints**: The feature should fit existing Zarr read and write workflows without changing how users reopen data arrays or use supported storage backends. Adding the convenience API must not break existing loading options or change the meaning of immediate versus deferred writes.


### Task 4 Preserve duck-array backend reads and lazy indexing semantics
Ensure that datasets opened from backends can expose and preserve non-NumPy duck arrays during lazy reads and loads, without forcing premature NumPy conversion, while keeping indexing, representation, and decoding behavior consistent for users.

- **Expectation**: Reading from a backend should work even when the backend provides a non-NumPy array type, such as a GPU or other duck array. Users should be able to inspect, lazily index, format, and load data without unexpected conversion failures, and indexed results should keep the expected shape and contents.

- **Constraints**: The upgrade must broaden supported array types without breaking existing lazy behavior, shape consistency, or normal eager conversion paths. Existing workflows that depend on indexing, display, and loading should keep working, including edge cases involving reversed selections and computed coordinates.


## Bug Fixes

### Task 5 Accept all integer degree dtypes in xr.polyval
Ensure that xr.polyval accepts polynomial degree coordinates expressed with any valid integer dtype, so users can evaluate polynomial coefficients produced or stored with platform-specific or non-default integer types without spurious validation failures.

- **Expectation**: Polynomial evaluation should work whenever degree labels are genuine integers, regardless of which concrete integer storage type was used. Users should only see validation errors for truly invalid degree labels, not for harmless integer dtype differences between platforms or datasets.

- **Constraints**: The fix must broaden valid integer inputs without weakening input validation overall. It must not change results for existing valid calls, and it must not allow non-integer degree labels to pass.


### Task 6 Preserve permission errors during xarray backend detection
Ensure that opening a dataset or data array from a file path without read permission fails with a permission-related error instead of a generic backend-matching failure during IO engine detection.

- **Expectation**: If a file exists but the process is not allowed to read it, xarray should report that access is denied. Users should see a permission failure that reflects the real cause, not a misleading indication that no suitable file format backend is installed or matched.

- **Constraints**: The change should improve diagnosis of unreadable files without altering normal file-opening behavior for readable inputs or broadly changing how unrelated engine-detection errors are handled.


### Task 7 Preserve provided BoundaryNorm behavior in DataArray plotting
Ensure that DataArray plotting honors a user-supplied BoundaryNorm consistently so discrete color mapping and colorbar rendering match the intended normalization boundaries, including cases where the plotted data does not reach the norm's upper bound.

- **Expectation**: Plots that are given an explicit discrete normalization should respect it exactly. Users should see the same binning, color assignment, and colorbar semantics they asked for, without the library silently shifting or recomputing the normalization.

- **Constraints**: The fix must be additive and non-disruptive: existing discrete plotting workflows should keep working, while explicit normalization inputs should no longer be altered behind the scenes.


### Task 8 Preserve reference-date timestamp formatting under pandas 2.0
Ensure that time encoding reference dates outside the nanosecond-precision datetime range continue to serialize with the same user-visible formatting after upgrading to pandas 2.0, so encoded units and round-tripped datasets remain stable.

- **Expectation**: Time reference dates should keep the same visible string format before and after the dependency upgrade. Supported datetimes should serialize consistently, and dates outside pandas' supported range should still remain representable without changing existing observable behavior.

- **Constraints**: The upgrade should remove version-dependent formatting drift without altering how unsupported dates are surfaced. Existing datasets should continue to encode and decode time references consistently across supported storage formats.


### Task 9 Preserve boolean dtype across encoded netCDF roundtrips
Ensure that boolean-valued xarray data remains boolean after being saved and loaded through the library's encoding/decoding pipeline, including repeated roundtrips, so persisted data preserves its logical type and behavior.

- **Expectation**: Boolean data that users save and reopen should still behave as boolean data, not silently change type after loading or after saving the loaded result again.

- **Constraints**: The change should only correct unintended loss of boolean type information, without changing the actual values, without adding new user configuration requirements, and without altering unrelated serialization behavior.


## Dependency Updates

### Task 10 Support pandas 2.0 dtype and time-series behavior
Ensure that upgrading to the newer release allows applications to work with `pandas>=2.0` without breaking common xarray workflows involving coordinate selection, datetime field access, resampling, and bin-based grouping, while surfacing clear warnings or errors for unsupported dtype cases.

- **Expectation**: After the upgrade, users should be able to adopt pandas 2.0 and still get the same practical xarray behavior for selection, date/time-derived fields, resampling, and binning. Unsupported low-precision index dtypes should not fail unpredictably; they should either work through safe coercion with a warning or raise a clear validation error when the input is invalid. Time-based operations should keep producing stable, predictable outputs across both regular pandas timestamps and calendar-aware time indexes.

- **Constraints**: Existing working indexing and time-series operations should continue to behave the same for users who are not relying on unsupported dtypes. The upgrade must avoid silent behavior changes in grouping boundaries, output types, or calendar handling, and it must keep deprecation and validation signals visible where inputs are no longer directly supported.


### Task 11 Migrate GRIB reading to the external cfgrib backend plugin
Ensure that GRIB file access continues to work for users upgrading to 2023.4.0 by resolving the `cfgrib` engine through the external backend interface instead of the library's internal backend, and ensure that attempts to open GRIB-based tutorial datasets clearly fail when the `cfgrib` dependency is not installed.

- **Expectation**: Upgrading should preserve the user-facing ability to read GRIB files through the `cfgrib` engine, but that support now comes from the separately installed backend plugin rather than from bundled internal integration. If the required GRIB reader dependency is missing, users should get an immediate and clear dependency error instead of ambiguous backend behavior.

- **Constraints**: Backward compatibility should be preserved for normal GRIB-reading workflows that already depend on the supported external backend package, while unsupported reliance on private bundled integration should no longer be assumed. Backend discovery should remain stable and predictable as external plugins are loaded.


### Task 12 Preserve nanosecond timestamp semantics during pandas 2.0 upgrade
Ensure that upgrading to pandas 2.0 does not change xarray's internal datetime behavior by continuing to treat nanosecond precision as the supported internal timestamp contract in precision-sensitive operations.

- **Expectation**: The library should preserve its existing time semantics across the pandas 2.0 upgrade by coercing internal timestamp handling back to nanosecond precision anywhere xarray relies on that assumption. Users should see stable datetime decoding, encoding, resampling, conversion, and calendar-related behavior, while expanded support for non-nanosecond pandas datetimes is not yet part of this release.

- **Constraints**: The upgrade should favor correctness and continuity over new datetime capabilities. It must avoid silently changing supported ranges, calendar conversion rules, or time-based operation results, and it should not introduce a promise that arbitrary pandas datetime precisions now work throughout the library.


## Breaking Changes

### Task 13 Remove deprecated rasterio-backed opening APIs in favor of rioxarray
Ensure that applications upgrading from 2023.3.0 to 2023.4.0 no longer depend on xarray's deprecated rasterio-opening APIs and instead treat geospatial raster loading through the supported external workflow as the required path.

- **Expectation**: After upgrading, xarray should no longer be expected to open raster files through its old built-in rasterio path. Any user workflow that needs raster dataset ingestion should be considered migrated to the supported external solution, and applications should treat the old xarray raster entry points as unavailable.

- **Constraints**: The upgrade should remove reliance on the retired raster convenience layer without changing unrelated dataset-opening behavior. Existing applications must not assume the old raster helper still exists, still warns, or still provides equivalent metadata and indexing behavior inside xarray.


## Performance Improvements

### Task 14 Avoid unnecessary copies for exact alignment
Ensure that exact alignment requests avoid unnecessary copying and reindexing work when inputs are already aligned, while preserving the existing exact-match contract and observable alignment behavior.

- **Expectation**: When users ask for exact alignment without copying, the operation should behave like a zero-work pass-through for inputs that are already aligned. The upgrade should improve efficiency without changing whether exact alignment succeeds or fails.

- **Constraints**: Only the performance characteristics should improve for the exact no-copy case. All compatibility checks, failure conditions, and behaviors for other alignment modes should remain unchanged.


### Task 15 Preserve existing CFTimeIndex instances during index casting
Ensure that upgrading to 2023.4.0 does not recreate or copy an index that is already a `CFTimeIndex`, while continuing to recognize and convert eligible object-dtype time indexes to `CFTimeIndex` where users expect CF calendar behavior.

- **Expectation**: Users upgrading to 2023.4.0 should see the same CF-time semantics as before, but without unnecessary duplication when the input is already in the correct CF calendar index form.

- **Constraints**: The update should improve efficiency only. It must not alter which inputs are recognized as CF-time indexes, and it must not introduce new failures for indexes that cannot be converted.


## Refactors

### Task 16 Preserve CF variable coding behavior through dedicated VariableCoders
Ensure that upgrading to 2023.4.0 preserves the observable CF encoding and decoding behavior of variables while the implementation is moved into dedicated VariableCoders, including correct handling of booleans, non-native endian arrays, dtype coercion, and fill values.

- **Expectation**: The upgrade must keep CF read/write behavior stable for users: variables should still round-trip with the same effective types and missing-data semantics, boolean fields should decode back to booleans, endian conversion should still produce arrays usable as native machine types, and fill-value handling should remain predictable and reject contradictory metadata.

- **Constraints**: The refactor must not change accepted inputs, round-trip expectations, warning conditions, or failure cases that users already rely on. Explicit metadata should continue to take precedence over automatic conversions, and automatic normalization should only happen when the prior behavior already implied it.


## Additional Changes
- Ensure that users can determine how to open a given file format as an xarray dataset, including when to use xarray's standard dataset-loading API and when format support depends on other packages or backends.
- Ensure that first-time GitHub contributors receive automated welcome messaging when they open their first issue, submit their first pull request, or have their first pull request merged.
- Ensure that grouped arithmetic and grouped reductions continue to behave predictably when the grouping labels contain missing values or when `groupby_bins` / resample inputs include elements that do not belong to any output group.
