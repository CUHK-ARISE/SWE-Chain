# Upgrade Specification from 2023.4.2 to 2023.5.0

## New Features

### Task 1 Add DataArray to Dask DataFrame conversion support
Ensure that users can convert a named DataArray directly into a Dask DataFrame for chunked tabular processing, with predictable column layout, dimension ordering, and validation of unsupported inputs.

- **Expectation**: Users should be able to take a named xarray DataArray and obtain a Dask DataFrame that reflects the same data and coordinates in tabular form. They should be able to control the row ordering through dimension order selection, optionally request index-based output where the shape allows it, and receive clear failures for invalid conversion inputs rather than partial or ambiguous results.

- **Constraints**: The feature must behave as a faithful tabular view of the original array rather than changing the data model. It should preserve meaningful labels and aligned coordinates, reject invalid shape or metadata configurations deterministically, and avoid regressions in ordering or column visibility across supported conversion cases.


### Task 2 Add bit-shift operator support for xarray arrays and grouped data
Ensure that users can apply left-shift and right-shift binary operators directly to xarray integer data structures without dropping to raw NumPy arrays, and that these operations behave consistently across regular, grouped, and lazy-backed data while continuing to fail for unsupported input types.

- **Expectation**: Users should be able to use bit shifting on xarray objects the same way they use other built-in arithmetic operators. Integer-based arrays and datasets should return shifted results directly, including for grouped and lazy data, while unsupported data types should still fail clearly instead of producing coerced or surprising results.

- **Constraints**: This feature should extend operator coverage without changing the established behavior of xarray objects. Existing metadata behavior, grouped computations, and lazy execution should remain consistent, and invalid inputs should still be rejected rather than implicitly altered.


### Task 3 Support array-preserving to_dict output
Ensure that dictionary export for xarray datasets and data arrays supports preserving array-backed data without forcing conversion to Python lists, while keeping backward-compatible list output, schema-only export, and optional encoding export available through the public `to_dict()` API.

- **Expectation**: Users should be able to choose between JSON-friendly list serialization and array-preserving serialization when exporting xarray objects to dictionaries. The export API should still support schema-only output, remain backward compatible for existing callers, and preserve requested encoding metadata through round-trip reconstruction.

- **Constraints**: The new serialization mode must extend current behavior without breaking established exports. Different export modes should stay consistent with reconstruction behavior, avoid unnecessary data conversion, and preserve metadata fidelity when users opt in to encoding details.


### Task 4 Generalize xarray chunked-array support beyond dask
Ensure that xarray users can work with registered chunked array backends other than dask through the same high-level chunking and I/O workflows. Ensure that chunk-aware operations select the appropriate backend automatically for supported arrays and reject unsupported or mixed chunked-array types with clear failures.

- **Expectation**: Users should be able to select a supported chunked execution backend for xarray data loading, chunk conversion, array creation, and zarr writing, while existing dask-based usage continues to work. Once data is backed by a supported chunked array type, xarray should carry out chunked computations through that backend consistently across common lazy operations instead of treating dask as the only valid parallel engine.

- **Constraints**: The feature must preserve current behavior for ordinary in-memory arrays and for dask-backed arrays, while preventing ambiguous backend selection and unsupported mixtures of lazy array types. Backend selection should be explicit or reliably inferred, and invalid combinations should fail rather than silently choosing the wrong execution engine.


## Bug Fixes

### Task 5 Handle read-only masked float arrays in xarray compatibility conversion
Ensure that xarray operations and constructors accept masked float inputs, including read-only masked arrays and masked scalars, without failing, and that masked elements are converted into the expected missing-value representation.

- **Expectation**: Masked inputs should work transparently in xarray. If a masked array or masked scalar is provided, xarray should return the same logical data with masked entries exposed as missing values, even when the original input cannot be written to.

- **Constraints**: The fix must not change the meaning of valid unmasked data. Only masked elements should become missing values, and existing successful conversions should keep behaving the same apart from no longer failing on read-only masked inputs.


### Task 6 Fix subset groupby binary alignment
Ensure that groupby-based binary operations return correctly aligned results when the grouped data only contains a subset of group labels relative to the other operand, so sliced or filtered inputs produce the same values as equivalent explicit selection workflows.

- **Expectation**: Grouped arithmetic should behave like normal label-aware arithmetic even after filtering or slicing the grouped data. If only some groups are present, the operation should use exactly those groups, produce correct values for those observations, and remain consistent with a manual align-then-operate workflow.

- **Constraints**: The upgrade should correct the misalignment bug without changing the basic grouping model, without inventing extra groups, and without weakening validation for incompatible grouped operations.


## Dependency Updates

### Task 7 Extend Python support window to align with NEP-29
Ensure that Python version support is dropped only on the NEP-29-aligned schedule, so users on still-eligible Python releases are not forced to upgrade earlier than expected.

- **Expectation**: Upgrading to this version should preserve compatibility with Python releases for the longer NEP-29-aligned support window. Users should only lose support for an older Python version once that version is old enough under the revised policy, rather than on the earlier schedule used before.

- **Constraints**: The update should avoid introducing unrelated dependency policy regressions. It should only delay Python deprecations to the intended schedule and keep the rest of the compatibility policy stable.


### Task 8 Align flox-backed groupby reduction semantics with standard xarray behavior
Ensure that grouped reductions behave consistently across execution backends after upgrading, especially for `sum` and `prod` on groups containing only missing values, and ensure unsupported `min_count` usage still raises an error instead of changing reduction semantics.

- **Expectation**: Users should see the same grouped aggregation results regardless of whether the optional flox acceleration path is enabled. Missing-data handling for additive and multiplicative group reductions should follow the library's standard defaults, and invalid reduction arguments should continue to fail predictably.

- **Constraints**: The upgrade must remove backend inconsistencies without widening APIs or altering unrelated grouped operations. Unsupported options must still be rejected, and previously correct grouped arithmetic behavior must not regress.


## Performance Improvements

### Task 9 Speed up CFTime-backed .dt accessors without changing results
Ensure that datetime accessor operations on CFTime-backed coordinates remain behaviorally consistent while becoming faster for long time indexes, including date-part extraction and rounding-style operations.

- **Expectation**: Datetime access on non-standard-calendar time coordinates should feel unchanged to users except for improved speed. Reading calendar fields and applying datetime rounding through .dt should produce the same observable results and object shape as prior versions.

- **Constraints**: The optimization must be non-breaking. It should preserve outputs, metadata shape, and normal datetime-access semantics while only reducing unnecessary work behind the scenes.


## Additional Changes
- Ensure that grouping by an external `DataArray` only succeeds when that grouper is exactly aligned to the target object, so coordinate-misaligned inputs fail clearly instead of producing grouped results based only on positional length.
