# Upgrade Specification from 2023.5.0 to 2023.6.0

## New Features

### Task 1 Support coordinate-aware curvefit guesses, bounds, and optional fit error suppression
Ensure that `DataArray.curvefit()` and `Dataset.curvefit()` can fit multidimensional data using per-slice initial guesses and bounds, and allow callers to choose whether optimization failures should raise or be surfaced as missing fit results.

- **Expectation**: Curve fitting should let users provide different starting guesses and parameter limits for different coordinate locations in a single call, rather than requiring manual loops. Users should also be able to opt into tolerant fitting so unsuccessful slices produce missing results instead of failing the entire fitting job.

- **Constraints**: The new flexibility must not silently accept misaligned array inputs or invalid mode values. Existing single-value guesses and bounds should continue to work unchanged, and partial failures should only be tolerated when the caller explicitly asks for that behavior.


### Task 2 Support partial curve fitting failures and dimension-aware fit inputs
Ensure that batch uses of `curvefit` can optionally tolerate individual optimization failures without aborting the entire operation, while also supporting per-slice initial guesses and bounds that align with the non-reduced dimensions of the data.

- **Expectation**: Users should be able to run curve fitting across many series without losing all results because a subset of fits fails. They should also be able to provide different starting guesses or bounds for different slices of the data, as long as those inputs align with the dimensions being preserved in the output.

- **Constraints**: The new flexibility must not change the outcome of successful fits or silently accept misaligned inputs. Invalid mode values or per-slice fit inputs that do not match the output grouping should fail clearly rather than being guessed or reshaped implicitly.


## Bug Fixes

### Task 3 Prevent weighted polyfit from mutating source xarray objects
Ensure that running weighted polynomial fitting does not modify the original data being fit, and that users can call polyfit with weights without their source xarray object being overwritten or corrupted.

- **Expectation**: Weighted polynomial fitting should behave like a read-only analytical operation. Supplying weights may affect the fit result, but it must not alter the input data, coordinates, or overall source object state.

- **Constraints**: The update should remove the side effect without changing the intended fitting workflow. Users should not need defensive copies just to protect their original data during weighted fitting.


### Task 4 Avoid shutdown-time file manager errors in script-based dataset workflows
Ensure that script-based dataset aggregation and export workflows complete without shutdown-time errors when cached backend files remain managed by xarray at interpreter exit.

- **Expectation**: Users should be able to run dataset loading and export code as a normal script and have the process exit cleanly. Successful reads and writes should not be followed by spurious cleanup errors just because the interpreter is shutting down.

- **Constraints**: The change should only remove false-positive shutdown noise, not weaken normal runtime behavior or change how users call the library. Existing successful workflows should keep working the same way aside from cleaner process termination.


### Task 5 Preserve empty variable-length string dtypes across backend roundtrips
Ensure that empty arrays representing variable-length strings retain their string dtype semantics when encoded, saved, and reopened, so users do not observe dtype changes during dataset roundtrips.

- **Expectation**: When a dataset contains an empty string-like array, saving and reopening it should still behave like a string array rather than changing into a numeric array. Empty and non-empty variable-length string arrays should be treated consistently.

- **Constraints**: The change must be narrowly scoped to genuine string arrays and must not alter unrelated object-array behavior. Systems with limited metadata support should degrade safely without inventing the wrong dtype.


### Task 6 Preserve DataArray dtype when reindexing empty arrays
Ensure that reindexing an empty DataArray preserves the original dtype instead of widening it during alignment and missing-value handling.

- **Expectation**: Reindexing should not unexpectedly change the data type of a DataArray just because the array is empty or because the operation creates missing entries. Users should observe dtype stability before and after reindex.

- **Constraints**: The fix should be limited to preserving observable data types during reindex and must not introduce regressions in normal reindex results or in how missing values are represented for supported dtypes.


### Task 7 Honor explicit empty Zarr chunk_store values
Ensure that writing data with `to_zarr(..., chunk_store=...)` uses an explicitly provided Zarr chunk store even when that store is currently empty, rather than treating the empty store as absent.

- **Expectation**: Providing a chunk store should depend on whether the caller supplied one, not on whether it already contains data. Empty-but-valid chunk stores must behave the same as pre-populated ones: they receive chunk data during write and can be used to read the dataset afterward.

- **Constraints**: The fix must not change behavior for callers who do not provide a chunk store. It should only correct the falsey-empty-store case and preserve normal read/write compatibility for valid chunk-store configurations.


### Task 8 Improve Array API astype compatibility
Ensure that xarray operations continue to work with Python Array API compliant array backends when dtype conversion is required, especially for string accessor operations and padding or missing-value handling paths that previously depended on non-standard array methods.

- **Expectation**: When xarray needs to change an array's dtype internally, that conversion should use a standards-compliant mechanism so the same user-facing operations work across NumPy and other Array API compatible backends. Users should observe successful execution and unchanged high-level results rather than backend-specific casting failures.

- **Constraints**: The fix should expand backend compatibility without changing the meaning of existing features. Results, shapes, and dtype behavior should stay consistent with prior releases except that previously failing standards-compliant backends should now work.


### Task 9 Handle optional import name collisions during duck typing
Ensure that optional duck-typed dependency detection does not fail when an installed package shares the expected import name but does not implement the expected interface. Ensure that environments with such package collisions continue to operate by falling back as if the optional dependency were unavailable.

- **Expectation**: Optional compatibility checks should be resilient to package name collisions. If a similarly named installed package does not provide the expected API and triggers an attribute-based failure during detection, the library should behave as though the optional dependency is not installed and continue running without crashing.

- **Constraints**: The change must reduce false failures from dependency discovery without masking normal successful integrations or changing behavior for correctly installed supported packages. It should only soften clearly dependency-detection-related import and attribute lookup failures.


## Breaking Changes

### Task 10 Deprecate DataArray cdms2 conversion methods
Ensure that xarray users who convert DataArray objects to or from cdms2 are clearly informed that this interoperability path is deprecated and should be treated as legacy behavior while remaining usable during the transition period.

- **Expectation**: The upgrade should preserve existing cdms2 conversion behavior for now, but any user invoking those conversions should receive a clear deprecation signal at call time so they can migrate off the deprecated interoperability path.

- **Constraints**: Users should still be able to use the legacy conversion workflow where their environment supports it, with no regression in returned data or metadata beyond the addition of a deprecation warning. The upgrade does not promise continued compatibility for unsupported modern dependency combinations.


## Performance Improvements

### Task 11 Improve concat scalability for large datasets
Ensure that concatenating or combining large datasets remains responsive and scales to large concat dimensions without changing the user-visible results, validation behavior, or handling of partially present variables.

- **Expectation**: Upgrading should make large concatenation workloads noticeably faster while keeping the same results and failure modes that users already rely on. Combining datasets should still produce the same merged structure, preserve coordinate alignment, and reject invalid inputs in the same user-visible situations.

- **Constraints**: Performance gains must not come at the cost of correctness. Existing successful concatenations should keep producing equivalent outputs, and existing invalid cases should still fail instead of silently changing structure or alignment.


## Additional Changes
- Ensure that development snapshots of the library are published as nightly wheels to the Scientific Python nightly package index so downstream users and integrators can install and test unreleased builds without building from source.
- Ensure that upgrading to 2023.6.0 no longer relies on TestPyPI as a source for development or nightly wheel builds, and that users understand nightly or pre-release distributions are provided through the supported replacement channel instead.
- Ensure that `groupby()` correctly resolves grouping labels when the grouper is provided as an `IndexVariable` or when grouping by a named level of a MultiIndex-backed coordinate.
