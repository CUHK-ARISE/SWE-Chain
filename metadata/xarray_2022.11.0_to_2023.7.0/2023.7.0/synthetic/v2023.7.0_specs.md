# Upgrade Specification from 2023.6.0 to 2023.7.0

## New Features

### Task 1 Broaden flox-backed grouped reductions to supported chunked arrays
Ensure that flox-backed grouped reduction operations accept supported chunked non-dask arrays in addition to NumPy and dask-backed data, without changing the observable behavior of existing supported inputs.

- **Expectation**: Grouped and resampled reductions should work with supported chunked array backends, not just dask, whenever the optimized flox execution path is enabled. Users should be able to use the same public aggregation APIs and get normal reduction behavior for eligible chunked arrays.

- **Constraints**: The change should expand backend compatibility without altering how existing supported arrays behave or bypassing the normal conditions for optimized grouped reductions. Unsupported data types should not silently gain support unless they meet the same chunked-array eligibility rules.


## Bug Fixes

### Task 2 Reject forward slashes in HDF5-backed NetCDF variable and dimension names
Ensure that exporting datasets with HDF5-based NetCDF engines does not crash unexpectedly when variable or dimension names contain '/'. Ensure invalid names are rejected up front with a clear validation error.

- **Expectation**: Writing a dataset to HDF5-backed NetCDF output should fail fast for names that are not representable in that storage model. Names containing '/' should be treated as invalid and reported immediately with a normal validation error.

- **Constraints**: The fix must only block truly unsupported names and must not regress successful exports for otherwise valid datasets. The user-facing behavior should be deterministic and consistent across supported HDF5-backed engines.


## Breaking Changes

### Task 3 Deprecate scatter plot hue_style and rely on hue data type semantics
Ensure that 1D and scatter plots no longer promise `hue_style` as a way to switch between discrete and continuous hue rendering, and ensure that users receive clear deprecation signaling while plots continue to behave consistently based on the hue variable type.

- **Expectation**: When users upgrade, scatter and similar 1D plots should no longer treat `hue_style` as an active control. Passing it should only warn that the option is deprecated. Plot coloring should instead follow the natural kind of data supplied for hue, and users should use legend or colorbar controls, or categorical hue values, to get the presentation they want.

- **Constraints**: The upgrade must preserve plot operability and avoid breaking common scatter workflows, while making it explicit that `hue_style` no longer changes results. Different hue value kinds should continue to render consistently across regular and faceted plots, without introducing crashes for date-like inputs.


## Documentation

### Task 4 Expand xarray Dataset API docstrings with executable examples
Ensure that xarray 2023.7.0 provides clearer, user-facing documentation for common `Dataset` operations by including concrete examples and related references, so users can understand expected inputs, outputs, and edge-case behavior without relying on source inspection.

- **Expectation**: Users upgrading to 2023.7.0 should find that major `Dataset` APIs are better documented with practical examples that show what the operation returns and how option values affect results. The library should be easier to learn and verify through documentation alone, while preserving the same public behavior.

- **Constraints**: The improvement must be non-breaking. It should add clarity and examples without changing how these APIs behave in user code or requiring code changes from existing consumers.


### Task 5 Document alternative chunked array backends
Ensure that users and backend authors can understand and rely on xarray's supported contract for wrapping chunked numpy-like arrays as alternatives to dask arrays, including how such arrays are recognized, chunked, computed, transformed, and written through the chunk manager interface.

- **Expectation**: Users should be able to use xarray with supported chunked array libraries other than dask, and backend authors should have a clear, stable description of the behavior their integration must expose so xarray can detect arrays, preserve chunk information, execute computations, apply array operations, and write results consistently.

- **Constraints**: Existing integrations should continue to behave as before, while the documented contract should define clear boundaries for what every backend must support versus what is optional. Alternative chunked array support should remain compatible with normal xarray computation and I/O expectations without imposing new behavior on users who stay on existing backends.


### Task 6 Clarify chunked duck-array integration contracts
Ensure that upgrading users and chunked duck-array backend authors can rely on clearly documented support expectations for wrapping numpy-like arrays and integrating chunked array frameworks with xarray, including which `ChunkManagerEntrypoint` methods are required, which xarray operations depend on them, and what behavior is expected when optional capabilities are not implemented.

- **Expectation**: Users should have a clear description of how xarray works with chunked duck arrays, what capabilities a backend must provide to participate in core operations, and which advanced behaviors are optional and may be unavailable unless the backend implements them. The upgrade should make support boundaries and expected outcomes understandable without changing existing runtime semantics.

- **Constraints**: The upgrade should improve clarity without introducing new behavioral guarantees beyond what supported backends already provide. Backends that do not implement optional features should continue to fail in a clear, expected way rather than appearing fully supported.


### Task 7 Add usage examples for core Dataset selection and aggregation APIs
Ensure that the upgrade documents how key Dataset selection and aggregation methods are expected to behave in common usage, including positional indexing, reductions across dimensions, and interpreting argmin/argmax results.

- **Expectation**: Users should be able to read the API documentation and immediately understand, from concrete examples, what these Dataset methods return and how to use the results. The docs should make it clear how positional indexing works, how reducing over a dimension changes the shape of the result, and how argmin or argmax outputs can be used to identify where extrema occur.

- **Constraints**: The change is documentation-only. It must improve clarity without altering how the library behaves or introducing contradictions between examples and actual API behavior.
