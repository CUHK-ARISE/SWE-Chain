# Upgrade Specification from 2025.9.1 to 2025.10.1

## Bug Fixes

### Task 1 Order coordinates to match dimension order in repr output
Ensure that when displaying Dataset or DataArray objects (via text repr and HTML repr), coordinates are listed in an order that matches the declared dimension order rather than the arbitrary internal storage order. Dimension coordinates should appear before non-dimension coordinates, and dimension coordinates should follow the same sequence as the dimensions they index.

- **Expectation**: When a user prints or displays any Dataset or DataArray, the Coordinates section should list dimension coordinates first in the same order as the object's dimensions, followed by any non-dimension coordinates. This ordering should be consistent across both plain-text and HTML notebook representations.

- **Constraints**: The change is purely cosmetic and presentation-oriented. No data structures, computation results, or programmatic coordinate access patterns should be affected. Only the visual ordering of coordinates in printed or rendered output changes.


### Task 2 Fix spurious error when writing scalar variables to Zarr with region={}
Ensure that calling Dataset.to_zarr() with region={} does not raise a ValueError for datasets containing scalar variables (variables with zero dimensions). Previously, passing an empty region dict caused a spurious validation error because the region-dimension intersection logic flagged all variables—including legitimate scalars—as non-matching when no region keys existed to intersect against.

- **Expectation**: Writing a dataset to Zarr with an empty region specification should succeed regardless of whether the dataset contains scalar (zero-dimensional) variables. The region-dimension compatibility check should only apply when the region actually specifies dimensional constraints.

- **Constraints**: The fix must not weaken validation for cases where region genuinely specifies dimension constraints. Only the empty-region edge case should be affected. All existing Zarr write workflows with non-empty region dicts must continue to validate dimension compatibility as before.


## Breaking Changes

### Task 3 Revert default netCDF engine preference order to netcdf4-first
Ensure that when no explicit engine is specified for netCDF read/write operations (open_dataset, open_dataarray, open_mfdataset, Dataset.to_netcdf, DataArray.to_netcdf, save_mfdataset), xarray selects the engine using the preference order netcdf4 > h5netcdf > scipy, reverting the v2025.09.1 change that had reordered the default to h5netcdf > scipy > netcdf4. Ensure that the netcdf_engine_order option in xr.set_options() still allows users to customize this preference order to any permutation or subset of the three engines.

- **Expectation**: When users read or write netCDF files without specifying an engine, xarray should prefer the netcdf4 backend over h5netcdf over scipy, matching the historical default prior to v2025.09.1. Users must still be able to override this default preference order globally through xr.set_options().

- **Constraints**: The revert must not remove the ability for users to customize engine preference. Explicit engine selection must always take precedence over the default order. The change must be backward-compatible with code that was written before v2025.09.1.


## Additional Changes
- Ensure that xarray reports the built-in `zarr` backend as supporting hierarchical groups so group-aware APIs and backend capability checks can use it for Zarr stores containing nested groups.
