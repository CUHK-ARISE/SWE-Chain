# Upgrade Specification from 2025.10.1 to 2025.11.0

## New Features

### Task 1 Support DataTree objects in xarray.merge() and xarray.concat()
Ensure that xarray.concat() and xarray.merge() accept DataTree objects as inputs and return a DataTree result, allowing users to concatenate or merge hierarchical tree-structured data along a specified dimension or across variables without resorting to manual per-node iteration via map_over_datasets.

- **Expectation**: When a user passes DataTree objects to xarray.concat(), the function should concatenate corresponding nodes across all trees along the specified dimension and return a new DataTree preserving the hierarchical structure. When a user passes DataTree objects to xarray.merge(), the function should merge variables at corresponding nodes across all trees and return a new DataTree. Both functions should validate that all inputs are of consistent type and that trees have compatible structures, raising clear errors otherwise. The return type should be DataTree when DataTree inputs are provided, and Dataset otherwise.

- **Constraints**: All pre-existing concatenation and merge behavior for non-tree objects must be preserved as a non-regression requirement. Mixing DataTree with non-DataTree objects in a single merge call is not permitted. Custom fill_value is not yet supported for DataTree merge. Trees must have matching hierarchical structure (isomorphism) to be concatenated. Type overloads must correctly distinguish DataTree inputs from Dataset/DataArray inputs for static type checking.


### Task 2 Support NETCDF4_CLASSIC format with h5netcdf engine
Ensure that users can write NETCDF4_CLASSIC-format files using the h5netcdf engine by specifying format='NETCDF4_CLASSIC' in to_netcdf(), so they can avoid using netcdf4-python (and its C dependencies) while still producing files compatible with applications that only support classic NetCDF4 features. Ensure that variables and attributes are automatically cast to NetCDF3-compatible types. Ensure that attempting to create sub-groups under the classic format raises an appropriate error. Ensure that an informative error is raised when the installed h5netcdf version is too old to support this feature.

- **Expectation**: When a user calls to_netcdf with engine='h5netcdf' and format='NETCDF4_CLASSIC', the library should produce a NetCDF4 file whose variables and attributes are restricted to the classic (NetCDF3-compatible) data model. All variable data and attribute values should be automatically cast to types supported by the classic format. Attempting to create hierarchical groups should be rejected with a clear error. If the installed h5netcdf version does not support native classic format writing, a clear error should inform the user of the version requirement.

- **Constraints**: Default writing behavior must not change for users who do not specify the classic format. The feature must not alter the content or structure of files written in the standard NETCDF4 format. Version compatibility must be checked at file-open time, not deferred to write time, so users receive immediate feedback. Attribute and variable encoding for classic mode must reuse the existing NetCDF3 encoding logic rather than introducing a separate implementation.


### Task 3 Support DataTree comparison in assert_allclose
Ensure that testing.assert_allclose() accepts DataTree objects and compares them for approximate equality across their entire tree structure. Previously, passing DataTree instances to assert_allclose() raised a TypeError because the function only handled Variable, DataArray, Dataset, and Coordinates types. Users who work with hierarchical data via DataTree had no built-in assertion utility for approximate comparison in tests.

- **Expectation**: When users call assert_allclose with two DataTree objects, the function should recursively compare all nodes in both trees for approximate numerical equality. If corresponding nodes differ beyond the tolerance, an AssertionError should be raised with a human-readable representation of the differences. The comparison should check both structural equality (matching coordinate names and tree paths) and value-level approximate equality across all variables at every node.

- **Constraints**: The addition of DataTree support must not alter the behavior of assert_allclose for any previously supported types. All existing tests and usage patterns must continue to work identically. The tolerance handling for DataTree comparisons must be consistent with how tolerances are applied for other supported types.


### Task 4 Support chunks='auto' for cftime datasets
Ensure that xr.open_dataset (and open_mfdataset) with chunks='auto' succeeds when the dataset contains cftime datetime variables (use_cftime=True or cftime-decoded coordinates). Previously this combination raised a NotImplementedError because dask cannot auto-chunk object-dtype arrays. The fix should also ensure that rechunking an already-chunked array containing cftime datetimes with chunks='auto' works correctly.

- **Expectation**: When a user opens or rechunks a dataset that contains cftime datetime coordinates using chunks='auto', the operation should succeed and produce reasonable chunk sizes rather than raising an error. The chunking system should internally estimate the byte size of cftime objects, translate that into an equivalent fixed-dtype chunk target, and let the chunk manager's normalization algorithm determine appropriate chunk boundaries. Chunk managers must be able to report their default auto-chunk size target.

- **Constraints**: Auto-chunking of standard (non-cftime) datasets must remain completely unaffected. Variables already loaded into memory should not be re-chunked during dataset opening. The chunk manager abstraction must remain extensible, with a clear contract for third-party implementations to supply their auto-chunk size. The byte-size estimation approach must be conservative and not introduce silent data corruption or incorrect chunk boundaries.


## Bug Fixes

### Task 5 Fix h5netcdf backend format=None handling to match netcdf4 backend
Ensure that the h5netcdf backend resolves format=None to a concrete default format consistent with the netcdf4 backend. Previously, passing format=None (or relying on the default) left the internal format state as None, leading to inconsistent behavior between the two backends. The fix must also ensure that the NETCDF4_CLASSIC format is accepted by the h5netcdf backend and that the resolved format value is properly propagated through store construction.

- **Expectation**: When a user opens a dataset using the h5netcdf backend without specifying a format (or explicitly passing None), the backend should behave identically to the netcdf4 backend by defaulting to the NETCDF4 format. The backend should also support the NETCDF4_CLASSIC format. Invalid format values should be rejected with a clear error message indicating which value was invalid.

- **Constraints**: The h5netcdf backend must never operate with an undefined or null format state. Its format handling rules must be consistent with the netcdf4 backend. Existing workflows that previously relied on the default format=None must continue to work without modification, as the resolved behavior is equivalent.


### Task 6 Stricter backend URL detection to prevent incorrect remote URL claiming
Ensure that xarray's automatic backend selection no longer incorrectly routes remote URLs to the netcdf4 or pydap backends when the URL does not point to a netCDF or DAP resource. Previously, opening a remote Zarr store (or any non-DAP, non-netCDF URL) without an explicit engine= argument could silently select the wrong backend if netcdf4 or pydap was installed, leading to confusing errors or incorrect data reads. Each backend's guess_can_open method must apply protocol-aware and extension-aware heuristics so that only genuinely compatible URLs are claimed.

- **Expectation**: When xarray opens a dataset from a URL without an explicit engine argument, each backend should only volunteer to handle URLs that match its supported protocol and file type. The netcdf4 backend should claim remote URLs only if they have a netCDF file extension. The pydap backend should claim remote URLs only if they carry explicit DAP protocol markers. The h5netcdf and scipy backends should not claim remote URLs at all. URI scheme detection should be case-insensitive. Extension detection for remote URLs should correctly ignore query parameters and URL fragments.

- **Constraints**: All existing local file opening workflows must continue to work unchanged. Backends must not break when the user explicitly specifies the engine argument, even for URLs that the backend would no longer auto-detect. The fix must not prevent any backend from opening resources it is genuinely capable of handling; it only restricts automatic selection heuristics.


### Task 7 Fix ValueError when indexing lazy-loaded data with empty arrays in h5netcdf and scipy backends
Ensure that indexing a lazy-loaded DataArray or Dataset variable with an empty integer array (selecting zero elements) does not raise a ValueError when using the h5netcdf or scipy backends. Previously, performing an empty selection on data that had not yet been loaded into memory (e.g., via `.isel(dim_0=[])`) and then accessing `.values` caused a crash with 'zero-size array to reduction operation maximum which has no identity'. After the fix, this operation should return an empty NumPy array, consistent with the behavior of the netcdf4 engine and of eagerly-loaded data.

- **Expectation**: When a user selects zero elements from a lazy-loaded variable via integer-array indexing, the backend indexer decomposition should gracefully handle the empty selection and produce an empty result. Accessing `.values` on the resulting DataArray must return an empty NumPy array without raising any exception, regardless of the storage backend.

- **Constraints**: The fix must only address the empty-array edge case without regressing any existing indexing behavior. All backends that previously worked with non-empty selections must continue to produce identical results. Backends that already handled empty selections correctly (e.g., netcdf4) must remain unaffected.


### Task 8 Fix error handling in decode_cf_variables to preserve original exception
Ensure that when an exception occurs during CF variable decoding in decode_cf_variables, the original exception is propagated to callers with its original type and traceback intact, annotated with context about which variable triggered the failure. Previously, the function attempted to construct a new exception of the caught type using a single-string-argument constructor call, which caused a TypeError for exception classes with non-standard constructors (e.g., those requiring additional positional arguments), masking the real error and preventing proper upstream error handling.

- **Expectation**: When variable decoding fails inside decode_cf_variables, the original exception must propagate to the caller with its original type and traceback preserved. Additional context about which variable caused the failure should be attached as a note on the exception rather than by constructing a new exception object. Callers must be able to catch the exception by its original type without encountering a secondary TypeError.

- **Constraints**: Error propagation from CF variable decoding must be transparent to upstream exception handlers. The original error identity and type must never be altered. Contextual information about the failing variable should be additive metadata, not a replacement of the original error.


### Task 9 Fix equivalent() for NumPy scalar NaN comparison in attribute merging
Ensure that the equivalent() function correctly identifies two NaN-valued attributes as equivalent regardless of whether they are Python float NaN or NumPy scalar NaN. Previously, after saving a DataArray to NetCDF and reloading it, NaN attributes (e.g., fill_value: np.nan) were silently dropped during concat or merge operations that use combine_attrs='drop_conflicts', because the NaN equivalence check was bypassed for NumPy scalar types.

- **Expectation**: The equivalence check for attribute values must treat NaN as equal to NaN in all common scalar representations. Attribute-merging strategies that rely on equivalence (such as drop_conflicts) must preserve NaN-valued attributes that match across inputs, even after serialization roundtrips that may change the NaN representation from Python float to NumPy scalar.

- **Constraints**: The change must be limited to fixing NaN-vs-NaN equivalence for scalar values. All other equivalence semantics—including array equivalence, list equivalence, and rejection of non-boolean comparison results—must remain unaffected. Non-NaN attribute comparisons must continue to work identically.


### Task 10 Restore Dataset.map() support for non-DataArray outputs and revise keep_attrs default
Ensure that Dataset.map() correctly handles mapping functions that return non-DataArray values (e.g., scalars, numpy arrays, or mixed DataArray/non-DataArray outputs) without raising AttributeError. Ensure that the keep_attrs parameter defaults to True so that variable and coordinate attributes are preserved by default. Ensure that when keep_attrs is explicitly set to False, all attributes on variables and coordinates are explicitly cleared.

- **Expectation**: Dataset.map() should accept any mapping function regardless of whether it returns DataArray objects or plain values. Attributes should be preserved by default, and explicitly stripped when the user opts out of attribute preservation. The method should never raise internal errors due to unexpected return types from the user-supplied function.

- **Constraints**: The fix must not alter behavior for existing usage patterns where the mapping function returns DataArray objects. Attribute handling must be deterministic: either all attributes are preserved or all are cleared, with no partial or inconsistent state. The change must not introduce new coordinate alignment or dimension inference side effects.


### Task 11 Fix drop_sel on MultiIndex with mixed-type levels
Ensure that Dataset.drop_sel and DataArray.drop_sel work correctly on MultiIndex coordinates whose levels have heterogeneous types (e.g., a MultiIndex stacked from a string dimension and an integer dimension). Previously, calling drop_sel with a tuple key on such a MultiIndex raised a KeyError because label types were silently coerced, while the equivalent sel call succeeded.

- **Expectation**: drop_sel should behave consistently with sel when operating on MultiIndex coordinates. Selecting and dropping by the same key on the same MultiIndex should both succeed without type-related errors. Label types should be preserved through the drop_sel pipeline so that mixed-type MultiIndex lookups resolve correctly.

- **Constraints**: The fix must not break any existing drop_sel usage on regular indexes or uniform-type MultiIndexes. The special handling for DataArray inputs must be preserved. Error handling semantics for missing labels must remain unchanged.


## Breaking Changes

### Task 12 Preserve attributes by default across all xarray operations
Ensure that all xarray operations (reductions, binary arithmetic, comparisons, groupby, rolling, resampling, weighted, apply_ufunc, where, isnull, notnull, map, and data-manipulation methods) preserve attributes by default when keep_attrs is not explicitly specified. Ensure that binary operations between two xarray objects combine attributes from both operands using a drop_conflicts strategy, keeping matching attribute key-value pairs and discarding conflicting ones. Ensure that users can restore the previous attribute-dropping behavior globally via xr.set_options(keep_attrs=False), per-operation via keep_attrs=False, or via context manager.

- **Expectation**: All xarray operations should preserve attributes by default. Users who do not pass an explicit keep_attrs argument should see attributes carried through reductions, transformations, binary operations, missing-data methods, and ufunc applications. Binary operations between two attributed objects should merge their attributes, keeping entries that agree and dropping entries that conflict. The previous default of discarding attributes should remain accessible via an explicit opt-out.

- **Constraints**: The opt-out mechanism for dropping attributes must remain fully functional. Global and per-call overrides must behave identically to how they worked before, only the default changes. Attribute merging in binary operations must be symmetric and must not silently discard non-conflicting metadata. No existing public API signatures should be removed or renamed.


## Performance Improvements

### Task 13 Optimize xarray.concat() memory usage and speed
Ensure that xarray.concat() does not allocate large intermediate index arrays proportional to the total concatenation size. Previously, concatenating DataArrays or Datasets along a dimension caused peak memory usage far exceeding the combined size of inputs and output (reported as 6x input size), and wall-clock time several times slower than np.concatenate, even with large chunk sizes and no coordinates or indexes requiring special treatment. The overhead should be minimized so that memory and time costs scale proportionally to the actual data size, not to redundant internal bookkeeping.

- **Expectation**: xarray.concat() should exhibit peak memory usage and execution time that scale proportionally to the combined size of the input data and output result, without large intermediate allocations. When some variables are absent from certain input datasets and reindexing is required, the internal reindexing mechanism should use a single reusable buffer with an efficient computation strategy rather than repeatedly constructing and querying index objects.

- **Constraints**: The optimization must not change the observable output of xarray.concat() for any valid input. All existing fill-value and reindexing semantics must be preserved. Memory and performance improvements must not introduce correctness regressions for any combination of input datasets, dimensions, coordinates, or fill values.


### Task 14 Optimize multi-dimension coarsening padding to a single pad operation
Ensure that coarsening a DataArray or Dataset along multiple dimensions with boundary='pad' performs padding efficiently in a single operation rather than serially per dimension. The optimization must reduce peak memory usage and execution time without altering the numerical result of the coarsen operation.

- **Expectation**: Multi-dimension coarsening with pad boundary should consolidate all padding into one operation instead of applying padding separately for each dimension. Dimensions that need no padding should be skipped. The coarsened result must remain numerically identical to the prior behavior.

- **Constraints**: All existing boundary modes and side configurations must continue to produce identical results. Single-dimension coarsening must not regress. No change in the public API or observable output beyond improved performance.


## Additional Changes
- Ensure that Dataset.unstack() works when fill_value is provided as a mapping that only covers a subset of variables. Previously, users had to supply fill values for every unstacked variable or risk a KeyError when an omitted variable was encountered.
- Ensure that xarray's discrete plotting helpers preserve explicitly customized bad, under, and over colors from a Matplotlib colormap. Previously, these colors could be lost or copied inconsistently when xarray rebuilt a discrete colormap for contour-style plots.
