# Upgrade Specification from 2025.11.0 to 2025.12.0

## New Features

### Task 1 Batch DAP4 dimension downloads and add checksums option in pydap backend
Ensure that the pydap backend batches dimension variable data downloads into a single HTTP request per file when using the DAP4 protocol, rather than issuing separate HTTP requests for each dimension variable. Ensure that a checksums option is available to control DAP4 checksum behavior. Ensure that open_datatree correctly forwards all user-supplied connection parameters (application, session, timeout, verify, user_charset) to the underlying store instead of ignoring them. Ensure that OpenDAP-internal metadata attributes such as 'path' and 'Maps' are excluded from user-facing dataset attributes.

- **Expectation**: When a user opens a remote DAP4 dataset, dimension data should be downloaded efficiently in bulk rather than one variable at a time, reducing total HTTP requests to roughly one metadata request plus one data request per file for dimensions. A checksums option should allow users to enable or disable DAP4 checksum verification. When opening a DataTree from a remote source, all connection parameters the user specifies should take effect. Internal OpenDAP metadata attributes should not leak into the user-visible dataset attributes.

- **Constraints**: The change must not alter existing behavior for DAP2 datasets or for non-dimension variables. Default settings must preserve prior behavior so that existing code continues to work without modification. The optimization must be transparent to users who do not opt into the checksums parameter. Lazy loading of non-dimension data variables must be preserved.


### Task 2 Support DataTree objects in combine_nested()
Ensure that xarray.combine_nested() accepts DataTree objects as input and produces a combined DataTree as output. Users working with hierarchical tree-structured data should be able to combine multiple DataTree instances along one or more dimensions using the same nested list-of-lists pattern already supported for Dataset objects. Ensure that passing a mix of DataTree and non-DataTree objects raises a clear error. Ensure that combine_by_coords() explicitly reports that DataTree support is not yet implemented.

- **Expectation**: combine_nested() is extended to support DataTree objects as first-class inputs. When given a grid of DataTree objects, it concatenates and merges them along the specified dimensions and returns a single combined DataTree. The return type matches the input type: Dataset inputs produce a Dataset, DataTree inputs produce a DataTree. combine_by_coords() explicitly communicates that DataTree support is not yet available.

- **Constraints**: DataTree and non-DataTree objects cannot be mixed in a single combine_nested() call. All existing Dataset and DataArray combining workflows must continue to work identically. Functions that do not yet support DataTree must fail explicitly with an informative error rather than producing undefined behavior.


### Task 3 Support decoding unsigned integers to np.timedelta64
Ensure that unsigned integer arrays (numpy dtype kind 'u') can be decoded into np.timedelta64 values via xarray's time decoding machinery. Previously, only float and signed integer arrays were supported in the numbers-to-timedelta conversion, causing unsigned integer inputs to raise an error or produce incorrect results.

- **Expectation**: Unsigned integer numeric data should be decodable to timedelta64 values just like signed integers and floats. Since unsigned integers cannot represent NaN or a negative sentinel, the decoder should assume no missing values are present and proceed with the conversion.

- **Constraints**: The change must not alter how existing float or signed integer timedelta decoding works. The missing-value detection strategy for unsigned integers must correctly reflect that unsigned types have no NaN representation.


## Bug Fixes

### Task 4 Coerce IndexVariable to Variable when assigning to data variables or non-index coordinates
Ensure that when an indexed coordinate is assigned as a data variable or as a non-index coordinate in a Dataset or DataArray, the resulting variable is coerced from IndexVariable to the base Variable type so that its data is mutable. Ensure that concat with coords='different' no longer raises a ValueError when a non-index coordinate happens to be an IndexVariable.

- **Expectation**: Assigning a coordinate-backed variable into a Dataset as a data variable or non-index coordinate should yield a standard mutable Variable, not an immutable IndexVariable. The IndexVariable type should only be used for variables that actually serve as dimension indexes. Concatenation operations that encounter non-index coordinates should complete successfully regardless of the underlying variable subtype.

- **Constraints**: The fix must not alter the behavior of actual index-backed dimension coordinates. Only variables that are not serving as indexes should be affected. Data integrity (values, dimensions, attributes) must be preserved through the coercion. Internal consistency invariants must be strengthened, not relaxed, to prevent IndexVariable from appearing where it should not.


### Task 5 Restore NetCDF4 backend URL guessing with zarr exclusion and shared DAP detection
Ensure that calling xr.open_dataset with a remote HTTP URL (without specifying an engine) continues to default to the netcdf4 backend, restoring the pre-2025.11.0 behavior that was broken by overly strict URL filtering. Ensure that remote URLs containing 'zarr' are excluded from NetCDF4 backend claiming so the zarr backend is correctly selected instead. Ensure that DAP URL detection is unified across the netcdf4 and pydap backends with expanded coverage of known DAP server path patterns.

- **Expectation**: When a user opens a remote dataset via URL without specifying an engine, the netcdf4 backend should be selected by default for nearly all remote URLs, preserving existing workflows. The exception is URLs that indicate zarr stores, which should be left for the zarr backend. The pydap backend should recognize a broader set of DAP endpoint URL patterns drawn from common OPeNDAP server conventions, and this detection logic should be shared rather than duplicated.

- **Constraints**: Backward compatibility for users who relied on the netcdf4 engine being auto-selected for remote URLs must be preserved. The zarr backend must not be blocked by netcdf4 claiming zarr-related URLs. DAP detection must be consistent between the netcdf4 and pydap backends and must not introduce false positives for non-DAP remote resources. Local file handling behavior must not regress.


### Task 6 Normalize indexers in LazilyIndexedArray to fix diff() on lazy-loaded data
Ensure that operations such as diff() work correctly on lazy-loaded datasets without requiring an explicit load() call. Previously, applying diff() or similar indexing-dependent operations on lazily-loaded data (e.g., GRIB2 backend arrays) raised alignment errors, while the same operation succeeded after calling load(). This regression was caused by a shortcut in LazilyIndexedArray indexing that bypassed slice normalization.

- **Expectation**: When indexing operations are applied to lazily-loaded array data, all resulting indexers must be properly normalized regardless of the prior indexing state. Users should be able to call diff() and other dimension-reducing or reindexing operations directly on lazy-loaded datasets and get the same results as when the data is eagerly loaded.

- **Constraints**: The fix must not break any existing indexing behavior or introduce performance regressions for eager-loaded data. All backend array types that rely on normalized slices must continue to work correctly. The lazy-vs-eager behavioral equivalence must be preserved for all indexing-dependent operations.


### Task 7 Fix Dataset.drop_attrs raising on custom indexes
Ensure that calling Dataset.drop_attrs on a Dataset with custom indexes that do not support casting does not raise an error. Previously, the method internally accessed the indexes property, which triggers index casting and fails for custom index implementations that cannot be converted to pandas Index objects.

- **Expectation**: When drop_attrs is called on a Dataset, the method should identify index variables without triggering any index casting or conversion. All variable attributes should be cleared regardless of the index type backing the dataset. The method should complete without raising for any conforming custom index implementation.

- **Constraints**: Existing behavior for datasets with default pandas-backed indexes must not regress. The fix must be limited to how index variables are identified internally and must not alter the attribute-clearing semantics for any variable type.


### Task 8 Properly handle type promotion and NA for extension arrays
Ensure that pandas extension arrays (Categorical, nullable integer, pyarrow-backed, etc.) are correctly handled during xarray's internal type promotion and NA-value operations. Previously, operations that mixed extension arrays with scalars or NA values could produce incorrect results, raise unexpected errors, or silently promote Categorical dtypes to object. Specifically:
- Ensure that result_type correctly computes a common dtype when extension arrays, scalars, and NA values are mixed.
- Ensure that NA / missing values for extension array dtypes are properly resolved via maybe_promote.
- Ensure that np.where with extension arrays handles scalar and 0-dimensional array broadcasting correctly.
- Ensure that as_shared_dtype correctly casts mixed extension arrays and scalars to a shared type without special-case branching.
- Ensure that unordered Categorical dtypes are preserved (categories merged) rather than being promoted to object.

- **Expectation**: When xarray performs type promotion across a mix of extension arrays, numpy arrays, scalars, and NA sentinels, the resulting dtype should correctly reflect the extension array dtype rather than falling back to object or raising an error. NA values for extension array dtypes should be resolved to the dtype's native missing sentinel. Unordered Categorical arrays with different category sets should be merged into a unified Categorical rather than promoting to object. Conditional selection (where) should work correctly when one branch is a scalar or 0-dimensional array paired with an extension array. Converting data to extension array dtypes via asarray should work even when the input is not already an extension array.

- **Constraints**: All existing non-extension-array code paths and behaviors must be preserved. Extension array support must integrate into the existing duck-array dispatch mechanism without requiring callers to special-case extension arrays. Functions that cannot handle extension arrays must fall back gracefully via NotImplemented rather than raising. The fix must not introduce new public API surface beyond what was already exposed.


## Refactors

### Task 9 Migrate development workflow from conda to pixi
Ensure that the development workflow uses pixi instead of conda for environment management. The documentation build configuration should no longer contain conda-specific environment detection or package listing logic. Development environments should be defined via a pixi manifest with composable dependency groups, task running, and lock file support.

- **Expectation**: The project's development tooling should use pixi as the sole environment manager. The documentation build process should not attempt to detect or list conda or pip environments. Contributors should be able to create environments, run tests, build documentation, and execute type checks through pixi commands. CI should resolve environments from the pixi manifest rather than conda environment files.

- **Constraints**: The migration must not affect the library's runtime behavior or public API. Documentation builds must continue to succeed without conda-specific checks. The development workflow transition should be transparent to end users of the library and only affect contributors and CI infrastructure.


## Additional Changes
- Users working with non-standard calendar types (e.g., 360-day, all-leap, no-leap) in xarray lacked clear documentation on the limitations of arithmetic operations involving cftime objects. This could lead to unexpected results or confusion when performing date arithmetic, time differencing, or resampling on datasets that use these calendars. Ensure that the user guide explicitly documents the known limitations and expected behavior boundaries of cftime arithmetic for non-standard calendars.
- Ensure that when xarray parses CF-compliant time-unit strings with textual reference dates, the resulting pandas `Timestamp` reference date uses the coarsest resolution that preserves the original value. Without this normalization, changes in pandas timestamp construction can leave parsed reference dates at unnecessarily fine resolution, which can alter inferred datetime precision during encoding and decoding.
- Ensure that xarray operations which only need array metadata or a shallow data reference do not access `Variable.data`, because doing so can materialize lazy or explicitly indexed arrays and strip their specialized wrapper types. Users working with lazy backend arrays should be able to perform metadata-preserving operations such as dropping encoding, padding, broadcasting, and CF datetime/timedelta encoding without forcing eager data conversion.
