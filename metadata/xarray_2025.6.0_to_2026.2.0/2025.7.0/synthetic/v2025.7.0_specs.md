# Upgrade Specification from 2025.6.1 to 2025.7.0

## New Features

### Task 1 Expose xarray.indexes as a public index API namespace
Ensure that xarray provides a stable public indexes namespace so users can access documented index classes through xarray.indexes, including RangeIndex and CoordinateTransformIndex, without relying on private or indirect imports.

- **Expectation**: Users should be able to discover and import the supported index-related classes from a single public `xarray.indexes` namespace, including through `xarray.indexes` after importing xarray.

- **Constraints**: The upgrade should broaden access to index APIs without breaking existing imports or changing the behavior of already supported index classes.


## Bug Fixes

### Task 2 Improve context on write-time encoding failures
Ensure that write operations clearly identify the variable or attribute responsible when encoding data for disk fails, so users can diagnose invalid values or metadata during serialization.

- **Expectation**: If saving a dataset fails during encoding, the error should make clear which variable or attribute triggered the failure while preserving the underlying error type and reason.

- **Constraints**: Do not alter normal serialization behavior or hide the original error. Only improve failure diagnostics, and do so consistently across write-time encoding paths.


### Task 3 Fix SciPy netCDF3 subset writes after lazy decoding
Ensure that datasets opened from netCDF3 files through the SciPy backend can be subsetted and written back to NetCDF without failing, including cases where variables undergo CF decoding such as stacked byte strings, booleans, native-endian conversion, or other elementwise decoding.

- **Expectation**: Opening a netCDF3 dataset with the SciPy engine, selecting a subset, and saving that subset back to NetCDF should succeed. Decoded values should stay lazily subsettable through common indexing and transpose operations instead of breaking when the data is later materialized or serialized.

- **Constraints**: Keep the decoded results the same while making chained read-select-write workflows safe. The fix should improve lazy behavior without changing the user-visible meaning of decoded data or requiring callers to eagerly load arrays first.


### Task 4 Auto-correct stale character dimension names for netCDF string writes
Ensure that writing datasets with fixed-width string variables back to netCDF still succeeds after subsetting or other shape changes, even when saved character-dimension metadata is stale. Ensure that inconsistent string-dimension metadata is corrected automatically and surfaced to users with a warning instead of causing serialization failures.

- **Expectation**: Saving a dataset containing string data back to netCDF should automatically reconcile outdated character-dimension metadata with the string width that is actually being written. If the library has to correct an inconsistent string-dimension name, it should warn the user and still produce a valid netCDF result instead of failing with a shape or broadcasting error.

- **Constraints**: Only intervene when stored string-dimension metadata is inconsistent with the data being written. Already-correct string encodings should behave as before, and ordinary netCDF writes without custom string-dimension metadata should remain unaffected.


### Task 5 Fix DataTree assert_equal mismatch reporting
Ensure that comparing two different DataTree objects with xarray.testing.assert_equal reports a normal DataTree equality failure with useful mismatch details instead of crashing with an internal ValueError.

- **Expectation**: DataTree equality assertions should fail cleanly and informatively. If two DataTree objects differ, users should get a readable explanation of where the difference is and what differs, not an unrelated internal exception.

- **Constraints**: Keep existing equality behavior intact for matching objects and for normal comparison semantics. The change should only make unequal DataTree comparisons fail in the expected, user-readable way.


### Task 6 Honor check_dim_order=False for DataTree equality assertions
Ensure that xarray.testing.assert_equal treats DataTree inputs consistently with other xarray objects when check_dim_order is disabled, so DataTree comparisons do not fail solely because corresponding datasets use a different dimension order.

- **Expectation**: Ignoring dimension order should also work for DataTree equality checks. If two DataTree objects are otherwise equivalent and differ only in axis ordering within matching nodes, equality comparison should succeed when dimension-order checking is turned off, but genuine content or structure differences should still be reported.

- **Constraints**: The fix should be narrowly scoped: opting out of dimension-order checking may relax order-only differences, but it must not hide real incompatibilities or alter normal strict comparisons unless the caller explicitly requests it.


### Task 7 Restore reliable timedelta64 disk decoding
Ensure that datasets and variables containing encoded numpy.timedelta64 values can be reopened and decoded without manual removal of a serialized dtype attribute, and ensure that decoded timedelta resolution follows the stored dtype by default unless the caller explicitly requests a different time unit.

- **Expectation**: Opening data files that contain encoded timedeltas should succeed without manual metadata cleanup. By default, decoded timedeltas should use the resolution described by the stored data, while an explicitly requested decode resolution should override that default. If stored timedelta precision is outside the supported range, decoding should still proceed with a warning and a compatible fallback resolution.

- **Constraints**: The fix must remove the regression without introducing new metadata conflicts or unpredictable dtype changes. Existing timedelta decoding modes should continue to work, explicit caller overrides must remain authoritative, and unsupported stored resolutions should degrade predictably instead of causing hard failures.


### Task 8 Fix timedelta64 CF encoding for 32-bit backends
Ensure that `numpy.timedelta64` data can be written and read through CF/netCDF encoding without spurious cast failures on formats limited to 32-bit integers, while preserving the original timedelta resolution in encoded metadata and decoding to that stored resolution by default.

- **Expectation**: Timedelta values should round-trip through file storage predictably. Writing them to older or more limited formats should succeed whenever the serialized values fit the target storage type, stored metadata should preserve the original timedelta precision, and decoding should either respect that stored precision or use an explicitly requested output precision.

- **Constraints**: The fix should not take away existing ways to control serialized units, storage type, packing, or decode resolution. It must avoid introducing metadata or defaults that turn a successful write/read cycle into a failure or a silent change in meaning.


### Task 9 Propagate variable names through backend string encoding
Ensure that writable backends preserve per-variable context while encoding variables for output, especially for string and char-array serialization, so backend warnings or failures identify the affected variable and char-array dimension-name handling remains associated with the correct variable.

- **Expectation**: When xarray encodes variables for storage, string-related encoding should keep track of which variable is being processed so any char-array or string warnings and errors point to the right variable. Serialization failures should also report which variable or attribute caused the problem without changing the underlying failure type.

- **Constraints**: Normal serialization behavior should stay the same for unaffected data. The change should add context and robustness without requiring callers to change ordinary save workflows or altering unrelated encoding results.


## Dependency Updates

### Task 10 Honor Zarr store consolidated metadata support
Ensure that Zarr v3 stores which explicitly do not support consolidated metadata can still be opened and used without attempting unsupported consolidated-metadata behavior.

- **Expectation**: If a Zarr store advertises that consolidated metadata is unsupported, the library should automatically use normal non-consolidated metadata behavior instead of attempting a consolidated path. Existing behavior should stay the same for stores that support consolidated metadata or do not declare otherwise.

- **Constraints**: Only stores that explicitly opt out of consolidated metadata should see changed behavior. Older or fully supported stores must remain backward compatible.


## Breaking Changes

### Task 11 Require Python 3.11+ and newer dependency floors
Ensure that upgrading to 2025.7.0 is treated as an environment compatibility change: the library should only be expected to run on Python 3.11 or newer and with the newer minimum supported dependency versions, while preserving normal behavior for users on supported environments.

- **Expectation**: Users upgrading to 2025.7.0 must move to a newer baseline environment. The release should behave as a support-matrix update rather than a feature redesign: existing workflows continue on supported setups, but the runtime and dependency stack must satisfy the new minimums and contextual errors should use normal Python 3.11 exception notes.

- **Constraints**: The change should only narrow which environments are supported. It should not otherwise alter successful user workflows on supported installations, and it should not require legacy compatibility layers that were only needed for older Python versions.


## Additional Changes
- Ensure that upgrading from 2025.6.1 to 2025.7.0 does not require application changes for this release-note item, because the provided evidence indicates compatibility validation around NumPy 2.3.0 without a corresponding production behavior change.
- Ensure that upgrading from 2025.6.1 to 2025.7.0 does not require user code changes for Pydap-backed string data handling, and that the release is treated as compatibility maintenance rather than a new runtime feature or breaking change.
- Ensure that reindexing with a coordinate created from a MultiIndex level works correctly. Previously, xarray's index normalization and PandasIndex reconstruction paths could mishandle or mutate the underlying pandas index metadata, causing incorrect behavior when a target coordinate originated from a MultiIndex level rather than a plain standalone index.
- Ensure that `Dataset.plot.streamplot(..., hue=...)` uses hue/color data in the axis order expected by Matplotlib. Previously, xarray passed `ds[hue].values` directly, which could leave the color grid transposed relative to the `x` and `y` dimensions and produce incorrect coloring or shape mismatches.
- Ensure that formatting logic only applies scalar float formatting to actual scalar/0-D values. Previously, any object with a floating dtype could be routed through `.item()`-based formatting, which was incorrect for non-scalar arrays and produced misleading or invalid string output in reprs and plot annotations.
