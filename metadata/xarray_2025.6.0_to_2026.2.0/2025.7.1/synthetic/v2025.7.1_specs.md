# Upgrade Specification from 2025.7.0 to 2025.7.1

## New Features

### Task 1 Add NDPointIndex for nearest-neighbor selection on irregular n-dimensional data
Ensure that xarray provides a built-in index for performing nearest-neighbor label-based selection on irregular, n-dimensional data (e.g., unstructured grids with multi-dimensional coordinates). Previously, users had to rely on external packages like xoak for this capability. The new index should integrate with xarray's existing .sel() API and support common label types including scalars, Variables, DataArrays, and plain array-likes with broadcasting semantics.

- **Expectation**: A new index type should be available that enables nearest-neighbor point-wise selection on datasets with irregular multi-dimensional coordinates. Users create the index via set_xindex by specifying the coordinate variables that define the spatial location of data points. Selection is performed through the standard .sel() API with method='nearest', supporting scalar values, Variable and DataArray objects, and plain array-like objects as labels, with automatic broadcasting across label inputs. The index should support equality comparison for alignment and renaming of coordinates and dimensions. The spatial tree backend should be pluggable to allow alternative implementations beyond the default KDTree.

- **Constraints**: The index only supports nearest-neighbor selection, not exact matching or range queries. All associated coordinates must be uniformly shaped and dimensioned. Every coordinate must receive a label during selection. Plain array labels must match the dimensionality of the indexed coordinates. The default tree adapter requires scipy as a dependency. The index does not support chunked or lazily-evaluated coordinates.


### Task 2 Add create_default_indexes parameter to skip index creation when opening datasets
When opening large datasets, xarray eagerly creates pandas indexes for all dimension coordinates, which forces the coordinate data to be loaded into memory even when the user does not need indexed access. Ensure that users can opt out of automatic default index creation when opening datasets via `open_dataset`, `open_dataarray`, `open_datatree`, `open_groups`, and `open_zarr` by passing `create_default_indexes=False`, thereby avoiding unnecessary memory consumption.

- **Expectation**: Users can pass `create_default_indexes=False` to any of the dataset-opening functions to prevent automatic creation of pandas indexes for dimension coordinates. By default (True), behavior is unchanged from prior versions. When disabled, coordinate variables remain present in the dataset but are not indexed, and their underlying data is not eagerly loaded into memory. This applies uniformly to single datasets, data arrays, data trees, and grouped opens.

- **Constraints**: Default behavior must remain backward-compatible: existing code that does not pass the new parameter must produce identical results with indexes created as before. Skipping default indexes must not break chunked (lazy) loading. Backends retain the ability to create their own custom indexes independent of this parameter. The parameter must be consistently available across all top-level dataset-opening functions.


## Bug Fixes

### Task 3 Raise error when custom index creates extra variables in set_xindex
Ensure that Dataset.set_xindex() no longer silently ignores extra variables returned by a custom index's create_variables() method. When a custom index creates variables whose names are not in the list of coordinate names passed to set_xindex(), a clear error must be raised instead of discarding those variables without warning. The error message must guide users toward the recommended factory method pattern using Coordinates.from_xindex() and Dataset.assign_coords().

- **Expectation**: When a custom index produces additional variables beyond those corresponding to the requested coordinates, set_xindex() must reject the operation with an informative error rather than silently dropping the extra variables. The error must clearly identify which variables are unexpected and suggest the recommended alternative approach for advanced use cases.

- **Constraints**: Backward compatibility must be preserved for all custom indexes that do not produce extra variables. The change must only affect the case where extraneous variables are returned. The error must be actionable, providing enough context for the user to understand what went wrong and how to achieve their goal through an alternative API path.


## Performance Improvements

### Task 4 Lazy repr for RangeIndex, MultiIndex, and CoordinateTransform coordinate variables
Ensure that displaying the repr of an Xarray Dataset or DataArray whose coordinates wrap a large pandas.RangeIndex, pandas.MultiIndex, or CoordinateTransform does not trigger full materialization of the index into a numpy array. Previously, calling repr() or _repr_html_() on such objects could allocate memory proportional to the full index size (e.g., 16 GB for a 2-billion-element RangeIndex), causing out-of-memory conditions or severe performance degradation.

- **Expectation**: Coordinate variables that wrap memory-efficient index structures (range-based indexes, multi-indexes, and coordinate transforms) must be recognized as lazy by the Variable layer. When their textual or HTML representation is requested, only the elements needed for display should be computed or retrieved, not the entire index. The repr output should still show representative values (head and tail elements) but must not allocate memory proportional to the full index size.

- **Constraints**: The refactoring must not alter the observable indexing semantics or the values produced by coordinate variable access. Non-lazy coordinate variables (e.g., those backed by standard pandas indexes or numpy arrays) must continue to behave as in-memory. The repr content should still display meaningful sample values for lazy coordinates, just without the cost of full materialization.
