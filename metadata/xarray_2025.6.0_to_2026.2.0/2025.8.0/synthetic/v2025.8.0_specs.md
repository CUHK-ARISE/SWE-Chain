# Upgrade Specification from 2025.7.1 to 2025.8.0

## New Features

### Task 1 Add DataTree.prune() method to remove empty nodes from tree
Ensure that DataTree provides a prune() method that removes empty nodes from the tree after filtering or selection operations. When a DataTree undergoes operations like sel() or isel(), nodes whose coordinate ranges fall outside the selection criteria end up empty (no data variables, or all data variables with zero-sized dimensions). These empty nodes should be removable via a dedicated prune() call, returning a clean tree containing only nodes with actual data while keeping intermediate ancestor nodes necessary to maintain the path to non-empty descendants.

- **Expectation**: Calling prune() on a DataTree returns a new tree with empty nodes removed. By default, nodes that have no data variables are pruned. An optional flag allows also pruning nodes where all data variables have zero-sized dimensions. Ancestor nodes that are empty themselves but required to reach non-empty descendants are retained. The operation is non-mutating.

- **Constraints**: The pruning operation must be non-destructive to the source tree. The default mode must only remove nodes with no data variables at all, while the stricter mode additionally removes nodes whose variables are all zero-sized. Tree structural integrity must be maintained: ancestor nodes needed to connect the root to non-empty descendants must be kept. Coordinate metadata on retained nodes must not be altered.


### Task 2 Add asynchronous load_async() methods to Dataset, DataArray, and Variable
Ensure that Dataset, DataArray, and Variable each expose a load_async() coroutine method that asynchronously loads lazily-opened data into memory from IO backends that support async access. The method must behave like the existing load() (modifying and returning the original object) but operate as an awaitable coroutine, enabling users to concurrently load multiple xarray objects without requiring dask. Backends that do not support asynchronous loading must raise NotImplementedError when load_async is invoked.

- **Expectation**: Dataset, DataArray, and Variable each gain a load_async() coroutine that asynchronously loads lazily-referenced data into memory and returns the modified object. When awaited, the method resolves all lazy backend-sourced data without blocking the event loop, enabling concurrent loading of multiple objects via standard asyncio patterns like asyncio.gather(). Chunked (dask-backed) data within a Dataset is still computed synchronously; only non-chunked lazy variables are loaded asynchronously. If the underlying storage backend does not support async loading, a NotImplementedError is raised. IndexVariable.load_async() is a no-op since its data is always in memory. Xarray does not impose any concurrency limits; users must manage concurrency themselves.

- **Constraints**: All existing synchronous loading and computation workflows must remain unaffected. The async loading feature must only activate when explicitly called by the user via load_async(); it must not change default loading behavior. Backend implementations that lack async support must fail clearly with NotImplementedError rather than silently degrading. The in-memory caching behavior of intermediate indexing wrappers must be preserved in the async path. The async API must not introduce any internal concurrency limiting or throttling.


### Task 3 Support DataTree.to_netcdf() writing to file-like objects or returning in-memory bytes
Ensure that DataTree.to_netcdf() can write to a file-like object (e.g. io.BytesIO) or return in-memory data as a memoryview when called without a filepath argument. Ensure that Dataset.to_netcdf() and DataArray.to_netcdf() support the h5netcdf engine when writing to file-like objects or returning in-memory data, and that their return type reflects either bytes or memoryview depending on engine. Ensure that open_dataset, open_dataarray, open_datatree, and open_groups accept bytes and memoryview objects as input.

- **Expectation**: DataTree.to_netcdf() should support the same in-memory and file-like output patterns as Dataset.to_netcdf(). Calling it without a filepath should return the serialized netCDF content in memory. Calling it with a seekable file-like object should write directly to that object. All netCDF open functions should accept raw bytes or memoryview objects representing file contents in addition to paths and file-like objects. The h5netcdf engine should be usable for in-memory writes across Dataset, DataArray, and DataTree. The scipy engine should warn about an upcoming change in its in-memory return type.

- **Constraints**: Existing write-to-path behavior for Dataset, DataArray, and DataTree must not regress. File-like objects that do not support seek may not work due to underlying HDF5 library limitations. The in-memory write feature for DataTree must use an engine that supports groups (not scipy). The deprecation path for the scipy engine's bytes return type must be communicated via a warning before any breaking change.


### Task 4 Add errors parameter to open_mfdataset for handling invalid files
Ensure that open_mfdataset provides a mechanism to gracefully handle invalid files among a batch of inputs. When one or more files in a multi-file open operation are invalid (corrupt, zero-byte, or unreadable), the user should be able to choose whether to raise an exception, receive a warning identifying each problematic file, or silently skip invalid files. The default behavior must remain raising an exception to preserve backward compatibility.

- **Expectation**: open_mfdataset gains an errors parameter that controls behavior when individual files fail to open. In raise mode, the original exception propagates. In warn mode, a warning is emitted for each invalid file identifying the file path and the cause, and processing continues with the remaining valid files. In ignore mode, invalid files are silently skipped. The returned dataset is produced only from successfully opened files, with correct combine ordering maintained regardless of how many files were skipped.

- **Constraints**: Backward compatibility must be preserved: callers that do not pass the new parameter must see identical behavior to previous versions. Invalid parameter values must be rejected with a clear error. When files are skipped, the dataset combination logic must correctly account for the reduced set of inputs regardless of the combine strategy used.


## Bug Fixes

### Task 5 Avoid redefining inherited dimensions in NetCDF group writes
Ensure that when a DataTree is written to NetCDF, dimensions already defined in a parent group with the same size are not redundantly redefined in child groups. Previously, every subgroup would declare its own copy of dimensions like 'x' and 'y' even though they were already present (with matching sizes) in the root or an ancestor group. The resulting files violated CF Conventions for group scope, which specify that dimensions are inherited from parent groups.

- **Expectation**: When writing hierarchical datasets to NetCDF, child groups must not redefine dimensions that already exist with the same size in any ancestor group. Dimensions should only be explicitly created in a child group when the child requires a different size than what would be inherited. This applies to all NetCDF-backed storage engines that support grouped writes.

- **Constraints**: Dimension inheritance must only suppress creation when sizes match; mismatched sizes must still produce a local dimension. Non-hierarchical write paths must not change behavior. The fix must not alter how unlimited dimensions are declared or ordered. Error handling for conflicting dimension sizes within the same group must be preserved.


### Task 6 Fix KeyError in convert_calendar when using a non-default dim argument
Ensure that convert_calendar does not raise a KeyError when the user supplies a dim argument that differs from the default value 'time'. The function must correctly use the caller-specified dimension name throughout its entire execution path, including the step that removes NaN entries corresponding to invalid dates in the target calendar.

- **Expectation**: convert_calendar should work correctly regardless of which dimension name the user specifies for the time coordinate. Users who name their time dimension something other than 'time' should experience the same correct calendar-conversion behavior as those using the default dimension name.

- **Constraints**: Fixing the non-default dim path must not regress the default dim='time' path. Calendar conversion correctness—including proper removal of invalid dates—must be preserved for all dimension names.


### Task 7 Fix transpose of boolean and native-endianness arrays read from disk
Ensure that calling .transpose() on a Dataset or DataArray containing boolean data loaded lazily from a NetCDF (or other backend) file no longer raises an AttributeError on the BoolTypeArray wrapper. The same must hold for arrays wrapped by NativeEndiannessArray. This was a regression from v2025.7.0 where transpose worked on lazily-loaded boolean data in prior versions.

- **Expectation**: Boolean and native-endianness coding wrappers must support the transpose operation so that lazily-loaded data from any backend can be transposed without first loading into memory. The lazy indexing layer must correctly propagate data-resolution calls through the wrapper chain regardless of whether the underlying array is a backend array or a coding adapter.

- **Constraints**: The fix must not alter the observable result of any previously working transpose or data-access operation. Coding wrappers must remain transparent to the user — transposition should yield identical data whether the array is loaded eagerly or accessed lazily.


### Task 8 Fix default engine detection to include h5netcdf as a fallback
Ensure that xarray automatically detects and selects the h5netcdf backend engine when it is the only netCDF-capable package installed. Previously, calling to_netcdf(), open_dataset(), or open_dataarray() without specifying an engine would raise a ValueError if only h5netcdf was available, because the default engine resolution logic only checked for netCDF4 and scipy.

- **Expectation**: When a user calls any netCDF read or write operation without explicitly specifying an engine, xarray should automatically detect and use whichever supported backend is installed. The detection should follow a defined priority order: netcdf4 is preferred, h5netcdf is the secondary fallback, and scipy is the tertiary fallback. If no supported backend is installed, the error message should clearly list all three supported options.

- **Constraints**: The existing default engine preference for netcdf4 must not be altered. Users who already have netCDF4 or scipy installed must see no change in behavior. The fix must only expand coverage to recognize h5netcdf as a valid fallback, not change the priority of existing backends.


### Task 9 Fix merge() to prevent mutating original input objects' attributes
Ensure that xarray.merge() and Dataset.merge() do not mutate the attributes (.attrs) of original input Dataset or DataArray objects when any join mode is used. Previously, using join values such as 'exact' or 'override' could silently alter the original objects' attributes as a side effect of the merge operation. Additionally, ensure that users are warned via a FutureWarning when merging overlapping variables under the default no_conflicts compatibility mode, as results may differ in the future.

- **Expectation**: Merging datasets must be a side-effect-free operation with respect to all input objects. No input dataset's variable attributes should be modified as a consequence of a merge call, regardless of the join strategy. Users should receive a FutureWarning when merging overlapping variables under the default compatibility mode to signal upcoming behavioral changes.

- **Constraints**: The fix must not alter any merge output values or raise new errors. Performance overhead from defensive copying should be minimized by only copying when attribute assignment is actually needed. The FutureWarning should only appear in the specific scenario of overlapping variables under the default compatibility setting, not in explicitly user-specified modes.


### Task 10 Validate unlimited_dims in to_netcdf against actual dataset dimensions
Ensure that unlimited_dims passed to xarray.DataArray.to_netcdf(), xarray.Dataset.to_netcdf(), or xarray.DataTree.to_netcdf() — whether supplied as an explicit keyword argument or inherited from dataset.encoding['unlimited_dims'] — only contains dimension names that are actually present in the object being written. When unlimited_dims contains dimension names not in the dataset (e.g., after swap_dims or rename_dims operations leave stale entries), a clear ValueError must be raised before any I/O is attempted, instead of allowing a cryptic TypeError to propagate from the underlying storage backend.

- **Expectation**: When writing a dataset to netCDF, any unlimited dimensions declared — whether explicitly or via encoding — must be validated against the dataset's actual dimensions before I/O begins. Invalid dimension references must produce a clear, actionable ValueError rather than a low-level backend crash. The validation must work regardless of which storage engine is used.

- **Constraints**: All previously working workflows where unlimited_dims correctly matches the dataset's dimensions must remain unaffected. The fix must not alter the semantics of valid unlimited_dims usage. Error reporting must happen early enough to prevent any side effects such as partial file writes. Both user-supplied and encoding-inherited unlimited dimension declarations must be validated.


## Breaking Changes

### Task 11 Deprecation cycle for stricter combine/concat/merge/open_mfdataset default keyword arguments
Ensure that the combine functions (concat, merge, combine_nested, combine_by_coords, open_mfdataset) begin a deprecation cycle for their default keyword arguments, transitioning from overly permissive defaults to stricter, more predictable, and more performant defaults. Ensure that a FutureWarning is emitted when the user has not explicitly set a keyword argument and the old default would produce different behavior than the new default. Ensure that a new global option (use_new_combine_kwarg_defaults) allows users to opt in to the new defaults immediately. Ensure that data_vars accepts None as a new semantic value meaning dimension-aware automatic selection. Ensure that internal callers of these functions pass explicit keyword arguments so they do not trigger deprecation warnings.

- **Expectation**: When users call combine functions without specifying keyword arguments for data_vars, coords, compat, or join, the library should warn (via FutureWarning) if the upcoming stricter defaults would produce different results than the current permissive defaults. Users should be able to opt in to the new defaults immediately via a global option. The new data_vars=None semantic should automatically choose whether to concatenate all data variables or only those that already have the concat dimension, based on whether the concat dimension is new or existing. Internal library code should not trigger these warnings.

- **Constraints**: The deprecation must be non-breaking in the current version — old behavior is preserved by default and only warnings are added. Internal library operations must not surface deprecation warnings to users. The opt-in mechanism must be a single global toggle. The warning must only fire when there is a genuine behavioral difference, not unconditionally. Error messages under new defaults must provide guidance about the default change to help users migrate.


## Documentation

### Task 12 Clarify chunks=None lazy behavior and eager loading in open_* functions
Ensure that the documentation for the chunks parameter in open_dataset(), open_dataarray(), open_datatree(), open_groups(), and open_zarr() clearly communicates the memory loading semantics of chunks=None. Specifically, it must be made clear that: (1) chunks=None does not use dask, (2) data is initially represented via internal lazy indexing, but (3) data is eagerly loaded into memory as numpy arrays when accessed. The previous wording ('skips using dask, which is generally faster for small arrays') was insufficient and led users to believe data would remain lazy throughout their workflow, causing unexpected memory consumption with large datasets.

- **Expectation**: When a user reads the documentation for any of the open_* data-loading functions, the description of chunks=None must make the eager-on-access memory behavior explicit so that users can make informed decisions about whether to use dask chunking for large datasets. The documentation should guide users toward understanding that chunks=None is best suited for small arrays or large arrays that will be sliced before computation, and that for large datasets where lazy evaluation is needed throughout processing, a dask-backed chunking option should be used instead.

- **Constraints**: The documentation update must not alter any function signatures, defaults, or runtime behavior. It must only improve the accuracy and clarity of existing parameter descriptions. The guidance must be consistent across all five open_* functions.


## Performance Improvements

### Task 13 Speed up Dataset.interp() for non-numeric scalar variables
Ensure that Dataset.interp() does not degrade in performance proportionally to indexer size when the dataset contains non-numeric (object, bytes, or unicode dtype) variables whose size along the interpolated dimensions is 1. Previously, calling Dataset.interp() on such datasets with large indexers was orders of magnitude slower than necessary because all non-numeric variables were routed through a reindex path regardless of their shape.

- **Expectation**: When interpolating a dataset that contains non-numeric variables (strings, objects, booleans) that are effectively scalar along the interpolated dimensions, the operation should complete in approximately constant time with respect to the number of interpolation points. The output values for those variables should be identical to what the reindex path would have produced — the variable's single value broadcast across the new coordinates.

- **Constraints**: The optimization must not alter the correctness of interpolation results for any variable type or shape. Existing behavior for multi-element non-numeric variables and all numeric variables must be fully preserved. The returned dataset must be independent of the source dataset's memory (no shared mutable state).


## Additional Changes
- Ensure that the Pydap Datatree backend tests do not fail intermittently due to element ordering. The tests previously compared two ordered lists, but the underlying data source does not guarantee a stable element order, causing spurious test failures.
- Ensure that composing lazy indexers in xarray preserves NumPy indexing semantics when an existing slice is followed by integer-array indexing. Previously, combining these operations could produce incorrect indices because the original slice was expanded too early and negative indices were not normalized relative to the sliced result.
- Ensure that slicing a `RangeIndex` down to zero elements yields a valid empty `RangeIndex` that can still be inspected and represented. Previously, deriving the step from an empty transform could fail or lose the original step information.
- Ensure that only supported pandas extension arrays are preserved as extension-backed data inside xarray. Pandas string extension arrays and `NumpyExtensionArray` wrappers should not be treated the same way as supported extension dtypes such as categoricals, because doing so leads to inconsistent dtype handling and pandas-version-specific breakage.
