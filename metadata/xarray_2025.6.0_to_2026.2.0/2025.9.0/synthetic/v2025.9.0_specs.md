# Upgrade Specification from 2025.8.0 to 2025.9.0

## New Features

### Task 1 Support rechunking by SeasonResampler for seasonal data analysis
Ensure that Dataset.chunk() accepts SeasonResampler (and any Resampler subclass) for datetime-like dimensions, not only TimeResampler. Ensure that passing a SeasonResampler to Dataset.chunk() computes correct seasonal chunk boundaries without silently dropping data. Ensure that improved error messages are raised when rechunking is attempted on virtual variables or non-1D variables. Ensure that SeasonResampler rechunking validates that the provided seasons cover all 12 months.

- **Expectation**: Users can pass any supported Resampler object (such as SeasonResampler or TimeResampler) to Dataset.chunk() on datetime dimensions to control how data is split into chunks along that dimension. The chunking operation computes chunk boundaries based on the resampler's grouping strategy and returns correctly sized chunks without silently dropping any data. Clear, descriptive errors are raised when the input variable is incompatible with resampler-based chunking or when the seasonal specification is incomplete.

- **Constraints**: Backward compatibility with existing TimeResampler-based chunking must be preserved. No data may be silently dropped during seasonal rechunking. Only resamplers that fully cover the calendar (all 12 months) are permitted for rechunking. The chunking output must always be consistent with the actual variable size. Custom Resampler subclasses that do not implement chunk computation must fail explicitly.


### Task 2 Add convenience methods to Coordinates (rename, drop, merge operator)
Ensure that the xarray Coordinates class provides direct convenience methods for common coordinate manipulation tasks: renaming dimensions (rename_dims), renaming variables (rename_vars), dropping variables (drop_vars), dropping dimensions (drop_dims), and merging two Coordinates objects via the | (or) operator. Users should not need to round-trip through a Dataset to perform these operations.

- **Expectation**: The Coordinates object supports direct renaming of dimensions and variables, dropping of variables and dimensions with configurable error handling, and merging of two coordinate sets using the pipe operator. All operations return new Coordinates objects without mutating the original. The merge operator follows established xarray conflict-resolution semantics for index and non-index coordinates.

- **Constraints**: New convenience methods must preserve the existing semantics of the equivalent Dataset operations. Error handling modes must be consistent with the rest of the xarray API. The merge operator must follow the same conflict-resolution rules as the existing merge method. No existing Coordinates functionality should regress.


### Task 3 Add load_datatree() for eager loading of DataTree from disk
Ensure that users can eagerly load a DataTree entirely into memory from a file or file-like object in a single call, analogous to how load_dataset() works for Dataset. Previously, users had to manually call open_datatree(), invoke .load(), and close the file handle themselves. The new load_datatree() function should handle all three steps automatically and be accessible as a top-level xarray API.

- **Expectation**: A new top-level convenience function must allow users to open, fully load, and close a DataTree in one call. The function mirrors the load_dataset/open_dataset pattern. The returned DataTree must be entirely in memory with no lingering file handles. Passing the 'cache' parameter must be rejected with a clear error since it has no effect in this eager-load context.

- **Constraints**: The new function must not introduce resource leaks. It must reject inapplicable parameters with appropriate errors rather than silently ignoring them. Existing dataset and dataarray loading APIs must continue to work identically. The DataTree returned must behave identically to one obtained by manually calling open_datatree followed by .load().


### Task 4 Support compute=False for DataTree.to_netcdf() and DataTree.to_zarr()
Ensure that DataTree.to_netcdf() and DataTree.to_zarr() support the compute=False parameter, returning a dask.delayed.Delayed object that allows users to defer the actual data writing to a later point. Previously, passing compute=False to these methods had no effect or was explicitly unsupported, forcing users to always write synchronously even when working with chunked (dask-backed) data in a DataTree.

- **Expectation**: When a user writes a DataTree to netCDF or Zarr with deferred computation enabled, the method should return a lazy handle (a Delayed object) that, when computed, completes all data writes and finalizes the file. The user should be able to integrate this into larger dask task graphs. When deferred computation is not applicable (e.g., writing to an in-memory buffer for netCDF), the method should raise a clear error. With the default synchronous mode, behavior should remain unchanged: netCDF writes return None (or memoryview for in-memory), and Zarr writes return the store object. All tree nodes should be written through a single root store using a hierarchical child-store mechanism, rather than opening and closing separate stores per node.

- **Constraints**: Default synchronous write behavior must not regress. File resources must be managed correctly in both deferred and immediate modes — no premature closes that would corrupt deferred writes, and no resource leaks that would leave files locked. The hierarchical store mechanism must correctly handle nested groups in the DataTree. Metadata consolidation for Zarr must still occur at the appropriate time.


## Bug Fixes

### Task 5 Fix open_dataset zarr backend inference for paths with trailing slash
Ensure that open_dataset correctly auto-detects the zarr backend when the file path ends with a trailing slash (e.g., 'data.zarr/'). Previously, a trailing slash caused the backend inference to fail, requiring users to explicitly pass engine='zarr' even though the path clearly indicated a zarr store. This commonly occurs when paths are constructed via shell autocomplete or programmatic directory listing.

- **Expectation**: When a user calls open_dataset with a path to a zarr store that includes a trailing slash, the library should automatically detect and use the zarr backend, behaving identically to when the path has no trailing slash.

- **Constraints**: The fix must not alter behavior for paths that already worked correctly. Only paths with a trailing slash that were previously unrecognized should now be handled. No other backend inference logic should be affected.


### Task 6 Unify default netCDF write engine selection across Dataset and DataTree
Ensure that DataTree.to_netcdf() and Dataset.to_netcdf() dynamically select the default write engine based on installed netCDF libraries, rather than hardcoding a specific backend. Ensure that DataTree.to_netcdf() works when only netCDF4 is installed and h5netcdf is not. Ensure that the engine preference order (netcdf4 > h5netcdf > scipy) is consistent across all netCDF write paths and matches the read-side engine selection logic. Ensure that format-incompatible backends are excluded from candidates (e.g., scipy excluded for NETCDF4 format, h5netcdf excluded for NETCDF3 formats). Ensure that netcdf4 is excluded from candidates when writing to file-like objects or memoryview targets.

- **Expectation**: When no engine is explicitly specified, both Dataset.to_netcdf() and DataTree.to_netcdf() should automatically detect which netCDF backend libraries are installed and select the most preferred one that is compatible with the requested format and output target. The preference order should be netcdf4 first, then h5netcdf, then scipy. The selection should account for format constraints (some formats are not supported by all backends) and target type constraints (some backends cannot write to in-memory targets). If no compatible backend is available, a clear error should indicate which libraries could be installed to enable the operation.

- **Constraints**: The automatic engine selection must never hardcode a single backend as the default. The write-side engine resolution must follow the same preference order as the read-side resolution. Explicitly specifying an engine must always take precedence over automatic selection. Existing code that passes engine explicitly must continue to work unchanged. The error messages when no suitable backend is found must be informative about which libraries are needed.


### Task 7 Fix contour plot color normalization with logarithmic norms
Ensure that contour and contourf plots correctly distribute colors across the full colormap when a non-linear norm (e.g., LogNorm) or a non-default locator (e.g., LogLocator) is provided. Ensure that the colors parameter is respected regardless of whether it is a single string or a sequence of color values.

- **Expectation**: Contour plots should automatically produce appropriately-spaced levels that match the given normalization scheme. When logarithmic normalization is active, the resulting plot should use the full range of the colormap with logarithmically distributed contour levels. When a user provides explicit colors (in any supported form), those colors should always be used instead of the colormap.

- **Constraints**: Default linear-norm contour plots must not regress in appearance. Explicit user-provided levels must always take precedence. The fix must not alter behavior of non-contour plot types such as pcolormesh.


### Task 8 Fix auto_complex keyword argument forwarding for open_datatree
Ensure that the auto_complex keyword argument is correctly distributed through the DataTree I/O code paths so that complex-valued data written via DataTree.to_netcdf(auto_complex=True) is properly decoded back into complex dtypes when read via xr.open_datatree(auto_complex=True) using the netcdf4 engine.

- **Expectation**: When a user round-trips complex-valued data through DataTree netCDF serialization with auto_complex enabled on both write and read, the data should be transparently decoded back to complex number arrays. The read-side API should honor the auto_complex flag identically to how open_dataset already does.

- **Constraints**: Fixing the DataTree path must not regress the existing Dataset-level complex number encoding/decoding. The parameter forwarding must be consistent across all DataTree I/O entry points that support the auto_complex option.


### Task 9 Downgrade unlimited_dims encoding mismatch from error to warning
Ensure that calling to_netcdf on a dataset whose encoding['unlimited_dims'] references dimensions no longer present in the dataset (e.g., after subsetting with isel) does not raise a ValueError. The stale unlimited_dims inherited from dataset.encoding should produce a warning instead of an error, so that existing workflows that subset and re-save datasets are not broken.

- **Expectation**: When a dataset carries stale unlimited dimension names in its encoding metadata (e.g., after a dimension-reducing selection), writing that dataset to a file should succeed with a warning rather than failing with an error. Explicitly passing invalid unlimited_dims as a keyword argument should still raise an error to catch intentional misuse.

- **Constraints**: Strict validation must be preserved for explicit API calls where the user directly specifies unlimited_dims. Only inherited encoding metadata should receive lenient treatment. The user must still be informed of the mismatch through a visible warning so they can correct the encoding if desired.


### Task 10 Fix DataTree.to_netcdf hardcoded h5netcdf default engine and refactor store writing
Ensure that DataTree.to_netcdf() does not hardcode h5netcdf as the default engine. When engine is not specified, the default engine must be resolved dynamically based on available backend libraries (preferring netcdf4, then h5netcdf, then scipy) and the requested format, consistent with Dataset.to_netcdf(). Ensure that calling DataTree.to_netcdf() without specifying engine succeeds when only netcdf4 is installed. Ensure that compute=False is supported for DataTree.to_netcdf() when writing to a file path.

- **Expectation**: When no engine is explicitly specified, DataTree.to_netcdf() should automatically select the best available netCDF backend library based on what is installed, with a preference for netcdf4 for disk-based writes. This behavior should be consistent with how Dataset.to_netcdf() resolves its default engine. If no compatible library is available, a clear error should be raised. Lazy (deferred) writing via compute=False should be supported when writing to a file path.

- **Constraints**: Default engine selection must be dynamic and based on the user's installed libraries, never hardcoded. The writing process must handle all subtree nodes through a single store connection rather than independently opening and appending to the file per node. Deferred computation must be supported for file-based writes. In-memory writes must still require immediate computation.


## Breaking Changes

### Task 11 Reclassify Day offset as non-Tick-like for CFTime resampling
Ensure that the Day cftime offset is treated as a non-Tick-like frequency, consistent with pandas 3.0 semantics. Ensure that when resampling CFTimeIndex data at daily frequency, the 'offset' parameter (when not None) and the 'origin' parameter (when not 'start_day') are silently ignored but produce RuntimeWarning diagnostics. Ensure that timedelta-to-offset conversion no longer yields Day instances, producing Hour-based equivalents instead. Ensure that CFTimeIndex rounding operations still work correctly with Day frequency by treating it as a 24-hour fixed duration.

- **Expectation**: The Day offset must behave as a calendar-day frequency, not a sub-daily tick. Resampling at daily frequency should not be influenced by offset or origin parameters; when users supply non-default values for these parameters with a daily or coarser frequency, the library should warn them that those arguments have no effect. Timedelta-to-offset conversion should always produce tick-level offsets (hours, minutes, seconds). Rounding operations on CFTimeIndex should continue to support Day frequency by internally treating it as a 24-hour duration.

- **Constraints**: Sub-daily tick offsets (hours, minutes, seconds) must be unaffected by this change. Only the Day offset changes its classification. Warnings must be user-visible runtime warnings, not errors. Rounding and shifting operations with Day frequency must continue to produce correct results despite the reclassification. No existing valid resampling workflows using tick-level frequencies should be broken.


### Task 12 to_netcdf() returns memoryview instead of bytes and uses consistent default engine
Ensure that Dataset.to_netcdf() and DataArray.to_netcdf() return a memoryview (not bytes) when called without a path argument. Ensure that the default engine for in-memory and file-like-object serialization is selected using the same preference order as open_dataset (netCDF4 > h5netcdf > scipy) instead of always defaulting to scipy. Ensure the previously emitted FutureWarning about the bytes-to-memoryview transition is removed. Ensure that calling to_netcdf with compute=False and no path raises NotImplementedError with a message referencing memoryview.

- **Expectation**: When serializing a dataset or data array to netCDF in memory (no file path provided), the result must be a memoryview object, avoiding an extra memory copy. The default engine for in-memory serialization must follow the same preference order used when opening datasets. No deprecation or future warnings related to the return type should be emitted. Attempting lazy (deferred) in-memory serialization must raise a clear not-implemented error.

- **Constraints**: The change must not break serialization to file paths or file-like objects. Callers that need bytes must be able to convert from memoryview trivially. Engine selection for writing must remain overridable by the user. Deferred computation for file-based writes must continue to work.


## Performance Improvements

### Task 13 Eliminate redundant Dask computations in DataTree serialization with cross-group dependencies
Ensure that DataTree.to_netcdf() and DataTree.to_zarr() do not perform redundant Dask computations when the DataTree contains cross-group dependencies. When variables in different groups share upstream Dask graph nodes, each upstream operation should be computed exactly once during serialization, matching the efficiency of saving equivalent data as a single Dataset. Ensure that DataTree.to_zarr() explicitly exposes all Zarr-related write parameters (synchronizer, chunk_store, consolidated, append_dim, region, safe_chunks, align_chunks, storage_options, zarr_version, zarr_format, write_empty_chunks, chunkmanager_store_kwargs) rather than accepting them through **kwargs.

- **Expectation**: When a DataTree with cross-group Dask dependencies is saved to netCDF or Zarr, the serialization process should optimize the Dask computation graph globally across all groups. Each Dask task in the graph should execute only once regardless of how many groups reference it. The number of Dask task evaluations when saving a DataTree should match the number when saving the equivalent data as a single Dataset. All Zarr write options should be directly accessible as named parameters on DataTree.to_zarr(). When delayed computation is requested, a proper Dask delayed object should be returned that handles store finalization after writes complete.

- **Constraints**: Existing single-Dataset serialization workflows must not be affected. Child store creation must faithfully inherit all configuration from the parent store. Store lifecycle management (close and sync) must be robust against exceptions during writing. Zarr metadata consolidation must remain automatic and correct for DataTree writes. Child group paths must be constructed in a way that is compatible with the underlying storage backend's metadata handling.


## Additional Changes
- Ensure that complex number variables stored in NetCDF4 files are correctly reconstructed when opened via open_datatree. Previously, the auto_complex mechanism was not triggered on the open_datatree code path, causing complex-typed data to be returned in its raw split-component representation instead of as proper complex arrays.
- Ensure that boolean scalar values are not treated as integer positional indexers in xarray. Indexing operations such as `obj[True]` or explicit indexer construction with `True` should fail with a TypeError rather than being coerced to positions 1 or 0.
- Ensure that xarray operations which internally build pandas `MultiIndex` objects continue to work on newer pandas versions that expect concrete list inputs rather than mapping views or other iterable wrappers. Users should be able to create and manipulate MultiIndex-backed coordinates without pandas constructor type errors.
