# Upgrade Specification from 2025.9.0 to 2025.9.1

## New Features

### Task 1 Extend DataTree.from_dict() to accept DataArray values, coords, and nested dicts
Ensure that DataTree.from_dict() supports constructing a DataTree from DataArray-coercible values (not only Dataset/DataTree objects), supports a 'coords' parameter for specifying coordinate variables at arbitrary tree paths, and supports automatic flattening of nested dictionaries when nested=True is specified. Ensure the previous positional-only parameter 'd' is renamed to 'data' and is no longer positional-only.

- **Expectation**: DataTree.from_dict() accepts DataArray-like values in addition to Dataset and DataTree objects. A separate 'coords' argument allows coordinate variables to be specified independently from data variables at any tree path. Nested Python dictionaries can be passed directly and are auto-flattened when nested=True is set. The method validates that no duplicate paths exist after canonicalization, that DataArray values are not placed at the root, and that DataArray values do not conflict with explicitly set parent nodes.

- **Constraints**: Existing usage patterns with flat dictionaries of Dataset and DataTree values must remain fully backward-compatible. The default behavior (nested=False) must not accept nested dicts to avoid ambiguity with existing type signatures. Coordinate and data variable namespaces must remain distinct. The tree construction order must be preserved to avoid parent-before-child insertion errors.


### Task 2 Support in-memory netCDF reads and writes with engine='netcdf4'
Ensure that the netCDF4 backend (`engine='netcdf4'`) supports reading netCDF data from in-memory `bytes` or `memoryview` objects and writing netCDF data to in-memory buffers (returning a `memoryview`), for both `Dataset` and `DataTree`. Previously, the netCDF4 engine only supported file-path-based I/O, while scipy and h5netcdf already supported in-memory operations. Ensure that xarray objects opened from in-memory bytes with `engine='netcdf4'` can be pickled. Ensure that `NetCDF4BackendEntrypoint.guess_can_open` correctly identifies in-memory `bytes`/`memoryview` containing valid netCDF data. Ensure that the default write engine selection accounts for in-memory targets appropriately via the configurable `netcdf_engine_order` option.

- **Expectation**: All xarray netCDF backends (netcdf4, scipy, h5netcdf) should uniformly support reading from in-memory byte data and writing to in-memory buffers. The netCDF4 engine should handle in-memory round-trips: write a Dataset or DataTree to memory and read it back without touching the filesystem. In-memory datasets should be pickleable, enabling use with distributed computing frameworks. The engine auto-selection logic should respect user-configurable engine ordering preferences and correctly distinguish in-memory targets from file-object targets.

- **Constraints**: The change must not regress any existing netCDF I/O workflows, including file-based reads/writes, multifile datasets, remote URI access, dask-backed lazy writes, or pickling of file-based datasets. The in-memory feature must integrate seamlessly with the existing engine selection, encoding validation, and unlimited dimensions handling. Lock semantics must remain correct for concurrent access patterns.


### Task 3 Hide empty sections in HTML reprs and auto-expand DataTree sub-groups
Ensure that the HTML repr for DataArray, Dataset, and DataTree hides sections that are empty (no coordinates, no non-default indexes, no attributes), rather than displaying empty collapsible panels. Ensure that the DataTree HTML repr automatically expands child sub-groups when the parent group has no data variables, making nested tree structures easier to browse. Ensure that DataArray names are properly HTML-escaped in the repr output.

- **Expectation**: When viewing the HTML representation of any xarray data structure, sections that contain no information (empty coordinates, only default indexes, no attributes) should not appear at all. DataTree groups that serve only as organizational containers (no data variables) should have their child sub-groups automatically expanded for easier navigation. DataArray names containing special HTML characters should display correctly without rendering issues.

- **Constraints**: Existing non-empty HTML representations must remain unchanged. The visibility logic for sections must match the existing text repr behavior for consistency. The auto-expand heuristic for DataTree sub-groups must not affect trees where group levels contain data variables. All user-facing display options that control index and children visibility must continue to be honored.


## Bug Fixes

### Task 4 Default Zarr fill_value to NaN for float variables in Zarr v3
Ensure that when writing Zarr v3 stores via Xarray, unwritten or lazily-computed float variable chunks default to a fill_value of NaN instead of zero. Previously, writing Zarr metadata with compute=False and then reading back the store would decode unwritten float data as all zeros under Zarr v3, while Zarr v2 correctly decoded them as NaN. This inconsistency caused silent data corruption for workflows relying on NaN to indicate missing or not-yet-written data.

- **Expectation**: When writing float variables to a Zarr store without an explicit fill_value, the library should default to NaN as the fill value for unwritten chunks, regardless of whether Zarr v2 or v3 format is used. Non-float variables should continue to use zero as the default fill value. Users should be able to override the default fill_value through the encoding parameter.

- **Constraints**: The change must not alter behavior for integer or other non-float types. Explicit user-provided fill values must always take precedence over the new default. Zarr v2 write behavior must remain unchanged to avoid regressions.


### Task 5 Restore pickle support for h5netcdf-backed datasets opened from file-like objects
Ensure that xarray datasets opened via `xr.open_dataset()` with `engine='h5netcdf'` from file-like objects (e.g., objects returned by `s3fs.S3FileSystem.open()`) can be successfully pickled and unpickled using cloudpickle or the standard pickle module. Previously, attempting to pickle such datasets raised `TypeError: h5py objects cannot be pickled`, breaking Dask-based parallel workflows over remote netCDF files.

- **Expectation**: Datasets backed by h5netcdf and opened from file-like objects or remote URIs must survive a pickle round-trip without raising errors. After unpickling, the dataset must be fully functional with data accessible as before. The system must distinguish between local file paths (which use cached file management) and file-like objects or remote URIs (which use pickle-safe file management). Pickling a dataset whose file has already been closed should produce a closed dataset on unpickle rather than an error.

- **Constraints**: Existing behavior for locally-opened h5netcdf datasets must not regress. The file management interface must remain consistent regardless of which manager implementation is used. Pickle support depends on the underlying file-like object's opener being pickleable; if it is not, the limitation is documented rather than silently failing. Resources must be properly cleaned up on close, and closed managers must not allow further data access.


### Task 6 Scipy backend no longer closes underlying file-like objects on close
Ensure that closing an Xarray Dataset or DataArray opened from a file-like object (e.g., BytesIO) with engine='scipy' does not close the underlying file-like object. Previously, the scipy backend would close the caller-supplied file handle when the Xarray object was closed, preventing subsequent reads or reuse of that file object. This was inconsistent with the h5netcdf backend, which correctly left the underlying file open.

- **Expectation**: When a user opens an Xarray object from a file-like object using the scipy engine and subsequently closes the Xarray object, the underlying file-like object must remain open and seeked to position zero, ready for further reads. The close operation should flush any pending writes but must not invalidate or close the file handle. This behavior must be consistent with how the h5netcdf backend handles the same scenario.

- **Constraints**: The fix must only change close behavior for file-like object inputs, not for file path inputs. Memory-mapped file access must remain unsupported for file-like objects. Normal file-path-based opens must continue to use the standard scipy netcdf_file behavior. Compressed (.gz) file handling must remain unchanged.


### Task 7 Fix align_chunks parameter not passed in Dataset.to_zarr()
Ensure that the align_chunks parameter on Dataset.to_zarr() is correctly forwarded to the backend so that automatic chunk alignment works for Dataset objects, not just DataArray objects. Ensure that chunk alignment handles the edge case where Zarr encoding chunk sizes are larger than the variable's dimension size. Ensure that the chunk misalignment error message clearly identifies which Dask chunks overlap on the same Zarr chunk and on which axis.

- **Expectation**: When a user writes a Dataset to Zarr with automatic chunk alignment enabled, the alignment must actually take effect, preventing silent data corruption during parallel writes. When the Zarr target chunk size exceeds the variable's dimension length, chunk computation must gracefully handle the mismatch without producing invalid chunk specifications. Chunk validation error messages must be actionable by clearly describing which chunks conflict and on which axis.

- **Constraints**: Existing Zarr write workflows that do not use align_chunks must not be affected. Chunk safety validation must remain intact and must not produce false negatives. The fix must not alter the public method signatures or introduce new required parameters.


### Task 8 Fix encoding of empty numpy.datetime64 arrays with standard/gregorian calendar
Ensure that encoding an empty numpy.datetime64 array with a 'standard' or 'gregorian' calendar encoding does not raise a ValueError. Previously, calling Dataset.to_netcdf on a dataset with a zero-length datetime64 coordinate and calendar set to 'standard' failed with 'zero-size array to reduction operation fmin which has no identity', while the same operation succeeded for non-empty arrays or when no calendar encoding was specified.

- **Expectation**: Encoding a zero-length datetime64 variable with any supported calendar, including 'standard' and 'gregorian', must succeed and produce a valid empty encoded output. The encoding path should handle empty arrays gracefully without attempting reduction operations that require at least one element.

- **Constraints**: The fix must not alter the encoding behavior or validation logic for non-empty datetime arrays. Calendar mismatch detection for pre-Gregorian dates must remain intact. Only the empty-array edge case should be affected.


### Task 9 Propagate coordinate attributes in Dataset.map() when keep_attrs=True
Ensure that Dataset.map() preserves coordinate attributes when keep_attrs=True. Previously, calling Dataset.map() (or operations that depend on it, such as weighted mean/sum via the Weighted API) with keep_attrs=True would correctly preserve data variable attributes but silently discard all coordinate attributes. After any such operation, surviving coordinates would have empty attrs dictionaries, losing metadata such as standard_name, long_name, units, and axis. This must be fixed so that coordinate attrs are propagated consistently with data variable attrs.

- **Expectation**: When a user performs any Dataset operation that maps a function over data variables (including weighted reductions like weighted mean) with keep_attrs=True, the resulting Dataset must retain the original attributes on all surviving coordinates. Coordinate metadata such as standard_name, long_name, units, and axis must not be lost.

- **Constraints**: The fix must not change behavior when keep_attrs is False. Attribute propagation for coordinates must follow the same overwrite semantics already established for data variables. The change must not alter coordinate values or indexes, only their metadata attributes. Existing tests for Dataset.map() and weighted operations must continue to pass.


### Task 10 Fix to_netcdf compute=False failure with Dask Distributed
Ensure that calling Dataset.to_netcdf with compute=False and subsequently executing the delayed result via dask.compute() completes successfully when using the Dask Distributed scheduler. Prior to this fix, this workflow raised a BlockingIOError due to file-locking conflicts when distributed workers attempted to concurrently access the target file. This is a regression fix restoring behavior that worked in xarray 2025.8.0.

- **Expectation**: When a user calls to_netcdf with compute=False and later executes the delayed computation with Dask Distributed, the file manager wrapping the target netCDF file must be serializable so that distributed workers can independently open the file without global state or lock contention. Each worker should be able to write its assigned chunks without triggering file-locking errors. The delayed write workflow must produce the same output file as the immediate (compute=True) workflow.

- **Constraints**: The fix must not regress existing to_netcdf behavior for synchronous writes (compute=True), local Dask scheduler usage, or any other file-backed storage workflows. File safety guarantees (proper close, resource cleanup, unclosed-file warnings) must be maintained. Serialization support must work transparently without requiring user-facing API changes.


### Task 11 Propagate coordinate attributes in Dataset.map()
Ensure that Dataset.map() preserves coordinate attributes when keep_attrs=True. Previously, calling Dataset.map() (or any operation built on it, such as weighted mean/sum/std) with keep_attrs=True correctly preserved data variable attributes but silently dropped all coordinate attributes, resulting in empty attrs dictionaries on surviving coordinates. This must be fixed so that coordinate metadata (e.g., standard_name, long_name, units) is retained through map operations.

- **Expectation**: When a user applies a function across a Dataset with attribute preservation enabled, the resulting Dataset should retain the metadata attributes on all coordinates that survive the operation. Weighted aggregation operations (mean, sum, std, etc.) on Datasets and DataArrays should preserve coordinate attributes when keep_attrs=True, just as they already preserve data variable attributes.

- **Constraints**: The default behavior when attribute preservation is not requested must remain unchanged. Only coordinates that existed before the operation should have their attributes restored; newly introduced coordinates should not inherit attributes from unrelated sources. The change must not break existing workflows that depend on the current attribute-dropping behavior when keep_attrs is not set to True.


### Task 12 Fix combine_attrs='drop_conflicts' for non-bool __eq__ results
Ensure that combine_attrs='drop_conflicts' does not raise a ValueError when merging attributes whose values have __eq__ methods that return non-boolean results (e.g., numpy arrays). When two attribute values cannot be meaningfully compared for equality, they should be treated as conflicting and the attribute should be dropped, rather than the operation failing with an exception.

- **Expectation**: Attribute equivalence checks during merge operations must never raise exceptions due to non-standard equality implementations on attribute values. When two attribute values cannot be compared (because equality returns a non-boolean or raises an exception), they should be treated as non-equivalent, causing the attribute to be dropped under the drop_conflicts policy.

- **Constraints**: Existing equivalence semantics for arrays, lists, and NaN values must be preserved. Only the handling of non-standard equality results is changed. All other combine_attrs modes must continue to work as before. The fix must not silently suppress legitimate comparison errors in non-merge contexts.


## Breaking Changes

### Task 13 Dataset.update() now returns None instead of Self
Ensure that Dataset.update() no longer returns the dataset instance and instead returns None, completing the deprecation of its return value. Any existing code that captures or chains on the return value of Dataset.update() must be updated to treat the call as a purely in-place mutation with no usable return value.

- **Expectation**: Dataset.update() should behave like dict.update(): it mutates the dataset in-place and returns None. Users who previously captured the return value for chaining or assignment should instead call update() as a standalone statement and reference the original dataset variable for subsequent operations.

- **Constraints**: Only the return value contract changes; the mutation semantics and variable-merging behavior of update() must be fully preserved. No other public API methods on Dataset should change behavior as a side effect of this modification.


### Task 14 Change default netCDF engine preference order and add netcdf_engine_order option
Ensure that the default netCDF engine preference order is changed from netcdf4 > h5netcdf > scipy to h5netcdf > scipy > netcdf4 for both reading and writing operations. Ensure that a new set_options() parameter named netcdf_engine_order is available to let users customize the engine preference order. Ensure that users who depend on the prior default behavior can restore it by setting netcdf_engine_order to ['netcdf4', 'h5netcdf', 'scipy']. Ensure that open_datatree and open_groups only auto-select engines that support hierarchical groups.

- **Expectation**: When users read or write netCDF files without specifying an engine, the library should default to h5netcdf first, then scipy, then netcdf4, selecting the first one that is installed and compatible with the requested format and target. Users should be able to override this preference order globally via set_options(). When opening hierarchical data (DataTree or groups), the engine auto-selection should only consider backends capable of reading groups. The previous behavior can be fully restored via a single set_options() call.

- **Constraints**: The engine preference order must be globally configurable without breaking explicit engine selections. Format-specific engine constraints must still be enforced regardless of the configured order. The configuration must be validated at set-time, not at use-time. Backward compatibility must be achievable through the new configuration option.


## Typing Updates

### Task 15 Enable full mypy type checking for all test files and fix scipy fallback import typing
Ensure that the xarray project enforces full mypy type checking (check_untyped_defs = true) across all test files, including test_coding_times and test_dask, and that all resulting type errors in both test and library code are resolved. Specifically, ensure that the scipy backend module's fallback import path for the optional scipy dependency is correctly typed so that mypy reports no errors when scipy is not installed.

- **Expectation**: All test modules should pass strict mypy type checking without exclusions. The scipy backend module should cleanly handle the case where scipy is an optional dependency from a type-checking perspective, providing a valid fallback base reference when scipy is absent.

- **Constraints**: Enabling stricter type checking must not break existing tests or change any runtime behavior. Type-ignore annotations should be minimal and precisely targeted rather than broad suppressions. The optional nature of the scipy dependency must be preserved.


## Refactors

### Task 16 Refactor backends module to separate writers from readers
Ensure that the xarray backends module cleanly separates data-writing concerns from data-reading concerns. Specifically:
- All write-oriented functions (to_netcdf, to_zarr, save_mfdataset, dump_to_store, and their supporting helpers) must be relocated out of the read-focused API module into a dedicated writers submodule.
- The standalone datatree I/O module must be eliminated, with its writer implementations merged into the same writers submodule.
- All public entry points (Dataset.to_netcdf, Dataset.to_zarr, DataArray.to_netcdf, DataArray.to_zarr, DataTree.to_netcdf, DataTree.to_zarr, xr.save_mfdataset) must continue to work identically from the user's perspective.
- The default write engine selection must honor the user-configurable netcdf_engine_order option from xarray.set_options and must detect NCZarr mode from path suffixes.
- BackendEntrypoint must expose a supports_groups class-level attribute so that engine guessing for group-aware operations (open_datatree, open_groups) can skip backends that lack group support.
- The NetCDF4 backend's engine-guessing probe must accept bytes and memoryview inputs in addition to file paths.

- **Expectation**: All write-path functions are consolidated under a single writers submodule while all public user-facing APIs (Dataset.to_netcdf, Dataset.to_zarr, DataArray.to_netcdf, DataArray.to_zarr, DataTree.to_netcdf, DataTree.to_zarr, xr.save_mfdataset) remain fully functional with identical signatures and behavior. Default write engine selection respects the user-configurable engine order setting and properly handles NCZarr paths. Backend entrypoints declare whether they support group operations, allowing engine guessing to filter appropriately when opening hierarchical data. The NetCDF4 backend can now probe bytes and memoryview objects directly when guessing whether it can open a given input.

- **Constraints**: No user-facing API signatures may change. Third-party backend entrypoints must not break due to the new supports_groups attribute. The refactoring must not alter the observable behavior of any write operation. The engine selection order must remain user-configurable. Error messages for unrecognized engines, invalid formats, and missing backend libraries must remain informative.


## Additional Changes
- Ensure that the Zarr encoding specification documentation accurately reflects the observable behavior of Zarr V2 and V3 formats. The previous documentation showed incorrect example output (suggesting _ARRAY_DIMENSIONS would appear when it might not, depending on format version) and lacked any explanation of format-version-specific encoding differences for dimensions and coordinates.
- Ensure that Dataset and GroupBy reduction paths that rely on numeric-only variable filtering no longer exclude datetime-like variables. Previously, the filter only accepted numeric and boolean dtypes, so grouped means and similar reductions could silently drop datetime-valued variables such as timestamps, even though those variables support aggregation semantics.
- Ensure that `GroupBy.groups` for multi-grouper operations only reports groups that actually contain observations. Previously, empty combinations produced by the encoded grouper state could appear in `.groups`, causing the public mapping to include zero-length groups that were not present in the underlying data.
- Ensure that `DataArray.to_dataframe()` and `Dataset.to_dataframe()` do not duplicate index coordinates as DataFrame columns when the xarray object uses a MultiIndex along a single dimension. Previously, the conversion excluded only dimension names, so component coordinates of a single-dimension MultiIndex could appear both in the DataFrame index and again as ordinary columns, breaking equality with the corresponding Series/DataFrame representation and making `reset_index()` produce duplicate columns. Coordinate and index level dtypes should also be preserved during the conversion.
