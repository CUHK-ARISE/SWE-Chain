# Upgrade Specification from 2025.12.0 to 2026.1.0

## New Features

### Task 1 Improve DataTree HTML display for large trees
Ensure that the `DataTree` HTML representation stays informative and usable as tree size grows: groups should be individually collapsible, show how much content they contain, expose index information in HTML output, and automatically collapse or truncate oversized trees according to configured display limits.

- **Expectation**: The HTML preview for `DataTree` should expose the same important structure users can inspect in other representations, while remaining readable for large trees. Users should be able to expand individual groups, see how much content a group contains, inspect indexes in HTML output, and avoid overwhelming notebook output because large trees collapse or truncate automatically based on display settings.

- **Constraints**: The change must preserve the meaning of the displayed tree and only improve how it is presented. Small trees should still render fully, while large trees should degrade gracefully through collapsing and truncation rather than by hiding important structure entirely or changing the underlying data.


### Task 2 Auto-create temporary indexes for 1D unindexed .sel() coordinates
Ensure that `Dataset.sel()` and `DataArray.sel()` support label-based selection on eligible one-dimensional coordinates even when the user has not explicitly created an index for that coordinate first.

- **Expectation**: Users should be able to select by label on any supported one-dimensional coordinate without pre-registering an index. The library should transparently perform that lookup for the current selection only, while still rejecting unsupported coordinate shapes and invalid selection names with the appropriate error types.

- **Constraints**: This upgrade should add convenience for eligible one-dimensional coordinates without silently changing stored index state, altering established indexed-selection behavior, or relaxing validation for unsupported selection targets.


### Task 3 Configurable coordinate compatibility for arithmetic
Ensure that users can choose how binary arithmetic resolves same-named non-index coordinates, including strict validation, conflict-tolerant merging, first-operand override, and the existing default behavior of dropping conflicting coordinates.

- **Expectation**: Users should be able to decide whether arithmetic between xarray objects strictly validates non-index coordinates, merges them when they do not conflict, keeps the left operand's coordinate without checking, or removes conflicting coordinates. The same compatibility choice should also be available when coordinate collections are merged directly.

- **Constraints**: This feature must not change ordinary arithmetic alignment rules or force behavior changes on existing users. If no new option is chosen, arithmetic should continue to behave as it did before for coordinate conflicts.


### Task 4 Extend Dataset.eval() to native N-dimensional evaluation
Ensure that Dataset.eval() can evaluate user expressions and simple assignments on datasets with more than two dimensions, while preserving array-friendly logical syntax and failing clearly for deprecated, unsupported, or unsafe usage patterns.

- **Expectation**: Users upgrading should be able to use Dataset.eval() for arithmetic, comparison, and assignment expressions on multidimensional datasets without hitting the previous dimensionality limit. The method should continue to accept familiar boolean expression syntax for array-wise logic, warn when callers rely on deprecated parser configuration, and reject unsupported or unsafe input instead of evaluating it.

- **Constraints**: The upgrade should broaden supported array shapes without turning Dataset.eval() into arbitrary Python execution. Valid existing expression workflows should remain predictable, while malformed, unsupported, or unsafe forms should fail clearly and safely.


## Bug Fixes

### Task 5 Improve xarray coordinate display ordering
Ensure that coordinates shown when displaying xarray objects are ordered by the object's dimensions so that each dimension coordinate appears before related auxiliary coordinates, producing a more intuitive and consistent representation.

- **Expectation**: Displayed coordinate lists should read in the same order as the object's dimensions, with primary dimension labels first, related helper coordinates shown beside the dimensions they describe, and scalar or unrelated metadata left to the end.

- **Constraints**: Treat this as a presentation-only change. It should make displays easier to read without changing the object's data model or causing different display surfaces to disagree about coordinate order.


### Task 6 Use StringDType for Zarr string reads
Ensure that reading Zarr string variables preserves them as native variable-length string data and that null-detection APIs treat StringDType-backed arrays according to the string dtype's configured missing-value sentinel.

- **Expectation**: Opening Zarr datasets with string variables should preserve those variables as native string arrays, and calling null-detection APIs on those arrays should report missing values based on the string dtype's configured sentinel.

- **Constraints**: Do not regress existing Zarr string decoding or alter null semantics for non-string data, and avoid introducing false missing values for ordinary string content.


### Task 7 Align open_zarr auto chunking with the Zarr engine
Ensure that `xarray.open_zarr()` treats an omitted `chunks` argument differently from an explicit `chunks="auto"`, so that explicit auto chunking is consistent with `xarray.open_dataset(..., engine="zarr")` while the existing default behavior remains unchanged when `chunks` is not provided.

- **Expectation**: Users who explicitly request automatic chunking when opening a Zarr store should get true auto-chunking behavior that matches the generic dataset-opening API, while callers who leave chunking unspecified should continue to see the same default behavior they had before the upgrade.

- **Constraints**: Only the meaning of explicitly requesting auto chunking should change. Existing callers that rely on the default chunk-loading behavior without specifying `chunks` should not see a regression.


### Task 8 Normalize keep_attrs behavior for single-input apply_ufunc and where
Ensure that xarray operations built on apply_ufunc handle coordinate and result attrs consistently when only one xarray object is involved, so keep_attrs preserve modes retain metadata and drop modes remove it instead of leaking attrs from the lone xarray input.

- **Expectation**: Attribute retention for apply_ufunc-based operations should no longer depend on how many xarray operands were provided. If callers choose to keep attrs, the returned object should consistently keep the relevant metadata; if callers choose to drop attrs, the returned object should not retain coordinate metadata from the only xarray input.

- **Constraints**: This fix should change metadata behavior only. It must not alter the computed data, shape, coordinates, or alignment rules of the affected operations, and it should preserve existing behavior outside the inconsistent single-input attr case.


### Task 9 Honor xindexes while tolerating sliced RangeIndex drift
Ensure that equality and identity checks do not treat equivalent floating-point RangeIndex xindexes as different solely because slicing introduced insignificant rounding drift, while preserving a strict mode for exact comparisons and continuing to reject genuinely different or differently typed indexes.

- **Expectation**: Normal equality and identity checks should accept range-based floating-point indexes that represent the same coordinates, even if one was produced by slicing and carries tiny rounding differences internally. Users must be able to request strict comparison when exact stored values matter, and identity checks must continue to notice missing, differently typed, or meaningfully different indexes.

- **Constraints**: Only insignificant floating-point drift should be tolerated. Real differences in index type, presence, length, or values must still be surfaced, and strict comparison must remain available for callers that depend on exact internal state.


### Task 10 Preserve datetime units in seasonal resampling
Ensure that seasonal resampling with `SeasonResampler` preserves the original datetime resolution of pandas-backed time coordinates instead of changing the output coordinate dtype during resample operations.

- **Expectation**: Season-based resampling should behave like other xarray resampling operations: the output time labels must keep the same datetime precision as the input instead of being silently promoted to a different resolution. Non-NumPy calendar handling should continue to work as before.

- **Constraints**: The upgrade should not change how seasons are defined, ordered, or reduced. It should only remove the unintended datetime precision change in the resampled coordinate and avoid regressions for alternate calendar inputs.


### Task 11 Fix pandas 3 string index compatibility
Ensure that xarray operations can accept pandas 3 string-backed indexes as coordinate or dimension inputs without failing during dtype conversion, including when building a new dimension from a string-valued pandas index.

- **Expectation**: String-valued pandas 3 indexes should behave as supported xarray inputs instead of crashing when xarray converts index data into coordinates or indexes.

- **Constraints**: The change should stay narrowly scoped to pandas 3 string index compatibility and should not alter how xarray handles unrelated index types or unsupported runtime environments.


### Task 12 Restore where() compatibility for CuPy-backed arrays
Ensure that where() works on xarray objects backed by cupy.array inputs instead of failing during dtype coercion when evaluating the condition.

- **Expectation**: Masking CuPy-backed xarray data should behave like masking on other supported array backends: the operation should run successfully, apply the mask, and return a normal result instead of failing because of backend-specific casting differences.

- **Constraints**: Preserve current masking behavior for already-working inputs. The change should only eliminate the backend compatibility failure, not alter how where() decides which values are kept or replaced.


### Task 13 Correct CombinedLock locked-state reporting
Ensure that `CombinedLock.locked()` reports the real lock state of a `CombinedLock`, returning locked only when at least one wrapped lock is currently acquired rather than whenever the combined lock contains lock objects.

- **Expectation**: The combined lock API should accurately expose whether the combined resource is currently locked. Calling `CombinedLock.locked()` should mirror the live state of the wrapped locks rather than treating the presence of lock objects as evidence that the lock is held.

- **Constraints**: The fix should not alter how callers construct or use the combined lock beyond correcting the reported lock status. Existing lock composition behavior should remain intact while the reported state becomes truthful.


### Task 14 Fix multi-variable GroupBy.map recombination
Ensure that mapping over grouped datasets defined by more than one grouping variable recombines the mapped groups correctly and does not fail when some grouped combinations are empty or when grouping metadata is missing an active index for one of the groupers.

- **Expectation**: Mapping over groups formed from multiple grouping variables should behave like a normal map operation: it should finish successfully and rebuild one correctly ordered result, including sparse group layouts where some group combinations have no members or grouping metadata is partially absent.

- **Constraints**: Keep existing successful groupby-map behavior unchanged while making multi-variable grouping robust. The fix should not alter unaffected results, should not invent data for missing groups, and should not make callers restructure valid inputs to avoid the bug.


### Task 15 CoordinateTransformIndex indexing bug fixes
Ensure that CoordinateTransformIndex handles indexing without shape corruption: transform-backed arrays should preserve expected dimensions for outer and vectorized selections, only drop dimensions for scalar integer selections, and accept NumPy label arrays as valid coordinate labels.

- **Expectation**: From a user perspective, transform-backed coordinates should index like normal xarray indexes. Array-based selections should keep the shape the caller requested, scalar integer selections should still reduce rank, and plain NumPy arrays should work as coordinate labels without changing the meaning of the selection.

- **Constraints**: The fix must be non-regressive: incomplete label selections should still be rejected, singleton dimensions chosen through non-scalar indexing should remain visible, and only true scalar picks should collapse dimensions.


### Task 16 Lock netCDF4 close operations
Ensure that closing xarray objects that use the netCDF4 backend is synchronized with the backend lock so concurrent cleanup does not trigger intermittent race conditions for file-backed, in-memory, or externally supplied netCDF4 datasets.

- **Expectation**: Any xarray workflow using the netCDF4 engine should close resources under the same synchronization used for backend access, eliminating intermittent close-time races without changing how users open or close datasets.

- **Constraints**: The fix should be limited to safe synchronization during cleanup. Supported netCDF4 usage patterns, dataset contents, and the normal close lifecycle should remain otherwise unchanged.


### Task 17 Clarify missing SciPy failures for NDPointIndex
Ensure that using `NDPointIndex` without `scipy` installed produces a direct, actionable dependency error instead of an indirect failure during index creation.

- **Expectation**: Users who invoke the SciPy-backed point index without the optional SciPy dependency should get a clear explanation that SciPy is required, and they should see that failure at the point where the index machinery is being created. Users with SciPy available should not experience any behavior change.

- **Constraints**: Do not change normal point-index behavior in supported environments; only improve how unsupported environments report the missing optional dependency.


## Dependency Updates

### Task 18 Automatic xindex replacement on reindexing
Ensure that calling `Dataset.set_xindex()` or `DataArray.set_xindex()` on coordinates that already have an index replaces that index in a single call instead of failing or requiring a prior `drop_indexes()` call.

- **Expectation**: Reapplying `set_xindex()` to an already indexed coordinate should behave as a direct replacement operation from the caller's perspective: the API should succeed, update the coordinate's index to the requested one, and eliminate the need for a manual index-removal step beforehand.

- **Constraints**: The upgrade should make index replacement easier without broadening what counts as a valid `set_xindex()` call or weakening other existing safeguards.


## Breaking Changes

### Task 19 Include indexes in identical comparisons
Ensure that Dataset.identical(), DataArray.identical(), and xarray.testing.assert_identical() treat indexes as part of identity, so objects are only considered identical when their indexed coordinate definitions and index semantics match in addition to their existing data, coordinate, name, and attribute checks.

- **Expectation**: Identity checks should now include whether coordinates are indexed and what those indexes mean, not just the raw data and metadata. Two objects that look the same by values should still be treated as different if their index attachment, index type, or index equality semantics differ, and comparison failures should clearly expose that the mismatch is in indexes.

- **Constraints**: Only identity checks become stricter; ordinary equality behavior should remain as before. The change should reject structurally different indexing, preserve existing outcomes when no indexes are involved, and still allow semantically equivalent custom indexes to compare as identical when their coordinate definitions match.


## Documentation

### Task 20 Clarify xarray.where attribute-handling modes
Ensure that users can predict how `xarray.where` handles attrs across `cond`, `x`, and `y`, including the case where `x` is a scalar and the default behavior leaves the result without attrs.

- **Expectation**: Users should be able to read the `xarray.where` API and understand which attribute-retention modes exist, what each mode guarantees, and why metadata may disappear by default when the true branch is a scalar.

- **Constraints**: Clarify the existing behavior without overstating guarantees: metadata should only be retained or merged when the selected policy allows it, and conflicting metadata should not appear as preserved by default.


### Task 21 Clarify xarray.dot coordinate alignment semantics
Ensure that the public documentation for xarray.dot() and DataArray.dot() clearly explains how coordinates affect dot-product results, including label-based alignment, the default handling of partially overlapping labels, and preservation of coordinates on dimensions that are not summed away.

- **Expectation**: Users should be able to read the dot-product documentation and correctly predict outcomes for reordered labels, partially overlapping labels, and retained non-reduced coordinates, with clear notice that strict matching is available when silent alignment is not acceptable.

- **Constraints**: The upgrade should document the current observable contract without changing the default behavior or suggesting results that differ from label-aware alignment.


### Task 22 Correct rolling and coarsen window documentation
Ensure that the public rolling-window documentation accurately describes standard rolling and coarsening windows, and does not imply exponential window behavior for DataArrayRolling, DatasetRolling, or Coarsen.

- **Expectation**: Users reading the rolling and coarsening API documentation should see accurate terminology for the kind of window being created. The update should only fix misleading wording and should not alter how the APIs behave.

- **Constraints**: This update must improve documentation clarity without changing results, supported usage, or observable runtime behavior for existing rolling and coarsening workflows.


### Task 23 Clarify combine API defaults and option semantics
Ensure that the public documentation for `combine_nested` and `combine_by_coords` clearly describes the current defaults and supported option semantics for the combine-related kwargs so users can predict how combination behaves without relying on warnings or source inspection.

- **Expectation**: Users reading the combine API docs should see the actual default settings and a clear explanation of how variable and coordinate selection works during combination, including the special meaning of `data_vars=None`.

- **Constraints**: The release should improve clarity without changing how combine operations behave in running code.


## Performance Improvements

### Task 24 Fast-path explicit standard xarray engines
Ensure that explicitly selecting a standard xarray engine when opening a dataset avoids first-call backend plugin discovery overhead, while preserving normal plugin lookup for non-standard engines and surfacing missing optional dependencies for known engines as dependency/import failures rather than unknown-engine failures.

- **Expectation**: Passing a known built-in engine by name should make dataset opening start quickly even on the first call, without changing which backend is used. Users should get a clear missing-dependency/import failure when they request a known engine that is unavailable, while third-party engines and unknown names should continue to follow the existing discovery and validation behavior.

- **Constraints**: Optimize only the common built-in-engine path. Existing extensibility for external backends must continue to work, unsupported engine names must still be rejected, and alternate explicit backend selection forms must keep working as before.


### Task 25 Optimize CFMaskCoder decode copying
Ensure that CF mask decoding produces the same masked output while reducing unnecessary array copying during decoding.

- **Expectation**: Decoding CF-masked data should preserve the decoded values users expect while using less memory and more predictable copying behavior, especially for large arrays.

- **Constraints**: The performance improvement must not alter the decoded content, type handling, or the expectation that decoding operates on an independent result rather than modifying the source data.


## Additional Changes
- Ensure that the h5netcdf backend only supports h5netcdf 1.4 or newer, and that users who persist complex-valued data through that backend get the backend behavior introduced in h5netcdf 1.4, aligned with NetCDF4-style storage semantics.
- Ensure that the contribution guidance clearly states the relevant Pixi version expectation needed for contributor setup and workflow use.
- Ensure that xarray label-resolution paths preserve pandas index dtype semantics when asking pandas to resolve labels, so pandas-backed indexes continue to work correctly for array-like selection and nearest-bound localization.
