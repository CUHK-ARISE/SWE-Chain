# Upgrade Specification from 2026.1.0 to 2026.2.0

## New Features

### Task 1 Support shared 1D coordinates in NDPointIndex
Ensure that NDPointIndex can be created and used with multiple coordinate variables that share a single lower-dimensional dimension, so scattered-point and trajectory datasets are supported instead of being rejected.

- **Expectation**: Users should be able to build one point index from multiple aligned 1-dimensional coordinates and use it to select scattered points or trajectory locations. This coordinate layout should be treated as supported input rather than invalid input.

- **Constraints**: The feature expands which coordinate layouts are accepted, but coordinates still need to be aligned and describe the same collection of points. Invalid or incompatible coordinate combinations should continue to fail.


## Bug Fixes

### Task 2 Fix reverse slice normalization for negative-step indexing
Ensure that negative-step slice indexers, including reverse selections such as `slice(-1, None, -1)`, work correctly during xarray indexing and do not fail after indexer normalization.

- **Expectation**: Reverse slicing should behave like standard Python slicing throughout xarray indexing. Users should be able to reverse a dimension or use other negative-step slices without unexpected runtime errors, and the resulting selection order should match normal Python expectations.

- **Constraints**: Keep existing indexing behavior stable for normal slice usage. The fix should remove the failure mode for reverse slicing without redefining how slicing works in cases that already behaved correctly.


### Task 3 Standardize positional argument handling in plotting APIs
Ensure that xarray plotting methods handle deprecated positional arguments consistently: faceted 2D DataArray plots that use positional `x` and `y` together with `col` or `row` must not fail in the plotting backend, deprecated positional plotting forms should surface as forward-compatibility warnings, and plot APIs that are intended to be keyword-only should reject positional configuration arguments immediately.

- **Expectation**: Deprecated positional plotting calls should either keep working with a visible future-facing warning or fail early with the appropriate Python error type when positional arguments are no longer supported. Faceted 2D plots must not crash because internal warning state is forwarded to the plotting backend.

- **Constraints**: Keep backward-compatible positional calls working where they are still temporarily supported, but make unsupported positional usage fail immediately and predictably. Internal deprecation bookkeeping must never alter the plotted result or be treated as a backend plotting option.


### Task 4 Prevent silent corruption in sharded Zarr writes
Ensure that writing Dask-backed arrays to sharded Zarr stores validates and aligns chunking against shard boundaries so unsupported layouts fail clearly instead of silently corrupting stored data.

- **Expectation**: Saving a Dask-backed array to a sharded Zarr store should treat each shard as the unit of safe parallel writing. Supported chunk layouts should either be aligned to shards automatically or succeed as-is when already shard-aligned, while incompatible layouts should fail explicitly instead of producing incorrect stored values.

- **Constraints**: Only sharded writes should become stricter. Existing valid shard-aligned workflows must keep working, non-sharded workflows must behave as before, and explicit opt-outs from safety validation must remain available.


### Task 5 Correct descending sortby NaN placement
Ensure that descending sortby operations on Dataset and DataArray keep NaN or null sort-key values at the end of the result instead of moving them to the beginning.

- **Expectation**: Descending sortby results should behave like normal descending order for real values while still placing missing values last, even when several sort keys are involved.

- **Constraints**: Keep the existing sorting interface and normal sort rules intact; only correct the incorrect front-placement of missing values in descending results.


### Task 6 Clarify missing-file errors in open_dataset
Ensure that calling `open_dataset()` with a non-existent local file path fails with a clear missing-file error instead of a backend-selection error.

- **Expectation**: Opening a dataset from a missing local path should tell the user that the file is missing. Other engine-detection failures should continue to behave as they did before.

- **Constraints**: Keep the update narrowly focused on clearer error reporting for genuinely missing local files. Do not alter successful opens or reclassify unrelated unsupported-input cases as missing-file errors.


### Task 7 Make missing chunk manager errors actionable
Ensure that chunked-array operations fail with actionable guidance when xarray cannot find a compatible Chunk Manager for the array type, including a package-install suggestion for known backends instead of only reporting an unrecognized type.

- **Expectation**: If xarray encounters a chunked array whose backend integration is unavailable, the failure should clearly tell the user that an optional dependency is missing. For known backends, the error should point users to the relevant integration package; for unknown backends, it should still explain that the issue is likely a missing dependency.

- **Constraints**: Do not change normal chunked-array execution or unrelated error handling. The update is limited to making missing chunk-manager failures clearer and more actionable.


### Task 8 Reject slice-based MultiIndex level selection in .sel
Ensure that .sel(...) rejects slice-based selection on MultiIndex levels and raises a clear error instead of returning incorrect results or inconsistent lookup failures.

- **Expectation**: Users should get an explicit failure when they attempt range-style selection on an individual MultiIndex level through .sel(...). Selecting by exact level values should continue to work, while unsupported slice input should never return partial, incorrect, or ambiguous data.

- **Constraints**: Keep valid selection patterns working as before. Only unsupported slice-based level filters should be blocked, and they should fail consistently with a clear user-facing error rather than producing wrong results.


### Task 9 Preserve string dtypes during index creation
Ensure that xarray preserves string dtypes when converting user-provided data into indexes instead of unnecessarily degrading them to object, while still handling unencodable string values safely and continuing to warn when float16 index data is promoted to float64.

- **Expectation**: String label data should keep its native string representation through index creation whenever that representation is supported. Inputs containing problematic string values should degrade gracefully to a generic object index rather than failing, and automatic float16 promotion should remain allowed but clearly warned as a future-facing compatibility concern.

- **Constraints**: Avoid introducing unnecessary dtype degradation or new failures during index creation. Existing workflows that rely on valid string labels should continue to work with better dtype fidelity, and float16-based index inputs should remain usable with a warning instead of breaking.


## Breaking Changes

### Task 10 Surface xarray deprecations and harden Unicode index creation
Ensure that upgrading to xarray 2026.2.0 surfaces xarray deprecations as user-visible FutureWarning notifications and preserves successful index or coordinate creation when pandas cannot coerce Unicode string-like values into its default index representation.

- **Expectation**: Deprecated xarray usage should still be deprecated, but the warning users receive should now consistently be a visible FutureWarning everywhere xarray intends the notice to be user-facing. Separately, creating indexes or coordinates from string-like data should keep working even when the underlying pandas string conversion cannot encode some Unicode values; xarray should fall back to a more permissive index type instead of aborting.

- **Constraints**: Keep current deprecated behaviors and migration paths intact except for making their warnings visible to end users. Preserve normal index semantics for existing successful inputs, and only relax behavior enough to avoid Unicode-related index construction failures.


## Typing Updates

### Task 11 Clarify open_zarr decode_coords modes
Ensure that xarray.open_zarr() clearly exposes the supported decode_coords options and their observable coordinate-decoding behavior so users can choose standard or expanded coordinate promotion without ambiguity.

- **Expectation**: Users opening Zarr datasets should be able to rely on decode_coords supporting both the boolean form and explicit string modes for normal versus broader metadata-driven coordinate decoding, and missing coordinate references should not cause dataset opening to fail.

- **Constraints**: This upgrade should clarify and formalize the API contract without changing dataset-loading behavior or adding failures for incomplete coordinate metadata.


## Documentation

### Task 12 Clarify supported Zarr dimension metadata requirements
Ensure that the Zarr encoding guidance clearly states how xarray discovers dimension names and that xarray does not claim to open arbitrary Zarr arrays that lack supported dimension metadata.

- **Expectation**: Users should be able to tell which Zarr metadata layouts xarray can read and understand that missing dimension metadata is a compatibility limitation, not a newly fixed behavior.

- **Constraints**: This upgrade is a clarification only. Supported Zarr stores should keep working the same way, and unsupported stores should not be described as newly supported.


### Task 13 Support MyST Markdown in documentation builds
Ensure that the documentation system supports MyST Markdown as a first-class authoring format so contributors can introduce Markdown-based docs and plan gradual migration from reStructuredText without breaking existing documentation workflows.

- **Expectation**: Contributors should be able to write project documentation in MyST-flavored Markdown and rely on the official docs workflow to process it, while retaining a supported path to gradually convert older reStructuredText content over time.

- **Constraints**: The new Markdown support should expand documentation authoring options without disrupting current docs builds or forcing an all-at-once migration of existing content.


### Task 14 Align documented xarray output with pandas 3 display semantics
Ensure that xarray's published examples and docstrings remain accurate after upgrading to pandas 3, especially for displayed datetime, timedelta, and index representations, so users do not see mismatches between documentation and actual interactive output.

- **Expectation**: Users consulting xarray documentation should see examples that match what xarray objects actually print in a pandas 3 environment. The visible change is in how temporal values and some index dtypes are rendered, not in what the APIs do.

- **Constraints**: Preserve existing library behavior and API contracts; only the user-facing documentation examples should be updated to reflect current display formatting.


### Task 15 Normalize Numpydoc rendering across public API docs
Ensure that public xarray API documentation renders correctly after upgrading to 2026.2.0, with valid Numpydoc sections for related links, examples, warnings, notes, parameters, and return values, and with `apply_ufunc` guidance links visible in the main function documentation.

- **Expectation**: Users reading the library's API reference or interactive help should see cleanly rendered documentation with the right sections in the right places. Related links, caveats, examples, and return-value descriptions should be easy to discover, and `apply_ufunc` should directly point readers to its main guide material.

- **Constraints**: This upgrade should improve documentation quality only. Existing code behavior and API contracts must remain unchanged while the docs become more accurate and easier to navigate.


### Task 16 Correct documentation wording and option labels
Ensure that the 2026.2.0 upgrade corrects wording mistakes in xarray documentation so users see accurate, grammatically correct descriptions of API behavior, supported inputs, dimensions, and documented option labels.

- **Expectation**: After upgrading, users reading the library documentation should encounter clearer and corrected wording that accurately describes the same APIs and concepts, including option names, accepted inputs, and dimensional terminology.

- **Constraints**: The release should improve documentation clarity only. Runtime behavior and observable library semantics must remain unchanged.


### Task 17 Preserve documentation link checks while exempting archived release notes
Ensure that documentation link maintenance fixes broken links in maintained docs without causing documentation validation failures for archived release notes that may contain stale historical links.

- **Expectation**: When documentation is validated, current docs should continue to have broken links corrected and checked, but archived release notes should not fail the validation process solely because historical links have gone stale over time.

- **Constraints**: This update must stay limited to documentation behavior. It should only relax link validation for archived release notes and must not weaken link quality checks for the rest of the docs.


### Task 18 Show the full package version in latest documentation
Ensure that the latest documentation displays the exact current package version and does not present development documentation as if it were a released version.

- **Expectation**: When users view the latest docs, the shown version should match the actual build they are reading, including any suffixes that indicate it is a development or non-final build.

- **Constraints**: Keep documentation version labeling accurate without changing normal release behavior or affecting how the library runs.


### Task 19 Add MyST Markdown documentation support
Ensure that documentation authors can write or migrate pages in MyST Markdown during the 2026.2.0 upgrade, with the documentation build recognizing that format as a supported source alongside existing documentation content.

- **Expectation**: After upgrading, teams should be able to add documentation pages in MyST Markdown or migrate existing pages to that format, and those pages should participate in normal documentation builds without changing runtime APIs.

- **Constraints**: The new Markdown support should expand documentation options without breaking current documentation workflows or affecting application behavior outside documentation builds.


## Performance Improvements

### Task 20 Speed up chunked dataset opening tokenization
Ensure that opening datasets with chunking enabled avoids unnecessary chunk-tokenization overhead while preserving correct Dask naming semantics when chunk layouts actually differ.

- **Expectation**: Opening a dataset with chunking should be cheaper because the library should not spend time recomputing chunk-based identity when an incoming token is already sufficient. At the same time, operations that really create different chunk layouts must remain distinguishable in the resulting lazy graph.

- **Constraints**: The optimization should be transparent to existing callers. It should remove unnecessary overhead without weakening the guarantee that materially different chunk layouts stay separate and safe.


## Additional Changes
- Ensure that contributors can see clear descriptions for exposed `pixi` tasks when listing available tasks, so common development commands are understandable directly from the CLI.
- Ensure that ordinary data writes and updates using the netCDF4-backed workflow no longer surface NumPy shape-assignment deprecation warnings to users.
- Ensure that users on Intel-based macOS can use the project's Pixi-managed environment without platform-specific failures or unsupported-platform workarounds.
- Ensure that `Dataset.stack()` and `DataArray.stack()` accept non-string hashable names for the new stacked dimension in stack flows that do not create an index, instead of failing early because the name is passed through Python keyword argument expansion.
